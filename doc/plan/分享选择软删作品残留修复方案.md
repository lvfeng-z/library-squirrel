# 分享选择软删作品残留修复方案（缺陷二）

> 非纯设计文档，需审查。关联任务图：share-lineage/TREE.md K 节点 S 分支（缺陷二 P2 待修）。测试报告案例见 `.claude/testing/runs/20260831-share-单机终审/VERIFY-分享终审单机.md`「缺陷清单」二。本版为 plan-reviewer 审查后修订（2026-09-01）：刷新 service.go 锚点、补存量记录/活但无活 store 边界、去带圈数字；并按用户裁决扩展前端多选交互调整（决策2）。

## 审查摘要

**关键声明（抽查项）**
- 声明1：收集器 `Collect` 经 GORM 自动排除软删作品——`export/repository.go:18` 注释「ListWorkByIds 批量查询作品（软删行自动排除）」，实现 `repository.go:72-81` 走 GORM `Find`（软删 scope 自动排除）；`collector.go:72` 在 `Collect` 中调用。软删作品不在收集结果中，分享内容本身已是「仅活作品」。
- 声明2：分享标题作品数用**原始选择集**长度 `len(p.WorkIDs)`（锚 `backend/share/service.go:549` `defaultTitle(len(p.WorkIDs), len(p.WorkSetIDs), p.Title)`）；记录行 `rec.WorkIDs` 存**原始选择集**（锚 `service.go:655` `marshalInt64s(p.WorkIDs)`）——软删作品计入计数与记录，与真实分享内容（manifest）不一致，即「声称 2 个作品实仅 1 文件」。
- 声明3：`missingShareTargets`（比对选择集与收集结果、返回缺失对象）**仅复原路径启用**（锚 `service.go:476-481`，`if rec != nil` 才查）；发布路径（`rec == nil`）跳过该校验。
- 声明4：前端选择集 store `syncWorkIds` 刻意**保留不在当前可见集的已选 ID**（跨搜索/翻页保持选中，锚 `frontend/src/store/UseWorkSelectionStore.ts:29-33` `retained = this.workIds.filter(id => !visibleSet.has(id))`）——软删作品从网格消失后仍留在选择集，前端无从区分「被搜索过滤」与「已删除」。
- 声明5：分享 record 的 `file_count`/`total_bytes`/`missing_files` 来自会话快照（锚 `service.go:650` `snap := sess.snapshot()`、`:662` `rec.FileCount = snap.FileCount`）——来自 manifest（已过滤）——**只有标题作品数与 work_ids 列表用原始选择集**，二者口径不一致。
- 声明6：多选开关状态**持久化到 settings**——`handleMultiSelectChange` 写 `settingsSaveSettings([{path:'appearance.multiSelectEnabled',...}])`（锚 `frontend/src/views/MainView.vue:323`），启动时 `loadMultiSelectSetting` 读回（`:307-316`）——决策2 要求**移除持久化**（开关状态不缓存，启动恒默认关）。
- 声明7：多选开关关闭时清空选择集（锚 `MainView.vue:319-322` `if (!multiSelectEnabled.value) workSelectionStore.clear()`）——「多选内容不缓存」的既有落实，保留。
- 声明8：WorkCard 图片点击经 **300ms 延迟发射 `imageClicked`** 打开详情（锚 `frontend/src/components/common/WorkCard.vue:52-55` `handleImageClicked`、`:105` 图片 `@click`）；勾选态复选框独立 `@click.stop` 切换（`:83`）——决策2 要求 **checkable（多选态）时点图即切勾选**、不打开详情。
- 声明9：`missingShareTargets` 仅遍历顶层 workIDs/workSetIDs（锚 `service.go:725-745`），**作品集成员作品被软删时不被捕获**——为已知边界（风险2）。

**待决策（均已裁决 2026-09-01，用户拍板）**
- 决策1（**已裁决：过滤重计**）：发布路径选择集 ∩ 收集结果（`intersectCollectedWorks`），标题/记录与 manifest 一致；否决「拒绝发布」（发布含已删即报错）——过滤重计最小改动、不引入新行为。
- 决策2（**已裁决：前端多选交互调整**）：三件事——①开关状态不缓存（移除 `appearance.multiSelectEnabled` 持久化，启动恒关）；②多选内容不缓存（关闭多选即清空选择集，保留现有 `MainView.vue:319-322`）；③多选态点图即勾选（`WorkCard` 在 `checkable` 时图片单击切勾选、不打开详情）。跨搜索/翻页保留（`syncWorkIds` 既有设计）为边界，不在本轮改动（见风险4）。
- 决策3（**已裁决：存量不迁移**）：已发布、work_ids 含软删作品的 active 记录不回填重算（存量内容 manifest 本就只含活作品，偏差仅在标题/work_ids 展示；重算需遍历分享表重收集，成本高收益低）。

**自曝风险**
- 风险1：过滤重计后，软删作品被静默省略——用户选 2 得 1，若不察觉会误以为全部已分享。属「静默省略」形态（manifest 本已如此）；如需提示可后续加「已跳过已删除作品 N」通知（不在本轮）。
- 风险2：作品集成员作品被软删时（选作品集分享），成员缺失不被 `missingShareTargets` 捕获（声明9）——作品集分享静默省略已删成员。本轮不处理（标题按「N 个作品集」计仍准确），列为已知残余。
- 风险3：**「活但无活 store 的作品」口径边界**——作品未软删、仍在 `Manifest.Works` 中，但无活 store，计入标题却贡献 0 文件。此类作品身份存在，与「软删残留」不同，不属本缺陷范围；`intersectCollectedWorks` 按「在 Manifest.Works 中」判定会保留它。
- 风险4：**跨搜索保留边界**（决策2）——`syncWorkIds` 的「跨搜索/翻页保持选中」是既有刻意设计（`UseWorkSelectionStore.ts:9-12` 注释），本轮不删除；若后续用户希望「选择只随当前可见集」（搜索/翻页即清），需另行调整 store 同步语义（涉及大库全选场景，见 store 注释「选择集可达万级」）。
- 风险5：方案一收窄仅作用于 `hostSessionBody`（`service.go:439`）内 `p` 的**值拷贝**（`startHostSupervised` 按值闭包），无跨调用副作用——复原路径（`rec != nil`）的 `p` 独立构造，不受收窄影响。
- 风险6：多选态点图即勾选后，双击图片仍打开资源文件（`WorkCard.vue:56-72` 未改）——双击会先两次切勾选再打开资源（勾选净返回原值），属可接受的轻微副作用；多选态打开**详情**需退出多选（单点已用于勾选）。

## 问题

**现象**（测试报告「缺陷清单」二）：软删作品 222 在多选栏/分享计数中仍算已勾选 → 分享 `share-1788141501286`（title「分享 2 个作品」）work_ids=[222,223]，但 222 已软删无活 store，实际仅分享 1 个文件。UI 实测多选中含已删 222。

**根因**：分三段——
1. **后端口径分裂**：分享内容（manifest）经 `Collect` 自动排除软删作品（声明1），但标题作品数与记录 work_ids 用原始选择集（声明2），导致「声称」与「实际」不一致。
2. **前端残留**：选择集 store 保留不可见 ID（声明4），软删作品无法自动剔除。
3. **多选交互**：多选开关状态持久化（声明6）、选择集跨搜索保留（声明4），使已删作品的残留状态跨会话/跨搜索延续，放大用户困惑（决策2）。

## 方案设计

### 方案一（决策1）：后端过滤并重计

在 `hostSessionBody`（`service.go:439`）收集成功后（`Collect` 于 `service.go:465`）、复原缺失校验（`:476-481`）之前，把本次发布的直接作品选择集收窄为「仍在收集结果中的部分」，标题计数与记录 work_ids 随之归真：

```go
phase("collecting")
model, err := s.collector.Collect(ctx, p.WorkIDs, p.WorkSetIDs)
if err != nil { ... }
// 发布形态：软删作品不在收集结果（Collect 经 GORM 自动排除）——收窄选择集，使标题
// 作品数与记录 work_ids 与真实分享内容一致（缺陷二：软删作品多选残留）
if rec == nil {
    p.WorkIDs = intersectCollectedWorks(p.WorkIDs, model)
}
```

- 辅助函数：`intersectCollectedWorks(workIDs []int64, model *export.ExportModel) []int64`——保留 `model.Manifest.Works` 中存在的直接作品 ID（保序、去重）。作品集成员不在 `workIDs` 中不受影响；作品集 ID 集不过滤（作品集按单元收集）。
- 效果：`defaultTitle`（`service.go:549`）与 `persistActiveRecord`（`service.go:655`）读到的 `p.WorkIDs` 已收窄 → 标题「分享 1 个作品」、记录 `work_ids=[223]`，与 manifest 一致。
- 复原路径（`rec != nil`）不动：复原必须忠实复现原记录清单（`missingShareTargets` 拒绝语义保留，声明3）。
- 值语义：收窄仅作用于 `hostSessionBody` 内 `p` 值拷贝，无跨调用副作用（风险5）。

### 前端多选交互调整（决策2）

#### 调整1：开关状态不缓存

- `MainView.vue:323` 移除 `settingsSaveSettings([{path:'appearance.multiSelectEnabled', value:...}])`；`:307-316` 移除 `loadMultiSelectSetting`（及其调用）——`multiSelectEnabled`（`:87`）恒默认 `ref(false)`，启动即关、会话内切换不持久化。
- `model/util/Settings.ts:29` 的 `appearance.multiSelectEnabled` 字段变为**休眠**（不再读写；旧 settings 文件中残留值被忽略，符合决策3 不迁移）。

#### 调整2：多选内容不缓存

- 保留 `MainView.vue:319-322`：多选开关关闭即 `workSelectionStore.clear()`——退出多选即清空选择集，重进多选从零开始（内容不缓存）。
- 跨搜索/翻页保留（`syncWorkIds`，声明4）为既有设计，**本轮不改**（风险4 边界）。

#### 调整3：多选态点图即勾选

- `WorkCard.vue` `handleImageClicked`（`:52-55`）改为：
  ```js
  function handleImageClicked() {
    clearTimeout(clickTimeout)
    if (props.checkable) {
      // 多选模式：点图即勾选（即时切换，不打开详情）
      checked.value = !checked.value
      return
    }
    clickTimeout = setTimeout(() => emit('imageClicked', props.work), 300)
  }
  ```
  - `checkable` 为多选态标记（`:17`，MainView 传 `:checkable="multiSelectEnabled"`，`:467/496`）；`checked` 为勾选模型（`:24`）。
  - 多选态单击即时切勾选，`checked` 变化经 `CardGrid` 重组勾选 ID 列表 → `checkedChange` → `MainView.handleWorkCheckedChange` → `syncWorkIds`（既有链路，零额外接线）。
  - 非多选态行为不变（300ms 延迟后发射 `imageClicked` 打开详情）。
  - 双击行为不变（`:56-72` 打开资源文件）——多选态双击先两次切勾选再打开资源，勾选净返回原值（风险6）。

### 存量记录边界（决策3）

已发布的 active 记录若 work_ids 含软删作品，标题/记录仍显示旧计数——**不迁移**（决策3）：存量分享的内容（manifest）本就只含活作品（Collect 已过滤），偏差仅在标题/work_ids 展示；重算需遍历分享表 + 重收集，成本高收益低。新发布经方案一归真后，存量偏差不再产生。
