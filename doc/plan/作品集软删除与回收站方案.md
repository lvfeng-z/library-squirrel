**自曝风险**

- 风险1：**递归 CTE 改造的正确性**——过滤位置在递归项的 JOIN（每步扩展时判 child 活性），写错位置（如只过滤锚点）不生效或误剪；用「活 parent → 已删 child（孙代活）→ 孙代作品不进传递包含 / 孙代经活路径仍可达」双向用例锚定（测试 7）。
- 风险2（**已随决策5 消解**）：原两步式 upsert 的两步窗口竞态——三列索引保留单语句原子，竞态面不存在，记录备查。
- 风险3（**已随决策5 消解**）：原两步式 Updates 的零值语义（struct Updates 跳零值、NULL 覆盖需 map 重建）——AssignmentColumns 单语句原生保留，记录备查。
- 风险4：存量回填（A 期一实机坑平移）——AutoMigrate 加列 NULL × `deleted_at = 0` 过滤不命中，全部存量作品集从查询消失；迁移必带 `UPDATE work_set SET deleted_at = 0 WHERE deleted_at IS NULL` 并以测试锚定（约束4）。
- 风险5：新装库上的旧索引 drop——实体 tag 移除后 AutoMigrate 不再建全量索引，全新库 `idx_work_set_site_site_set` 从未存在；drop 用 `DROP INDEX IF EXISTS`（persistent_store 先例 migrate.go:135 形态），不用 GORM `Migrator().DropIndex`（work 先例 :235 对全新库行为未验证）。
- 风险6：**双软删交互**——已删作品集 X 的成员含已删作品 w（work 已软删、A 保留其关联行）：两行关联并存互不干扰；复原 X 后成员列表经 work 侧活行过滤只见活作品，w 复原后自动回到 X。方向自洽，但此交互无既有测试覆盖，补锚定用例（测试 3 扩展）。
- 风险7：`ListWorkSetsByWorkId`（work 所属作品集列表，workSet/service.go:423-440）依赖 `GetById` 出错时 `continue` 的容错跳过已删集——行为正确但属隐式依赖，审计记录、不改动（显式化收益低）。
- 风险8：作品集条目筛选若用户期待「按成员作品条件搜已删集」（如找含某标签作品的集），本方案平铺字段体系不覆盖——列为延后增强，首版不做（与 J「store 条目不进 SearchCondition 体系」同裁决逻辑）。
- 风险9：迁移中途失败的中间态——`DROP INDEX` 成功而 `CREATE UNIQUE INDEX` 失败时，库暂无业务键唯一约束，窗口期 upsert 的冲突检测失守（可插重复活行）；下次启动 `HasIndex(新名)` 幂等重跑补建后自愈（work 先例同形态，迁移整体非事务包裹）。
- 风险10：**三列索引的同毫秒双删撞索引（决策5 已知代价，实证确认）**——同键两代已删行的 deleted_at 同值（同毫秒删除）时，第二个软删的 UPDATE 报 `UNIQUE constraint failed: site_id, site_work_set_id, deleted_at`。触发需「删 A → 重下建 A' → 同毫秒再删 A'」，人工与程序路径均无产道；失败为**显式报错**（非静默损坏），不加防御代码，测试锚定该行为（测试 1）。**实施实录（2026-08-22）**：端到端测试的覆盖复原用例（连续「删 A → 建 A' → 覆盖软删 A'」三步同毫秒）直接命中此约束——最近的程序化产道即覆盖复原分支与前置软删连续执行；真实用户操作两次删除间隔远超毫秒，测试垫 2ms 模拟真实间隔（backupGovernance 毫秒竞态先例同款处理），行为测试（migrate_workset_test.go）保留锚定。

## 一、背景与定位

B 是 A 软删手法向 work_set 的同类推广：work_set 单表软删 + 两关联表行原地保留 + 查询面补基线/活性过滤 + 三列唯一索引释放业务键 + 回收站第三条目类型。与 A 的两点差异：①work_set 无自有资源文件（封面/内容均来自作品），**无文件策略决策**（A 的决策1 乙不适用，删除/复原零文件 IO）；②work_set 有 upsert 依赖（声明6）——work 表的部分唯一索引形态会令 upsert 单语句失效，裁决以三列全量唯一索引化解（决策5，A 的 work 表无 upsert 故无此牵出）。

删除语义变化：现行删除作品集 = 物理删行 + 清全部关联（声明2），不可恢复；B 后 = 软删入回收站、可复原、TTL/彻底删除兜底——与作品删除语义对齐。

### 1a. 决策5 背景：唯一索引形态抉择（已裁决：三列全量唯一索引）

**为什么部分索引不可行（upsert 视角）**：软删行需释放业务键（删除后可重新下载同键作品集）。若用部分唯一索引（`WHERE deleted_at = 0`，work/persistent_store 先例形态）达成，则现行 `BatchUpsert`/`Upsert` 的 GORM `clause.OnConflict{Columns: {site_id, site_work_set_id}, DoUpdates: ...}`（生成 SQLite `INSERT ... ON CONFLICT (site_id, site_work_set_id) DO UPDATE ...`）必然失败——SQLite 规定带列目标的 ON CONFLICT 只能匹配无 WHERE 子句的唯一索引（声明6 实测报错）。

**谁在用 upsert**：work 入库链——作品下载完成时把插件报回的作品集信息批量 upsert 进 work_set（`upsertWorkSets`，work/service.go:1370）；单条保存 `SaveOrUpdateByCompositeKey`（workSet/service.go:338）。语义需求 =「该键有**活**行 → 更新其元数据（名称/描述/时间等 8 列，含 NULL 覆盖）；无活行 → 新建（已删行不复活，与 work 重新下载天然隔离同语义）」。

**形态对比与裁决**：

| 形态 | 做法 | 裁决 |
| --- | --- | --- |
| **丁·三列全量唯一索引（已裁决采纳）** | `UNIQUE(site_id, site_work_set_id, deleted_at)`：活行（deleted_at=0）唯一占键、死行（时间戳互异）释放键；upsert 的 OnConflict Columns 补 deleted_at 即可，单语句原子保留 | **采纳**（用户 2026-08-22 提议）。四场景实证通过（决策5）；代价 = 同毫秒双删撞索引（风险10，显式报错非静默损坏，评估可接受）+ 索引形态与 work/persistent_store 的部分索引并存（形态差异由 upsert 能力需求驱动，非局部性能特例；且三列约束更强——同键同刻死行至多一代，部分索引对死行无约束） |
| 甲·部分索引 + 两步式 | 事务内：①按 (site_id, site_work_set_id) 批量查活行；②键已有者按 ID `Updates(map[...])` 显式列更新、无者 `Create` 批量新建 | 弃——两步竞态（事务包裹兜底）+ map Updates 零值语义（原 AssignmentColumns 的 NULL 覆盖需手工重建）均为新增复杂度 |
| 乙·部分索引 + 无目标 DoNothing + 回查 | `INSERT ... ON CONFLICT DO NOTHING`（无列目标可匹配任何唯一约束含部分索引）整批插入，再回查活行逐个 UPDATE | 弃——跳过粒度粗（撞主键等其他约束也静默跳过）、回查+逐行更新绕，本质还是两步 |
| 丙·软删时改键释放 | 不改索引，软删时把 site_id/site_work_set_id 改写 NULL 释放键，复原时恢复原键 | 弃——键列失真（记录不再如实反映原站点身份，违 RECORD_STATE_TRUTHFUL 精神）；「查该键的已删行」失去判据 |

## 二、数据模型与迁移

### 2.1 实体（entity/work_set.go）

```go
// 对照 work（entity/work.go:15）同款
DeletedAt      soft_delete.DeletedAt `gorm:"column:deleted_at;index;softDelete:milli" json:"deletedAt"`
```

- SiteID / SiteWorkSetID 的 `uniqueIndex:idx_work_set_site_site_set` tag **移除**——三列唯一索引由手写命名迁移建（AutoMigrate 不表达含软删列的复合唯一索引），tag 保留会在新库重建两列全量索引、与三列索引冗余并存。

### 2.2 迁移（migration/migrate.go 后置命名迁移，决策5 三列形态）

```sql
-- 幂等标记：新索引名 HasIndex；顺序 = drop 旧 → 回填 → 建新（回填在无索引约束下执行不受阻；
-- 存量重复活键若存在，建索引时显式暴露——旧两列全量唯一索引保证存量无此形态）
DROP INDEX IF EXISTS idx_work_set_site_site_set;
UPDATE work_set SET deleted_at = 0 WHERE deleted_at IS NULL;   -- 存量回填（约束4）
CREATE UNIQUE INDEX idx_work_set_site_site_set_gen ON work_set(site_id, site_work_set_id, deleted_at);
```

## 三、四条链（recycleBin 编排 + workSet 提供能力）

### 3.1 软删链（workSet.Service 新增 SoftDeleteWorkSet）

校验活行（`repo.GetById` 软删过滤下仅命中活行，nil → ErrWorkSetNotFound）→ 事务内 `repo.Delete`（GORM softDelete 改写为打毫秒时间戳一条 UPDATE）。两关联表零操作（决策1 保留）。对照 `SoftDeleteWork`（work/service.go:554）去掉文件与任务两段。

### 3.2 复原链（recycleBin.Service 新增 RestoreWorkSet）

1. `GetDeletedWorkSet(id)` 校验已删条目（nil → ErrRecycleItemNotFound）；
2. 业务键冲突检测：`SiteID.Valid && SiteWorkSetID.Valid` 时查活行 `GetBySiteAndSiteWorkSetID`（重新下载建了同键新集的场景）——占位且 overwrite=false → ErrRestoreConflict；overwrite=true → `SoftDeleteWorkSet(占位集)`（占位集转回收站，反悔可再复原，对照 RestoreWork :239-243 形态）；NULL 键（本地手建集）不参与唯一性、无冲突（声明11）；
3. `RestoreDeletedWorkSet(id)` 清标志（Unscoped Updates 一条 UPDATE）。关联从未离开，封面/层级/成员全量自恢复，**无文件还原、无从属复活段**。

### 3.3 彻底删除链（recycleBin.Service 新增 PurgeWorkSet）

校验已删条目 → `DeleteWorkSetAndAssociations(id)` 事务内物理级联：re_work_work_set.DeleteByWorkSetId + re_work_set_work_set 双向删 + work_set 行 `DeleteUnscoped`（现行 `Service.Delete` 的级联体平移，workSet/service.go:299-315）。无文件、无备份面（对照 PurgeWork 的 backup 清理段不适用）。

### 3.4 TTL（runCleanup 第三轮）

workSet 仓储新增 `ListDeletedBefore(expireBefore)`（GORM IncludeDeleted + `deleted_at > 0 AND deleted_at < ?`，对照 work/service.go:613 同名方法）→ 逐条 PurgeWorkSet。保留期读同一 `GetRecycleBinSettings()`（决策2）。

## 五、upsert 微改（决策5：OnConflict 目标补列）

三列索引下 SQLite 的 `ON CONFLICT (site_id, site_work_set_id, deleted_at)` 可匹配全量唯一索引，`BatchUpsert`（workSet/repository.go:47）与 `Upsert`（:80）保留单语句形态，仅 `clause.OnConflict` 的 `Columns` 补 `{Name: "deleted_at"}`（插入行 deleted_at 由 soft_delete CreateClause 显式写 0，与表中活行（0）冲突 → DoUpdates 更新元数据；与死行（时间戳≠0）不冲突 → 新建放行，已删行不复活）。DoUpdates 的 AssignmentColumns 列集不变（NULL 覆盖语义原生保留）。接口签名与调用方（work/service.go、app.go 适配器）零改动。

## 六、查询与 DTO（回收站作品集条目）

### 6.1 查询（search 模块新增，与 QueryRecycleStorePage 并列）

`QueryRecycleWorkSetPage`——原生 SQL，谓词提取函数 `buildRecycleWorkSetWhere`（列表专用；TTL 圈定走仓储 ListDeletedBefore 不经此，谓词无共用需求故不提共用函数）：

```sql
SELECT ws.id, ws.site_id, ws.site_work_set_id, ws.site_work_set_name, ws.nick_name,
       ws.create_time, ws.deleted_at,
       COALESCE(s.site_name, '') AS site_name,
       (SELECT COUNT(*) FROM re_work_work_set rwws
        JOIN work w ON rwws.work_id = w.id AND w.deleted_at = 0
        WHERE rwws.work_set_id = ws.id) AS alive_member_count
FROM work_set ws
LEFT JOIN site s ON ws.site_id = s.id
WHERE ws.deleted_at > 0
  [AND (ws.site_work_set_name LIKE ? OR ws.nick_name LIKE ?)]  -- Name 非空
  [AND ws.site_id = ?]                                          -- SiteId 非 null
  [AND ws.deleted_at >= ? / <= ?]                               -- 时间范围（0=不限）
ORDER BY ws.deleted_at DESC|ASC, ws.id DESC
```

条件体系 = 平铺字段（决策3 + J 的 store 条目分轨先例：workSet 无标签/作者关联，不进 SearchCondition 体系）。活成员数子查询让用户复原前知道集内还有几个活作品（已删成员不计、复原后自动回位）。

## 十、测试计划（内存 SQLite 基建，声明13）

1. **迁移与索引**：三列唯一索引生效（活行撞键报错、死行不占键、同毫秒双删撞索引——风险10 行为锚定）+ 存量回填（预置 NULL 行迁移后全 0）+ 二次启动幂等；
2. **upsert 三列目标**：键有活行→更新且 NULL 覆盖语义保持；键被软删行占→新建不复活；混合批部分更新部分新建；
3. **软删与关联保留**：软删后 GORM 查询面不可见 + 两关联行原样（行数与内容不变）+ 双软删交互（已删集 ∋ 已删作品，各自复原互不干扰，风险6）；
4. **复原链**：NULL 键无冲突直复；Valid 键撞活集→overwrite=false 拒绝 / true 占位集转回收站再复原本集；占位集可再复原；
5. **彻底删除**：work_set 行 + 两关联行物理消亡；活作品不受波及；
6. **TTL**：过期圈定与清理、未到期不清、与 work/store 轮共享设置；
7. **传递包含 CTE**（风险1）：活 parent → 已删 child（child 下有活孙代）→ 孙代作品不进 parent 传递包含；孙代经其他活路径仍可达；环路检测：经已删节点闭合的环建边被拒（决策4 全量侧）；
8. **WorkSet 条件活性**：已删集的成员不被「不在集 X」条件排除（消费面 #2）；
9. **作品集搜索基线**：QueryWorkSetPageByConditions 空条件与有条件两态均不含已删集；
10. **回收站条目查询**：基线谓词 + Name/SiteId/时间过滤 + 活成员数（含已删成员不计）；
11. 前端 `yarn build` 绿 + dev 实机手测（删除→主列表消失→回收站第三 tab 可见/筛选/复原含冲突覆盖→彻底删除→TTL 到期清理；WorkSetDialog 删除入口）。
