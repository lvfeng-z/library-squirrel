**自曝风险（强制暴露）：**

## 1. 背景与目标

### 1.1 问题

当前 ResourceType（image/video/article/document/unknown）与 store_type（6 角色）均为**封闭枚举**：真相源在 SDK `contract` 子包，主程序 entity + SDK dto 经 const 别名 re-export（编译期绑定），`ResourceTypeRegistry` 包级 `var map` 字面量初始化 5 个预定义 spec，**无运行时注册 API**。后果：插件无法声明新资源形态（如纯音频、新文档格式、3D 模型）——即使插件想Create 一个 audio 资源，`ValidateResourceType`（`resource_type.go:220`）也会因 `"audio"` 不在 Registry 而抛 `ErrResourceTypeInvalid`。

### 1.2 目标

G 的定位是「**封闭枚举的受控开放**」——不破坏现有严格识别不变量（空/未知 ResourceType 与 store_type 在写入路径抛错、不推断不兜底），而是提供受控扩展机制：

1. **audio 落地**（主程序内置）：audio 作为主程序内置第 6 种 ResourceType，填补通用音频资源形态（使纯音频资源可被识别、存储与播放）。
2. **开放机制**（插件自定义类型）：让插件在受控前提下声明新 ResourceType（经 capabilities 通行证 + manifest 结构化声明），主程序注册进 Registry，使前端渲染分发（resourceViewer）与完整性校验自动扩展到新类型。

### 1.3 不变量红线（G 的生命线）

开放机制**绝不能变成「任意字符串当类型」**。守卫手段（借鉴 Eclipse contentTypes，见第 7 节）：把合法性校验从「单纯运行时拒绝」**前移到注册时强校验齐全的能力契约**——插件声明新类型时必须同时声明合法的 Roles 组合（StoreType∈内置 7 角色、Min≤Max、PrimaryRoles∈Roles），主程序注册时校验，拒绝坏 spec；运行时见到的类型必然合法。写入路径的 `ValidateResourceType`/`ValidateStoreType` 语义不变，**不引入任何 Infer/Default 兜底**。

## 2. 现状地基（4 路调研整合）

### 2.1 ResourceTypeRegistry 封闭枚举机制

- `ResourceTypeSpec`（`resource_type.go:42-47`）四字段：`ResourceType`（类型值）、`Roles []StoreRoleSpec`（结构角色+基数，`StoreRoleSpec{StoreType,Min,Max}`，Min=0 可选/1 必含，Max=0 不限/1 单例）、`PrimaryRoles []string`（展示主体优先级链）、`StoreStandards map[string]StoreStandard`（各角色文件标准，描述性不校验内容）。
- Registry 是 `map[string]ResourceTypeSpec`（`resource_type.go:51-57`），5 个预定义 spec 是包级 `var`（`:69,82,101,116,131`），无 `Register` 函数、无 `init()`、无运行时写入 API。
- `validStoreTypes`（`resource_type.go:60-67`）是独立的合法 store_type 集合（6 角色），与 Registry 是**两个独立封闭集合**。
- `ValidateResourceType`（`:216-224`）：空→`ErrResourceTypeEmpty`，不在 Registry→`ErrResourceTypeInvalid`，unknown 在 Registry 不报错。
- `ValidateStoreType`（`:227-232`）：不在 `validStoreTypes`→`ErrStoreTypeInvalid`。
- `ResolvePrimaryStore`（`:185-211`）：按 `PrimaryRoles` 链取第一个实际存在的 store；spec nil/PrimaryRoles 空时降级链 `videoMain→image→首个非thumbnail`，**读路径专用不抛错**。

### 2.2 插件 Create 声明 ResourceType 的写入路径（RESOURCE_TYPE_STRICT）

```
插件 TaskHandler.Create → proto.TaskCreateResponse.resourceType
  → protoToTaskCreateResponse 透传(不默认化/不校验)  task_handler_proxy.go:479-501
```

关键：proto→dto 透传**不默认化**（「不推断」的体现）；task 表 NULL=未声明 by design；严格校验**仅在 saveResource 落 resource 时**；替换分支（existing resource）不校验、不改动 ResourceType（by design，保留原值）。grep 确认无任何 ResourceType 推断兜底代码。

### 2.3 前端渲染分发（已开放，零改动可承载新类型）

- `ResourceViewer.vue` 用 `v-if`/`v-else-if`/`v-else` 模板链分发（非 switch/map/component:is）。`previewType = getResourcePreviewType(resource)`（`ResourceViewer.vue:26`）优先返回 `resource.resourceType`，空/unknown 按扩展名嗅探降级（`utils/ResourceUtil.ts:34-47`）。
- 内置渲染器 5 个（`renderers/Image|Video|Article|Document|Unknown.vue`），静态 import。
- 插件 resourceViewer 经 `HandlerRegistryStore.resourceViewerByType(resourceType)`（`frontend/src/store/HandlerRegistryStore.ts:17-24`）**精确字符串匹配**、按 order 取最小；注册侧 `convertToResourceViewerHandler`（`useSlotSyncListener.ts:73-84`）resourceType 必填但**只判 isBlank，不校验枚举值**。
- `ResourceViewer.vue:29` 对所有 previewType 查插件 handler，`:80` 插件 `PluginBoundary v-if` 优先于内置链——**插件命中即覆盖内置**。插件渲染器接收 `{context: render.Context}`（SDK dto/render，断链契约）。
- ResourceType TS 常量在 `frontend/src/constants/sectionCode.ts:32-38`（`as const` 对象，**非 union 类型**）；`resource.resourceType` 类型本就是开放 `string`。**全文无 `switch(resourceType)`/`Record<5种类型>`/穷尽性断言**（grep 0 命中）。

### 2.4 完整性三态（Spec 驱动，新类型自动跟随）

- 三态 `0/1/2`：0=未校验（resourceType 未注册/空/unknown）、1=完整（每角色数量∈[Min,Max]）、2=不完整（缺角色或超量）。
- `ComputeResourceComplete`（`resource_type.go:170-179`）纯集合运算无 IO，两调用点共用：`taskManager/model.go:1086-1119`（下载完成算）、`resource/merge_service.go:208-236`（合并产出 videoMain 后重算）。
- 落盘字段 `Resource.ResourceComplete sql.NullInt64`（`entity/resource.go:17`）。
- **完整性判定完全依赖 Spec 的 Roles 基数**——新类型注册时声明 Roles，完整性校验零计算改动自动覆盖。

### 2.5 capabilities 与 contractVersion 现状

- `capabilities` 是 plugin.json 声明式 `[]string`（`plugin_types.go:34`），现有 2 值 `workOrderQuery`/`workSetRelationQuery`（`loader.go:71-76`）；SDK 侧能力是可选 Go interface（`WorkOrderQuerier`/`WorkSetRelationQuerier`，`dto/work_set_dto.go:11-27`），声明（通行证）与实现（interface）分离。capabilities **不做值合法性校验**（宽容模式）。

- `contractVersion` 真相源 `library-squirrel-sdk/transport/contract.go:15` = 2；安装期（`service.go:329`）+ 加载期（`loader.go:173`）双校验；校验逻辑 `loader.go:44-55`（过新/过旧拒绝，==0 缺字段放行）。与 `configSchemaVersion` 正交（前者 host↔plugin 协议，后者插件配置结构）。

### 2.6 共享枚举单源

SDK `contract` 子包（`contract.go:9-16` StoreType、`:21-24` Generation、`:28-34` ResourceType）是字符串值真相源；主程序 entity（`resource_type.go:10-16`、`resource_store.go:10-19`）与 SDK dto（`dto/handler_dto.go:14-28`）经 const 别名 re-export。Registry（规约逻辑：Roles/PrimaryRoles/StoreStandards）在主程序 `entity/resource_type.go:51`，是主程序领域知识（非 SDK 契约）。

### 2.7 audio/audioTrack 现状

- `audioTrack` 是 video 的可选 store 角色（`resource_type.go:88-89`，`Min:0,Max:1`），StoreStandard「分离流音频原料」、`.m4a/.mp3/.aac`、`downloaded`。

## 3. 设计决策（决策1–8 均已定）

- **决策1（已定）**：audio 主程序内置第 6 种 ResourceType。理由：audio 是通用资源形态（纯音频，与 image/video 同级），不应依赖特定插件；走 const 单源享受共享枚举保护、防字面量漂移。开放机制（Registry 运行时注册 API）独立服务插件自定义类型。二者共享「Registry 从封闭到开放」的基建改造。
- **决策2（已定）**：audio 用新增 `audioMain` 角色（对称 videoMain），store_type 内置扩展 6→7。理由：audioTrack 当前定位是「video 分离流原料」，复用其作 audio 主体会语义重叠；新增 audioMain「可播放音频主体」语义清晰、与 videoMain 结构对称。
- **决策3（已定）**：`contractVersion` bump 2→3。理由：T3 改变主程序对 `resource.resource_type` 合法值判定语义（从严到宽），带新类型声明的插件在旧主程序被拒、新主程序接受，用 contractVersion 明示代际避免「同 manifest 不同行为」困惑。configSchemaVersion 不受影响。
- **决策4（已定）**：声明载体 = capabilities 通行证 `CapabilityResourceTypeProvider` + manifest 新增 `resourceTypes []ResourceTypeDeclaration` 结构化声明段。理由：capabilities 是 `[]string` 薄通行证（语义「我实现了某可选能力」），不能承载结构化 spec；分两层保持 capabilities 边界洁净，结构化声明段复用现有 manifest→installDTO→entity→loader 管道。
- **决策5（已定）**：插件自定义 ResourceType 允许声明新 store 角色，但**本次仅预留不实现**。本次插件 Roles.storeType 限内置 7 角色（`validateSpecForRegister` 校验），「插件自定义 store 角色」作为新待办（节点 G'）延后；本次设计预留不阻塞——Registry 运行时注册机制对 store_type 同样适用（`validStoreTypes` 未来可走同一注册模式），`validateSpecForRegister` 的 StoreType 校验是未来放开点。
- **决策6（已定）**：audio 主程序内置基础 AudioRenderer（HTML5 `<audio>`），与 image/video 内置渲染器一致，保证无插件时开箱可用。实现极简（参照 VideoRenderer 的 `<video>` 模式）。
- **决策7（已定，审查补充）**：两插件声明同一 type 值的命名空间冲突——`Register` 返回 `ErrResourceTypeAlreadyRegistered` 拒绝重复 + 加载日志告警；后注册者该类型不生效，但**不阻断该插件其他能力**（其他自定义类型、前端扩展点）加载。理由：插件类型独立加载、独立注册，一个类型的冲突不应株连整个插件。
- **决策8（已定，审查补充）**：插件自定义类型强制反向域名前缀（如 `com.example.interactiveNovel`），`validateSpecForRegister` 校验前缀格式、禁止裸通用词（`audio`/`image`/`video` 等内置名及未来可能内置化的通用词）。理由：防插件抢占未来内置类型名——若放任插件注册裸 `audio`，主程序未来想内置 `audio` 时已被插件占坑、且历史 resource 已绑插件 spec，回退不可逆。

## 4. 方案设计

### 4.1 数据模型：ResourceTypeRegistry 开放机制

**Registry 从无锁 `var map` 改为并发安全的注册表结构**（读多写少，`sync.RWMutex`）：

```go
// resourceTypeRegistry 资源类型中央注册表。
// 内置类型(预定义)在包级初始化时注册;插件自定义类型经 Register 运行时注册(注册时强校验)。
type resourceTypeRegistry struct {
    mu    sync.RWMutex
    specs map[string]ResourceTypeSpec
}

// ResourceTypeRegistry 全局注册表实例(替换原 var map)。
var ResourceTypeRegistry = &resourceTypeRegistry{
    specs: map[string]ResourceTypeSpec{
        ResourceTypeImage:    imageResourceTypeSpec,
        ResourceTypeVideo:    videoResourceTypeSpec,
        ResourceTypeArticle:  articleResourceTypeSpec,
        ResourceTypeDocument: documentResourceTypeSpec,
        ResourceTypeUnknown:  unknownResourceTypeSpec,
        ResourceTypeAudio:    audioResourceTypeSpec, // 决策1+2:audio 内置第6种
    },
}

// Register 注册资源类型规约(插件自定义类型用)。注册时强校验 spec 合法性,拒绝坏 spec。
func (r *resourceTypeRegistry) Register(spec ResourceTypeSpec) error {
    if err := validateSpecForRegister(spec); err != nil {
        return err
    }
    r.mu.Lock()
    defer r.mu.Unlock()
    if _, exists := r.specs[spec.ResourceType]; exists {
        return ErrResourceTypeAlreadyRegistered
    }
    r.specs[spec.ResourceType] = spec
    return nil
}

// Unregister 反注册(插件卸载用)。内置类型不可反注册。
func (r *resourceTypeRegistry) Unregister(resourceType string) {
    r.mu.Lock()
    defer r.mu.Unlock()
    // 内置类型(含 audio)受保护,不可卸载——通过白名单判断
    if isBuiltinResourceType(resourceType) {
        return
    }
    delete(r.specs, resourceType)
}

func (r *resourceTypeRegistry) Lookup(resourceType string) (ResourceTypeSpec, bool) {
    r.mu.RLock()
    defer r.mu.RUnlock()
    s, ok := r.specs[resourceType]
    return s, ok
}
```

**适配现有函数**（签名不变，改内部实现走 Registry.Lookup）：
- `LookupResourceTypeSpec`（`resource_type.go:139`）：`Registry.Lookup` → 返回 `*ResourceTypeSpec`。
- `ValidateResourceType`（`:216`）：`Registry.Lookup` 命中即合法——**「在 Registry 中存在」语义不变**，来源从编译期扩为编译期+运行时。
- `ValidateResourceStructure`（`:150`）、`ComputeResourceComplete`（`:170`）：内部 `Registry.Lookup` 取 spec。

## 6. 不变量与红线（守住勿回退）

5. **读路径安全降级**：`ResolvePrimaryStore` spec nil 降级链保留，插件反注册后读旧数据不 panic。
6. **签名稳定**：`LookupResourceTypeSpec`/`ValidateResourceType`/`ComputeResourceComplete`/`ResolvePrimaryStore` 外部签名不变，调用点零改动。
