# 方案 B：统一暂停恢复机制

## Context

当前暂停机制存在设计矛盾：

- **Paused 是稳态**（可跨重启持久化），但下载阶段暂停的任务**占用 goroutine、信号量槽位和文件句柄**
- `Resume()` 需要区分三种暂停形态（下载阶段/setup 阶段/从未启动），代码路径复杂
- `AllChildrenTerminal()` 将 Paused 视为终态，导致父任务被提前清理
- 从未进入过 Processing 的子任务（Waiting→Paused）在 Resume 时向无消费者的 channel 发信号，静默丢失

**目标**：所有暂停的任务统一释放 goroutine 和信号量，恢复时统一重新调度（`tryDispatch`），不再依赖 channel 唤醒。

## 设计原则

1. **Paused 任务不持有 goroutine**：无论是下载阶段暂停、setup 阶段暂停还是从未启动，暂停后一律退出 goroutine、释放信号量
2. **Paused 任务保留在内存**：作为数据结构留在 `parentMap`/`taskMap` 中，前端仍可见
3. **Paused 不再是终态**：`AllChildrenTerminal()` 不再包含 Paused，父任务不会被提前清理
4. **恢复统一走 `tryDispatch`**：重置 context 后通过 `tryDispatch` 重新调度，由 `executeTask` 根据 `resumeFromDB` 决定走 `resumeFromPersistedState`（续传）还是 `run()`（从头执行）

## 改动清单

### 1. `model.go` — downloadLoop：暂停后直接退出 goroutine

**当前**（约 412-430 行）：收到 pauseCh 后 drain，然后**阻塞**在 `resumeCh` 等待恢复。

**改为**：drain 完成后**直接返回** `runResultPaused`，goroutine 退出。

```go
// 修改前：
case <-m.pauseCh:
    m.drainReader(buf)
    m.currentFile.Sync()
    m.currentFile.Close()
    close(m.drainDone)
    m.setState(TaskStatePaused)
    select {
    case <-m.resumeCh:
        m.doResume()
        continue
    case <-m.ctx.Done():
        m.setFailed("任务被取消")
        return runResultDone
    }

// 修改后：
case <-m.pauseCh:
    m.drainReader(buf)
    m.currentFile.Sync()
    close(m.drainDone)
    m.setState(TaskStatePaused)
    return runResultPaused
```

变更说明：
- 移除 `m.currentFile.Close()`（defer 统一关闭 reader 和 file）
- 移除整个 `select { resumeCh / ctx.Done }` 块
- 返回 `runResultPaused` → `executeTask` 退出 → defer 释放信号量 → goroutine 结束

### 2. `model.go` — 新增 `prepareForResume()` 方法

重置运行时状态，为重新调度做准备：

```go
// prepareForResume 重置任务的运行时状态，准备重新调度
// 由 ResumeTaskTree 在 tryDispatch 前调用
func (m *ManagedTask) prepareForResume() {
    m.cancel()
    m.ctx, m.cancel = context.WithCancel(context.Background())
    m.pauseCh = make(chan struct{}, 1)
    m.currentReader = nil
    m.currentFile = nil
    m.totalWritten = 0
    // 根据 pending_resource_id 决定续传或重新执行
    m.resumeFromDB = m.task.PendingResourceID.Valid
}
```


### 4. `manager.go` — `ResumeTaskTree`：统一通过 `tryDispatch` 重新调度

**当前**（约 485-504 行）：遍历子任务调用 `child.Resume()`，依赖 channel 唤醒机制。

**改为**：遍历 Paused 子任务，`prepareForResume` + `tryDispatch`。

```go
// 修改前：
for _, child := range parent.GetChildren() {
    if err := child.Resume(); err != nil {
        logger.Log.Errorf("[TaskManager] 恢复子任务 %d 失败: %v", child.taskId, err)
    }
}

// 修改后：
for _, child := range parent.GetChildren() {
    if child.GetState() != TaskStatePaused {
        continue
    }
    child.prepareForResume()
    m.tryDispatch(child)
}
```

说明：
- `tryDispatch` 尝试获取信号量：成功则 `go m.executeTask(child)`，失败则入 `waitingQueue` 并设为 `Waiting` 状态
- `executeTask` 根据 `resumeFromDB` 标记自动选择 `resumeFromPersistedState`（续传）或 `run()`（从头执行）
- `parentMap` 中找不到时仍回退到 `loadAndStartTaskTree`（应用重启后的恢复场景）

### 5. `manager.go` — `buildOrReuseChild`：移除"场景一"内存复用逻辑

**当前**（约 225-230 行）：如果内存中存在 Paused 的 ManagedTask，直接复用并调 `Resume()`。

**改为**：不再复用内存中的 Paused 任务。因为方案 B 下 `ResumeTaskTree` 直接在内存中 `tryDispatch`，不会走到 `loadAndStartTaskTree` → `buildOrReuseChild` 路径。此场景仅在应用重启后才触发，此时内存中不可能有残留任务。

移除以下代码块：
```go

        *pausedChildren = append(*pausedChildren, existing)
        return existing
    }
    // ... 场景二、场景三保留
}
```

同时移除 `loadAndStartTaskTree` 末尾的"恢复之前暂停的子任务"循环（约 195-200 行）：

### 7. `manager.go` — `StopTaskTree`：兼容无 goroutine 的 Paused 子任务

**当前**（约 507-528 行）：对 Waiting 子任务调 `cancel()` + `setFailed()`，对 Processing 子任务调 `Stop()`。

**问题**：方案 B 下暂停的子任务没有 goroutine，状态为 Paused，既非 Waiting 也非 Processing，当前代码会跳过它们。

**改为**：增加 Paused 状态的处理：

```go
for _, child := range parent.GetChildren() {
    state := child.GetState()
    if state == TaskStatePaused {
        // 方案 B：暂停任务无 goroutine，直接标记为失败
        child.setFailed("任务被用户停止")
        continue
    }
    if state == TaskStateWaiting {
        m.removeFromQueue(child.taskId)
        child.cancel()
        child.setFailed("任务被用户停止")
        continue
    }
    child.Stop()
}
```

## 改动影响分析

### PauseTaskTree 执行流程（改造后）

```
PauseTaskTree
  ├─ Processing 子任务 → child.Pause()
  │   ├─ setup 阶段: cancel() + setState(Paused) → run() 返回 runResultPaused → goroutine 退出
  │   └─ download 阶段: pauseCh → drain → setState(Paused) → downloadLoop 返回 runResultPaused → goroutine 退出
  │   └─ executeTask defer 释放信号量
  ├─ Waiting 子任务 → removeFromQueue + setState(Paused)
  └─ Finished/Failed 子任务 → 跳过
```

所有子任务暂停后：无 goroutine 存活、无信号量占用、文件句柄已关闭。任务和父任务保留在内存中，前端显示为 Paused。

### ResumeTaskTree 执行流程（改造后）

```
ResumeTaskTree
  ├─ parent 在 parentMap 中（应用未重启）
  │   └─ 遍历 Paused 子任务 → prepareForResume() + tryDispatch()
  │       ├─ 有信号量槽位 → go executeTask(child)
  │       │   ├─ resumeFromDB=true → resumeFromPersistedState()（续传）
  │       │   └─ resumeFromDB=false → run()（从头执行）
  │       └─ 无信号量槽位 → 入 waitingQueue，状态变为 Waiting
  └─ parent 不在 parentMap 中（应用重启）
      └─ loadAndStartTaskTree()（从数据库加载，现有逻辑不变）
```

### 关键状态流转

| 暂停前状态 | 暂停后 | prepareForResume | tryDispatch 后 | executeTask 路径 |
|-----------|--------|-----------------|---------------|-----------------|
| Processing（下载中） | Paused，goroutine 退出，pending_resource_id 有效 | resumeFromDB=true | Processing/Waiting | resumeFromPersistedState（续传） |
| Processing（setup 中） | Paused，goroutine 退出，无 pending_resource_id | resumeFromDB=false | Processing/Waiting | run()（从头执行） |
| Waiting（从未启动） | Paused，无 goroutine，无 pending_resource_id | resumeFromDB=false | Processing/Waiting | run()（从头执行） |

## 前置变更：SDK 添加 Continuable 字段

### 背景

当前 `TaskResourceDTO`（插件返回给主程序的资源描述）缺少 `continuable` 字段。插件无法在运行时告知主程序当前资源是否支持在已有文件上续传。主程序只能通过 `PendingResourceID` 是否存在来猜测。

需要区分两个层面的 Continuable：
- **`Task.Continuable`**（数据库字段）：静态属性，标识任务类型是否支持续传，仅用于展示
- **`TaskResourceDTO.Continuable`**（新增，插件响应字段）：运行时属性，由插件在 `Start`/`Resume` 响应中声明当前资源是否可续传

### SDK 改动（library-squirrel-plugin-sdk）

#### 1. Proto 定义 — `proto/plugin.proto`

`TaskResourceDTO` 添加字段：

```protobuf
message TaskResourceDTO {
  int64 resourceId = 1;
  string url = 2;

  string format = 4;
  string localPath = 5;
  string remotePath = 6;
  int64 size = 7;
  int32 completeness = 8;
  string suggestName = 9;
  optional bool continuable = 10;    // 新增：插件声明当前资源是否支持续传
```


### 主程序使用 Continuable 的改动

#### `model.go` — `resumeFromPersistedState()` 中根据 Continuable 决定续传策略

**当前逻辑**（约 560-600 行）：有 `PendingResourceID` 且文件存在 → 调用插件 `Resume` → 追加模式打开文件 → `downloadLoop`。

**改为**：调用插件 `Resume` 后，检查响应中的 `Continuable`：

```go
// 3. 调用插件 Resume
param := &sdkdto.TaskResParam{...}
newReader, newResp, err := m.pluginExec.Resume(m.ctx, param)
if err != nil {
    m.setFailed(...)
    return runResultDone
}

// 4. 根据插件响应的 Continuable 决定续传策略
continuable := newResp != nil && newResp.Resource != nil &&
    newResp.Resource.Continuable != nil && *newResp.Resource.Continuable

if continuable {
    // 续传：以追加模式打开文件，从已下载位置继续
    file, err := os.OpenFile(localPath, os.O_WRONLY|os.O_APPEND, 0644)
    ...
    m.totalWritten = downloadedBytes
} else {
    // 不可续传：截断文件从头开始
    file, err := os.OpenFile(localPath, os.O_WRONLY|os.O_TRUNC, 0644)
    ...
    m.totalWritten = 0
}
```

#### `model.go` — `prepareForResume()` 简化

续传决策不再依赖 `resumeFromDB` 标记（因为真正的决策在 `resumeFromPersistedState` 内部基于插件响应），`prepareForResume` 只负责重置运行时状态：

```go
func (m *ManagedTask) prepareForResume() {
    m.cancel()
    m.ctx, m.cancel = context.WithCancel(context.Background())
    m.pauseCh = make(chan struct{}, 1)
    m.currentReader = nil
    m.currentFile = nil
    m.totalWritten = 0
    // 有 PendingResourceID 则走 resumeFromPersistedState（内部再根据 Continuable 决定续传/重新下载）
    // 无 PendingResourceID 则走 run()（从头执行）
    m.resumeFromDB = m.task.PendingResourceID.Valid
}
```

插件在 `Start` 和 `Resume` 方法的返回值中设置 `Continuable`：

## 不涉及的部分

- **前端**：无改动。状态推送（PushStateChange/PushParentStateChange）保持不变
- **TaskExecutor 接口**：Pause/Resume/Start 不变
- **loadAndStartTaskTree**：核心逻辑不变，仅移除"场景一"和末尾的 pausedChildren 循环
- **Pause() 方法**：保持不变（pauseCh + drainDone 机制不变）
- **flushLoop / addToPending**：保持不变

## 验证方式

1. `task dev` 启动应用
2. 创建包含 5+ 子任务的父任务，开始执行
3. **测试暂停**：执行中点击暂停，验证：
   - 父任务和所有子任务显示为「已暂停」
   - 无 goroutine 存活、无信号量占用（可开始其他任务验证）
4. **测试恢复**：点击恢复，验证：
   - 所有暂停子任务正确恢复（含下载续传和从头执行两种情况）
   - 父任务状态正确跟随子任务变化
5. **测试恢复后再暂停**：恢复执行后再次暂停，验证行为一致
6. **测试停止**：暂停后点击停止，验证所有子任务正确标记为失败
7. **测试跨重启恢复**：暂停后重启应用，点击恢复，验证从数据库正确加载并续传
8. `go vet ./backend/taskManager/...` 无警告
