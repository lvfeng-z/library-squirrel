**待决策（需用户拍板）**：
- 决策1（**已重定：完全复用，无分叉**）：多作品确认粒度 = **任务粒度整体决策**——后端对每个冲突作品推一条 `taskStatus-duplicateDetected` 事件（同 taskId、不同 existingWorkId，现有载荷与推送接口不动），前端现有列表弹窗天然渲染多行（`UseReplaceConfirmStore.add` 不去重，声明12），答复复用 `ConfirmReplace(taskId, action)` 整任务整体替换/跳过（声明11）。仅一处前端小改：`remove` 按 taskId 清理全部行（现只删首个，声明12）。逐作品决策需新接口新 UI，违背「完全复用」，弃。用户设想与实际**无冲突**。
- 决策2（**已重定：完全复用，无分叉**）：替换执行复用既有角色级能力 `SoftDeleteWorkStoreRoles(ctx, workId, roles)`——roles 传交集角色即天然「角色交集替换」（声明4），备选「作品资源面全量替换」为不复用的伪选项，删。用户设想与实际**无冲突**。
- 决策3（**已重定：完全复用，无分叉**）：元数据与关联处理复用对齐——work 行字段按 manifest 覆盖更新（对齐插件任务含元数据板块的替换）、标签/作者/作品集关联合并去重挂载（复用 import `ensure*` 系对已有作品的挂载路径，不删本地已有关联）。用户设想与实际**无冲突**。
- 决策4（**已重定：完全复用，无分叉**）：确认挂起语义 = 完全复用普通任务的既有交互闭环——弹窗为模态强制（声明13），确认期间 UI 遮罩挡住任务操作栏，暂停/停止**实际不可达**（与普通任务同构）；真正的中断窗口在**确认之后**（弹窗关、软删后、暂存中），该窗口收口按既有回滚单点闭环（声明10）。确认等待原语对 RunCtx 取消仅作**防御性**处理（防插件停用清场等旁路），不做确认阶段的暂停/停止分态。用户设想的 UI 遮罩疑点**证实属实**，且因此简化了确认回路设计。
- 决策5（已确认）：零交集命中作品自动并入 ReplaceWorks（不经用户确认直接增补挂载到已有作品）——接收侧新可感知行为，现状为静默跳过、改后为静默增补。对齐插件任务「查重命中即挂载、弹窗只决定确认」既有语义（`backend/taskManager/model.go:922-927`），导入结果统计按「确认替换 / 自动增补」拆分计数明示。

**自曝风险**：
- 风险1：插件任务 WaitingForInput 靠「执行返回→回命令等待→确认命令重入」实现，而策略任务的 `Execute` 同步阻塞占用 actor goroutine——`postCmd(cmdConfirmReplace)` 投进去无人消费。**必须为策略任务另开答复通道**（StrategyHandle 持确认通道，`Manager.ConfirmReplace` 按任务类型分流投递）。此路径是本方案最大的控制面改动，含挂起等待期间的信号量槽位释放/重取（设计二「信号量槽位」条）与 RunCtx 取消防御性打断（声明13——确认阶段暂停/停止实际不可达，复杂度低于插件任务）。实施后须专项测试整体答复唤醒、排队唤醒、跨重启重弹、并发额度不被等待任务挤占。
- 风险2：taskManager 现有两处查重判定（`model.go:880-918` 与 `manager.go:525-575`）是近似重复的内联逻辑，改接新判定能力时须行为等价（尤其「查询失败保守弹窗」「空交集保留替换定位」两分支），回归靠现有 `duplicate_gate_test.go` 兜底。
- 风险3：替换链的**中断窗口**（软删后、回灌落库前的暂停/停止/崩溃）必须闭环：若回滚只挂「执行失败路径」而漏「停止路径」，中断后停留「旧 store 软删 + 新 store 未挂」半替换态。本方案经『软删后中断窗口与回滚收口』节对齐插件任务的既有自洽环收口（声明10），实施须专项验证三态（暂停/停止/崩溃）。
- 风险4：manifest 的 resource 结构（分享方作品结构）与接收方已有作品的 resource 结构可能不同（resource 实体无站点侧身份键，无法一一对应），决策2 的「角色交集替换」是绕开对应键的设计，若存在「同角色多 resource」作品（多页图文）语义为整体换血，需用户确认可接受。
- 风险5：多作品回滚清单为执行器**内存态**（软删成功后经 StrategyHandle 登记）——若进程恰在「软删完成、钩子登记完成前」崩溃，钩子丢失，死行只能靠回收站 TTL 收尾或用户停止后重试重弹。与插件任务崩溃边界同源（软删行即持久还原点，声明10），实施时评估是否需要数据驱动兜底。

## 背景与目标

用户实机测试「本机自分享 → 本机自接收」：预期弹覆盖确认、文件被替换，实际两者皆无（查重命中静默跳过，`导入完成：新建作品 0 / 跳过 1`）。根因：收件入库复用 import 的幂等跳过语义，与普通下载（插件任务重下）的「行级判定 + 覆盖确认 + 替换链」轨道分叉。

**目标**：share-receive 的收件查重接入普通下载轨道——同一套查重判定（键 + 行级门槛）、同一交互形态（任务面板 WaitingForInput + 覆盖确认弹窗）、同一替换链（软删备份 + 失败回滚复活）。查重判定逻辑提取为**独立能力**，本期 share-receive 接入，zip 导入（import 的另一消费方）后续接入（用户已拍板：zip 导入也弹覆盖确认，但本期不做）。

**非目标**：zip 导入的覆盖确认接入（仅预留能力面）；插件任务既有查重行为变更（仅把内联判定改为调用共享能力，行为等价）。

## 现状：两条查重轨道

| 维度 | 普通下载（插件任务） | share-receive（经 import） |
| --- | --- | --- |
| 查重键 | `(site_id, site_work_id)`，任务实体字段 | 相同，manifest 作品经站点名映射转本库站点（声明8） |
| 判定门槛 | 行级：所选板块与已有作品活行角色求交，交集非空才弹（声明2） | 无门槛，命中即跳过（声明1） |
| 用户决策 | WaitingForInput + ConfirmReplace（声明3） | 无 |
| 命中后 | 替换链：软删备份 → 新行挂载 → 失败回滚复活（声明4） | existing 一概不动（声明7） |

分叉点即三处：门槛判定、用户决策点、替换链。

## 设计

### 已定决策（用户拍板）

- zip 导入后续也接入覆盖确认，本期不做；查重判定逻辑提取为独立依赖，app 装配处自行组合，供后续消费方接入。
- 交互形态用任务面板 WaitingForInput（对齐插件任务），不用「失败 + 确认重试」的回收站形态。
- 零交集命中作品自动并入 ReplaceWorks（决策5，静默增补）。

### 决策重定依据（用户「完全复用」设想的核查结论）

决策1-4 初版曾列为「待决策」；用户质疑「查重逻辑与用户确认替换逻辑应**完全复用原有**，本不该存在这些决策」。逐项核查结论（对应锚点均在摘要声明）：

- 决策1（确认粒度）：现有前端覆盖确认弹窗**已为多任务列表形态**且答复为任务粒度（声明11），`store.add` 不去重令同 taskId 多行可渲染（声明12）——完全复用 = 每个冲突作品推一条现有 `taskStatus-duplicateDetected` 事件（同 taskId）+ `ConfirmReplace(taskId, action)` 整任务答复，唯一小改是 `store.remove` 按 taskId 清理全部行。「逐作品决策」需新事件载荷/新答复接口/新弹窗形态，违背完全复用，弃。
- 决策2（替换资源面）：`softDeleteReplaceTargets` 本就以 `(workId, roles)` 参数化（声明4），roles 传交集角色即「角色交集替换」——复用即所求，「作品资源面全量替换」是伪选项。
- 决策3（元数据/关联）：对齐插件任务「含元数据板块的替换即覆盖更新」+ 复用 import `ensure*` 系挂载路径，无独立选择余地。
- 决策4（确认挂起）：覆盖确认弹窗为**模态强制**（声明13），确认期间 UI 遮罩挡住任务操作栏、暂停/停止实际不可达——与普通任务同构；后端对 WaitingForInput 收到 pause 仅落 Paused 不取消在途（`model.go:768-781`），是防御性处理。故确认回路对中断仅需防御性取消分支，不做暂停/停止分态；真正中断窗口在确认答复之后（设计六）。

结论：用户设想成立，决策1-4 收敛为「完全复用」形态，不再存在取舍；四者的残余工作量是：决策1 前端一行 remove 修正、决策4 确认等待原语本身（StrategyHandle 新增方法，本属新执行面能力而非分叉）。

### 一、查重判定能力提取（新模块 `backend/duplicate`）

**职责**：输入「作品查重键 + 期望板块角色」，输出三分类判定。纯查询判定，无副作用。

```go
// DuplicateCheckItem 查重输入：站点名（manifest/URL 域，内部做名称→本库站点映射）+ 站点侧作品 ID + 该作品期望的板块角色集合（空=全量语义）
// DuplicateCheckResult 查重输出三分类：
//   未命中（本库无此作品，全新建）
//   命中无冲突（已有作品活行角色与期望角色零交集——不弹窗，保留已有作品 ID 供替换定位，对齐 model.go:915 现语义）
//   命中冲突（交集非空，携带交集角色明细，供弹窗展示）
type DuplicateChecker interface {
    Check(ctx context.Context, items []DuplicateCheckItem) ([]DuplicateCheckResult, error)
}
```

- 输入收**站点名**而非本库 siteID：三个消费方中 share-receive/zip 导入的键源在 manifest 域（站点名），统一名称入口；插件任务侧由调用方把 task.SiteID 反查站点名（一次查询，换取键形态全链统一——架构一致性优先）。站点名映射逻辑自 `mapExistingSites` 提取（声明8），实现组合 `ListSitesByNames` 仓储查询。
- 实现组合：站点名映射 + 作品批量定位（`ListWorksBySiteAndWorkIDs` 同型查询）+ resource 角色集合（复用声明6 的 `ListStoreTypeSetsByWorkIds`）+ 交集纯函数（`intersectRoles`/`sortedStoreRoles` 自 taskManager 迁入）。「查询失败保守弹窗」「板块空时已有任意活行即冲突」两分支语义随迁。
- 装配：app.go 构造一次，注入 taskManager（替换其两处内联判定）与 share（ReceiveExecution）。
- taskManager 改接后：`WorkChecker`/`WorkStoreRoleChecker` 两依赖（`model.go:278-282`）的职责被 `DuplicateChecker` 收编，按 DEAD_CODE_CLEANUP 评估退役。
- 模块 README 按 `doc/module-spec-template.md` 建立。

### 二、确认回路扩展（ExecutionStrategy 支持 WaitingForInput）

**问题**（风险1）：插件任务的确认是「执行返回 → 回命令等待 → `cmdConfirmReplace` 重入 run」；策略任务的 `Execute` 同步阻塞在 actor goroutine 内，cmdCh 无人消费。

**方案**：StrategyHandle 增加确认等待方法：

```go
// WaitReplaceConfirm 覆盖确认等待（决策1 完全复用形态）：置任务 WaitingForInput，对每个
// 冲突作品复用现有 PushDuplicateDetected 逐条推送（同 taskId 多事件、现有载荷与事件名不动，
// 前端 add 不去重自然渲染多行，声明12），阻塞直至用户整体答复或 RunCtx 取消。
// 返回整体决策（replace/skip，任务粒度，对应现有 ConfirmReplace 单值答复）；
// RunCtx 取消时返回取消信号，Execute 按约定不上报终态交控制面接管。
// 取消分支为防御性——模态弹窗期间暂停/停止实际不可达（声明13），真正中断窗口在确认之后。
WaitReplaceConfirm(conflicts []ConflictInfo) (decision ReplaceDecision, canceled bool)
// SetTerminalRollback 登记终态回滚（失败/停止时由控制面 setFailed 单点统一触发——
// 对齐插件任务回滚单点，见『软删后中断窗口与回滚收口』节；Execute 的取消返回路径
// 无法区分暂停与停止，不得自行回滚）
SetTerminalRollback(rollback TerminalRollback)
// TerminalRollback 终态回滚载荷：被软删的 victim store 清单（多作品）等，
// 由执行器在替换软删成功后登记
```

- 控制面：`strategyHandle` 实现内置确认通道；`Manager.ConfirmReplace` 按任务是否策略型分流——插件任务走既有 postCmd 路径不动，策略任务向确认通道投递答复。任务注册进 `waitingForInputMap`（供查找与前端状态展示），答复/取消时移除（对齐 `manager.go:687` 现有清理——任务停机路径自该确认注册表摘除，防后续确认命令误投）。
- **事件载荷与答复接口零新增**：对每个冲突作品调一次现有 `PushDuplicateDetected`（`progress_pusher.go:146`，同 taskId、不同 existingWorkId）；前端 `add` 不去重自然渲染多行，现有 `ReplaceConfirmDialog` 列表与 `ConfirmReplace(taskId, action)`/`ConfirmReplaceBatch` 接口完全复用（声明11/12）。唯一前端小改：`store.remove` 按 taskId 清理全部行（现只删首个匹配行，声明12）。
- 跨重启：等待中关 App = 无持久化决策，重启后手动恢复重跑 Execute → 重新拉 manifest 重新查重新弹窗（对齐插件任务 `skipDuplicateCheck` 执行期标记的内存态语义——运行期内确认替换后置位跳过查重、排队任务被唤醒时**特意保留**防二次弹窗，`backend/taskManager/model.go:566-571`；跨重启任务实例重建、标记随零值消失即重查重弹）。
- **RunCtx 取消打断等待（防御性）**：模态弹窗期间暂停/停止实际不可达（声明13，与普通任务同构），取消分支仅为防插件停用清场等旁路命令——控制面暂停/停止经 `runCancel` 取消 runCtx（`model.go:712`、`model.go:779`、`model.go:809` 等路径），策略执行的取消映射已有约定「RunCtx 取消时策略返回而不上报终态」（`model.go:665-667`、`execution_strategy.go:19-23`）——等待原语内部对 ctx 取消的 select 分支是本方案新建义务，取消链本身不新建；不做确认阶段的暂停/停止分态。
- **信号量槽位**：策略任务现状经 handleRunCmd 取信号量槽后进入执行（`runOnce`→`runStrategy` 分流，`backend/taskManager/model.go:653-663`），即 Execute 运行期间**占槽**。本方案要求 `WaitReplaceConfirm` 挂起等待期间释放槽位、答复/取消唤醒后重新排队取槽（**新建改动**，对齐插件任务命中冲突不入队不占槽的既有形态——`backend/taskManager/manager.go:564-575`，564 行注释「覆盖冲突：放入等待确认队列，不参与信号量派发」）——多策略任务同时等待不挤占并发额度。
- **业务中立纪律（执行面/控制面分离对齐）**：`WaitReplaceConfirm`/`SetTerminalRollback` 的载荷与语义只含任务域通用概念（已有作品 ID、冲突角色、替换决策、victim store 清单），禁止 manifest 作品 ID、分享链路概念漏入 taskManager——原语供后续消费方（zip 导入、插件任务执行面外提）复用。插件任务的「执行返回 + 确认命令重入」与策略任务的「执行内挂起等待」是同一控制面状态（WaitingForInput）的两种达成路径，本次**不合并**（插件任务轨道不动红线）；两轨收敛归插件任务执行面物理外提的延后计划（taskManager 模块 README「执行面策略」条所载延后项）届时自然完成。

### 三、替换能力抽取（resource 模块提供，两发起方复用）

`softDeleteReplaceTargets`/`restoreReplaceTargets` 的核心是**能力**（输入 `(workId, roles)` 纯领域参数，不感知任务语义，声明4），自 taskManager 抽为 resource 模块能力接口（`resource_store` 关联与活行过滤本就归 resource 域）：

```go
// 替换前置软删：软删作品下所选角色活行 store（已完成行移文件入备份、未完成行废弃）；返回被软删行清单（供回滚登记）
SoftDeleteWorkStoreRoles(ctx, workId, roles) (victims []StoreRef, err error)
// 失败回滚复活（按清单）：清本次新建行、备份还原文件、复活 victim。清单来源两途——
// 插件任务按 workId 数据驱动派生（同键最新死代圈定），策略任务用执行器登记的 victim 清单（多作品）
RestoreReplacedStores(ctx, scope RestoreScope) error
```

- taskManager 两个发起场景改接（行为等价，`deriveRevivableStores`/`deriveReplaceVictims` 等私有派生函数随迁 resource 模块）。
- `restoreReplaceTargets` 的「策略任务直接跳过」守卫（风险3 所在中断窗口的旧假设）删除——share-receive 接入替换后该假设不成立；插件任务路径的回滚仍由 `setFailed` 单点触发（声明10），策略任务回滚改经 `SetTerminalRollback` 登记的钩子在同一单点触发。
- 插件任务回滚中的「清本次新建行」依赖任务执行期 streams 状态；策略任务场景 ingest 相位三（ingest 内部阶段：相位一查重圈定、相位二文件落盘、相位三单事务入库）为单事务原子性——事务失败即整体不落库、事务成功即任务成功，故该步骤对策略任务天然不需要。

### 四、ingest 替换模式（ManifestIngestor 扩展）

```go
// IngestOptions 回灌选项：ReplaceWorks = 经用户确认要替换的 manifest 作品 ID 集（空 = 现状全跳过语义，zip 导入沿用）
type IngestOptions struct { ReplaceWorks map[int64]struct{} }
Ingest(ctx, manifest, fileSource, opts *IngestOptions)  // opts 为 nil 时行为与现签名完全一致
```

替换分支（`partitionWorks` 输出的 existing 中命中 ReplaceWorks 者——ReplaceWorks 全集 = 冲突确认替换集与零交集自动并入集的并集，见设计五）：

1. **资源面**（决策2 复用形态）：软删已有作品在**交集角色**上的活行 store（经能力三，走备份）；manifest 的 resources + stores 新建挂载到已有作品（新增角色与交集角色都挂）；本地独有角色（manifest 未含）保留不动。被软删光活行 store 的已有 resource 成空壳——物理删其残留关联行（`resource_store` 关联对软删行保留是替换链语义，此处空壳 resource 行按 DEAD 行处理规则净化，实施时对齐 `STORE_ASSOCIATION_LIVENESS_FILTER` 纪律）。
2. **元数据**（决策3 复用形态）：work 行字段按 manifest 覆盖更新（站点侧名称等），workID 不变。
3. **关联合并**（决策3 复用形态）：标签/作者/作品集关联按现有 `ensure*` 系（`ingest.go:397-419`）的 find-or-create 去重挂载到已有作品——本地已有关联不删，manifest 关联增量挂载。
4. **失败回滚**：ingest 相位三单事务失败 → 事务回滚不动库 → Execute 上报 Fail，由控制面 `setFailed` 单点触发执行器登记的回滚钩子复活软删行（设计六；软删发生在拉文件前、事务外，同插件任务时序）。
5. 导入结果统计扩展：`CreatedWorks/SkippedWorks` 之外增 `ReplacedWorks` 计数并按「确认替换 / 自动增补」拆分（决策5 明示形态），完成日志同步（「导入完成：新建 X / 替换 Y（确认 a / 增补 b）/ 跳过 Z…」）。

### 五、share-receive 接线（ReceiveExecution 时序改造）

```
反解载荷 → 拨中继 → 拉 manifest
→ 【新】DuplicateChecker.Check（manifest 作品键 + 作品角色集合）
→ 【新】命中冲突非空 → handle.WaitReplaceConfirm(冲突列表) → 整体决策（复用 ConfirmReplace 答复）
     （模态弹窗期间暂停/停止不可达，取消仅防御性——声明13）
→ 【新】ReplaceWorks 非空（确认替换与零交集并入）→ SoftDeleteWorkStoreRoles（各作品，交集角色）→ SetTerminalRollback 登记回滚清单
→ stageFiles 暂存（被裁决跳过的作品其文件条目不拉）
→ ingest 回灌（ReplaceWorks 全集；跳过作品走既有跳过；新作品走既有创建）
→ 成功清理暂存 Finish（现有）；失败/停止的回滚经 setFailed 单点钩子统一触发（设计六）
```

- 查重点在 **manifest 拉取后、文件拉取前**：确认发生在数据传输前，用户选跳过即省去对应作品的全量传输。
- **命中无冲突（零交集）作品的下游动作 = 并入 ReplaceWorks**（不经确认直接挂载到已有作品）——对齐插件任务「查重命中即挂已有作品，弹窗与否只决定用户确认、不决定挂载位置」语义（`backend/taskManager/model.go:915-916` 空交集仍置 existingWorkId、`model.go:922-927` existingWorkId>0 即挂已有作品置替换标志）。两种场景同一机制：① 初次执行时本地独有角色保留、manifest 新增角色直接增补挂载（如本地仅 audio 活行、manifest 带 image+video，不弹窗直接增补）；② 软删后恢复/重跑时延续替换（交集角色已软删成死行，软删步骤对其 no-op，manifest 挂载完成收尾）。此为接收侧新可感知行为（原静默跳过 → 静默增补），已列决策5 明示。
- 用户裁决**跳过**的作品不经此路径（软删未发生、活行在，恢复重跑重查命中冲突重新弹窗——对齐插件任务跳过标志内存态语义）；混合交集作品（部分角色冲突、部分零交集）被裁决跳过时为**整作品跳过**，其零交集角色同样不增补（对齐插件任务跳过即整任务的语义）。
- **失败/停止的暂存清理责任**：暂存保留供重试（既有语义，不新增清理路径）；任务删除后由启动清扫 `CleanupOrphanReceiveStaging` 回收任务行已不存在的暂存目录兜底（既有机制，`backend/share/task_execution.go:381-384`）。
- 决策不持久化（`skipDuplicateCheck` 执行期标记语义，见设计二「跨重启」条）：暂停/恢复/重试/跨重启均重跑 Execute 重新查重；软删前中断重新弹窗，软删后中断落零交集并入 ReplaceWorks 延续（设计六）。

### 六、软删后中断窗口与回滚收口

**中断窗口** = `SoftDeleteWorkStoreRoles` 成功之后、ingest 相位三（单事务入库）提交之前——含文件暂存全程与回灌事务执行中。此窗口内暂停/停止/崩溃若无闭环，即停留「旧 store 软删 + 新 store 未挂」半替换态（风险3）。确认阶段（弹窗打开）因模态遮挡不产生暂停/停止（声明13），中断窗口实际自**确认答复后、软删成功时**起算。插件任务对此已有自洽解法（声明10），share-receive 全面对齐：

1. **回滚单点 = setFailed**（`model.go:1964-1976`）：全部 Failed 置位——含停止路径——都经此单点触发回滚复活；**暂停不触发**，软删悬空是合法中间态（等恢复延续）。
2. **暂停 → 恢复 = 延续替换不重弹**：软删后该作品活行角色集合变小，恢复重跑的查重落「命中无冲突（零交集）」分类（既有分支，`model.go:915-916` 空交集不弹窗、保留已有作品 ID 供替换定位），经设计五「零交集并入 ReplaceWorks」机制挂载 manifest 收尾——替换语义自然延续，用户不需二次确认（已有一次确认在先，对齐插件任务排队唤醒保留 `skipDuplicateCheck` 的防二次弹窗意图，`model.go:566-571`）。
3. **停止 = 终态回滚复活**：控制面置 Failed 经单点钩子复活软删行；此后用户重试则活行复原、查重重新命中重新弹窗——即「停止 + 重试」构成二次确认的退出路径。
4. **崩溃 = 软删行持久还原点**（`model.go:1312-1314`）：软删行本身即还原锚，重启后停止该任务即回滚，或重试延续替换；不依赖执行期内存状态。

share-receive 落地形态：

- 执行器在软删成功后立即经 `SetTerminalRollback`（设计二）登记 victim 清单与涉及作品；控制面 `setFailed` 单点统一触发钩子复活（多作品清单由执行器自持——插件任务的 `m.workId` 单值与 streams 新建行状态不适用于策略任务多作品场景）。
- Execute 的取消返回路径（暂停/停止共用 RunCtx 取消，无法区分）**不做回滚**——统一交终态单点，杜绝「暂停即回滚」破坏恢复延续。
- ingest 相位三单事务原子性：回滚不需「清本次新建行」步骤（事务失败整体不落库、成功即任务成功，设计三末条）。
- 「替换后失败」与「软删后中断」共用本节收口——风险3 的半替换态在此闭环；钩子登记前的崩溃窗口见风险5。

## 对插件任务（普通下载）执行流程的影响面（实施红线）

插件任务的执行流程**结构与时序不变**——查重点（执行入口、下载前）、软删点（确认后、Start 前）、下载形态（流式直写最终位置、partial 续传）、回滚点（setFailed 单点）全部保持原位。方案改动全部为「实现搬家」性质：

1. 查重判定改接（阶段1）：两处内联判定的「定位+交集计算」换调 duplicate 模块；控制面动作（existingWorkId 赋值、WaitingForInput 置位、事件推送、确认重入）**不动**。
2. 替换链改接（阶段2）：实现迁 resource 模块，调用点与调用时机不变。
3. setFailed 分流（阶段3）：插件任务走原 restoreReplaceTargets 路径，语义不变（守卫删除对 strategy 为 nil 的任务无影响）。
4. ConfirmReplace 分流：插件任务维持既有 postCmd 路径，前端旧接口不动。
5. 唯一可感知差异：task.SiteID 反查站点名的一次额外查询（键形态统一代价，设计一）。

行为等价回归锚：`backend/taskManager/duplicate_gate_test.go`、`backend/taskManager/replace_softdelete_test.go`。实施中若发现任何「为 share-receive 方便而动插件任务控制面语义」的诱惑，视为越界，回到本节红线。

另注：两条链路的**物理时序差异不拉平**——插件任务流式直写最终位置，share-receive 先暂存后整包回灌。暂存形态的三项既有设计锚：暂存目录不在 store/ 白名单子树（fsmonitor 不感知）、断点续传锚＝暂存文件已落盘字节数、拉取流经 E2E 解密。方案对齐的是判定门槛、用户决策形态、替换与回滚链三件语义，不是执行时序的物理形态。
