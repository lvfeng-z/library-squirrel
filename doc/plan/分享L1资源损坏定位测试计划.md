# 分享接收 L1 资源损坏与进度超100% 定位测试计划

## 审查摘要

**背景**：L1/L2 双机终审实测（`VERIFY-K-M-N-L双机终审.md` 对账记录，Excel B10/B11）发现：多作品同任务接收（父+子任务树，L 交付）时**部分作品文件损坏（非必现）**，且被损坏作品**进度渲染超出 100%**。原因不确定；双机环境上下文不互通，实测协调困难。本计划先定位根因、再谈修复。

**已核验（带锚点）**：
- 收件暂存与续传：`backend/share/task_execution.go:36-38`（staging 根目录 `share-receive`）、`:443-474`（stageFiles：进度基数=全部条目声明字节，初始进度=已暂存字节盘点）、`:519-539`（stageFile：`0<暂存大小<声明大小`→从 offset=暂存大小续传，`==声明`→跳过）、`:562-592`（appendFetch：应答头 offset/size 校验，实收≠声明→`errStreamTruncated`）。
- 宿主侧并发流上限：`backend/share/session.go:49` `defaultMaxStreams = 8`（对齐中继默认，READ 记录于 `share/README.md:41`）。
- 任务级并发：`app.go:1180` taskManager `NewManager(maxParallel=ImportSettings.MaxParallelImport)`；默认 `MaxParallelImport=3`（`backend/settings/service.go:41`）→ **有效并发流 = min(maxParallel, 8)，默认 3**。
- 父任务进度聚合：`backend/taskManager/manager.go:1285-1395`（子任务快照 atomic 进度求和 + `PushParentProgress`）。
- 既有测试基建：`backend/share/receive_test.go:569` `TestReceiveExecutionResumeFromStaging` 已断言「续传 offset=已暂存字节 + 拼接内容与源一致」；`share_test.go:1100/1132` 在驻守卫两面（跳过重拨/退出后可重拨）。**未见**并发多流 hash 校验、大文件（100MB）、崩溃注入类测试（推断：据测试清单盘点，未见即未有，非代码反证）。

**待决策**：
- D1：压力测试并发档位——默认 `MaxParallelImport=3` 使「8 并发流」压测实际只到 3 流；是否临时调高该设置（或新增测试专用并发档）以触达 8 流上限。
- D2：进度>100% 若为纯前端渲染缺陷，修复归属前端还是统一后端进度口径（本计划先定位，修复归属届时定）。

**自曝风险**：
- 损坏**非必现**——单机桩测可能无法复现；需预留迭代预算，复现失败则退回双机复核矩阵（§6）。
- 单机桩测（relaystub + 真实宿主会话，同进程）与真实网络（经真实中继）存在 relay 帧转发细节差异——若根因在 relay 侧，桩测不现；双机复核为最终裁决面。
- 本计划只定位与测试，**不含修复代码**；修复在定位后另立任务。

## 1. 背景与症状

- 症状一（文件损坏）：多作品同任务（父「拉取分享」容器 + 每作品一子任务）接收时，部分作品文件损坏（非必现；L1/L2 两次测试均现，具体作品不固定）。
- 症状二（进度>100%）：被损坏作品的任务进度渲染超出 100%。
- 观察约束：双机各自跑一端，上下文不互通 → 实时交叉验证困难，需「各自落证据、事后离线比对」的策略（§6）。

## 2. 根因候选（均未证实，按嫌疑排序）

| 编号 | 假设 | 机制 | 指向代码 |
|---|---|---|---|
| H1 | 宿主侧并发流服务缺陷 | 宿主单隧道并发服务 N 个收件流（上限 8），流间帧/缓冲隔离缺陷→某流拿到别的流的数据或错位字节 | `session.go` 流调度（`defaultMaxStreams=8` 的并发面） |
| H2 | 收件侧续传 offset 缺陷 | 暂存文件大小与实际有效内容不一致（中断残留/并发写竞态）时，从错误 offset 续传→gap/重复段 | `task_execution.go:519-539` |
| H3 | 应答头校验盲区 | `appendFetch` 的 offset/size 校验存在未覆盖路径（如重试后应答头错配未被拒） | `task_execution.go:562-592` |
| H4 | 进度>100% 独立缺陷 | 子任务 `ReportProgress(total, done)` done 双计（初始暂存盘点+续传 delta 重复）或父任务聚合超 100%；**可能与文件损坏无关** | `task_execution.go:453-474`、`manager.go:1385` |
| H5 | 暂存→导入转换缺陷 | `stagedFileSource` 读取的暂存文件与真实写入不一致（缓冲/flush 时序）；或导入复制并发竞态 | `task_execution.go:137`（Ingest） |

> 说明：TCP 只保证连接内字节完整性，不保证「并发流各自得到正确字节」——H1 与 H2 是首要嫌疑；H4 与损坏很可能相互独立，需分轨。

## 3. 测试策略

- **优先单机可控复现**：复用现有 `relaystub_test.go`（中继桩）+ 真实宿主会话 + 真实收件执行器（`receive_test.go` 基建），同进程双角色。单机可确定性放大并发/文件数/中断点，逐文件 hash 校验，不受双机上下文约束。
- **双机复核兜底**（§6）：宿主端导出源文件 hash 清单、收件端导出收件文件 hash 清单，**事后离线比对**——两机各自跑脚本，不需实时互通。
- **两症状分轨**：文件损坏（H1/H2/H3/H5）与进度>100%（H4）各自独立测试，避免互相干扰。

## 4. 单机测试矩阵

> 公共设施：为 receive 测试夹具补 **hash 校验**（暂存文件与导入内容 sha256 与源一致）与**大文件**（≥100MB 真实字节，勿用小缓冲拼凑）、**崩溃注入**（执行中途强杀协程/取消 ctx）。现有 `ingestor.contents` 断言内容等价，需升级为逐字节 hash。

## 5. 进度>100% 独立定位（H4）

- 捕获路径：子任务 `ReportProgress`（`task_execution.go:465/484` 的 done 累计）→ taskManager 快照 atomic（`manager.go:1393-1395`）→ 父聚合（`:1385`）→ 前端渲染。
- 定位问题：在链路每级加断言/打点，判断超值出现在「收件执行 done 计算」「快照 atomic 更新」「父聚合」「前端渲染」哪一级。
- 特别核对：重试任务的初始进度（`task_execution.go:474` 已暂存字节盘点）与续传 delta 是否重复计入；父任务重试子任务时聚合是否残留旧值。

## 6. 双机复核方案（缓解上下文不互通）

1. **宿主端**：分享发布后脚本导出 `源文件hash清单.json`（作品→文件→{sha256, size, relPath}）。
2. **收件端**：接收完成（含失败重试）后脚本导出 `收件文件hash清单.json`（暂存与导入后两处）。
3. **离线比对**：比对脚本按 relPath 对齐两清单，输出差异（缺失/大小不符/hash 不符）与进度超值记录。
4. 复测矩阵与单机 T1/T3/T4 对齐（并发档、文件大小、中断点），双机不互通仅影响实时协调，不影响事后比对。

## 9. 执行结论（2026-08-30）

### 复现与根因

- **复现**：新增测试 `TestL1TunnelDropResume`（传输中途 dropTunnel 断连）在修复前**稳定失败**——收件文件 sha256 与源不符。
- **根因**（`backend/share/task_execution.go`）：`fetchWithRetry` 内层重试对**同一 offset 重发 file 请求**，而 `appendFetch` 的应答 body 以 **O_APPEND 追加写**暂存。传输中断时首次尝试已落盘部分字节；内层重试再从同 offset 追加 `head.Size` 字节 → 暂存文件超长（声明字节 + 部分字节）→ 收件内容损坏；同时部分字节被 `onProgress` 计过一遍、重试又计一遍 → **进度超 100%**。两症状同源。
- **非必现成因**：仅「传输中断且内层 `fetchWithRetry` 重试」路径触发；正常拉取/取消/预写续传均不触发，故既有测试未覆盖。
- **修复**：`fetchWithRetry` 在 body 已部分消费内容（`r.got > 0`）后失败时**不再内层重试**，交外层 `stageFile` 按实际落盘字节重算续传锚（该逻辑本已正确）→ 文件不超长、进度不双计。

### 测试结果

- 修复前：并发/续传/取消/100MB/限速用例全绿；`TestL1TunnelDropResume` FAIL（hash 不符）。
- 修复后：7 项定位测试全绿；`go test ./backend/share/` 全绿；`go build ./backend/...` 通过。
- `-race` 因环境 cgo 工具链缺失不可用（Windows 已知限制），未执行。
