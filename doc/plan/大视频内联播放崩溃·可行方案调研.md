## 审查摘要

### 关键声明（抽查项，均有本会话实测锚点）

- **声明1·崩溃源规格**：实测崩溃的作品133 videoMain = H.264 High@L5.2、3840×2160、50fps、24.7Mbps、1.56GB、524s。证据：`ffprobe -show_entries stream`（输出 `codec_name=h264 profile=High level=52 width=3840 height=2160 bit_rate=24742274`）。
- **声明2·非 Go 后端崩溃、非 JS 异常、非经典 AV**：崩溃时 `server.log` 末尾为启动完成行（`log/server.log:3961`）无 panic；`frontend.log` 末尾停在挂载日志（`log/frontend.log:1226-1227`）error handler 未记录异常；Windows 事件查看器崩溃时段无 library-squirrel/WebView2 的 1000/1002 记录（`Get-WinEvent -FilterHashtable @{LogName='Application';Id=1000,1002,1026} -MaxEvents 25`）→ 符合 WebView2 渲染进程原生静默终止（Crashpad 不写系统日志）。
- **声明3·排除 GPU 硬件加速根因**：经 `application.WindowsOptions.AdditionalBrowserArgs: ["--disable-gpu"]` 注入（Wails3 通路 `webview_window_windows.go:2078-2079`），实测 WebView2 浏览器主进程命令行带 `disable-gpu PRESENT`（`powershell Get-CimInstance Win32_Process` 抓取）+ 用户观察到弹窗动画掉帧（GPU 合成关闭副作用），**133 仍崩** → 根因不在 GPU 解码/渲染路径。注：环境变量 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 通路**无效**（Wails3 Go loader 在 `webviewloader/env_create.go:169` 强制置空），必须走 Options 通路。
- **声明4·现状内联播放实现**：`VideoRenderer.vue` 用 `<video :src preload="none">`，源取 `videoMain?.filePath || videoTrack?.filePath`，经 `buildStoreUrl` → `/store/{encoded}` → 后端 `StoreFileHandler.ServeHTTP`（`http.ServeFile` 支持 Range，已流式传输）。证据：`frontend/src/components/resource/renderers/VideoRenderer.vue:13-31`、`backend/assetserver/store_handler.go:54-110`。
- **声明5·关键判别实验结论**：
  - **实验A（HLS 切片文件）**：ffmpeg `-codec copy` 把 133 切成 87 个 .ts 分片（保 4K 不重编码，秒级生成 215x 实时速度），hls.js 播放 → **不崩、有画面**。分片实测 `width=3840 height=2160`（4K 未降级）。
  - **实验B（纯前端 MSE，不写磁盘）**：从原文件 `/store/` Range 服务按 4MB 块流式拉取 → mp4box 在 JS 内存重封 fMP4 → MSE `appendBuffer` → **读完整整 1564MB 不崩**（仅探针的 mp4box 分段编排未调通导致无画面，且循环终止条件 bug 触发 416，均非崩溃）。
  - 两者共同点：**不让 `<video>` 一次性接收整文件 / 不让 Chromium 自管大缓冲**，即不崩。
- **声明6·根因定性**：根因为 Chromium 媒体管线在 `<video :src>` 模式下对超规格源（大体积/高码率）的缓冲管理失控，致渲染进程内存触及上限被静默 kill。**精确机制无 dump 不可 100% 锁定**，但「缓冲失控」由实验A/B 的对照组强支撑（切片/MSE 限制缓冲即不崩）。

### 待决策（实施时拍板，当前不阻塞）

- 决策1·**三条可行路径选哪条**（见第三节，均已实测不崩）：路A 零磁盘纯前端 MSE / 路B HLS 按需临时切片 / 路C HLS 后端流式管道不落盘。
- 决策2·**触发时机**：用户主动点按钮生成 vs 打开大视频详情自动处理。
- 决策3·**阈值**：多大规格走特殊处理（当前无 size/码率字段，`persistent_store` 仅 `width/height/status`，`persistent_store.go:17-26`；视频不填 width/height，须读文件 ffprobe 判定）。

### 自曝风险

- 风险1·**路A 的画面未实测调通**：实验B 只证明"不崩"，mp4box 的 init/media segment 编排（`initializeSegmentation`/`onSegment` 顺序、codec 字符串）未调到出画面。正式实现需重写探针逻辑，存在"调通后发现仍有问题"的小概率。
- 风险2·**seek（拖进度条）**：路A（纯前端 MSE 按 offset 顺序拉取）和路C（后端流式管道）都难随机定位，需额外按时间→字节偏移的索引机制；路B（HLS）天然支持 seek（m3u8 有时间映射）。
- 风险3·**HEVC 兼容**：实测作品45（HEVC 4K）当前"黑屏有声"——Chromium 无 HEVC 软解、依赖系统 GPU 硬解（本机有 HEVC 扩展时可用）。三条路径若保原 codec，HEVC 仍受此限制；若 HLS/MSE 管线统一转 H.264 则顺带解决（但引入重编码开销，与"不重编码保画质"取舍）。
- 风险4·**精确崩溃阈值未知**：720p/1080p/多大规模会崩无边界，阈值（决策3）靠经验。

## 一、问题与根因

**问题**：播放大视频（4K/50fps/24.7Mbps，1.5GB）时整个 app 崩溃。`preload="none"`（提交 `60f4e33`）挡住了"打开详情即崩"，但点播放仍崩。

**根因（高置信度，机制为推测）**：`<video :src>` 让 Chromium 媒体管线自管整个大源的缓冲，缓冲累积失控致渲染进程内存爆被静默 kill（声明2/6）。`--disable-gpu` 二分排除 GPU 路径（声明3）。**避免崩溃的关键 = 不让 Chromium 一次性接管整文件的缓冲**——切片或 MSE 人工控制缓冲均可（声明5）。

## 二、三组对照实验结果

| 方案 | 崩溃 | 画质 | 磁盘写入 | 实测状态 |
|---|---|---|---|---|
| `<video :src>`（现状） | **崩** | 4K | 无 | 已知 |
| HLS 切片文件（hls.js） | **不崩** | 4K | +≈原文件大小 | ✅ 有画面 |
| 纯前端 MSE（mp4box，不写磁盘） | **不崩** | 4K | **零** | ✅ 不崩（画面未调通） |

## 三、三条可行路径（实施时选一）

### 路A·零磁盘纯前端 MSE（用户偏好"不写磁盘"）

- 从原文件 `/store/` Range 服务按字节流式拉取 → mp4box 在 JS 内存重封 fMP4 → MSE `appendBuffer`。**全程零磁盘、后端零改动**。
- 优点：完全不写磁盘、后端零改动、复用现有 Range 服务。
- 缺点：前端实现最复杂；实验B 仅证"不崩"，mp4box 分段编排待调通出画面；seek 难做（需时间→字节偏移索引）。
- 实施要点：mp4box 标准用法（`createFile`→`appendBuffer(fileStart)`→`onReady`→`setSegmentOptions`+`initializeSegmentation`+`start`→`onSegment` 出 fMP4 分片→喂 SourceBuffer），codec 字符串须从 `info.tracks[].codec` 动态取（探针写死 `avc1.640028,mp4a.40.2` 是简化）。

### 路B·HLS 按需临时切片，关闭即删

- 用户打开大视频详情 → 后端 ffmpeg `-codec copy` 秒级切到 `os.TempDir()` → hls.js 播 → 关闭详情删分片。
- 优点：hls.js 现成成熟、有画面、seek 天然支持、切片秒级。
- 缺点：运行时临时文件（≈原文件大小，关闭释放，不污染资源库）；每次进详情重切（秒级可接受）。
- 实施要点：临时目录前缀（如 `ls-hls-`）+ 启动清理残留（仿合并 `CleanupResidualTempFiles`）；store 模型零改动（不入库）。

### 路C·HLS 后端流式管道不落盘

- 后端开流式 endpoint：goroutine 跑 `ffmpeg -i 原文件 -c copy -movflags +frag_keyframe+empty_moov -f mp4 pipe:1`，stdout 经 HTTP chunked 推前端，前端 hls.js 或 MSE 消费。
- 优点：零磁盘、保原 codec、复用 ffmpeg。
- 缺点：后端要做流式 endpoint（中等复杂度）；seek 需后端按时间重启管道。

### 选型建议（实施时参考）

- 若"绝对不写磁盘"是硬需求 → **路A**（已证不崩，补画面实现）。
- 若求实现速度与成熟度 → **路B**（hls.js 现成、有画面、seek 自然）。
- 若要零磁盘且避开前端 mp4box 复杂度 → **路C**（后端流式管道）。

## 五、复现/验证命令备忘

```bash
# 探测源规格
ffprobe -v error -select_streams v:0 -show_entries stream=codec_name,profile,level,width,height,bit_rate -of default=noprint_wrappers=1 "<videoMain绝对路径>"

# 切 HLS（不重编码，秒级）
ffmpeg -y -i "<src>" -codec copy -start_number 0 -hls_time 6 -hls_playlist_type vod -hls_segment_filename "<out>/seg_%04d.ts" "<out>/index.m3u8"

# 抓 WebView2 进程确认 Chromium 标志注入
powershell Get-CimInstance Win32_Process -Filter "Name = 'msedgewebview2.exe'"
```
