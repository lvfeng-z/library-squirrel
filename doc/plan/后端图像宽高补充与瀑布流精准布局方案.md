# 后端图像宽高补充与瀑布流精准布局方案

## Context（背景与现状）

### 问题链路
瀑布流（`CardGrid.vue`，A2 方案）在滚动加载时出现「某列长段空白 → 加载后该列扎堆 → 其他列空白」的震荡。

**根因**：前端在图片 `load` 前无法知道图片高度（后端 DTO 不含图像尺寸），`placeItem` 用塌陷的 `offsetHeight`（~60px，只剩 info 文本区）计入列高，导致列高估算严重失真；图片 `load` 后高度暴涨，且为保「追加零移位」只做单列重排（`relayoutColumnFrom`），无法全局重平衡 → 震荡。

### 已排除的方向
- 检测列高 / 直接检查 DOM：数据源（`offsetHeight`）在图片 `load` 前就是塌陷的，换测量方式无效（浏览器渲染的物理限制）。
- 检测空白触发加载：空白是「高度算不准」而非「内容不够」，加载更多不解决根因，且要填平需移动已有卡片 → 回到 A1 闪烁。

### 治本方向
**后端在资源入库时提取图像宽高（width/height 像素值），随 DTO 透传到前端**。前端 `CardGrid` 在 `placeItem` 时用宽高按列宽等比预算卡片高度 → 首屏即均衡，图片 `load` 后高度与预算一致（无需重排）。这是唯一能让「追加零移位」与「列间均衡」兼得的解。

> 采用用户指定的 **width / height 像素值**（非宽高比）：像素值更直白、DB 可读、前端可灵活派生比例或绝对值，且 `image.DecodeConfig` 原生返回的就是像素值。

## 目标

1. `PersistentStore` 实体新增 `Width` / `Height` 字段，记录图片像素尺寸（非图片资源为 0）。
2. 资源入库时自动提取宽高，覆盖所有落盘路径（流式下载、一次性写入、本地导入）。
3. 宽高随 `PersistentStoreDTO` 透传到前端。
4. `CardGrid` 用宽高预算卡片高度，首屏精准布局；无宽高时回退到 A2 的 `ResizeObserver` 重排。
5. 旧数据（宽高为 0）不阻塞，前端 fallback。

## 总体数据流

```
插件返回图片字节流 → taskManager.downloadLoop 写入 storeWriter
  → persistentStore.storeWriter.Complete() / Store() / StoreFromExternal()
    → [新增] 文件落盘后 util.DecodeImageDimensions(absPath) 读头部解码
    → 填 store.Width / Height → repo.Save/Update（与状态更新合并，不增加 DB 次数）
  → entity.PersistentStore{Width, Height}
  → NewPersistentStoreDTO → ResourceFullDTO.thumbnailStore/workStore.{width,height}
  → 前端 bindings（wails3 generate bindings -ts 重新生成）
  → WorkCardItem.resource.thumbnailStore.{width,height}
  → CardGrid getDimension(item) → placeItem 预算卡片高度
```

### 2. 宽高解码工具（新增）
新建 `backend/util/image.go`，提供纯函数：

```go
package util

import (
    "image"
    _ "image/gif"
    _ "image/jpeg"
    _ "image/png"
    "os"
    "strings"

    _ "golang.org/x/image/bmp"
    _ "golang.org/x/image/webp"
)

// imageExts 支持解码的图片扩展名（与前端 WorkCard IMAGE_EXTENSIONS 对齐）
var imageExts = map[string]bool{
    ".jpg": true, ".jpeg": true, ".png": true,
    ".gif": true, ".webp": true, ".bmp": true,
}

// IsImageExt 判断扩展名是否为可解码的图片格式
func IsImageExt(ext string) bool {
    return imageExts[strings.ToLower(ext)]
}

// DecodeImageDimensions 读取图片头部，返回宽高（像素）。仅读头部几 KB，不解码全图。
// 格式不支持或文件损坏时返回 error（调用方容错，宽高留 0）。
func DecodeImageDimensions(filePath string) (width, height int, err error) {
    f, err := os.Open(filePath)
    if err != nil {
        return 0, 0, err
    }
    defer f.Close()
    cfg, err := image.DecodeConfig(f)
    if err != nil {
        return 0, 0, err
    }
    return cfg.Width, cfg.Height, nil
}
```

- 用 `image.DecodeConfig`（只读头部，O(几 KB)，不解码全图，性能可控）。
- 空白导入注册格式：标准库 jpeg/png/gif + `golang.org/x/image` 的 bmp/webp。
- **webp 支持需新增依赖** `golang.org/x/image`（见决策点 1）。

### 3. persistentStore.Service 提取宽高（内聚，不改 taskManager）

新增私有方法（`backend/persistentStore/service.go`），在文件落盘后、写库前/同次 Update 中填宽高：

```go
// fillImageDimensions 若记录为图片，读取文件头部解码填入 Width/Height。
// 解码失败时仅记日志、留 0，不阻断入库主流程。
func (s *Service) fillImageDimensions(store *domain.PersistentStore, absPath string) {
    if store == nil || !store.FilenameExtension.Valid || !store.FilePath.Valid {
        return
    }
    if !util.IsImageExt(store.FilenameExtension.String) {
        return
    }
    w, h, err := util.DecodeImageDimensions(absPath)
    if err != nil {
        logger.Log.Warn("提取图片宽高失败，留空",
            zap.String("path", absPath), zap.Error(err))
        return
    }
    store.Width = w
    store.Height = h
}
```

三个落盘点调用（均不增加 DB 操作次数）：

**a. `storeWriter.Complete()`（service.go:86-113，原图流式下载完成）**
在 `record.Status = StoreStatusComplete` 之后、`repo.Update` 之前插入：
```go

```
> `storeWriter` 是包内私有结构，`fillImageDimensions` 可提为包级函数 `fillImageDimensions(store, workDir)` 供 `storeWriter` 与 `Service` 共用，避免给 `storeWriter` 注入 `*Service`。

**c. `StoreFromExternal()`（service.go:480-537，本地导入）**

### 2. CardGrid 新增 getDimension prop + placeItem 预算
`frontend/src/components/common/CardGrid.vue`：

props 新增：
```typescript
getDimension?: (item: T) => { width: number; height: number } | undefined | null
```

布局常量（与 `WorkCard` 样式对齐）：
```typescript
const CARD_PADDING = 8        // .card-grid-container padding 4*2
const MAX_IMG_HEIGHT = 400    // WorkCard .work-card-image max-height = calc(500-100)
const INFO_HEIGHT = 60        // info 区（WorkInfo + AuthorInfo）估算，各卡同值不影响列均衡
const MIN_REAL_HEIGHT = 100   // offsetHeight ≥ 此值视为图片已 load
const DEFAULT_CARD_HEIGHT = 300 // 无宽高且未 load 时的默认估值
```

`placeItem` 用预算高度计入列高：
```typescript
function estimateCardHeight(el: HTMLElement, index: number, colWidth: number): number {
  const dim = props.getDimension?.(props.items[index])
  if (dim && dim.width > 0 && dim.height > 0) {
    // 图片按列宽等比缩放，受 max-height 限制
    const innerWidth = colWidth - CARD_PADDING
    let imgHeight = (innerWidth * dim.height) / dim.width
    if (imgHeight > MAX_IMG_HEIGHT) imgHeight = MAX_IMG_HEIGHT
    return imgHeight + INFO_HEIGHT
  }
  // 无宽高：图片已 load 用真实值，否则用默认估值
  return el.offsetHeight >= MIN_REAL_HEIGHT ? el.offsetHeight : DEFAULT_CARD_HEIGHT
}
```

`placeItem` 内 `columnHeights[col] = y + estimateCardHeight(el, index, colWidth) + GAP`，其余逻辑不变。

> `INFO_HEIGHT` 是估算值，但**对所有卡片相同**，只影响容器整体高度，不影响列间均衡（均衡由图片高度比例决定，比例来自真实宽高，是准的）。图片 `load` 后 `ResizeObserver` 仍会用真实 `offsetHeight` 经 `relayoutColumnFrom` 微调——双保险。

## 数据迁移策略

**不主动回填**（推荐）：旧 `persistent_store` 记录 `width/height = 0`，前端 `getDimension` 返回 `undefined` → `CardGrid` fallback 到 A2 的 `ResizeObserver` load 后重排（旧数据首屏有推移，`load` 后修正）。

| 策略 | 评估 |
|------|------|
| **不回填（推荐）** | 零迁移风险；旧数据首屏有推移但 `load` 后正常；新数据精准，随使用占比自然上升 |
| 启动时全量回填 | 阻塞启动、大量 IO；不推荐 |
| 后台懒回填 | 空闲时批量解码限速回填；复杂度高；可选增强，非本次 |

可选增强：提供一个「重建宽高」的后台任务（管理员手动触发，限速遍历 `width=0` 的图片记录解码回填），不在本次范围。

## 容错

| 场景 | 处理 |
|------|------|
| 非图片资源（video 等） | `IsImageExt` 过滤，不解码，`width/height = 0` |
| 图片解码失败（损坏/格式异常） | `DecodeImageDimensions` 返回 error，warn 日志，留 0，**不阻断入库** |
| webp | 引入 `golang.org/x/image/webp` 支持；若不引入则 webp 留 0 fallback |
| 旧数据 `width=0` | 前端 `getDimension` 返回 `undefined`，fallback 到 `ResizeObserver` |
| 宽高提取异常 | 永不影响资源可用性（下载已完成，提取是增强） |

## 风险与决策点

1. **webp 支持**：引入 `golang.org/x/image`（推荐，webp 是常见格式，否则 webp 作品仍失真）vs 不引入（webp 留 0 fallback）。**推荐引入**。
2. **数据迁移**：不回填（推荐）vs 懒回填。**推荐不回填**，可选增强另开。
3. **`INFO_HEIGHT` 估算值**：固定 60px（推荐，不影响均衡）vs 让使用方传入更精确值。
4. **`getDimension` 重复逻辑**：抽 `ImageDimension.ts`（推荐 DRY）vs 各使用方内联。
5. **清理 `visualWidth/visualHeight`**：本次顺手清理（推荐）vs 保留。
6. **SDK 仓库改动**：本方案需改 `library-squirrel-sdk`（同级目录的独立仓库），需确认 SDK 仓库的可提交性（是否一并提交 + 版本号）。**待确认**。
