# 配置升级迁移方案（plugin_storage schema_version + 迁移钩子）

> 本文档属派生图 plugin-convention-release-prep 的 E 节点（配置升级迁移）。状态：主要决策已定（决策1–9），待用户审查，E 本身未动手实现；其阻塞子节点 K（重装路径修复）已实现并通过实测。

## 审查摘要

**关键声明（抽查项，每条挂锚点）：**

- 声明1：`plugin_storage`（插件统一 KV 存储）是**扁平 KV**，按 `(plugin_id, key)` 唯一键、`value` 为不透明 `NullString`、无版本维度——`backend/base/model/entity/plugin_storage.go:11-17`。
- 声明2：插件 settings（用户配置项）与插件自存 KV **共用 `plugin_storage` 单表**——`backend/plugin/plugin_setting_service.go:56,92-94`。
- 声明3：升级/重装**保留 plugin_id**——`backend/plugin/service.go:350-362`（`reusePlugin` 分支）+ `service.go:397`（`plugin.ID = reusePlugin.ID`）；配置行不被安装/卸载/重装/deactivate 删除（仅 `DeleteValue`/`ResetSetting` 主动删）——**物理不丢，真正风险是语义丢失**。
- 声明4：**写侧**链路 `pluginContext.SetValue`（`backend/plugin/extension/plugin_context.go:160`）持有 `pluginInfo.ID`，host 可在此层盖版本戳、插件无感；`PluginInfo` 结构见 `backend/plugin/extension/loader.go:410`。
- 声明5：**读侧** `GetValue` 返回解密明文 `string`、`GetAllValues` 返回 `map[string]string` 解密明文（`backend/plugin/plugin_storage_service.go:32-44,66-84`）；SDK 接口 `library-squirrel-sdk/dto/context.go:13,17`；proto `library-squirrel-sdk/proto/plugin.proto:334,338,378,387`。
- 声明6：`contractVersion`（「契约稳定性与版本化」节点落地）是 host↔plugin **协议轴**（`backend/plugin/extension/loader.go:34,44`），与新增的 `configSchemaVersion`（插件配置 schema 轴）**正交**。

**待决策：** 主要决策已定（见『已定决策』决策1–9）；剩余仅 proto 字段命名、Go 返回形式（结构体 vs 多返回值）等实现细节，不阻塞实施。

**自曝风险：**

- 风险1（**已由 K 节点修复，记录在案**）：原"`ReinstallFromPath` 升级路径在 installed 态撞 `ErrPluginAlreadyExists`"——K 节点已修（`install`/`installCore` 加 `reinstall` 标志，`service.go:342,352-354`，`ReinstallFromPath` 传 true 走 `reusePlugin` 覆盖分支），并通过用户实测。不再构成风险。
- 风险2：读接口**破坏性变更**（`GetValue`/`GetAllValues` 返回带版本）波及所有现有插件，需跨**主程序 + SDK + localImport + pixivSuite** 四仓库同步适配并 **bump contractVersion**；现有插件不升级则与新版主程序不兼容。
- 风险3（已定 best-effort，其代价为风险）：迁移报错时按决策7跳过该 key 继续激活——若被跳过 key 的旧 schema 值会导致插件运行时崩溃，则该次激活可能异常；靠 host 第⑤节告警 + 下次 Activate 幂等重跑兜底（插件发版修转换函数后自愈）。
- 风险4：per-row 版本**不保证跨 key 原子性**——联动配置（如 settings 里 `select`+`min`+`max`）迁移过程中存在 key 间版本不一致的暂时窗口；host 第⑤节能感知"存在 < 目标的行"但不懂联动语义，靠幂等重跑最终一致 + 插件 step 设计（联动 key 放同一 step）缓解。

## 已定决策（用户拍板）

1. **版本声明位置**：`plugin.json` 顶层加 `configSchemaVersion`（整数，缺省=0=legacy 不管理）。
2. **版本信息归属**：每行 `plugin_storage` 自带 `schema_version`（per-row，配置数据自包含版本）；不用全局 meta-key。
3. **降级处理**（stored > declared）：告警 + 不自动迁移。
4. **迁移归属**：插件自编排；插件要看到版本号。
5. **存储模型**：维持扁平 KV + SQLite 介质（不引入 JSON 文档/json path；扁平 KV 是可演进基线，未来需结构化操作在同一 SQLite 介质上增强）。
6. **读接口形态**：不新增并行接口；版本号并入现有 `GetValue`（单条）与 `GetAllValues`（全量）两个读接口；不废弃 `GetAllValues`；取消"空 key=全量"——两接口各自独立职责、各自返回带版本。
7. **迁移失败策略**：best-effort——迁移中某 key 的转换函数报错时，跳过该 key、记告警日志、继续激活（不 fail-closed）；**不要求跨 key 原子性**。重跑 = 下次插件 Activate 再执行 `MigrateConfig`，per-row 幂等（只处理仍 `schema_version < target` 的 key，已迁 key 版本=target 自然不重选）；**此"重跑"不是任务模块（taskManager）的失败重跑**，二者无关。
8. **legacy（configSchemaVersion=0）盖戳与比较**：host 对所有插件一视同仁盖戳（legacy 盖 0）；host 第⑤节检测告警对 `configSchemaVersion=0` 的插件整体跳过（不比较/不告警/不迁移，行为同今日）；`configSchemaVersion=0` 是保留值专指 legacy/未声明，新插件声明必须 ≥1（dev-guide 约束）。
9. **host 代盖的合理性**：版本戳虽由 host 在写入时盖，但**值来源是插件声明**（`plugin.json` 的 `configSchemaVersion`，经 `PluginInfo` 传入）；host 只是机械代盖，不决定、不改变、不推断版本值——故"主程序控制版本戳"不成立，决策权在插件声明。迁移时插件用新格式写回、host 盖 target，逐 key 版本准确（迁了的=target，未迁的保留历史戳）。

## 现状与问题

`plugin_storage` 是扁平 KV（声明1），settings 与自存 KV 共表（声明2）。当前**无 schema 版本维度**。读 `GetSettings`（`plugin_setting_service.go:42-70`）逻辑为"读声明 → 叠存储值 → 缺 key 取默认"，恰好暴露三类**静默语义丢失**（升级时无任何机制拦截）：

1. **key 改名**：旧 key 行变孤儿（不可见），新 key 取默认 → 用户选择静默丢失。
2. **值含义/格式变**：旧值喂入新逻辑 → 静默错配或报错。
3. **加密预期变**：明文/密文标记错位 → 解密失败。

共性：插件没有任何钩子把旧存储值转换到新 schema。本任务即补版本感知 + 迁移钩子。经声明3，"物理丢失"当前不会发生，本任务只解决"语义丢失"。

## 与 contractVersion 的关系（正交两轴）

| 维度 | contractVersion（「契约稳定性与版本化」节点已落地） | configSchemaVersion（本任务新增） |
|---|---|---|
| 管什么 | host↔plugin 协议/API 兼容 | 插件自有持久化配置的 schema |
| 谁定义 | host 侧封闭（loader.go:34,37） | 插件自定义（plugin.json 声明） |
| bump 语义 | 破坏性协议变更，host 拒绝不兼容插件 | 配置结构变更，触发配置迁移 |
| 校验/触发点 | install 预检（service.go:291）+ 加载终检（loader.go:171） | 加载/激活期与行内 `schema_version` 比较触发迁移 |

正交：迁移在 contractVersion 校验通过之后触发——协议不兼容的插件根本不会被激活（loader.go:171 拦截），谈不上迁移。

## 方案

### ① 版本声明：plugin.json 顶层 configSchemaVersion（决策1）

`plugin.json` 顶层新增整数 `configSchemaVersion`（插件声明的目标 schema 版本）。缺省=0=legacy：无此字段的旧插件解析为 0，host 永不做版本比较、永不告警，行为同今日（决策8）。解析路径：`PluginManifest` → `PluginInstallDTO` → `Plugin` entity（加列）+ `PluginInfo`（loader.go:410，供 host 盖戳与比较）。

### ② 当前版本存储：plugin_storage 加 schema_version 列，host 写入代盖（决策2、9）

- `plugin_storage` 加 `schema_version`（int，默认 0）列；legacy 已存在行=0。
- **写入代盖**：`pluginContext.SetValue`（plugin_context.go:160）取 `pluginInfo.ConfigSchemaVersion`（值来自插件声明，决策9），随值写入该行 `schema_version`。插件全程无感——`SetValue`/`SetValueEncrypted` 签名不变。
- **legacy 盖戳**（决策8）：所有插件一视同仁盖戳，legacy 插件盖 0。
- 加密项的版本戳同样盖在行上（加密是 value 维度、版本是 schema 维度，正交）。

### ③ 读接口破坏性加版本（决策4、6）

`GetValue`/`GetAllValues` 返回带上 `schemaVersion`，让插件能看到每条配置的版本（决策4）。不新增并行接口、不合并、不取消 GetAllValues（决策6）：

```proto
message StorageValue { string value = 1; int32 schemaVersion = 2; }
message StorageValueResponse { string value = 1; int32 schemaVersion = 2; }       // GetValue 单条
message AllStorageValuesResponse { map<string, StorageValue> values = 1; }         // GetAllValues 全量，value 由 string 改 StorageValue
```

- 读返回**不带 `encrypted`**：插件自知哪些 key 加密（settings 声明里有；自存 KV 是它自己 `SetValueEncrypted` 存的），迁移写回按自身认知选 `SetValue`/`SetValueEncrypted`。读返回保持 `{value, schemaVersion}` 简洁。
- 读返回 `value` 仍是解密后明文（主程序侧解密，plugin_storage_service.go:40-43,73-81）。
- 破坏性变更 → bump `currentContractVersion`（loader.go:34）；现有插件需同步升级契约版本并适配新返回类型（风险2）。

### ④ 迁移执行：插件自编排 + best-effort（决策4、7）

- **执行点**：插件 `Activate(ctx)` 函数体内，注册扩展点之前、读配置之前，作为第一件事。
- **机制**：插件读自身配置（带版本，经③）→ 找出 `schemaVersion < 目标 configSchemaVersion` 的 key → 转换（改名/改格式/改加密预期）→ 经现有 `SetValue`/`SetValueEncrypted` 写回（host 盖当前版本戳，②）→ 经 `DeleteValue` 清理改名后的旧 key。
- **失败策略（决策7，best-effort）**：某 key 转换函数报错时，跳过该 key、记告警日志、继续激活（不 fail-closed）；不要求跨 key 原子性。**幂等重跑**：下次 Activate 再跑 `MigrateConfig`，per-row 只选仍 `< target` 的 key（已迁 key 版本=target 不重选），自动断点续传；此重跑与任务模块（taskManager）的失败重跑无关。
- **SDK 助手降样板**：SDK 新增 `plugin.MigrateConfig(ctx, target int, steps map[int]MigrateStep) error`——内部读全量（带版本）、按 `stored < target` 逐步执行 `steps[stored+1]…`、写回盖戳、遇错 best-effort 跳过+告警。插件 Activate 只调一次：
  ```go
  func Activate(ctx pluginsdk.PluginContext) {
      plugin.MigrateConfig(ctx, 3, map[int]plugin.MigrateStep{
          2: migrateV1to2, // dlQuality -> downloadQuality
          3: migrateV2to3, // quality 字符串 -> 枚举
      }) // best-effort：内部遇错跳过+告警，不阻断激活
      // 注册扩展点、读配置 ...
  }
  ```
- 编排完全在插件，host 不参与迁移执行、不解析配置语义。

### ⑤ host 侧安全网：检测 + 告警（不执行）

host 在加载流程（`extension/loader.go`）读各行的 `schema_version` 与插件声明的 `configSchemaVersion` 比较（决策8：`configSchemaVersion=0` 的 legacy 插件整体跳过）：
- 全部 `==` 目标 → 正常。
- 存在 `<` 目标的行且 Activate 后仍未被迁移（行版本仍旧）→ 日志告警，提示用户配置可能需手动检查。给"健忘插件"安全网。
- 存在 `>` 目标的行（降级，决策3）→ 告警 + 不迁移。

host 只检测告警、不执行迁移。注意：host 能感知"存在 < 目标的行"但不懂联动语义（风险4），半迁移的语义一致性最终靠插件幂等重跑保证。

### ⑥ 与 settings 声明的关系（统一）

settings 与自存 KV 同表，走同一套 MigrateConfig：迁移改的是 plugin_storage 行的值/版本，settings 自动受益（下次 `GetSettings` 读到迁移后的值）。不分两套迁移机制。

## 范围外（显式）

- 不解决"物理丢失"（声明3 核验当前不存在）。
- 不强制插件迁移——legacy 插件（configSchemaVersion=0）行为不变；host 只提供版本可见性 + 告警。
- 不引入配置回滚/快照（失败策略已定 best-effort + 幂等重跑，不做版本快照回退）。
- 不保证跨 key 原子性（风险4，靠幂等重跑 + step 设计缓解）。
- 不改存储模型（维持扁平 KV + SQLite）。
- 完整沙箱/信任属「插件信任模型」节点（D，未开始）。
- 任务-插件版本绑定（task 表无版本）属另一节点（L，延后）。
