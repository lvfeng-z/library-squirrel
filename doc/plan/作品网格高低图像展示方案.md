# 作品网格高低图像展示方案

## Context（背景与现状）

### 问题现象
`WorkGrid.vue` 中同一行的 `work-card`，当某张图像高度低于同行其他卡片时，出现「顶部对齐、底部参差不齐、info（标题/作者）位置高低不一」的丑陋视觉。

### 根因分析
当前布局链路（`WorkGrid.vue` + `WorkCard.vue`）：

1. `.work-grid` 是固定 4 列 CSS Grid，`grid-template-columns: repeat(4, 1fr); gap: 6px`（`WorkGrid.vue:171-175`）。
2. Grid item `.work-grid-container` **默认 `align-self: stretch`** → 同一行的容器外框被拉伸到该行最高卡片的高度（外框已等高）。
3. 但容器内部的 `work-card`（class `.work-grid-work-card` 为空，`WorkGrid.vue:189-190`）**没有设置 `height: 100%`** → 其高度仅等于自身内容（图像 + info），并顶部对齐于容器。
4. `.work-card-image` 设了 `width: auto` + `max-height: calc(500px - 100px) = 400px` + `margin-top/bottom: auto`（`WorkCard.vue:138-145`）——**意图是垂直居中**，但因为外层 `work-card` 没有撑满容器高度，居中并未生效。
5. 不同作品宽高比不同 → 在固定列宽下图像渲染高度不同 → 顶部对齐、底部参差、info 参差。

**一句话**：外框其实已经等高，问题在于内部的 `work-card` 没有撑满外框，导致图像顶部对齐、底部留白裸露。

### 关键约束（影响方案选型）
- **固定 4 列**，列宽 `1fr` 随容器宽度伸缩，无响应式断点。
- **存在无限滚动追加**：`MainView.vue:352` 通过 `el-scrollbar` + `v-el-scrollbar-bottomed` 指令滚动到底自动 `queryWorkPage(true)`；`WorkQueryView` 有「加载更多」按钮。→ 方案必须考虑「追加内容时是否重排/跳动」。
- 卡片带**拖拽**（`draggable`）、**勾选**（`checked`）、**点击**交互；交互通过 `work` 对象传参，**不依赖 DOM 索引**。
- 图像 `fit='contain'`，保留原始宽高比、不裁剪。

## 核心论点

用户诉求是「**同一行** + **高低不同** + **美观**」三者兼得。但只要**强制成行**，同一行的卡片高度就必须统一：

- 要统一高度 → 要么**留白**（短图上下大片空白），要么**裁剪**（长图被切）；
- 想**真正展示高度差异** → 必须**放弃严格成行**，改用**瀑布流**（每个卡片按自身高度紧凑堆叠）。

所以唯一能「美观展示高低不同图像」的方向是**瀑布流**。其余方案都是在「整齐」与「保留高度差异」之间做不同程度的妥协。

## 方案对比

| 方案 | 美观度 | 真实展示高度差异 | 改动量 | 追加加载体验 | 副作用 |
|------|--------|------------------|--------|--------------|--------|
| **A 瀑布流（推荐）** | ★★★★★ | ✅ 是 | 中 | 见 A1/A2 分述 | 放弃严格成行 |
| B 等高居中（修复现状） | ★★★ | ❌ 否（留白） | 极小 | 无影响 | 短图上下大留白 |
| C cover 裁剪统一高度 | ★★★ | ❌ 否（裁剪） | 小 | 无影响 | 长图内容被裁 |
| D 现状（顶部对齐） | ★ | ❌ 否 | — | — | 底部参差（当前） |

---

## 推荐方案 A：瀑布流（Masonry）

放弃严格成行，每个卡片按真实高度紧凑堆叠（小红书 / Pinterest 风格）。这是图片资源库场景下唯一能真正美观呈现高低不同图像的做法，且对当前 `fit='contain'` 不裁剪的语义完全兼容。

瀑布流有两条实现路径，按「实现成本 / 追加体验」权衡：

### A1：CSS `columns`（纯 CSS，改动极小）—— 首选 MVP

改动仅限 `WorkGrid.vue` 的 `<style>`，不动模板、不动 `WorkCard.vue`、不引入 JS：

```css
/* WorkGrid.vue */
.work-grid {
  column-count: 4;        /* 由 grid 改为 multi-column */
  column-gap: 6px;
}
.work-grid-container {
  /* 原有 padding/border-radius/background/transition/overflow 保留 */
  break-inside: avoid;    /* 关键：禁止卡片被列分页切断 */
  width: 100%;
  margin-bottom: 6px;     /* 列布局只有水平 column-gap，垂直间距用 margin-bottom 补 */
  display: block;
}
```

- **优点**：几行 CSS，零依赖；浏览器原生布局，**图片异步加载完成后自动回流**，无需手动监听 `load`；拖拽、勾选、点击与布局完全解耦，无需改造。
- **缺点 1（顺序）**：`columns` 按 DOM 顺序**先填满第一列再下一列**，视觉阅读顺序是「从上到下，再从左到右」，而非「从左到右，再从上到下」。对本项目影响极小——交互靠 `work` 对象、不靠索引，用户浏览图片墙也按视觉而非编号。
- **缺点 2（破坏滚动加载语义，实测确认致命）**：`columns` 是「竖向顺序填充 + `balance` 平衡」，与无限滚动「append-only 向下增长」的语义根本冲突。元素数量变化时，`balance` 把**全部元素**重新分配到各列，导致：① 已有卡片的位置（所在列、Y 坐标）发生变化；② 新加载的卡片被插入到**已浏览区域（上方/中间）**，而非追加到底部。这违反「滚动加载 = 新内容在下方」的用户预期，**无法用 CSS 修复**，是 A1 的致命缺陷。

### A2：JS 瀑布流（追加零闪烁）—— 当前选定方案

**背景**：A1 已实施，瀑布流观感理想，但 `MainView` 滚动加载追加新卡片时明显闪烁。闪烁根因：CSS `columns` 默认 `column-fill: balance`，追加内容时浏览器**重新平衡全列、已有卡片跨列重定位**（x/y 坐标剧变）。

A2 改用**绝对定位 + JS 计算**，把「卡片放在哪一列、什么 Y 坐标」完全交给 JS 控制：

- **追加新卡片只定位新卡片，已有卡片坐标不动 → 追加零闪烁**（直接解决用户痛点）；
- 视觉顺序符合从左到右、从上到下（优于 A1 的按列填充）。

**残留：图片 load 后的局部推移**

后端 `ResourceFullDTO` / `PersistentStoreDTO` **不含图像宽高**（已查证 `models.ts:581`、entity 无 width/height 字段），图片加载前无法预知高度。卡片初始用占位高度定位，图片 load 完高度变化后，需重排该列后续卡片（单向往下推移）。相比 A1 的跨列跳动，方向单一、范围受限，观感可接受。若要彻底消除（真·零闪烁），需后端补充图像宽高比字段（后端改动，列为**可选增强**，不阻塞本次）。

**实现设计**（在 `WorkGrid.vue` 内实现，单一使用方，避免过度抽象）：

数据结构：
```typescript
const COLUMN_COUNT = 4
const GAP = 6
const containerRef = ref<HTMLElement>()
const itemRefs = ref<HTMLElement[]>([])
const columnHeights = reactive<number[]>(new Array(COLUMN_COUNT).fill(0))
```

定位单个卡片到最短列：
```typescript
function placeItem(el: HTMLElement, colWidth: number) {
  const minCol = columnHeights.indexOf(Math.min(...columnHeights))
  const x = minCol * (colWidth + GAP)
  const y = columnHeights[minCol]
  el.style.width = colWidth + 'px'
  el.style.transform = `translate(${x}px, ${y}px)`
  columnHeights[minCol] = y + el.offsetHeight + GAP
}
```

增量追加（零闪烁核心）：
```typescript
watch(() => props.workList, (newList, oldList) => {
  nextTick(() => {
    const colWidth = getColumnWidth()
    const startIdx = oldList?.length ?? 0       // 只定位新增卡片
    for (let i = startIdx; i < newList.length; i++) {
      placeItem(itemRefs.value[i], colWidth)
    }
    updateContainerHeight()
  })
})
```

重排触发时机：
- 首次 `workList` 赋值 → 全量布局；
- `workList` 追加 → 仅定位新增（增量，不闪）；
- 容器宽度变化（`ResizeObserver` 监听 `containerRef`）→ 全量重排；
- 单卡片高度变化（图片 load / 文本换行，`ResizeObserver` 监听每个卡片）→ 从该卡片起重排同列后续。

容器样式：
```css
.work-grid { position: relative; }              /* 移除 column-count，作为绝对定位基准 */
.work-grid-container {
  position: absolute;
  /* width / transform 由 JS 设置；移除 margin-bottom 和 break-inside */
}
```

**注意事项**：
1. 卡片 ref 用函数式 `:ref="el => itemRefs[i] = el"` 收集，`nextTick` 后 DOM 就绪再定位。
2. `ResizeObserver` 回调需防抖/判断真实高度变化，避免高频重排。
3. `.work-grid` 高度由 JS 设为最高列，撑开 `el-scrollbar` 内容，保证 `v-el-scrollbar-bottomed` 正常触发。
4. 拖拽/勾选/点击通过 `work` 对象传参，绝对定位下完全兼容。
5. 列宽随容器宽度变化（等价原 `1fr`），无响应式断点，固定 4 列。

**落地步骤**：
1. `WorkGrid.vue` `<style>`：`.work-grid` 去掉 `column-count`、改 `position: relative`；`.work-grid-container` 改 `position: absolute`，移除 `margin-bottom` / `break-inside`。
2. `<script setup>` 增加布局逻辑（列高数组、`placeItem`、`relayoutAll`、`relayoutFrom`、`watch`、`ResizeObserver`）。
3. `<template>`：容器绑 `ref="containerRef"`，卡片用函数式 `:ref` 收集。
4. `task dev` 验证：追加不闪、图片 load 后局部推移可接受、resize 正常、拖拽/勾选正常。

### 对 `WorkCard.vue` 的可选微调（A1/A2 通用）
当前 `.work-card-image` 的 `width: auto` + `max-height: calc(500px - 100px)` 在瀑布流下仍可工作，但有两处可优化（非必须）：

1. **单图最大高度**：`max-height: 400px` 在瀑布流里会让超长图（如长条漫画）被压扁、浪费列空间。建议调大（如 `maxHeight` 传入 `700` 或单独配置），或对极端长图保留限制避免单张占满整列。
2. **窄图填充**：`width: auto` 会让窄图（竖图）在列宽内居中、两侧留白。若希望图片占满列宽，可改为 `width: 100%; height: auto`（高度按比例自适应）。

> 这两项是观感调优项，方案 A1 落地后可按实际效果决定是否调整，不阻塞主流程。

## 备选方案 B：等高居中（修复现状，最小改动）

不改变 Grid 行结构，只让「外框等高」的效果正确传导到卡片内部：

```css
/* WorkCard.vue */
.work-card { /* 新增 */ height: 100%; }
.work-card-image { /* 现状 margin:auto 已是居中意图，撑满后自然生效 */ }
```
配合让 info 区域固定在底部（`margin-top: auto` 已隐含）。

- **效果**：所有卡片外框等高、info 底部整齐对齐、图像在框内垂直居中，顶部与底部留白对称分布。
- **适用**：若**坚持严格成行**、且能接受短图上下留白，这是改动最小（约 1 行）的修复。
- **不推荐为主选**：宽高比差异大时，短图上下大片留白依然不美观，没有真正解决「高低不同」的展示诉求。

## 备选方案 C：cover 裁剪统一高度

所有图像渲染为固定高度（如该行最高或某固定值），`object-fit: cover` 居中裁剪：

- **效果**：最整齐划一，行结构完美。
- **不推荐**：**裁掉图像内容**，与资源库「完整呈现作品」的目标冲突，且违背用户「展示高低不同图像」的初衷。
