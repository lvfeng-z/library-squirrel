# 主程序统一资源模型与多流任务重构方案

> 目标:把"1 作品 = 1 主文件 + 1 缩略图"的固定槽资源模型,重构为"1 Resource 挂 N 个 typed store"的**统一资源模型**,并把任务模块升级为"同一任务经**单一接口**产出并并发写入多个 store"。
> 资源不再按"主资源 / 缩略图"分两个世界,而是按**生成方式**分为 `downloaded`(流式下载,可续传)与 `derived`(一次性派生,不可续传)两类——两者在 taskManager 眼里都是"一个 reader 拷到 store",走同一套执行与替换逻辑。
> 这是一次主程序架构升级,为 Bilibili 等视频站点(音视频分离的 DASH)提供原生支持,同时消除"派生型资源(如缩略图)被硬编码为特殊第三类"的历史结构债。完成后,下载分离轨道、下载单张图片、生成缩略图,都是同一条多流路径的不同实例。
> 配套插件计划见 `bilibili-plugin-plan.md`(薄消费者,依赖本方案)。

## 决策记录:为何统一派生型资源(方案 B + 单接口形态)

**问题**:最初添加缩略图时,将其作为 `Resource` 的固定列(`ThumbnailStoreID`)与主资源耦合;后为让缩略图能独立重执行,在 `runMode`/`parseSections`/`runSectionCombo`/`downloadLoop` 中大量插入 `hasThumbnail` 分支,并引入"板块 B 完成顺带生成 / 板块 C 独立执行 / 备份→生成→失败还原"三套缠绕逻辑。这是"派生型资源被硬编码为特殊类"的代价。

**根因**:资源被隐式分成两个世界——可流式下载的主资源,与需要独立生成路径的派生资源。多轨方案若只把"主资源"泛化为流集合、缩略图仍走独立 `GetThumbnail`,则裂缝被保留:未来任何新的派生型资源(GIF 预览、海报、索引文件……)都会重蹈缩略图覆辙(被迫加板块、加 `runMode` 字段、加 `sectionCode`、加 `GetXxx` 接口、加 `StoreType` 分支)。

**决策**:本次一并填平裂缝——所有资源(含缩略图)统一为 `resource_store` 行 + `generation` 标签;`TaskHandler` 收敛为**单一接口**,所有 store(含派生型)从 `Start`/`Resume` 返回的 `[]*StoreSpec` 流集合产出。

**接口形态抉择(单接口)**:派生型资源在 SDK 上选择**全部并入单一流式接口**(而非保留独立 `Derive` 调用),理由:达成"一个世界、一个接口、一套执行逻辑"的彻底统一;taskManager 对 downloaded/derived 不做类型分流,统一为 reader→store 拷贝。

**时序难题的化解**:派生型"常依赖主资源先就绪"的担忧,通过**边界界定**消解——
- 进入任务流的派生型,**必须是插件能独立产出的**(现网缩略图即此类:`GetThumbnail(taskData)` 仅凭 taskData 从站点拉取,不依赖主资源本地文件,见 `model.go:1237`)。
- **依赖本地主资源文件的派生**(如 ffmpeg 截帧)不进入任务流,归入「合并动作」(用户手动触发,主程序端执行,见工作流十一)。

由此,流集合内的派生型在 `Start` 时即可产出,无跨进程等待;taskManager 仍按"先 downloaded 后 derived"顺序消费(保险),但不构成硬阻塞。

## 一、核心语义(贯穿全方案)

1. **粒度非对称:启动面可细,控制面在任务级**。
   - **启动面**(`Start` 首次 / `Redownload` 重执行 / `Resume` 恢复):粒度可细到 **store_type 子集**——可选只下某些类型(如仅 videoTrack、仅缩略图);本次 `ManagedTask.streams` 只含所选 role 的 streamController。
   - **控制面**(`Pause` / `Stop`):粒度为**该任务当前活跃的全部 stream**(= 本次启动所选子集),用户不感知、也不操作单个 store,前端控制按钮仍是一个任务一个。
   - 暂停/停止不是"作用于 Resource 的全部 store",而是"本次跑起来的 stream 集合";二者仅在"一任务一活跃实例"(见第 7 条)时等价。
2. **生成方式二分**。每个 store 带 `generation`:`downloaded`(流式 reader,支持断点续传)或 `derived`(一次性 payload,不可续传)。二者执行路径统一,仅 reader 的来源不同。
3. **描述面可细分**。状态描述(向前端推的 statusText/phase)允许反映内部流粒度,例如其余轨道完成、仅剩视频轨在跑时推"正在下载视频资源"。控制聚合,描述可细。
4. **派生型边界**。任务流内的派生型由插件独立产出;依赖本地主资源文件的派生归「合并动作」,不在任务流内。
5. **本期内置播放不在范围**。应用核心是下载与存储管理;播放仍由外部程序承担(`appLauncher`)。"可合并作品"通过独立合并动作产出可外部播放的单文件。
6. **合并独立于任务执行**。合并是用户在"可合并的作品"上手动触发的动作,不属于下载流程。
7. **一任务一活跃实例,执行形态受状态约束**。
   - 一个任务同一时刻**至多一个活跃 `ManagedTask`**——不允许并发执行其 Resource 的不同 store 子集。前端只为终态任务提供非全量入口、不为活跃任务提供执行入口;**后端必须防御性校验**(启动前确认目标任务无活跃实例),不依赖前端约束。
   - **首次执行(任务状态=已创建)仅允许全量执行**(全集 storeRoles);**仅终态任务**才允许非全量执行(选 storeRoles 子集,即 Redownload)。当前前端已是此逻辑。

## 二、现状(调研结论)

- `Resource` 实体(`backend/base/model/entity/resource.go`):`WorkStoreID *int64`(主文件)+ `ThumbnailStoreID *int64`(缩略图),两个**固定** store 槽。无资源类型/角色/生成方式概念。
- `PersistentStore`(`persistent_store.go`):一条记录 = 一个文件(`FilePath` 唯一索引;`FileName`/`FilenameExtension`/`Status`/`Width`/`Height`)。纯文件记录,与生成方式无关——本方案保持不变。
- Resource:Work 在 DB 层是 1:N(`ListByWorkId`/`GetEnabledByWorkId`/`ListByWorkIds` 返回切片),但上层硬编码单数。
- 资源由 `taskManager/model.go` 的 `saveResource`(564–623)在下载流程中创建,**一次任务执行只建/更一条 Resource**。
- `ManagedTask`(`model.go:292-299`)与 `downloadLoop`(`model.go:627-705`)**单流**:单 `reader`、单 `storeWriter`、单 `workStoreId`,EOF → `storeWriter.Complete()` → `TaskStateFinished`。
- **缩略图硬编码为第三类**:板块 B(`runSectionCombo` `model.go:427-443`)下载完成时 `if hasThumbnail` 顺带生成缩略图;板块 C(`model.go:446-451`)独立路径;`doSaveThumbnail`(`model.go:1212-1254`)背负"备份旧(`StoreTypeThumbnail`)→调 `GetThumbnail`→失败还原"兜底。三处分支即三层耦合。
- **板块机制硬编码**:`runMode{workInfo, resource, thumbnail}`(`model.go:51-55`)三布尔;`sectionCode` 1/2/3(`model.go:65-69`)顺序码;`parseSections`/`runSectionCombo` 写死 A→B→C 顺序。每加一类资源要改四处。
- **板块选择无持久化(恢复缺口)**:`runMode` 是纯内存态,task 实体(`entity/task.go`)无字段记录所选板块。`resumeTaskTrees`(`manager.go:121-124`)固定 `runModeFull`;`prepareForResume`(`model.go:911-923`)不重置 runMode,故同进程内复用 ManagedTask(parentMap 命中,`manager.go:611-617`)时板块侥幸保留,跨重启(parentMap 未命中走 `resumeTaskTrees`)则非全量任务退化为全量;`buildOrReuseChild`(`manager.go:283-316`)名含"Reuse"实则始终 `newManagedTask`。`resumeFromPersistedState`(`model.go:731-844`)只认 `resource.WorkStoreID` 续传主资源,不考虑板块。
- 终态由内存 `TaskState`(28–39)驱动;`ResourceComplete` 是信息性字段,不参与状态机。`PersistentStore.Status`(Complete=1)用于 `resumeFromPersistedState`(790–797)的续传判定。
- 播放:`appLauncher` 全外部(Photos / 电影和电视 / PotPlayer / OpenPath),**无应用内播放器**。前端 `WorkCard.vue:59-70`、`WorkDialog.vue:128-130,285` 经 `appLauncherOpenImage` 打开 `resource.workStore.filePath`。
- 备份:`store_backup_orchestrator.go` 的 `StoreType` 枚举(47–52)仅 `StoreTypeWork`/`StoreTypeThumbnail`;`BackupStores`(94–140)/`RestoreAllStores`(144–219)的 switch(198–203)只处理这两种。
- 回收站:`recycleBin/snapshot.go` 的 `ResourceSnapshot`(47–54)只有 `WorkStoreBackupID`/`ThumbnailStoreBackupID` 两个固定字段;`SoftDeleteWork`(work/service.go:550–700)按这两个字段备份,`RestoreWorkFromSnapshot`(750–868)同构重建。
- DTO/搜索:`WorkFullDTO.Resource` 单数(`sdk dto/work_dto.go:28`);`search/repository.go:237` 硬编码 `LIMIT 1` 取一条 enabled resource;`work/service.go:1138-1148` 取 `resources[0]` 组装 `ResourceFullDTO`。
- SDK:`TaskHandler`(`sdk dto/task_handler.go`)`Start`/`Resume` 返回单 `io.ReadCloser`;`GetThumbnail(taskData)` 返回 `*ThumbnailResponse{Data,Format}`(unary);`WorkResponse.Resource *TaskResourceDTO`(Format/Size/SuggestName/Continuable)。底层 gRPC:`Start`/`Resume` 为 server streaming(`StreamChunk`),`GetThumbnail` 为 unary。

## 三、工作流 1:数据模型 —— Resource 挂多个 typed store(带生成方式)

### 1.1 新增关联子表 `resource_store`

把 Resource 的两个固定列泛化为 N 个 typed 关联,并标注每个 store 的生成方式:

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | int64 | 主键(BaseEntity) |
| `resource_id` | int64 | 所属 Resource(索引) |
| `store_type` | string | `main` \| `thumbnail` \| `videoTrack` \| `audioTrack` \| `merged`(开放枚举,可扩展) |
| `generation` | string | `downloaded`(流式可续传) \| `derived`(一次性派生) |
| `store_id` | int64 | 指向 `persistent_store.id` |
| `order_idx` | int | 同类型内排序(可选) |

- `store_type` / `generation` 常量集中定义(与备份编排器的 `StoreType` 枚举统一),供 taskManager、backup、recycleBin、DTO、前端共用。两者为开放集合:新增类型只需追加常量,不改表结构。
- `generation` 与 `store_type` 独立:由 `store_type` 决定业务角色,由 `generation` 决定执行与续传语义。典型映射:`main`/`videoTrack`/`audioTrack`/`merged` = `downloaded`;`thumbnail` = `derived`。但映射不硬编码进执行器——执行器只读 `generation`。
- `PersistentStore` 实体**不变**(仍是纯文件记录)。可选 P2:加 `duration`/`codec`/`bitrate` 媒体元数据字段,供合成与展示。

### 1.2 迁移(向后兼容)

1. `migration/migrate.go` 注册新实体 `ResourceStore`,GORM AutoMigrate 建表。
2. 数据迁移:遍历现有 `Resource`,把 `WorkStoreID → (store_type=main, generation=downloaded)`、`ThumbnailStoreID → (store_type=thumbnail, generation=derived)` 写入 `resource_store`。
3. 删除旧列:`WorkStoreID`/`ThumbnailStoreID`。SQLite 3.35+ 支持原生 `DROP COLUMN`,在迁移中用 raw SQL 执行(GORM AutoMigrate 不删列)。迁移需幂等(先判断列是否存在)。
4. 迁移后代码**只从 `resource_store` 读写 store 关联**,旧列彻底退役。

### 1.3 Repository

- `ResourceRepository` 增 `ListStoresByResourceId`、`ListStoresByResourceIds`(批量,避免 N+1)、`AddStore`、`RemoveStore`、`GetStoreByType`、`ListStoresByGeneration`。
- 遵循 `BASE_REPOSITORY_REUSE` / `ELIMINATE_N_PLUS_1_QUERY`(P0)。

### 1.4 task 实体:持久化所选板块(配合工作流八)

当前 task 实体(`entity/task.go`)无字段记录本次执行所选板块,runMode 纯内存态,导致跨重启恢复丢失板块选择(见第二节现状)。新增字段:

| 列 | 类型 | 说明 |
|---|---|---|
| `store_roles` | string(逗号分隔) | 本次执行所选 store_type 集合,如 `thumbnail`、`main,videoTrack`;空/全集表示全量 |
| `include_work_info` | bool | 是否执行作品元数据板块(配合 store_roles 还原完整 runMode) |

- 两字段完整重建 `runMode{workInfo, storeRoles}`。
- 写入时机:任务创建/Redownload 时写入;首次执行(已创建)写全集,符合核心语义 7"首次仅全量"。
- 读取时机:`resumeTaskTrees`/`buildOrReuseChild` 恢复时读回重建 runMode,不再固定 Full(见工作流八 6.4)。
- 迁移:旧数据无此字段,读取时按"全集"兜底(等价旧行为,不引入退化)。

## 四、工作流 2:SDK 单接口改造(派生型并入流集合)

### 2.1 统一为"流集合"模型(单一接口)

任务下载统一建模为"插件经**单一接口**产出一组 StoreSpec,taskManager 把每个 spec 的 reader 拷到对应 store"。**单资源插件(图片)= 集合大小 1(main);多轨插件(Bilibili 视频)= 集合大小 N(videoTrack+audioTrack);派生型(缩略图)= 集合中的 derived 元素**。`downloadLoop` 恒为多流,N=1 时等价于单文件下载。项目处于开发期,无需任何历史兼容——`TaskHandler` 直接改造为多轨原生单接口,不存在单轨/多轨、下载/派生两种模式,taskManager 无类型断言、无分流、无包装。

### 2.2 SDK:`Start`/`Resume` 返回 `[]*StoreSpec`,移除 `GetThumbnail`

在 `library-squirrel-sdk/dto` 改造 `TaskHandler`:**只改 `Start`/`Resume`**(返回值从"单个 reader"改为"流集合 `[]*StoreSpec`"),`GetThumbnail` **移除**(其语义并入流集合的 derived 元素),其余 5 个方法(Create/CreateWorkInfo/Retry/Pause/Stop)签名不变。新增 `StoreSpec`、`TaskResumeParam` 两个类型,移除 `WorkResponse.Resource` 与 `ThumbnailResponse`(字段迁移进 `StoreSpec`)。

```go
// StoreSpec 单条资源产出声明(对应一个 store)
type StoreSpec struct {
    Role        string        // store_type: main | thumbnail | videoTrack | audioTrack | ...
    Generation  string        // downloaded | derived
    ReadCloser  io.ReadCloser // 资源数据流(downloaded=流式网络 reader;derived=一次性 payload 包装的 reader),调用方负责 Close
    Format      string        // 文件扩展名(原 WorkResponse.Resource.Format / ThumbnailResponse.Format 迁移至此)
    Size        int64         // 远程大小;-1 未知(derived 通常已知)
    SuggestName string
    Continuable *bool         // 是否支持续传(derived 恒为 false)
}

// TaskResumeParam 续传参数(每条 downloaded 轨独立偏移;Pause/Stop 仍用 TaskResParam,不需偏移)
type TaskResumeParam struct {
    Task          *TaskDTO
    StreamOffsets map[string]int64 // role → 该轨已写入字节数(仅未完成的 downloaded 轨出现;derived 轨不出现,未完成即整轨重产)
}

// TaskHandler 改造后(多轨原生,单一接口)
type TaskHandler interface {
    Create(url string) (*TaskCreateResult, error)                         // 不变
    CreateWorkInfo(task *TaskDTO) (*WorkResponse, error)                  // 不变
    Start(task *TaskDTO) ([]*StoreSpec, *WorkResponse, error)             // 单 reader → 流集合(含 derived)
    Retry(task *TaskDTO) (*WorkResponse, error)                           // 不变
    Pause(param *TaskResParam) error                                      // 不变(任务级)
    Stop(param *TaskResParam) error                                       // 不变(任务级)
    Resume(param *TaskResumeParam) ([]*StoreSpec, *WorkResponse, error)   // per-role 偏移(仅 downloaded 续传;derived 重产)
}
```

- `WorkResponse` 收敛为只承载作品级信息(Work/Site/SiteAuthors/SiteTags/WorkSets),**移除 `Resource` 字段**;原 `TaskResourceDTO` 的 Format/Size/SuggestName/Continuable 整体迁移进 `StoreSpec`。
- **derived 元素的 ReadCloser**:插件把一次性 payload(`[]byte`)包装为 reader 返回,如 `io.NopCloser(bytes.NewReader(payload))`;taskManager 无感,统一按 reader 拷贝。
- 各插件统一返回一个切片:pixiv/local 双元素(`{Role:"main",Generation:"downloaded"}` + `{Role:"thumbnail",Generation:"derived"}`);Bilibili 视频三元素(videoTrack+audioTrack 为 downloaded,可另含 thumbnail 为 derived)。
- taskManager **无类型断言、无分流、无包装**:`specs, resp, err := handler.Start(task)` 恒为流集合,`downloadLoop` 只有一条多流路径,downloaded/derived 走同一拷贝循环。
- SDK 版本号 bump(破坏性变更,开发期可硬切);主程序与三个插件(pixiv/local/Bilibili)同步升级。

### 2.3 gRPC 传输适配

底层 `Start`/`Resume` 仍是 server streaming,但 `StreamChunk` 增加 `role` 字段,标识每个 chunk 属于哪条轨道:

- 插件端:把多个 spec 的 reader 数据按 `role` 分段(或交错)推送到同一条 stream;某条轨道数据推完即对该 role 发送结束标记。
- 主程序端:按 `role` 把 chunk 分发到对应 `streamController` 的写入队列。
- `GetThumbnail` unary RPC **退役**(proto 中移除);其能力由 `Start` 流中 `role=thumbnail` 的元素承载。
- derived 元素在流中表现为:一次性推送完整 payload 后对该 role 结束(等价于"流式但瞬时 EOF")。插件端无需等待主资源落盘(见决策记录:进入流集合的派生型插件可独立产出)。

## 五、工作流 3:执行编排(downloaded/derived 统一)

### 3.1 单流控制器 + 资源级聚合

引入**单流控制器**与**资源级聚合**两层:

```go
// streamController 管理单个 store 的传输(downloaded/derived 通用:都是 reader→store 拷贝)
type streamController struct {
    role        string
    generation  string        // downloaded | derived
    reader      io.ReadCloser
    storeWriter StoreWriter
    store       *entity.PersistentStore
    written     int64
    state       streamState   // downloading | paused | completed | failed
    mu          sync.Mutex
}
```

- `ManagedTask` 持有 `streams []*streamController`(按 role 索引)。
- `downloadLoop` → 每条 spec 一个 goroutine,各自跑"read→write→累计 written"循环(逻辑沿用现有单流实现,下沉到 streamController)。**downloaded 与 derived 走同一段拷贝代码**,差异仅在 reader 来源(网络流 vs 内存 payload),对 streamController 透明。
- **消费顺序**(保险,非硬阻塞):先并发消费全部 downloaded 流,再消费 derived 流。因进入流集合的派生型插件可独立产出,此顺序不构成等待;但保持"主资源先就绪"的自然语义,且便于 phase 描述。
- **完成判定**:全部 stream `completed` → `TaskStateFinished`;任一 `failed` → `TaskStateFailed`(但保留已完成 stream 的 store,供续传只补失败项)。

### 3.2 续传语义(按 generation 区分)

- **downloaded 轨**:`Resume(TaskResumeParam{StreamOffsets[role]=store.written})`,从自身偏移 Range 续传。
- **derived 轨**:`StreamOffsets` 不含该 role(不可断点);未完成时整轨重新产出(插件重新生成 payload)。已完成则不出现在 Resume 返回的流集合中。
- **重启后续传**:不依赖内存——taskManager 读每条 stream 对应 `PersistentStore`(Status + 文件大小)得出各轨完成度;downloaded 未完成轨按偏移续传,derived 未完成轨整轨重产,已完成轨跳过。

## 六、工作流 4:控制面(资源级聚合)

| 操作 | 行为 |
|---|---|
| **Pause** | 广播到该 Resource 全部活跃 stream:各 stream 关闭上游连接、保留 store 与 `written`(downloaded),状态置 `paused`。derived 若已读完则自然完成,未读完则中止后整轨重产。 |
| **Resume** | 调插件 `Resume(TaskResumeParam)`:为**本次所选 role 中**未完成的 downloaded stream 按 offset 重建 reader;derived 未完成轨整轨重产(未选 role 不参与)。状态置 `downloading`。 |
| **Stop** | 广播关闭全部 stream + 清理。 |
| **重启后续传** | 按各 stream 对应 `PersistentStore`(Status+大小)得出完成度:downloaded 续传、derived 重产、已完成跳过。 |

> 控制信号是 Resource 级一个,内部广播到 N 条 stream;对用户/前端只有一个"暂停/恢复/停止"。

## 七、工作流 5:统一替换语义(缩略图不再特判)

当前缩略图的"备份旧→生成新→失败还原"(`doSaveThumbnail` `model.go:1212-1254`)是**板块 C 专属**兜底。本方案将其**下沉为所有 store 的通用替换语义**:

- 任何 store(无论 downloaded/derived)在"重新生成前已存在旧值"时,统一走:`StoreBackupOrchestrator.BackupStores(workId, storeType)` 备份旧 store → 生成新 store → 失败则 `RestoreAllStores` 还原。
- 替换触发场景:板块重执行(Redownload)命中已存在作品、`ConfirmReplace` 替换流程。
- 复用现有 `StoreBackupOrchestrator` 的板块隔离备份能力(见工作流九扩展 `StoreType` 后)。
- `saveResource`(`model.go:564-623`)改为:创建/更新一条 Resource,然后按 spec 集合挂 N 条 `resource_store`(每条 spec 一个 store)。**不再有缩略图专属生成分支**——thumbnail 只是集合中 generation=derived 的一个元素。

## 八、工作流 6:板块 / Redownload 退化(消除硬编码板块)

这是相对原多轨方案**新增的工作流**,直接消除"派生型重蹈覆辙"的根因——板块从"固定三布尔"退化为"store_type 集合"。

### 6.1 板块退化:仅缩略图降级,作品元数据板块保留

原三板块:`A=workInfo`(作品元数据)、`B=resource`(主资源)、`C=thumbnail`(缩略图),均为独立顶层板块。退化后:

- **作品元数据板块(`workInfo`)保留为独立板块**:作品信息本质是元数据,非资源 store,继续单独选择执行。
- **缩略图板块(C)移除**:不再是独立顶层板块,降级为资源集合内 `store_type=thumbnail` 的一项。
- **资源板块演化为 `store_type` 集合**:原"主资源固定槽 + 缩略图固定槽"被 `storeRoles []string` 取代,可含 main/thumbnail/videoTrack/audioTrack 等任意子集。

```go
// 旧:runMode{workInfo, resource, thumbnail} 三布尔 + sectionCode 1/2/3
// 新:workInfo 独立板块保留;资源由 store_type 集合表达(缩略图降级为其中一项)
type runMode struct {
    workInfo   bool       // 作品元数据板块(独立保留)
    storeRoles []string   // 资源板块:store_type 子集(main/thumbnail/videoTrack/...)
}
```

- 新增资源类型时,`storeRoles` 天然容纳(加一个字符串),**无需改 `runMode` 结构、无需加 `sectionCode`、无需改 `parseSections` 分支**——这正是消除"派生型重蹈覆辙"的关键。

### 6.2 Redownload IPC 契约退化

```
// 旧:Redownload(taskIds, sections []int)   sections 为顺序码 A=1/B=2/C=3
// 新:Redownload(taskIds, storeRoles []string, includeWorkInfo bool)
```

- 前端"重下资源"→ `storeRoles=["main","videoTrack","audioTrack"]`;「重下缩略图」→ `storeRoles=["thumbnail"]`。
- 未来"重下 GIF 预览"→ `storeRoles=["gifPreview"]`,**零骨架改动**。
- `sectionCode` 顺序码常量、`parseSections` 的 switch 全部退役。

### 6.3 runSectionCombo 重写

- 不再写死 A→B→C 顺序分支,改为:若 `includeWorkInfo` 先跑作品信息板块;然后按 `storeRoles` 集合,调 `Start`/`Resume` 取流集合,**过滤出所选 role 的 spec** 执行(downloaded 流式 / derived 一次性,统一拷贝)。
- **`ManagedTask.streams` 恒等于本次 `storeRoles` 过滤后的子集**:未选的 role 不建 streamController,因此 Pause/Stop 天然只作用于所选 store——这正是核心语义 1「控制面粒度」的来源。
- 终态规则不变:含任一 downloaded/derived 资源板块 → 终态(Finished/Failed);仅 workInfo → 非终态(保持执行前状态、不持久化)。

### 6.4 板块选择的持久化与恢复(修复跨重启恢复缺口)

当前 `resumeTaskTrees`(`manager.go:121-124`)固定 `runModeFull`,跨重启恢复会丢失非全量任务的板块选择(见第二节现状)。本节配套修复,让"启动面粒度可细"(核心语义 1)在暂停-恢复全生命周期自洽:

- **写入**:任务创建/Redownload 时,将所选 `storeRoles` + `includeWorkInfo` 持久化到 task 实体(见 1.4)。首次执行写全集(全量)。
- **恢复读取**:`resumeTaskTrees`/`buildOrReuseChild` 不再固定 `runModeFull`,改为从 task 实体读回 `storeRoles`/`includeWorkInfo` 重建 runMode。无论同进程复用(parentMap 命中)还是跨重启重建,板块选择一致。
- **`resumeFromPersistedState` 适配**:当前跨重启续传只认 `resource.WorkStoreID`(主资源)。多轨后,续传范围须与持久化的 storeRoles 一致——按所选 store_type 续传其对应 store(downloaded 续偏移、derived 整轨重产、已完成跳过),而非只续主资源。未选的 role 不参与续传。

> 修复后,用户选了哪些 store,暂停/恢复/跨重启续传都精确作用这些 store,不退化为全量。

## 九、工作流 7:前端状态描述(描述面可细分)

- taskManager 据 stream 集合状态计算 **phase 文本**,随进度事件推前端。规则(可扩展):
  - 全部在跑 → "正在下载"(或"正在下载视频、音频资源")。
  - 仅剩视频轨在跑 → "正在下载视频资源";仅剩音频轨 → "正在下载音频资源"。
  - 仅剩 derived(如缩略图)在跑 → "正在生成缩略图"。
  - 合成阶段(合并动作进行中,见工作流十一)→ "正在合成"。
  - 全部完成 → "已完成"。
- phase 反映"当前活跃/剩余"的轨道,属于描述面;**不暴露**单轨暂停等内部不一致(控制是整体的)。
- 前端任务列表/详情展示 `statusText`,与数字进度并列。

## 十、工作流 8:任务进度

`TaskProgressDTO`(sdk `dto/task_dto.go`)新增可选字段:

- `totalBytes` / `finishedBytes`(跨轨聚合,可选):全部 downloaded stream 的 Size 之和 / 已写之和(derived 一次性产物计入 finished 后的总量)。
- `schedule`(沿用):百分比。
- `statusText`(见工作流九):资源级 phase 描述。

## 十一、工作流 9:合并动作(独立于任务执行,= 依赖本地文件的派生)

> 这是"依赖本地主资源文件的派生"的归宿——不进入任务流(插件无法访问主程序磁盘文件),由主程序端在完整文件上执行。

### 11.1 新模块 `backend/merge/`

- Handler:`MergeResource(ctx, resourceId)` —— 找到该 Resource 的 `videoTrack`+`audioTrack` store(本地完整文件),执行 `ffmpeg -i video -i audio -c copy -movflags +faststart <out>`,产物存为新 `PersistentStore`(store_type=`merged`,generation=`downloaded`),挂回该 Resource。
- 这是对两个完整文件做平凡 remux,无流式合并、无确定性、无 skip-N 问题。
- 合成进度:对大文件可经现有事件通道推 phase("正在合成"),合成通常很快。
- ffmpeg 查找:系统 PATH → 主程序/插件捆绑位置;找不到 → 返回明确中文错误(合并是用户主动触发,无需静默降级)。

### 11.2 产物去向(由用户设置决定)

设置项 `mergeStrategy`(`select`):

| 模式 | 行为 |
|---|---|
| `overwrite`(覆盖) | 新建 `merged` store,删除原 `videoTrack`/`audioTrack` store 及其 PersistentStore 文件。 |
| `keep`(保留,默认建议) | 新建 `merged` 类型 store,原始 `videoTrack`/`audioTrack` 保留为真相源(可重新合并/删除 merged)。 |

### 11.3 前端

- 作品卡片/详情:对"含 videoTrack+audioTrack 且(无 merged 或允许重复合并)"的作品,展示「合并」动作。
- 外部打开优先级:`merged` > `main` > 其它。本期对"仅有轨道、未合并"的作品,打开行为不在范围(合并动作即为获得可播放文件的途径)。
- 合并 wrapper + 前端 action + 设置项接入。

## 十六、风险

1. **taskManager 是核心**:`downloadLoop` + `ManagedTask` 多流化是最高风险点,需保证暂停/恢复/重启续传的 per-stream 状态与资源级聚合语义正确,且升级后的 pixiv/local(N=1 + derived 缩略图)行为不退化。建议阶段 2 配充分单测 + 集成验证。
2. **单接口时序**:派生型并入 `Start` 流集合后,插件需保证 derived 元素可独立产出(不依赖主资源本地文件)。边界界定已在决策记录中明确——依赖本地文件的派生归「合并动作」。若未来插件产生"必须读本地主资源才能派生"的需求,需走合并路径或新增宿主文件读取能力,不得破坏单接口时序。
3. **derived 续传不可行**:derived 轨不可断点续传,未完成时整轨重产;大体积 derived(若未来出现)会有重复生成成本。当前 derived 仅缩略图(小体积),无影响。
4. **StreamChunk role 复用**:多轨数据复用一条 gRPC stream,需保证 role 标识的分段/交错推送与主程序端按 role 分发的正确性,尤其交错推送时的顺序与背压。
5. **DROP COLUMN 迁移**:依赖 SQLite 3.35+;需在迁移中幂等判断列存在性,并备份 DB 后执行。
6. **SDK ABI(破坏性)**:`TaskHandler` 改签名 + 移除 `GetThumbnail` 为破坏性变更;开发期硬切,需 SDK + 主程序 + pixiv/local/Bilibili 四者同步升级,无过渡期。
7. **Redownload IPC 破坏性**:`sections` 顺序码 → `storeRoles` 字符串,前端与后端契约需同步改造。
8. **快照兼容**:旧 `ResourceSnapshot` 两字段需能还原(映射为 main=downloaded + thumbnail=derived),新快照带版本号。
9. **合并的 ffmpeg 依赖**:合并依赖外部 ffmpeg;缺失时合并不可用(明确提示),不影响下载/存储。
10. **一任务一活跃实例的后端防御**:前端不为活跃任务提供执行入口、只为终态任务提供非全量入口,但后端不可依赖前端约束——`startTaskTrees`/`Redownload` 入口须校验目标任务无活跃 `ManagedTask`(且首次执行仅全量、非全量仅终态)。否则并发执行同一 Resource 的不同 store 子集会破坏暂停/停止的"任务级"语义(见核心语义 1、7)。
11. **跨重启恢复的板块一致性**:板块选择(storeRoles/includeWorkInfo)须持久化到 task 实体(见 1.4),`resumeTaskTrees`/`buildOrReuseChild` 读回重建 runMode 而非固定 Full。否则非全量任务(如仅重下缩略图)跨重启恢复退化为全量,多轨下会触发大体积 videoTrack/audioTrack 重下。`resumeFromPersistedState` 当前只续主资源,须适配为按 storeRoles 续传对应 store。
