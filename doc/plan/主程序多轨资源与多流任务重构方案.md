# 主程序多轨资源与多流任务重构方案

> 目标:把"1 作品 = 1 主文件"的资源模型,重构为"1 Resource(作品资源)可挂多个 typed store(主文件/缩略图/视频轨/音频轨/合并产物)",并把任务模块从"单文件流式传输"升级为"同一任务并发传输多个 store"。
> 这是一次主程序架构升级,为 Bilibili 等视频站点(音视频分离的 DASH)提供原生支持。完成后,下载分离轨道将和下载单张图片一样简单(每条轨道 = 一个普通可续传 HTTP 文件)。
> 配套插件计划见 `bilibili-plugin-plan.md`(薄消费者,依赖本方案)。

## 一、核心语义(贯穿全方案)

1. **操作粒度 = Resource**。一个任务下载一个 Resource;暂停/恢复/停止作用于该 Resource 下的**全部** store,用户不感知、也不操作单个 store。前端控制按钮仍是一个任务一个。
2. **描述面可细分**。状态描述(向前端推的 statusText/phase)允许反映内部流粒度,例如其余轨道完成、仅剩视频轨在跑时推"正在下载视频资源"。控制聚合,描述可细。
3. **本期内置播放不在范围**。应用核心是下载与存储管理;播放仍由外部程序承担(`appLauncher`)。"可合并作品"通过独立合并动作产出可外部播放的单文件。
4. **合并独立于任务执行**。合并是用户在"可合并的作品"上手动触发的动作,不属于下载流程。

## 二、现状(调研结论)

- `Resource` 实体(`backend/base/model/entity/resource.go`):`WorkStoreID *int64`(主文件)+ `ThumbnailStoreID *int64`(缩略图),两个**固定** store 槽。无资源类型/角色概念。
- `PersistentStore`(`persistent_store.go`):一条记录 = 一个文件(`FilePath` 唯一索引;`FileName`/`FilenameExtension`/`Status`/`Width`/`Height`)。
- Resource:Work 在 DB 层是 1:N(`ListByWorkId`/`GetEnabledByWorkId`/`ListByWorkIds` 返回切片),但上层硬编码单数。
- 资源由 `taskManager/model.go` 的 `saveResource`(564–623)在下载流程中创建,**一次任务执行只建/更一条 Resource**。
- `ManagedTask`(`model.go:292-299`)与 `downloadLoop`(`model.go:627-705`)**单流**:单 `reader`、单 `storeWriter`、单 `workStoreId`,EOF → `storeWriter.Complete()` → `TaskStateFinished`。
- 终态由内存 `TaskState`(28–39)驱动;`ResourceComplete` 是信息性字段,不参与状态机。`PersistentStore.Status`(Complete=1)用于 `resumeFromPersistedState`(790–797)的续传判定。
- 播放:`appLauncher` 全外部(Photos / 电影和电视 / PotPlayer / OpenPath),**无应用内播放器**。前端 `WorkCard.vue:59-70`、`WorkDialog.vue:128-130,285` 经 `appLauncherOpenImage` 打开 `resource.workStore.filePath`。
- 备份:`store_backup_orchestrator.go` 的 `StoreType` 枚举(47–52)仅 `StoreTypeWork`/`StoreTypeThumbnail`;`BackupStores`(94–140)/`RestoreAllStores`(144–219)的 switch(198–203)只处理这两种。
- 回收站:`recycleBin/snapshot.go` 的 `ResourceSnapshot`(47–54)只有 `WorkStoreBackupID`/`ThumbnailStoreBackupID` 两个固定字段;`SoftDeleteWork`(work/service.go:550–700)按这两个字段备份,`RestoreWorkFromSnapshot`(750–868)同构重建。
- DTO/搜索:`WorkFullDTO.Resource` 单数(`sdk dto/work_dto.go:28`);`search/repository.go:237` 硬编码 `LIMIT 1` 取一条 enabled resource;`work/service.go:1138-1148` 取 `resources[0]` 组装 `ResourceFullDTO`。

## 三、工作流 1:数据模型 —— Resource 挂多个 typed store

### 1.1 新增关联子表 `resource_store`

把 Resource 的两个固定列泛化为 N 个 typed 关联:

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | int64 | 主键(BaseEntity) |
| `resource_id` | int64 | 所属 Resource(索引) |
| `store_type` | string | `main` \| `thumbnail` \| `videoTrack` \| `audioTrack` \| `merged` |
| `store_id` | int64 | 指向 `persistent_store.id` |
| `order_idx` | int | 同类型内排序(可选) |

- `StoreType` 常量集中定义(与备份编排器的 `StoreType` 枚举统一),供 taskManager、backup、recycleBin、DTO、前端共用。
- `PersistentStore` 实体**不变**(仍是纯文件记录)。可选 P2:加 `duration`/`codec`/`bitrate` 媒体元数据字段,供合成与展示。

### 1.2 迁移(向后兼容)

1. `migration/migrate.go` 注册新实体 `ResourceStore`,GORM AutoMigrate 建表。
2. 数据迁移:遍历现有 `Resource`,把 `WorkStoreID → (main)`、`ThumbnailStoreID → (thumbnail)` 写入 `resource_store`。
3. 删除旧列:`WorkStoreID`/`ThumbnailStoreID`。SQLite 3.35+ 支持原生 `DROP COLUMN`,在迁移中用 raw SQL 执行(GORM AutoMigrate 不删列)。迁移需幂等(先判断列是否存在)。
4. 迁移后代码**只从 `resource_store` 读写 store 关联**,旧列彻底退役。

### 1.3 Repository

- `ResourceRepository` 增 `ListStoresByResourceId`、`ListStoresByResourceIds`(批量,避免 N+1)、`AddStore`、`RemoveStore`、`GetStoreByType`。
- 遵循 `BASE_REPOSITORY_REUSE` / `ELIMINATE_N_PLUS_1_QUERY`(P0)。

## 四、工作流 2:任务模块多流化(本次主战场)

### 2.1 统一为"流集合"模型

把任务下载统一建模为"下载一组 stream 到一组 store"。**单资源插件(图片/单文件)= 集合大小 1(role=main);多轨插件(如 Bilibili 视频)= 集合大小 N**。`downloadLoop` 恒为多流,N=1 时等价于单文件下载。**项目处于开发期,无需任何历史兼容**——`TaskHandler` 直接改造为多轨原生,不存在单轨/多轨两种模式,taskManager 也无需分流或包装。

### 2.2 SDK:TaskHandler 直接改造为多轨原生

在 `library-squirrel-sdk/dto` 改造 `TaskHandler`:**只改 `Start`/`Resume` 两个与流数本质相关的方法**(返回值从"单个 reader"改为"流集合 `[]*TrackStream`"),其余 6 个方法签名不变。新增 `TrackStream`、`TaskResumeParam` 两个类型,移除 `WorkResponse.Resource`(其字段迁移进 `TrackStream`)。

```go
// TrackStream 单条轨道流(对应一个 store)
type TrackStream struct {
    Role        string        // store_type: main | videoTrack | audioTrack | ...
    ReadCloser  io.ReadCloser // 轨道数据流(调用方负责 Close)
    Format      string        // 文件扩展名(原 WorkResponse.Resource.Format 迁移至此)
    Size        int64         // 远程大小;-1 未知
    SuggestName string
    Continuable *bool
}

// TaskResumeParam 续传参数(每轨独立偏移;Pause/Stop 仍用 TaskResParam,不需偏移)
type TaskResumeParam struct {
    Task          *TaskDTO
    StreamOffsets map[string]int64 // role → 该轨已写入字节数(已完成轨不出现)
}

// TaskHandler 改造后(多轨原生,单一接口)
type TaskHandler interface {
    Create(url string) (*TaskCreateResult, error)                         // 不变
    CreateWorkInfo(task *TaskDTO) (*WorkResponse, error)                  // 不变
    Start(task *TaskDTO) ([]*TrackStream, *WorkResponse, error)           // 单 reader → 流集合
    Retry(task *TaskDTO) (*WorkResponse, error)                           // 不变
    Pause(param *TaskResParam) error                                      // 不变(任务级)
    Stop(param *TaskResParam) error                                       // 不变(任务级)
    Resume(param *TaskResumeParam) ([]*TrackStream, *WorkResponse, error) // 单偏移 → per-role 偏移
    GetThumbnail(taskData string) (*ThumbnailResponse, error)             // 不变
}
```

- `WorkResponse` 收敛为只承载作品级信息(Work/SiteAuthors/SiteTags/WorkSets),**移除 `Resource` 字段**;原 `TaskResourceDTO` 的 Format/Size/SuggestName/Continuable 整体迁移进 `TrackStream`。
- 各插件统一返回一个切片:pixiv/local 单元素(`{Role:"main"}`),Bilibili 视频双元素(videoTrack+audioTrack)。
- taskManager **无类型断言、无分流、无包装**:`streams, resp, err := handler.Start(task)` 恒为流集合,`downloadLoop` 只有一条多流路径。
- SDK 版本号 bump(破坏性变更,开发期可硬切);主程序与三个插件(pixiv/local/Bilibili)同步升级。

### 2.3 ManagedTask 重构

引入**单流控制器**与**资源级聚合**两层:

```go
// streamController 管理单个 store 的传输(复用现有单流拷贝循环逻辑)
type streamController struct {
    role        string
    reader      io.ReadCloser
    storeWriter StoreWriter
    store       *entity.PersistentStore
    written     int64
    state       streamState // downloading | paused | completed | failed
    mu          sync.Mutex
}
```

- `ManagedTask` 持有 `streams []*streamController`(按 role 索引)。
- `downloadLoop` → 每条 stream 一个 goroutine,各自跑"read→write→累计 written"循环(逻辑沿用现有单流实现,下沉到 streamController)。
- **完成判定**:全部 stream `completed` → `TaskStateFinished`;任一 `failed` → `TaskStateFailed`(但保留已完成 stream 的 store,供续传只补失败项)。

### 2.4 控制面(资源级聚合)

| 操作 | 行为 |
|---|---|
| **Pause** | 广播到该 Resource 全部活跃 stream:各 stream 关闭上游连接、保留 store 与 `written`(对齐 pixiv 的 Pause 语义),状态置 `paused`。 |
| **Resume** | 调插件 `Resume(TaskResumeParam{StreamOffsets[role]=store.written})`,为每条未完成 stream 重建 reader(各轨从自身偏移 Range 续传),状态置 `downloading`。 |
| **Stop** | 广播关闭全部 stream + 清理(对齐 pixiv Stop)。 |
| **重启后续传** | 不依赖内存:重启后 taskManager 读每条 stream 对应 `PersistentStore`(Status + 文件大小)得出各轨完成度与偏移,据此 `Resume`。已完成轨跳过,未完成轨续传。 |

> 关键:控制信号是 Resource 级一个,但内部广播到 N 条 stream;对用户/前端只有一个"暂停/恢复/停止"。

### 2.5 saveResource 多 store

`saveResource`(model.go:564–623)改为:创建/更新一条 Resource,然后按 stream 集合挂 N 条 `resource_store`(每条 stream 一个 store)。缩略图仍走 `GetThumbnail` 独立路径(不变)。

### 2.6 任务进度

`TaskProgressDTO`(sdk `dto/task_dto.go`)新增可选字段:

- `totalBytes` / `finishedBytes`(跨轨聚合,可选):全部 stream 的 Size 之和 / 已写之和。
- `schedule`(沿用):百分比。
- `statusText`(见工作流 3):资源级 phase 描述。

## 五、工作流 3:前端状态描述(描述面可细分)

- taskManager 据 stream 集合状态计算 **phase 文本**,随进度事件推前端。规则(可扩展):
  - 全部在跑 → "正在下载"(或"正在下载视频、音频资源")。
  - 仅剩视频轨在跑 → "正在下载视频资源";仅剩音频轨 → "正在下载音频资源"。
  - 合成阶段(合并动作进行中,见工作流 4)→ "正在合成"。
  - 全部完成 → "已完成"。
- phase 反映"当前活跃/剩余"的轨道,属于描述面;**不暴露**"视频轨暂停但音频轨在跑"这类内部不一致(控制是整体的,不会出现单轨暂停)。
- 前端任务列表/详情展示 `statusText`,与数字进度并列。

## 六、工作流 4:合并动作(独立于任务执行)

### 6.1 新模块 `backend/merge/`

- Handler:`MergeResource(ctx, resourceId)` —— 找到该 Resource 的 `videoTrack`+`audioTrack` store(本地完整文件),执行 `ffmpeg -i video -i audio -c copy -movflags +faststart <out>`,产物存为新 `PersistentStore`,挂回该 Resource。
- 这是**对两个完整文件做平凡 remux**,无流式合并、无确定性、无 skip-N 问题。
- 合成进度:对大文件可经现有事件通道推 phase("正在合成"),合成通常很快。
- ffmpeg 查找:系统 PATH → 主程序/插件捆绑位置;找不到 → 返回明确中文错误(合并是用户主动触发,无需静默降级)。

### 6.2 产物去向(由用户设置决定)

设置项 `mergeStrategy`(`select`):

| 模式 | 行为 |
|---|---|
| `overwrite`(覆盖) | 合并产物作为 `main` 挂载,删除原 `videoTrack`/`audioTrack` store 及其 PersistentStore 文件。 |
| `keep`(保留,默认建议) | 新建 `merged` 类型 store,原始 `videoTrack`/`audioTrack` 保留为真相源(可重新合并/删除 merged)。 |

### 6.3 前端

- 作品卡片/详情:对"含 videoTrack+audioTrack 且(无 merged 或允许重复合并)"的作品,展示「合并」动作。
- 外部打开优先级:`merged` > `main` > 其它。本期对"仅有轨道、未合并"的作品,打开行为不在范围(合并动作即为获得可播放文件的途径)。
- 合并 wrapper + 前端 action + 设置项接入。

## 七、DTO / 搜索 / 前端适配

### 7.1 DTO(stores 为主 + 便捷访问器)

- `ResourceFullDTO`:直接以 `stores []*ResourceStoreDTO`(含 `storeType`/store 信息)为主;可保留 `workStore`/`thumbnailStore` 作为便捷访问器(指向 `stores` 中对应类型),以收敛前端取主文件路径的改动面。
- `WorkFullDTO.Resource` 保持单数(代表该作品的主资源);多资源场景(如 pixiv 多页=N 作品)不变。
- 新增能力标记:DTO 暴露 `mergeable`(含 videoTrack+audioTrack)供前端显示「合并」按钮。
- DTO 组装 `work/service.go:1138-1148`:仍取该作品代表 Resource,但 store 集合从 `resource_store` 批量装载(避免 N+1)。

### 7.2 搜索

- `search/repository.go:237` 的 `LIMIT 1` 语义保留(每个作品取一条代表 resource 用于网格展示);多 store 不影响搜索结果集,store 细节在详情接口取。

### 7.3 前端

- 现有 `WorkCardItem.resource`、`WorkDialog.getResourceFilePath` 等"取主文件路径"路径保留(取 `merged`/`main`)。
- 新增 track/merge 感知:合并按钮、轨道列表展示(可选)、statusText 展示。
- 主题令牌、wrapper 规范等遵循前端规则。

## 八、备份 / 回收站适配

- `StoreType` 枚举(`store_backup_orchestrator.go:47-52`)扩展:`StoreTypeVideoTrack`/`StoreTypeAudioTrack`/`StoreTypeMerged`;`BackupStores`/`RestoreAllStores` 的 switch(198–203)追加分支。备份/还原按 Resource 的**全部 store**进行(遍历 `resource_store`)。
- `ResourceSnapshot`(`recycleBin/snapshot.go:47-54`):把两个固定字段泛化为 `stores []StoreSnapshot`(含 `storeType` + backupId)。快照加版本号,兼容旧快照(旧两字段 → main+thumbnail)。
- `SoftDeleteWork`/`RestoreWorkFromSnapshot`(work/service.go):按 store 集合遍历,不再硬编码两个固定字段。
- 合并产物 store 同样纳入备份/还原(`merged`/`main` 类型)。

## 十一、风险
1. **taskManager 是核心**:`downloadLoop` + `ManagedTask` 多流化是最高风险点,需保证暂停/恢复/重启续传的 per-stream 状态与资源级聚合语义正确,且升级后的 pixiv/local(N=1)行为不退化。建议阶段 2 配充分单测 + 集成验证。
2. **DROP COLUMN 迁移**:依赖 SQLite 3.35+;需在迁移中幂等判断列存在性,并备份 DB 后执行。
3. **SDK ABI(破坏性)**:`TaskHandler` 改签名为破坏性变更;开发期硬切,需 SDK + 主程序 + pixiv/local/Bilibili 四者同步升级,无过渡期。
4. **快照兼容**:旧 `ResourceSnapshot` 两字段需能还原,新快照带版本号。
5. **合并的 ffmpeg 依赖**:合并依赖外部 ffmpeg;缺失时合并不可用(明确提示),不影响下载/存储。
