# 阶段 3 落地差距核查(板块 / Redownload 退化)

> 本文是《主程序统一资源模型与多流任务重构方案》(下称"主方案")**阶段 3** 的落地细化,对照现有代码逐函数给出"现状 → 目标 → 改法",供执行时逐项对照。
> 前置阅读:主方案「核心语义 1(粒度非对称)、7(一任务一活跃实例)」、工作流八(板块退化,6.1–6.4)、1.4(task 持久化字段)。
> 阶段 3 目标(主方案):runMode 退化为 `{workInfo, storeRoles}`;Redownload IPC `sections` → `storeRoles + includeWorkInfo`;task 实体持久化所选板块;恢复时读回重建 runMode(修复跨重启退化为全量的缺口);runSectionCombo 按 storeRoles 过滤执行。

## 总览

改动分三层:
- **声明层**(不依赖阶段 2 多流,可与阶段 0/1 并行先行):task 字段、runMode 结构、parseSections 退役、Redownload IPC、前端契约。
- **恢复链路**(横跨声明层):mode 从"调用方传参"改为"task 派生属性"。
- **执行层**(依赖阶段 2 多流 + 阶段 0 resource_store):runSectionCombo 按 storeRoles 过滤、resumeFromPersistedState 按 storeRoles 续传。

## 四、重要发现(降低风险 / 影响排期)

1. **"一任务一活跃实例"的后端防御现状已满足**(对应主方案核心语义 7、风险 10):
   `loadAndStartTaskTrees`(`backend/taskManager/manager.go:152-203`)已有重复执行保护——快照 `taskMap`/`parentMap`,同一任务/父单元已运行则跳过。所有执行入口(Start / Resume / Redownload)都经此函数,覆盖完整。
   → **阶段 3 无需新增并发防御代码**,主方案风险 10 可降级为"已具备,确认即可"。

2. **前端"仅终态提供非全量入口"已实现**(对应核心语义 7):
   `TaskOperationBarActiveV1.vue:175-181` 的 `isTerminalState()`(FINISHED/PARTLY_FINISHED/FAILED)配合 `v-if/v-else`——活跃任务只显示常规操作(开始/继续/暂停),终态才显示板块勾选 popover。
   → 前端无需新增"终态门控"逻辑,仅需把 checkbox 的值从数字改为 store_type 字符串。

3. **阶段 3 执行层(C/G)强依赖阶段 0 + 阶段 2**:
   - C 要从 `Start` 返回的 `[]*StoreSpec` 流集合过滤(阶段 2 才有)。
   - G 要遍历 `resource_store` 表(阶段 0 才有)、并按 generation 续传(阶段 2 的 streamController)。
   → **阶段 3 无法在阶段 2 之前完整闭环**。

4. **F2(mode 派生重构)是阶段 3 的中枢**:把 mode 从"调用方临时参数"改为"task 派生属性"后,F1(跨重启读回)自然成立,且让 Start/Resume/Redownload 三条入口的 mode 来源统一,是根除"恢复固定 Full"缺口的关键一步。

## 五、落地顺序建议

鉴于发现 3,建议把阶段 3 拆为两步:

- **阶段 3a(可与阶段 0/1 并行先行)**:声明层 E/A/D/B/H + 恢复链路 F1/F2/F3。
  纯声明层 + mode 派生;此时 `Start` 仍可返回单元素流集合(N=1),runSectionCombo 过滤逻辑已能工作(集合大小 1)。完成即可修复"跨重启恢复退化为全量"的缺口。
- **阶段 3b(阶段 2 多流化之后)**:执行层 C/C'/G。
  多流过滤与多 store 续传,依赖阶段 2 的 `streamController` 与阶段 0 的 `resource_store`。
