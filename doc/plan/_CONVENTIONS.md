# doc/plan/ 文档规范

> 本目录存放计划/设计/方案文档。**无论文档由哪个技能或命令生成，落盘到此目录一律遵守本规范。**
> 目的：把"通读全文找错"的审查，改成"读 20 行摘要 + 抽查锚点 + 回答决策"。

## 首段强制：审查摘要

每份文档在标题之后、正文之前，必须有 **「审查摘要」** 一节（≤20 行），含三类清单：

- **关键声明（抽查项）**：正文中所有"已核验 / 已就位 / 零改动 / X 已支持 Y / 现状是…"类论断，全部登记在此，每条挂证据：
  - 证据 = `相对路径/文件.ext:行号`，或可复现命令（`grep …` / `go test …`），或 `<未核验>`
  - 未登记、或标 `<未核验>` 的论断，审查时默认不信
  - 条目编号：声明1、声明2、声明3……
- **待决策（需用户拍板）**：编号列出（决策1、决策2……），每条标注"是否阻塞实施"
- **自曝风险（作者没把握 / 可能错的地方）**：强制暴露（风险1、风险2……），比事后被审查出来高效

## 可读性铁律（强制）

审查摘要与正文都要"自包含可读"——读者不查外部、不猜符号就能懂。四条硬约束：

1. **术语首次出现自带最小解释**：任何函数名 / 类型名 / 字段名 / 概念名 / 缩写，第一次出现时跟半句话说明它是什么。审查摘要尤其严格——它是独立入口，出现的术语必须当场解释，不能依赖正文。例：写 `InferKind（据 stores 推断 resource.kind 的函数）`，而非裸 `InferKind`。
2. **禁用非通用符号**：不用 `§` `※` `†` 等排版符号做章节引用或标注；章节引用用中文"第N节"或"『节名』节"。
3. **禁自创代号前缀**：清单编号只用本规范定的"声明N / 决策N / 风险N"（中文词 + 数字）。**禁止**自创 `P`/`PR`/`F`/`S`/`I`/`A` 等任何字母前缀——枚举式替换字母永远追不完（C/D/R 刚汉化，转头又冒出 P/PR），根除办法是只允许中文词编号。要区分层级（如 design 级 vs plan 级）用文字（"plan 级声明"），不用新字母。
4. **跨文档引用不用对方代号**：引用另一份文档的结论时，写"design.md 已确认 ResourceComplete 是死字段"，不写"F5 证实"——读者不会去翻对方文档的编号表；必须指向对方具体位置时写"design.md 第N节"。

## 文档分类与审查维度的关系

**审查摘要（首段）固定三轴**：关键声明 / 待决策 / 自曝风险——这是审查契约，不可改名、不可增类，审查员与审查者按此操作。

**正文组织分类可自由**（如分成事实/决策/方案/实施/风险等小节），但映射到审查三轴：

- 事实类 → **关键声明**：审查员独立核验锚点
- 决策类 → **待决策**：审查员查漏"该问没问的"
- 风险类 → **自曝风险**：审查员查漏"未自曝的高风险"
- 方案/实施类 → 不在审查维度：不深究，交给编译/测试兜底

**硬约束**：无论正文用什么分类，凡"已核验 / 已就位 / 零改动"类**事实声明**，必须登记到首段摘要的关键声明项并挂锚点（不能只留在正文的事实类小节里）——否则审查员够不到、视为未核验；方案/实施里夹带的这类事实同样要提到关键声明。

## 声明锚点硬约束

凡涉及"代码现状 / 已有支持 / 已核验"的论断（摘要的关键声明项与正文），必须挂 `file:line` 或可复现命令。无锚点的声明视为未核验。审查者只需抽查 1–2 条关键声明的锚点即可判定文档可信度。

## 阶段清单（实施契约，涉及实施/改造的计划必填）

涉及代码实施、大规模改造或多文件变更的计划，**必须在正文「设计」之后、「实施」之前给出「阶段清单」**。它是执行契约：每个阶段对应一次独立的子代理/会话执行单元，阶段边界即上下文边界。纯调研、纯决策、纯进度记录文档可省略，但须在标题下注明"非设计文档，无需审查"。

### 阶段清单格式

阶段用「阶段N」编号（沿用"中文词+数字"铁律，禁止 `Phase N` / `P1` 等字母前缀），每阶段字段固定：

- **目标**：一句话、可验证——阶段完成时能明确判断对错
- **涉及文件**：精确到相对路径文件。不精确 = 执行者会探索整仓库 = 上下文膨胀
- **验证命令**：只构建/测试本阶段触及包的小范围命令（如 `go build ./backend/xxx`、`go test ./backend/xxx/...`）。**禁止全量构建**（`yarn build`、`go test ./...`、`wails3 build`）作为常规阶段验证
- **退出标准**：验证命令通过 + 具体断言（如"xx 测试通过""前端可编译"）
- **依赖**：依赖哪个阶段；无依赖 = 独立，可并行执行
- **模型建议**：`主模型`（需全局判断）/ `便宜模型`（机械性、循环量大、结果可人工审）/ `本地模型`（纯机械）
- **交接摘要**：阶段完成后必须产出的紧凑记录（≤5 行：改了哪些文件 / 动了什么逻辑 / 遗留与风险 / 验证结果）

### 阶段划分纪律（防上下文膨胀）

1. **阶段大小上限**：每阶段应能在 ~150–200 次工具循环内完成（约一个子代理运行）。超出即再拆子阶段。判断依据：涉及文件数 × 验证链长度。
2. **依赖刻画**：不同模块（独立文件集）切独立阶段、可并行；有数据流依赖的串行，用交接摘要衔接。
3. **验证小范围化**：每阶段验证只触及本阶段包的构建/测试，禁止默认全量——全量构建输出灌入上下文是 token 膨胀主源。
4. **交接摘要**：执行阶段 N 的会话/子代理只读：计划阶段清单 + 阶段 N 涉及文件 + 阶段 N-1 交接摘要，不读阶段 N-1 的执行历史。
5. **执行载体**：每阶段在独立子代理/新会话中执行，阶段间不共享执行上下文；「模型建议」为便宜模型/本地模型的阶段可交对应模型子代理，不消耗主模型配额。

阶段划分若有实质分歧或作者不确定，把划分方式列为「待决策」项。

## 审查姿势（给审查者）

读审查摘要 → 随机抽查几条关键声明的锚点 → 回答待决策项 → 重点看自曝风险。**无需通读正文**——正文是给执行者与留档用的。

## 例外

纯进度记录、检查清单、调研笔记（不含架构决策与事实声明）可省略审查摘要，但须在标题下注明"非设计文档，无需审查"。

## 与技能契约的关系

`requirements-analyst` 技能的计划模板已内置本规范的首段结构；本规范是**目录级真相**，约束一切落盘到此的文档，与具体技能解耦。
