### 待决策（已拍板 2026-08-11）
- 决策1：**B 加唯一索引 + 迁移**。entity 改普通 index 为唯一索引 `(work_id, local_author_id)`/`(work_id, site_author_id)`；migrate.go 命名迁移：LOCAL/SITE 分别按 `(work_id, 对应 author_id)` 去重保留最早 id + Drop 旧普通索引。SQLite NULL 不参与唯一性，两类互不冲突
- 决策2：**增量保留**（`SaveBatchOnConflict`，OnConflict DoNothing，不删历史关联）
- 决策3：**增量追加**（已存在跳过）

### 实施修正（相对原方案）
- 修正1：LOCAL 增量用 `SaveBatchOnConflict`（DoNothing）而非 `UpsertBatch`。`UpsertBatch` 的 DoUpdates 含 `namespace`（`backend/reWorkTag/repository.go:81`），而 `buildLocalTagLinks` 不设 namespace（零值 NULL），用它会把已存在 LOCAL 关联的 namespace 覆盖成 NULL——同类零值覆盖。DoNothing 完全跳过已存在行
- 修正2：`work.NewService` 依赖 `*reWorkTag.Service`/`*reWorkAuthor.Service`（非 repository），需在 service 本地 `Repository` 接口 + Service 转发方法 + work 层 Writer 接口三处都补 `DeleteSiteByWorkId`/`SaveBatchOnConflict`
- 编译：`CGO_ENABLED=0 go build .` 通过；`go test ./backend/work/... ./backend/reWorkTag/...` 通过

### 自曝风险
- 风险1：SITE 关联仍走"删后重建"，用户若在 UI 改过 SITE 关联的 namespace（`reWorkTag.UpsertBatch` 注释暗示 UI 支持），重复入库会被插件值覆盖。语义上 SITE 关联归插件管，可接受；但需确认 UI 是否真有此入口
- 风险2：`last_use` 移出 `DoUpdates` 后，`site_tag`/`site_author` 的 last_use 不再被任务导入清成 NULL；当前转换函数本就不设 last_use，故改为"保留原值"。`site_tag` 无 `UpdateLastUseByIds` 对应入口（`site_author` 有，`siteAuthor/repository.go:185`），last_use 更新机制不对称属既有问题，不在本次范围
- 风险3：决策1 选 A 时，应用层"先查后插"在 MaxOpenConns=1 + 事务内无并发，TOCTOU 安全；但若未来放开并发写需重新评估

## 一、背景与症状

任务执行（插件返回 `WorkResponse`）→ `SaveWorkInfo` 入库时，存在两个独立缺陷，都会导致"用户已建立的关联被清空"：

1. **site→local 桥接丢失**：用户手动把 `site_tag` 绑定到 `local_tag`（`site_tag.local_tag_id`）后，下一次该 site_tag 随任务重复入库时，桥接被清成 NULL。作者同理。
2. **作品↔local 关联丢失**：用户在 UI 给作品手动加了本地标签/作者关联（`re_work_tag`/`re_work_author` 中 `tag_type`/`author_type=LOCAL` 的行），下一次该作品随任务重复入库时，关联被全删后仅用插件数据重建，用户手动加的丢失。

## 二、根因

### 缺陷1：BatchUpsert/Upsert 的 DoUpdates 列表越界

`ON CONFLICT(site_id, site_tag_id) DO UPDATE SET local_tag_id = excluded.local_tag_id` 中，`excluded` 指向待插入新行；新行由 `taskSiteTagDTOToEntity` 构造，`LocalTagID` 为零值（`sql.NullInt64{Valid:false}` → NULL）。于是已存在行的 `local_tag_id` 被覆盖为 NULL。`base_site_tag_id`、`last_use` 同理（也不在插件 DTO 里）。

### 缺陷2：Phase 3 全量替换策略

`saveWorkInfoInTx` 的 Phase 3（`backend/work/service.go:1544-1592`）对三张关联表统一 `DeleteByWorkId` 后重建。`DeleteByWorkId` 不分 type，把用户手动加的 LOCAL 关联一并删掉；重建仅用插件返回的 `SiteAuthors`/`SiteTags`/`LocalAuthors`/`LocalTags`/`WorkSets`。

## 三、修复方案

### 方案1：清理 DoUpdates 列表（缺陷1）

把不归插件管的字段从 `DoUpdates` 移除，upsert 只更新插件实际管理的字段。

- `siteTag`（`BatchUpsert` + `Upsert`）：保留 `site_tag_name`/`description`/`update_time`，移除 `local_tag_id`/`base_site_tag_id`/`last_use`。`namespace` 本就不在列表（`namespace` 由 site_tag 表自身字段保留，不受 upsert 影响）
- `siteAuthor`（`BatchUpsert` + `Upsert`）：保留 `author_name`/`fixed_author_name`/`site_author_name_before`/`introduce`/`homepage`/`update_time`，移除 `local_author_id`/`last_use`

用户手动绑定入口（`UpdateBindLocalTag`/`UpdateBindLocalAuthor`，声明9）走独立 UPDATE，不受影响。

### 方案2：Phase 3 增量同步（缺陷2）

核心原则：**SITE 关联由插件权威管理（按 type 删后重建），LOCAL 关联由用户管理（保留），插件建议的 LOCAL 关联增量追加（去重），workSet 增量保留**。

#### 2.1 re_work_tag（已有唯一约束，最干净）
- 新增 `DeleteSiteByWorkId(ctx, workId)`：`WHERE work_id=? AND tag_type=SITE`
- Phase 3 改：
  - 删 SITE 关联（`DeleteSiteByWorkId`）→ 重建 SITE 关联（`buildSiteTagLinks`，含 namespace 镜像）
  - LOCAL 关联：**不删**。插件返回的 local（`buildLocalTagLinks`）走 `UpsertBatch(links, LOCAL)` 增量——已有 `UpsertBatch`（声明5）按 `(work_id, local_tag_id)` 冲突 DoNothing 式更新 namespace，不存在则插入

#### 2.2 re_work_author（无唯一约束，依决策1）
- 新增 `DeleteSiteByWorkId(ctx, workId)`：`WHERE work_id=? AND author_type=SITE`
- **决策1 选 A（推荐）**：新增 `SaveLocalLinksIncremental(ctx, workId, localLinks)`——先 `ListRelationsByWorkId` 取现有 LOCAL 关联的 `local_author_id` 集合，过滤掉 links 中已存在的，`CreateBatch` 余下部分。无 schema 变更
- **决策1 选 B**：给 `re_work_author` 加唯一索引 `(work_id, local_author_id)` 与 `(work_id, site_author_id)`，先迁移历史重复行（保留最早一条），再用 OnConflict DoNothing。更彻底但有迁移成本
- Phase 3 改：删 SITE 关联 → 重建 SITE（`buildSiteAuthorLinks`）；LOCAL 不删 + 增量追加

#### 2.3 re_work_work_set（依决策2）
- **决策2 选增量保留（推荐）**：Phase 3 不再 `DeleteByWorkId`，改用 `SaveBatchOnConflict`（声明7，OnConflict DoNothing）只加新 workSet 关联；用户手动加的关联与 `is_cover`/`sort_order`/`site_sort_order` 元数据全部保留。`buildWorkSetLinks` 的 max+1 续排逻辑不变
- **决策2 选全删重建**：维持现状（本次不修 workSet，仅修 tag/author）

## 四、实施步骤

1. **DoUpdates 清理**：改 `backend/siteTag/repository.go`（2 处）+ `backend/siteAuthor/repository.go`（2 处）
2. **reWorkTag**：新增 `DeleteSiteByWorkId`
3. **reWorkAuthor**：新增 `DeleteSiteByWorkId` + LOCAL 增量方法（决策1 选 A 时为 `SaveLocalLinksIncremental`，选 B 时加唯一索引 + 迁移）
4. **Phase 3 改造** `backend/work/service.go:1538-1594`：
   - author：`DeleteByWorkId` → `DeleteSiteByWorkId`；LOCAL 部分改增量
   - tag：`DeleteByWorkId` → `DeleteSiteByWorkId`；LOCAL 部分改 `UpsertBatch(LOCAL)`
   - workSet（决策2 选增量）：`DeleteByWorkId`+`CreateBatch` → `SaveBatchOnConflict`
5. **编译验证**：`go build ./...`（Windows 用 `task build` 或 `CGO_ENABLED=0 go build`）
6. **回归测试**：重点验证「同一作品二次入库」场景——site→local 桥接保留、UI 手动加的 LOCAL 关联保留、SITE 关联按插件最新值更新

## 五、影响范围

- **行为变更**：重复入库不再清空 site→local 桥接（缺陷1）、不再删除用户手动加的 LOCAL 关联（缺陷2）
- **不受影响**：首次入库（无 ON CONFLICT 触发，无既有 LOCAL 关联可删）；用户手动绑定入口（独立 UPDATE）；namespace 维度（`re_work_tag.namespace` 走 SITE 重建镜像，site_tag.namespace 不在 DoUpdates）
- **未覆盖**：Phase 3 SITE 关联的"删后重建"在事务内原子完成（`saveWorkInfoInTx` 单事务），无中途丢失风险；workSet 增量模式下"插件移除 workSet"不生效（语义变更，决策2 已权衡）
