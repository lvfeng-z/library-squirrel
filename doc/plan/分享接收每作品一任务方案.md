# 分享接收每作品一任务方案

## 审查摘要

**关键声明（抽查项）**：
- 声明1：share-receive 收件现状为**单任务整体下载**——执行面 `ReceiveExecution.Execute` 时序「拉 manifest（整体）→ `planReplace` 全作品批量查重 + `WaitReplaceConfirm` 任务粒度整体确认 → `stageFiles` 逐文件暂存 → `ManifestIngestor.Ingest` 整 manifest 导入 → 清理暂存 Finish」——`backend/share/task_execution.go:62-136`
- 声明2：任务模块的**父任务为纯容器、无执行面**——父任务只聚合子任务状态（`ParentTask`），执行策略只绑定叶子/独立任务；「拉 manifest → 知道作品数 → 建子任务」无法由父任务在执行中完成——`backend/taskManager/model.go:2132`（`ParentTask` 聚合结构）、`backend/taskManager/manager.go:1044-1054`（`claimParent` 容器守卫）
- 声明3：现有任务创建能力无法直接建内置父子树——`CreateTask`（`backend/task/service.go:371-391`）支持 `Pid`/`HasChild` 但不写 `task_type`/`payload`（其入参 `CreateTaskRequest` 无这两字段，`backend/base/model/dto/task_dto.go:224-234`）；`CreateBuiltinTask`（`backend/task/service.go:399-418`）只建独立叶子（`has_child=false`、无 `pid`）
- 声明4：share-receive 任务载荷（`shareReceivePayload`）现为六字段（中继拨号/展示地址/token/E2E 密钥/密码摘要），无「作品过滤」与「manifest 来源」——`backend/share/receive.go:125-134`；载荷版本锚校验 `schemaVersion`——`backend/share/receive.go:157-168`
- 声明5：manifest 拉取能力可被 Receive 同步复用——`fetchWithRetry`（含退避）为包级函数，`newReceiveClient` 以 payload 构造拨号客户端——`backend/share/task_execution.go:554`、`backend/share/receive_client.go:107`
- 声明6：manifest 结构支持按作品拆分——`WorkRecord.Resources[].Stores[].StoreID` 引用 `Files[]` 条目，可据作品聚合出文件子集——`backend/export/manifest.go:140-164`、`191-203`
- 声明7：`ManifestIngestor.Ingest` 按 `manifest.Works` 逐作品处理，传入「只含单作品的子 manifest」即可只导入该作品（站点/作者/标签/作品集为 find-or-create 幂等，重复导入查重跳过）——`backend/import/ingest.go:134`（三相主流程注释）、`backend/import/ingest.go:62-67`（接口签名）
- 声明8：前端任务列表已支持树形展示（`treeData`/`treeLazy`/`treeLoad`，父任务聚合态/子任务缩进渲染）——`frontend/src/components/common/TaskList.vue:26-28`、`139-144`
- 声明9：`CleanupOrphanReceiveStaging` 启动清扫按「任务行已不存在」回收暂存目录——`backend/share/task_execution.go:616`
- 声明10：覆盖确认弹窗已为**多任务列表形态**（`store.list` 按 taskId 逐条渲染、整批替换/跳过答复）、答复接口为任务粒度 `ConfirmReplace(taskId, action)`——`frontend/src/components/dialogs/ReplaceConfirmDialog.vue:46-59,77`、`frontend/src/apis/http/wrappers/task.ts:113-118`
- 声明11：落地页元数据 `metaPayload` 现为三字段（Title/WorkCount/Source），**无作品名**——`backend/share/protocol.go:166-168`（metaPayload 定义）、`backend/share/session.go:330`（注册时构造 metaPayload）
- 声明12：metaPayload 仅 **register** 上传，bind（复原重绑）不传——`backend/share/protocol.go:157-162`
- 声明13：manifest 作品名可提取（WorkRecord 的 `SiteWorkName`/`NickName` 字段）——`backend/export/manifest.go:129-133`

**待决策（需用户拍板）**：
- 决策1（**已裁决：接受**）：manifest 获取方式 = **Receive 同步预拉一次 + 落盘共享目录，子任务读本地**。放弃备选「子任务各自重新拉 manifest」（N 次收集、清单可能不一致）与「父任务编排拉取」（需扩展 taskManager 父任务执行面，违背父任务纯容器模型，声明2）。代价是 Receive 阻塞一次网络请求，详见风险1
- 决策2（**已裁决：不兼容存量，用户拍板**）：新代码不做存量整体任务兼容——子任务载荷恒有 `ManifestPath`/`ManifestID`；存量 share-receive 任务（载荷无 `ManifestID`，即 `ManifestID==0`）执行时视为过时载荷显式 Fail（用户可读文案「请删除本任务后重新接收分享」），不做任何迁移或降级。见设计五
- 决策3（**已裁决：共享文件不存在，用户拍板**）：本库数据模型中同一 persistent_store 不会被多作品挂载引用，拆分不产生跨子任务重复拉取/重复落盘，方案不做共享文件去重处理
- 决策4（**已裁决：落地页 + 收件侧都要展示作品名，并入本次方案，用户拍板**）：分享涉及的每个作品名称两处展示——① 收件侧 `ShareReceive` 返回 DTO 带作品名列表（前端接收反馈展示，见设计九）；② 分享落地页（中继 web 页）渲染每个作品名——分享方发布时把作品名列表明文随 register 上传中继（扩展 `metaPayload`，见设计十）。作品名**不做内容过滤**（合规风险自担，见风险7）
- 决策5（已裁决：接受）：建树后落盘失败窗口语义 = 回滚删除已建任务树返回错误文案（见设计三）

**自曝风险**：
- 风险1：Receive **同步拉 manifest** 阻塞一次网络往返（首次接收可接受），且拉取失败时**无任务可重试**——Receive 直接返回用户可读文案，用户重新点「开始拉取」（对比当前任务执行中失败可任务面板重试）。密码错误/分享失效等终态错误在此前置暴露，体验更直接但丢失任务重试载体
- 风险3：**多子任务并发挂起确认**——拆分后每子任务独立 `WaitReplaceConfirm`，多作品冲突时多子任务并发 WaitingForInput。前端 `ReplaceConfirmDialog` 的列表本身支持多 taskId 聚合渲染（声明10），但「多 taskId 并发挂起 + 逐任务答复 + 部分答复后其余继续跑」的真实链路未实机验证
- 风险4：**manifest 残留**——共享 manifest 落父任务目录，子任务各自清自己的文件暂存，manifest 在父任务行删除前残留（几百 KB 级，磁盘可接受），由 `CleanupOrphanReceiveStaging` 按父任务行删除兜底回收（声明9）
- 风险5：**单作品分享 = 父+1 子**——不做单作品折叠特例，恒为「父容器 + N 子任务」树形态（对齐任务树 parent+1child 不折叠既有语义，`backend/task/service_create_test.go:222-257`）
- 风险6：**N 子任务并发拨号中继压力**——拆分后最多 N 个子任务并发各自 `newReceiveClient` 拨号（每请求一条 TCP 流），受分享方会话**并发流上限 8** 约束（既有约束，`backend/share/README.md`「并发流上限 8」），N>8 时多余流排队；分享方上传带宽/中继转发压力随并发升高，未经实机压力测试
- 风险7：**落地页作品名明文上传中继（离开 E2E 加密域）**——作品名随 register 明文传中继，中继可读；落地页公开展示可能含成人/敏感名称，合规/隐私风险由用户承担（决策4 已接受「不考虑违法风险」，不做内容过滤）
- 风险8：**作品名列表规模与协议帧限制**——大分享（数十~数百作品）的 `WorksName` 数组上传帧大小、中继落地页渲染量未核验——relay 侧契约（PROTOCOL.md）在 `library-squirrel-relay` 仓库，当前工作目录不可达，需 relay 仓库确认帧限制与渲染上限

## 背景与目标

分享方勾选多个作品发布分享后，收件方当前只创建**一个** share-receive 任务：整个 manifest 捆绑下载、整体查重确认、整体导入。收件人无法按作品粒度管理——单个作品失败/暂停会影响全部，进度只有一行。

**目标**：收件方收到分享链接后，创建**父子任务树**——一个「拉取分享」父任务（容器，聚合进度），其下**每个作品一个独立子任务**（各自下载/暂停/恢复/重试/查重确认/进度）。同时**两处展示分享涉及的每个作品名称**：收件侧（`ShareReceive` 返回 DTO 带作品名列表，接收反馈展示）+ 分享落地页（中继 web 页渲染作品名列表，分享方发布时上传作品名元数据）。分享方模型不变（一个链接、一份整体 manifest、隧道维持照旧）。

**非目标**：分享方侧按作品拆分发布；zip 导入按作品拆分；收件方「先选后下」作品清单交互。

## 现状：收件单任务整体下载链路

```
ShareReceive(link) ──► 创建 1 个 share-receive 任务（payload=连接参数）──► StartTasks ──► 任务面板 1 行「拉取分享」
                                                                                │
                                        ReceiveExecution.Execute（整体）◄───────┘
                                              ├─ 拉 manifest（整体一次拉全）
                                              ├─ planReplace：全作品批量查重 + WaitReplaceConfirm 整体决策
                                              ├─ stageFiles：逐文件暂存（断点续传锚=字节数）
                                              ├─ Ingest：整 manifest 导入
                                              └─ 清理暂存 → Finish
```

任务面板只有一行，整包下载。拆分子任务的前提是**先知道作品列表**——而作品列表只在 manifest 拉下来后可知（声明5）。

## 设计

### 一、总览：父子任务树数据流

```
ShareReceive(link)：
  ├─ 解析链接 → newReceiveClient（payload 形态）
  ├─ 【新】同步拉 manifest（fetchWithRetry 复用，声明5）→ 校验 schemaVersion → 解析作品列表 N
  ├─ 【新】CreateBuiltinTaskTree：父任务「拉取分享（{host}）」（task_type=share-receive、has_child=true、pid=NULL）
  │         + N 子任务（pid=父ID、has_child=false、task_type=share-receive、payload=连接参数+manifestPath+manifestID）
  ├─ 【新】manifest 落盘 workDir/share-receive/{parentID}/manifest.json（共享清单）
  ├─ StartTasks([父任务ID])（整树启动——taskManager 的 processParentUnit（构建父任务单元并加载其全部子任务供聚合与派发的处理函数）整树加载后 dispatch 全部子任务，`backend/taskManager/manager.go:288-292`）
  └─ 返回 {parentTaskId, workCount, workNames}（决策4 之①，作品名列表供收件侧展示）

每个子任务（ReceiveExecution.Execute 改造，只处理自己作品）：
  ├─ 反解 payload → 读本地共享 manifest.json（workDir + payload.ManifestPath）→ 校验
  ├─ 【新】过滤本作品子集（Works/Resources/Stores/Files，按 manifestID）
  ├─ planReplace：只查本作品（DuplicateChecker.Check 单条目）→ WaitReplaceConfirm（本作品冲突）→ 软删+回滚登记
  ├─ stageFiles：只拉本作品引用文件，暂存目录 share-receive/{childID}/
  ├─ Ingest：子 manifest（只含本作品）导入
  └─ 清理本任务暂存 → Finish（manifest.json 在父目录，不动）

父任务：纯容器，taskManager 现有聚合（Finished/PartlyFinished/Failed），零改动（声明2）。
```

### 二、manifest 获取与共享（决策1）

**Receive 同步预拉一次**，作为整棵子树的唯一清单源，落盘父任务目录共享给所有子任务。理由：

- **父任务纯容器**（声明2）决定了「拆分子任务必须在任务创建时完成」，而拆分需要作品列表 → 拉 manifest 必须发生在 Receive（任务创建前）
- 子任务读**本地共享 manifest**：只收集一次、清单全树一致（分享方内容变化不影响已建子任务），且子任务启动快（无网络往返）
- 备选对比：
  - 「子任务各自拉 manifest」：N 次收集、N 倍 manifest 传输、各子任务清单可能不一致（分享方库变动）、分享方中途离线则子任务拉 manifest 失败——弃
  - 「父任务编排拉取」：父任务有执行面，执行中拉 manifest 动态建子任务——需扩展 taskManager 父任务执行面，违背纯容器模型，改动面跨任务模块核心——弃

失败语义：manifest 拉取失败（分享方离线/网络/中继/密码错）→ Receive 直接返回用户可读文案（`receiveUserMessage`），**不创建任何任务**（无残留）；用户修正后重新点「开始拉取」。这是与「任务失败重试」不同的失败载体，见风险1。

### 三、父子树创建能力（task 模块扩展）

现状缺口（声明3）：`CreateBuiltinTask` 只建叶子、`CreateTask` 不支持 task_type/payload。新增能力：

```go
// task.Service 新增（BuiltinTaskControl 接口同步扩展，app.go 适配器实现）：
// CreateBuiltinTaskTree 创建内置任务树：1 个父容器（task_type=taskType、has_child=true、pid=NULL）
// + N 个子任务（pid=父任务ID、has_child=false、task_type=taskType）。事务内建父得 ID → 回填子 pid。
// 返回父任务（含 ID）。children 顺序即子任务展示顺序。
func (s *Service) CreateBuiltinTaskTree(ctx context.Context, taskType string, parentName string, children []BuiltinTaskChild) (*entity.Task, error)

// BuiltinTaskChild 子任务入参：任务名 + 载荷（执行面自有 JSON）
type BuiltinTaskChild struct { TaskName string; Payload string }
```

- 父任务与子任务 `HasChild` 恒落 0/1（`sql.NullBool.Valid=true`），对齐任务树查询二值圈定契约（`CreateBuiltinTask` 注释，`backend/task/service.go:410-412`）
- 事务内建父+子：父 ID 回填子 pid（外键引用 task.id，pid 不可为 0）
- 复用 `BaseRepository` 的 Create 能力，不引入新表
- 失败回滚（决策5）：父任务创建成功后、子任务全部建成前，任一步失败（manifest 落盘失败/建子任务中断）→ Receive 显式删除已建任务树（`DeleteTask` 含子任务）并返回用户可读文案，不留孤儿父任务或子任务

share 侧接口（`BuiltinTaskControl`，`backend/share/service.go:59-64`）扩展一个方法 `CreateBuiltinTaskTree`，app.go 适配器组合 task.Service 实现。

### 四、子任务载荷扩展（决策2 相关）

```go
type shareReceivePayload struct {
    SchemaVersion int    `json:"schemaVersion"`
    RelayDial     string `json:"relayDial"`
    RelayHost     string `json:"relayHost"`
    Token         string `json:"token"`
    KeyB64        string `json:"keyB64"`
    PasswordHash  string `json:"passwordHash"`
    // 新增（子任务；旧载荷二者缺省 → ManifestID==0 过时载荷，由设计五判定 Fail）
    ManifestPath  string `json:"manifestPath"` // 共享 manifest 落盘路径（workDir 相对，正斜杠；relPath 域）
    ManifestID    int64  `json:"manifestID"`   // 本任务负责下载的 manifest 作品 ID（0=过时载荷，不兼容存量，设计五 Fail）
}
```

- 加可选字段**不递增** schemaVersion（对齐 `backend/export/manifest.go:8-10` 版本纪律：加字段向后兼容）；旧载荷新代码可解析（新字段零值 → `ManifestID==0`），执行时按过时载荷 Fail（决策2 不兼容存量），新载荷旧代码（不存在，应用整体升级）无需考虑
- 子任务只存连接参数 + 清单定位 + 作品过滤，**不重复存 manifest 内容**（manifest 落盘共享文件）

### 五、子任务执行（ReceiveExecution 改造）

`Execute` 统一走子任务路径（决策2 不兼容存量，无整体下载分支）：

```
反解 payload → 校验（ManifestID==0 → Fail「请删除本任务后重新接收分享」——过时载荷）
→ 读本地共享 manifest（filepath.Join(workDir, payload.ManifestPath)）→ 校验 schemaVersion
→ 据 ManifestID 从 manifest.Works 定位本作品
→ 构造子 manifest（见『子 manifest 构造』节）
→ planReplace（只对本作品：DuplicateChecker.Check 单条目 + WaitReplaceConfirm 本作品冲突）
→ stageFiles（只拉本作品引用文件；跳过作品整作品跳过的既有语义保持）
→ Ingest（子 manifest）
→ 清理本任务暂存目录 share-receive/{childID}/（manifest.json 在父目录，不动）
→ Finish
```

- 查重/替换确认粒度**自然变为每作品独立**（设计七）：每个子任务只查自己作品、只确认自己作品的冲突、只软删自己作品的替换目标——这比现状「一次确认所有作品」更细，正是「每作品一任务」的收益之一
- `stageFiles` 的 `fileSkipSet` 在子任务域内退化为「本作品内跳过作品的共享文件判定」（引用映射只含本作品引用文件时，无共享则退化为恒不跳过）——子任务内处理，无需跨任务感知
- 断点续传锚不变：子任务独立暂存目录，按字节数对齐判定

### 六、子 manifest 构造

子任务导入用「只含本作品」的子 manifest（纯数据组装，不改 `ManifestIngestor` 接口）：

- `Works`：仅保留本作品（manifestID 匹配的 WorkRecord）
- `Files`：仅保留本作品所有 `Resource.Stores[].StoreID` 引用的 FileEntry 条目（声明6）
- `Sites`/`LocalAuthors`/`SiteAuthors`/`LocalTags`/`SiteTags`/`WorkSets`：**保留全集**（find-or-create 幂等，声明7；并发子任务导入同一站点/作者/标签/作品集 → SQLite 单写者事务串行 → 查重跳过，无并发写冲突）
- `Meta` 计数按子 manifest 实际内容更新（或保持——仅展示用途，不参与导入判定）
- 复用 `Deserialize`/`Serialize` 往返（`backend/export/manifest.go:211-217`）

作品集成员关系（`WorkSetLinks`，声明6 中「仅保留两端均在导出闭包内的边」）在子 manifest 中天然保留（WorkSetRecords 全集 + 本作品的成员边）。

### 七、查重/替换确认粒度（继承既有能力）

沿用《分享接收查重接入普通下载轨道方案》已落地的能力，零新增基建：
- 查重 `DuplicateChecker.Check`（`backend/duplicate` 模块，三分类判定）
- 确认原语 `WaitReplaceConfirm`/`SetTerminalRollback`（StrategyHandle，任务粒度）
- 替换能力 `SoftDeleteWorkStoreRoles`/`RestoreReplacedStores`（resource 模块）
- Ingest 替换模式 `IngestOptions.ReplaceWorks`/`AutoMergeWorks`（import 模块）

**差异**：原来一次 WaitReplaceConfirm 整体决策所有冲突作品（`backend/share/task_execution.go:277-292`）；拆分后每个子任务各调一次（只含自己作品的冲突列表）。前端确认弹窗为多任务列表形态（声明10），多子任务并发挂起时的表现见风险3。

### 八、暂存与清理适配

- 子任务文件暂存：`workDir/share-receive/{childID}/`（沿用现目录约定，任务行一个子目录）
- 共享 manifest：`workDir/share-receive/{parentID}/manifest.json`
- 清理：
  - 子任务 Finish → `os.RemoveAll(share-receive/{childID}/)`（现有逻辑）
  - manifest 在父目录：子任务不动；父任务行删除后由 `CleanupOrphanReceiveStaging`（声明9）回收 `share-receive/{parentID}/`（含 manifest）；终态但行保留的父目录残留 manifest 可接受（风险4）
  - 子任务行删除（用户单独删某作品任务）→ 清扫回收其暂存，父任务继续聚合其余子任务

### 九、前端调整

- `ShareReceiveDialog`（`frontend/src/components/dialogs/ShareReceiveDialog.vue`）：`shareReceive` 返回值从 `int64` 改 DTO `{parentTaskId, workCount, workNames}`（决策4 之①）；成功反馈展示作品名列表（收件人创建任务即知分享内容），仍引导任务面板
- 任务面板：树形展示已支持（声明8）——父任务「拉取分享（{host}）」聚合进度，子任务按作品名展示（site_work_name 优先、次 nick_name、空则「作品 {manifestID}」），各自状态/进度/操作栏
- 确认弹窗：多子任务并发 WaitingForInput 的渲染核对（声明10 已是多任务列表，验证逐任务答复链路）

### 十、分享落地页展示作品名（决策4 之②）

**现状**：落地页元数据 `metaPayload` 仅三字段（Title/WorkCount/Source，声明11），落地页无法展示具体作品名；作品名只在 E2E 加密的 manifest 内，中继不可读。

**目标**：收件人点开分享链接（落地页）即知分享涉及的每个作品——分享方发布时把作品名列表明文上传中继，落地页渲染作品名列表。

**设计**：

- `metaPayload` 扩展加 `WorksName []string`（`json:"worksName,omitempty"`）：各作品名取 manifest `WorkRecord` 的 `site_work_name` 优先、次 `nick_name`（声明13）；空名作品以「作品 {manifestID}」占位，与收件侧子任务命名规则一致
- 填充时机：`session.go:330` 构造 `metaPayload` 处（register 时）从 `cfg.model.Manifest.Works` 提取；**仅 register 上传，bind（复原重绑）不传**（声明12，中继侧已存，复原链接不变）
- **明文上传 = 作品名离开 E2E 加密域**（中继可读）——落地页要明文渲染，属设计内边界扩展；作品名**不做内容过滤**（决策4，合规风险见风险7）
- **relay 侧**（`library-squirrel-relay` 仓库，不在当前工作目录）：落地页接收 `metaPayload.WorksName` 并渲染作品名列表；协议帧大小限制与渲染上限须在 relay 仓库核验（风险8），本方案给出契约（register 帧 meta 携带 worksName 数组）与验收，实际改造在 relay 仓库执行

### 十一、对分享方与既有轨道的影响面

- 分享方：**唯一改动点 = metaPayload 扩展**（发布 register 时上传作品名，设计十）；发布直跑/复原/share_record 其余零改动——收件侧的父子树拆分对分享方透明（仍是一个会话、一份 manifest、全部文件可拉）
- 导入/查重/替换/确认基建（duplicate/import/resource/taskManager）：**零改动**——全部复用既有能力
- task 模块：新增一个创建方法（设计三），不触碰执行/控制语义
- relay 仓库：落地页渲染作品名列表（设计十契约，relay 侧改造）
- 唯一被改变语义的点：收件方收到一个链接 → 任务面板从「1 行整体任务」变为「1 父 + N 子 树」
