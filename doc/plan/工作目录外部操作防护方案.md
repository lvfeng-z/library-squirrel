# 工作目录外部操作防护方案

## 审查摘要

**关键声明（抽查项）**
- 声明1：fsmonitor 检测域为路径层面（Move/Delete/Untracked/DirMove 四类语义变更），内容指纹只取文件头部 64KB——自动修复模式只处理路径层面变更，内容篡改不在范围内。锚：`backend/fsmonitor/deps.go:49`（`fingerprint.NewHeadComputer`）、`backend/util/fingerprint/fingerprint.go:30-36`
- 声明2：修复能力边界——Untracked（外部新增）仅提示不入队；store 域 Delete 的 restore 动作未接入（backup 域 Delete 仅支持 ack）。锚：`backend/fsmonitor/repair.go:72-75`、`backend/fsmonitor/repair.go:253-255`
- 声明3：fsmonitor 平台能力按 `runtime.GOOS` 在 `NewPlatformDeps` 注入、能力缺省留 nil 降级——workdirGuard 沿用此装配模式。锚：`backend/fsmonitor/deps.go:47-69`
- 声明4：fsmonitor 装配点 app.go:943（NewPlatformDeps）、app.go:951（NewService）、app.go:1373（NewHandler）。锚：`app.go:943`、`app.go:951`、`app.go:1373`
- 声明5：`FsmonitorSettings` 现有 UsnEnabled/SuppressEnabled 两开关，默认值双源（`NewSettings` 与 `defaultSettings` 须同步）。锚：`backend/settings/model.go:60-64`、`backend/settings/service.go:33`
- 声明6：前端设置页已渲染 fsmonitor 开关。锚：`frontend/src/views/Settings.vue:335`（usnEnabled）、`frontend/src/views/Settings.vue:364`（suppressEnabled）
- 声明7：外部变更确认修复走 `ChangeConfirmDialog`。锚：`frontend/src/components/dialogs/ChangeConfirmDialog.vue:4`

**待决策（需用户拍板）**
- 决策1：自动修复策略按设置项实现——每 (domain+kind) 组合的**固定可选项**由后端定义（受 `apply` 能力约束），用户自选默认动作；开关默认关闭；自动执行失败降级入队。可选项集见「设计一」。**阻塞实施**
- 决策2：离线对账（启动时）发现的批量变更是否自动处理？建议**不自动**，保留人工确认（离线批量高发诱因是环境异常——挂载断开/云盘占位/杀软隔离，自动处理会造成无感知批量失效）。不阻塞
- 决策3：workdirGuard 探测时机为「设置页进入 + workDir 变更后」，不做常驻监控。不阻塞

**自曝风险（作者没把握的地方）**
- 风险1：自动 sync 无法区分「用户有意的整理移动」与「外部程序的移动」，一律跟随——语义与 fsmonitor 既有人工 sync 相同，只是自动化，不新增判别能力。
- 风险2：探针探测失败返回 ACCESS_DENIED，无法区分受控文件夹拦截 / ACL 只读 / 磁盘异常三类来源，引导文案只能覆盖多因，不精确归因。
- 风险3：跨平台边界——受控文件夹访问依赖用户手动开启（需管理员+知情），不配置即无「阻止」效果；macOS/Linux 无用户态阻止机制，workdirGuard 为 no-op。
- 风险4（auto-ack 破坏性）：store Delete 自动 ack = `MarkInvalid`（记录级软删），资源从库中消失；实时批量删除（目录级操作）或文件暂时不可见时会触发用户无感知的批量失效。锚：`backend/persistentStore/service.go:258-262`
- 风险5（backup 跨模块副作用）：backup Delete 自动 ack 会经 `backupRefCleaner.ClearBackupRefs` 清理引用方列（persistent_store.backup_id / plugin.BackupID）——文件暂失时自动 ack 即删清单行+清引用，不可逆性高于 store 域。锚：`backend/fsmonitor/repair.go:156-161`
- 风险6（探针自反馈）：Windows Probe 在 workDir 写/删临时探针文件，会触发 fsmonitor 实时 Untracked/Delete 变更——需 `storeRegistry.Suppress` 登记或专用探针路径，否则探测自身产生误报。锚：`backend/fsmonitor/repair.go:174-178`（既有抑制用法）

## 背景与目标

- **问题**：workDir（用户可配置的资源库根目录，见 `backend/settings/model.go:6`）可能被用户手动操作或第三方软件（清理/同步/备份类）修改，破坏 persistent_store（资源文件落盘记录）与 backup（保管清单）的记录与磁盘文件一致性。
- **现状**：fsmonitor 已覆盖「检测」——运行时 fsnotify + 启动离线对账 + USN 离线追溯，识别外部移动/删除/新增/目录改名，提供人工确认修复（sync/restore/ack 三动作）。
- **目标**：在检测层之上增加两层能力——
  - **设计一 · fsmonitor 自动修复模式**：路径层面变更按用户配置的策略自动处理，减少人工确认负担。
  - **设计二 · WorkDirGuard**：按平台自动装配的「阻止外部操作」模块，Windows 用受控文件夹访问引导 + 探针探测，macOS/Linux 预留接口降级。
- **明确不做**：全量内容完整性校验（sha256 全库扫描对庞大资源库 IO 成本过高，已放弃）。

## 现状（已核验）

fsmonitor 的修复流：语义变更（`SemanticChange`，携带 Kind/Domain/路径/关联行 ID）经 `dispatchSemanticChange`（语义变更派发函数，入队+通知前端）派发（`service.go:250`）→ `RepairManager`（修复管理器，维护待修复队列+执行确认动作）`Enqueue` 入队 → 前端收到 `fsmonitor:change` 事件弹确认 → 用户调 `ConfirmChange(id, action)` → `apply` 按 Domain/Kind 路由执行。其中 Untracked 不入队、store 域 Delete 的 restore 未接入（声明2）。

平台装配模式：`NewPlatformDeps` 按 `runtime.GOOS` 注入平台能力（实时事件源、USN 离线追溯），能力缺省留 nil、消费侧降级（声明3）。这是本项目既定的「跨平台能力自动装配」范式，WorkDirGuard 沿用。

## 方案设计

### 设计一：fsmonitor 自动修复模式

**配置**（决策1）：`FsmonitorSettings` 增加两个字段，默认值双源同步（声明5 既有约束，参照 `backup_governance_test.go` 双源锚定测试）：
- `AutoRepairEnabled bool`（json/koanf `autoRepairEnabled`，**默认 false**——用户显式开启）
- `AutoRepairPolicies map[string]string`（json/koanf `autoRepairPolicies`，key = `"<domain>:<kind>"`，value = 所选动作；未配置的组合回落内置默认）

**固定可选项集**（决策1）：每 (domain+kind) 组合的可选项由后端常量表定义，来自 `apply` 实际支持的动作（不可选项不暴露，选了会报错）：

| key | 可选项 | 内置默认 | 依据 |
|---|---|---|---|
| `store:Move` | {sync, restore} | sync | `applyMove` 支持两动作 |
| `store:DirMove` | {sync, restore} | sync | `applyDirMove` 支持两动作 |
| `backup:Move` | {sync, restore} | sync | `applyBackup` Move 支持两动作 |
| `store:Delete` | {ack} | ack | restore 未接入（声明2），仅 ack 可选 |
| `backup:Delete` | {ack} | ack | 文件已失，仅 ack |
| 任意:Untracked | （不可配置） | — | 不入队（声明2），无动作 |

无选择空间的组合（两处 Delete，可选项单元素）不提供配置 UI，前端显示固定值即可。

**执行流**：`dispatchSemanticChange`（`service.go:250`）改造——自动模式开启时先尝试自动执行，成功则不入队、直接通知前端（事件 payload 加 `autoHandled bool`）；失败或无默认动作才 `Enqueue` 留人工（决策1 的降级）。
- `RepairManager` 增加 `AutoApply(ctx, sc)`：按当前策略表（`AutoRepairPolicies` 覆盖 + 内置默认）查动作，命中则调用既有 `apply(ctx, sc, action)`（复用现有修复逻辑，含抑制登记），成功返回 true。
- **ctx 传递**：`dispatchSemanticChange` 当前无 ctx 参数（`service.go:250`）。`handleFileChange` 有 ctx（`service.go:310`）可直接传入；`runOfflineReconcile` 自身无 ctx 参数（`service.go:112`），其派发闭包捕获的是函数体内的 `context.Background()`（`service.go:113`）——改造时把该 ctx 显式传入派发链路。
- **来源区分**（决策2）：`dispatchSemanticChange` 增加来源参数（live/offline）。**自动修复仅对 live（运行时实时事件）生效**；offline（启动离线对账）发现的变更一律入队人工确认——离线批量高发诱因是环境异常（挂载断开/云盘占位/杀软隔离），自动处理会造成无感知批量失效（风险4）。
- 复用既有 `apply` 的一个收益：自动执行天然带上操作抑制（`storeRegistry.Suppress`），不会与软件自身写入互相误报。

**审计与前端**：自动执行记 Infof 日志（含变更描述 + 自动动作）；`Emit` 事件带 `autoHandled`，前端据此不弹确认、改为聚合提示（设计三）。

### 设计二：WorkDirGuard 模块（跨平台自动装配）

新包 `backend/workdirGuard/`，沿用声明3 的装配范式：

```go
// Guard 工作目录外部操作防护能力（平台相关；无可用机制的平台返回 no-op 实现）
type Guard interface {
    // Probe 探测 workDir 当前是否可写（被系统保护机制拦截时返回明确错误）
    Probe(ctx context.Context, workDir string) error
    // Info 返回当前平台防护机制与用户引导文案（供前端渲染）
    Info() Info
}
type Info struct {
    Platform   string `json:"platform"`   // windows / linux / darwin
    Mechanism  string `json:"mechanism"`  // 机制名：受控文件夹访问 / 无内置机制
    Supported  bool   `json:"supported"`  // 该平台是否有可用阻止机制
    Guide      string `json:"guide"`      // 引导文案（如何配置防护）
}
```

- **装配**：`NewPlatformGuard() Guard` 按 `runtime.GOOS` 返回 Windows 实现或 no-op 实现。app.go 装配点与 fsmonitor 同源（新增 `app.WorkDirGuard` + `app.WorkDirGuardHandler`）。
- **Handler**：`GetWorkDirGuardInfo(ctx, workDir)` 返回 `Info + probeErr`（前端调用点：设置页工作目录区块 + workDir 保存后）。
- **Windows 实现**（`guard_windows.go`）：
  - Probe：在 workDir 下写临时探针文件再删除，失败返回错误（受控文件夹拦截或 ACL 只读都会表现为 ACCESS_DENIED，风险2）。**探针路径须登记操作抑制**（`storeRegistry.Suppress`，参照 `repair.go:174-178`）或使用不进入 fsmonitor 扫描白名单的专用路径，否则探测自身触发实时变更提示（风险6）。
  - Info：Mechanism=「受控文件夹访问」，Guide=操作步骤（Windows 安全中心 → 病毒和威胁防护 → 勒索软件防护 → 受控文件夹访问 → 开启 + 添加文件夹 + 允许应用白名单本程序 exe）。
  - 语义说明：受控文件夹访问是系统级功能，本模块只做引导 + 探针，不强制（风险3）。
- **其他平台**（`guard_other.go`）：no-op。`Supported=false`，Info 说明「当前平台无内置阻止机制，依赖 fsmonitor 检测兜底」。原因：macOS 无受控文件夹对等物，TCC（应用隐私授权）管的是应用能否访问目录、不阻止外部修改；Linux `chattr +i`（不可变属性）需 root/CAP_LINUX_IMMUTABLE，POSIX ACL 是身份级、无法按进程区分（同 Windows 的 ACL 局限）。

**ACL 自主设置可行性确认记录**（决策4 的结论，为未来项留档）：经确认，Windows 上程序**可以不经用户确认**把 workDir 设为访问受限——前提是 workDir 的 Owner 为当前用户（用户自建目录满足），因对象 Owner 恒有 WRITE_DAC（改 ACL 权限），非提权进程对自有目录改 ACL 不需要 UAC。**本方案不采用**（用户拍板维持受控文件夹访问），原因：ACL 按身份区分、限制不了用户本人（owner 恒可改回，提权可 takeown 绕过）；有改错锁死风险需救援设计；网络盘 DACL 不可靠。若未来改走 ACL 自主设置，须补：Owner SID 检测、设置页知情确认按钮 + 一键还原、网络盘排除。

### 设计三：设置与前端

- **Settings.vue**：
  - fsmonitor 区块（`Settings.vue:329-341` 的 USN 开关同款 divider）加「自动修复」开关，v-model 绑定 `settings.fsmonitor.autoRepairEnabled`；开启时展示策略下拉——**仅渲染有选择空间的组合**（store:Move / store:DirMove / backup:Move），每项可选项由后端策略 schema 接口提供（不写死前端）。
