# 分享中继带宽限流方案（正式方案）

> 关联任务图：share-lineage/TREE.md C 节点派生分支 **O（中继带宽限流）**。状态：**定稿·含待决项**（2026-09-01，决策1-5 已裁决；决策6 同会话串行耦合待决，裁决后转可执行）。与 `doc/plan/分享接收拨号统筹方案.md`（连接数拥塞，接收方侧）**正交**——拨号统筹治「连接数」，本方案治「带宽公平性（字节/秒）」，两者互补不冲突。实施仓库：`library-squirrel-relay`（盲转中继服务，独立仓库，AGPL）。

## 审查摘要

**关键声明（抽查项）**
- 声明1：中继现治理 = 连接数滑动窗口限流（`dialPerIPPerMinute=60` 每 IP 每分钟拨号上限、`registerPerIPPerHour=5` 每 IP 每小时注册上限，`library-squirrel-relay/config.go:47-50,81-83`）+ 单会话流量总量上限（`maxSessionTrafficBytes=64GiB`，config.go:70 为 64<<30，超限硬杀会话，`library-squirrel-relay/relay.go:418-434`），**无带宽速率（字节/秒）限制**。
- 声明2：分享方 App 逐流限速 16MiB/s × 单会话并发流上限 8 = 单会话聚合可达 128MiB/s——`backend/share/session.go:49-50`。
- 声明3：中继慢消费者守卫在投递侧——`deliver`（把隧道帧投递进收件人写缓冲的函数，`library-squirrel-relay/tunnel.go:238-250`）对 128 帧缓冲（`tunnel.go:20`）做**非阻塞**投递，缓冲满即返回 false，`serve()`（隧道读循环，`tunnel.go:151-154`）据此断流。此守卫决定限速插入点（见「插入点」节）。
- 声明4：线协议拨号来源 IP 一律 `conn.RemoteAddr()`（`relay.go:52-54`）；X-Forwarded-For 信任头（`trustProxyHeaders` 配置）仅 HTTP 落地页路径生效（`preview.go:98-108`），对自定义 TCP 帧协议不可用。
- 声明5：分享方 `streamPacer` 为线性逐字节限速器（`backend/share/session.go:824-846`），中继减速背压会让它自然暂停，无需主仓改动。
- 声明6：中继已有周期清扫循环（`relay.go:492-513`），限流器清理挂载于此（每小时，`relay.go:505-509`）；每接收方 IP 限速器的清理可复用此挂载点。

**待决策（决策1-5 已裁决 2026-09-01 用户拍板；决策6 待决）**
- 决策1（阻塞）：A 会话级默认 **64MiB/s**、B 接收方 IP 级默认 **32MiB/s**；口径锚「单流上限 × 并发接收者余量」，不锚家庭上行典型值（详见「决策1」）。
- 决策2（阻塞）：B 的接收方 IP 判定 = `conn.RemoteAddr()`，与拨号限流同源（详见「决策2」）。
- 决策3（阻塞）：超限策略 = **减速（背压）**，非拒绝/断流。
- 决策4（阻塞）：**保留**单会话总量层 + **新增**速率层；不新增 IP 级总量。
- 决策5（阻塞）：默认值**开启宽松真实值**（64/32MiB/s）；`0=不限` 保留为运算符覆盖语义。
- 决策6（阻塞阶段2，**待决**）：B 级限速的同会话串行耦合是否接受——serve() 单隧道读循环内等待 B pacer 会连带降速同会话其他接收方（详见正文「决策6」）。**待用户拍板：接受耦合 vs 改 per-stream 限速。**

**自曝风险**
- 风险1：固定默认值不随部署上行自适应——繁忙部署上单会话 64MiB/s 仍可能占可观带宽；须按「配置设计」节的公式调配置。
- 风险2：反向代理/CDN 后 B 的键退化为代理 IP，经同一代理的全部接收者共享 B 额度——保守但公平粒度变粗，与拨号限流同源（已知局限，键型一致优先）。
- 风险3：限速等待在隧道读循环内，重负载下分享方控制帧（保活/关流）处理延迟微增；每帧等待有界（≤ 帧长 ÷ 速率）故影响微小（极低速率下的误杀悬崖见风险6）。
- 风险4：作者中继生产配置具体值未定，方案给出公式与示例，实际值由作者按部署上行与预期并发测算后定。
- 风险5：**B 级限速同会话串行耦合**（决策6 待决）——B pacer 等待在 serve() 共享读循环内，某接收方 IP 预算耗尽时同会话其他接收方被连带降速（整会话被最受限接收方兜底）；若接受则补决策，若改 per-stream 则插入点重设计。
- 风险6：**极低速率下 keepalive 误杀悬崖**——单帧等待=帧长÷速率，速率 < ~430B/s 时单帧等待超隧道保活超时（tunnel.go:185 的 tunnelReadTimeout=75s），保活循环误判隧道死亡；sanitize 对速率设正值下限（≥1KiB/s）防此悬崖（见「配置设计」）。
- 风险7：**决策1/5「正常单次传输不受限」依赖经验假设**「分享方实际上行 5-30MiB/s」（无代码锚点）——1Gbps 级上行分享方（罕见但存在）时 A 会对单分享生效、决策5「存量无感」前提松动；属预期防御非误伤。

## 背景与缺口

**现状**：中继（`library-squirrel-relay`）现有治理只有**连接数限流**（每 IP 每分钟拨号 60、每 IP 每小时注册 5 等滑动窗口，`access.go:72-108` 的 `rateLimiter`）+ **单会话总流量上限**（64GiB（64<<30），超限硬杀会话，`relay.go:418-434` 的 `accountTraffic` → `killSession`）。**没有带宽速率（字节/秒）限制**（声明1）。

**风险**：分享方 App 逐流限速 16MiB/s（主仓 `session.go:50` 的 `defaultStreamRate`）× 8 流 = 单会话聚合可达 **128MiB/s**（声明2）。典型生产中继（1Gbps ≈ 125MB/s 上行）上，**一个活跃分享会话即可占满整个中继带宽**直到撞 64GiB 总量上限，期间其他会话被饿死——公平性缺口。

## 限流粒度（讨论已覆盖）

| 粒度 | 约束对象 | 维度 | 优点 | 代价 |
|---|---|---|---|---|
| A. 会话级速率 | 单个分享的聚合传输 | 资源提供方 | 匹配分享方上行 + 防单分享占中继；与总量上限粒度一致 | 多接收者共享该额度 |
| B. 接收方 IP 级 | 单个接收方的聚合下载（跨会话） | 资源消费方 | 防一个接收者跨分享占用中继 | 需按接收方 IP 跨会话聚合 |
| C. 流级 | 单条流 | — | 分享方已做 16MiB/s，无增量 | 不约束聚合 |

**C 排除**：分享方已逐流限速（16MiB/s），流级在中继侧无增量；缺口在聚合维度（A/B）。

## 决策落定

**决策1（A、B 速率默认值口径）**：A=64MiB/s、B=32MiB/s。
- **不锚「家庭上行典型值」**：A 约束的是「单分享从中继流出的聚合速率」，锚家庭上行（如 5MiB/s）会压**多接收者并发**——同一分享 2 个接收者各拉 1 流（各 ≤16MiB/s）聚合即超 5MiB/s，被错误限速。
- 口径 = **单流上限（16MiB/s）× 并发接收者余量**：A=64 允许 4 条满速流聚合。假设「分享方实际上行 5-30MiB/s」（典型家庭上行，经验值无代码锚点，风险7）下正常单次传输**不受限**；1Gbps 级上行分享方（罕见但存在）时 A 会对单分享生效，属预期防御非误伤。B=32 允许单接收者同时满速拉 2 个分享（2×16MiB/s），3+ 并发全速分享即限。
- 「部署上行 ÷ 预期并发会话数」公式归**作者中继配置建议**（见「配置设计」），非代码默认。

**决策2（B 的接收方 IP 判定）**：`conn.RemoteAddr()`，与拨号限流同源。
- 键型全链一致优先：B 的 pacer 键与 `dialPerIP` 同一推导（`relay.go:52-54`），否则同一接收者被按两套键分开计数、聚合失真。
- XFF 不适用于线协议：`trustProxyHeaders` 仅 HTTP 落地页路径生效（声明4）；自定义 TCP 帧协议经 L4 代理部署时不注入头。代理后按代理 IP 聚合，与拨号限流同属已知局限（风险2）。
- 无需持久记录接收方来源 IP：流开启时从连接推导、作内存 pacer 键即可；处置面已有 `RegIP`（分享方注册来源 IP 字段）与溯源日志覆盖。

**决策3（超限策略）**：减速（背压）。
- 拒绝/断流会逼接收方重试拨号，重演「分享接收拨号统筹方案」刚修掉的「限流→重试→更限流」反馈环（拨号爆炸撞中继 `rate_limited`）。
- 背压零协议改动、零新错误码、分享方 `streamPacer`（声明5）天然承接。

**决策4（两层总量+速率）**：保留总量层 + 新增速率层。
- 总量防**失控/泄漏**（低速率长时长仍会累积到 64GiB 总量上限），速率管**公平**——线性 pacer 约束的是**生命周期平均速率**（空闲后允许突发追赶，非逐窗口硬上限），两者正交不冗余。
- 不新增 IP 级总量：B 的速率已限单 IP 持续吞吐，滥用归既有封禁/举报体系（`autoBanReportThreshold` 同实例累计被举报达阈值自动封禁）。

**决策5（默认值兼容）**：默认开启宽松真实值（64/32MiB/s）。
- 与中继既有防御默认姿态一致——现有限值（64GiB 总量、1000 会话等）全部是真实值而非 0=不限。
- 默认值宽松到**典型家庭上行**（5-30MiB/s，经验假设）下单次传输零影响，存量部署升级实际无感（只有 128MiB/s 级病理聚合被压）；1Gbps 级上行分享方会触及 A，属预期防御而非破坏性变更（风险7）。
- `0=不限` 仍保留为运算符覆盖语义（与 `maxSessionTrafficBytes=0` 同惯例），负值钳 0；正值下限由 sanitize 兜底（≥1KiB/s，防风险6 的 keepalive 误杀悬崖）。

**决策6（B 级同会话串行耦合，**待决**）**：B 的 pacer 等待插在 serve() 单隧道读循环内（tunnel.go:143-154）——阻塞循环即阻塞整条隧道读取，同会话其他接收方被连带降速，整会话吞吐被最受限接收方 B 值兜底（≈min(A, B(最受限接收方))）。A/B 描述为「正交」实为共享循环串行耦合（审查风险5）。
- **现状对照**：无限速时，慢消费者被断流（deliver 非阻塞缓冲满 → kill，声明3），快接收方不受累；限速后行为从「杀慢者保快者」变为「拖慢整会话」——未披露的行为变化。
- **频度低**：B 仅在「某接收方跨多分享全速拉取」（默认 32MiB/s = 2 个满速分享聚合）时触发。
- **待裁决**：(a) 接受耦合——补决策，B 定位为「跨会话兜底保险」，同会话串行降速为已知取舍；(b) 改 per-stream 限速——writeLoop 侧 + 慢消费者守卫区分「限速中」与「真死」；更复杂，且 serve() 单循环在缓冲满时仍耦合，解耦不彻底。**此决策阻塞阶段2 的插入点选择。**

## A+B 结合设计

**A 与 B 正交，叠加生效（取 min）**：
- **A（会话级）**：中继每会话维护逐字节速率 pacer，约束「资源提供方维度」——分享方是唯一资源提供方（P2P 架构），单分享传输不得超过合理速率。
- **B（接收方 IP 级）**：中继每接收方 IP 维护聚合速率 pacer，该 IP 所有下载流（跨会话）共享额度，约束「资源消费方维度」——防一个接收者跨分享占用中继。
- **叠加**：单条下载流实际速率 = min(会话速率 A, 接收方 IP 聚合速率 B)。转发循环对每帧**依次等待**两个 pacer（线性 pacer 串联即取 min，快的一侧等待≈0）。

### 插入点（核码校准）

**限速等待必须放在隧道读循环 `serve()` 的 DATA 分支内（`accountTraffic` 之后、`deliver` 之前，`tunnel.go:148-151` 之间），不是写接收方连接前。**

原因：`writeLoop`（`tunnel.go:311-339`）是收件人连接唯一写者，慢消费者守卫在投递侧——`deliver` 对 128 帧缓冲做非阻塞投递，缓冲满即返回 false → 断流（声明3）。若在 `writeLoop` 限速，`serve()` 仍按隧道到达速率灌缓冲 → 4MB（128×32KB）很快灌满 → **被限速的流被误杀**。

`serve()` 内等待的效果：阻塞隧道读循环 → 隧道不读 → TCP 背压传回分享方 → 分享方 `streamPacer` 自然暂停（声明5），与背压传导描述一致；`writeLoop` 慢消费者守卫**原样保留**（真死连接仍由写失败断流，限速期缓冲因投递侧已限速而不灌满）。

> **待决（决策6）**：`serve()` 内等待对同会话多接收方有串行耦合——某接收方 B 预算耗尽时整会话连带降速（详见「决策6」）；若裁决改 per-stream 限速，本节插入点与「pacer 机制设计」随之重设计。

### 背压传导（复用现成链路，非新协议）

中继限速减速 → 从隧道读得慢 → 发送方写阻塞 → 发送方 `streamPacer` 自然暂停 → 发送方不会多推。对接收方：收到被限速的数据流。**主仓零改动。**

### 机制复用

现有 `rateLimiter`（`access.go:72-108`）是**连接数滑动窗口**（count-based），带宽限速需新增 **bytesPacer**（线性逐字节速率计，对齐主仓 `streamPacer` 形态，声明5）。A、B 复用同一 pacer 机制，分别按会话/IP 键实例化。

### 与拨号统筹的关系

「分享接收拨号统筹方案」（接收方侧）把并发流压到 ≤8——但仍允许 8×16=128MiB/s 聚合；本方案 A 正是压这个病理值。两者互补：拨号统筹治「连接数拥塞」，本方案治「带宽公平性」。

## 配置设计

新增 2 个配置键（`library-squirrel-relay/config.go`，单位字节/秒，与现有字节类字段一致）：

| 键 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `sessionBytesPerSec` | int64 | 67108864（64MiB/s） | 单会话下行速率上限（0=不限） |
| `recipientIPBytesPerSec` | int64 | 33554432（32MiB/s） | 单接收方 IP 下行聚合速率上限（0=不限） |

- **sanitize**（`config.go:111-139`）：负值钳 0；**0=不限** 是合法语义（与 `maxSessionTrafficBytes=0` 同惯例）；正值下限兜底 **≥1KiB/s**——防风险6 的 keepalive 误杀悬崖（低于 ~430B/s 时单帧等待超隧道保活超时 75s）。
- **0=不限 语义**：运算符显式置 0 即关闭对应维度限速（决策5 保留的覆盖语义）。
- **PROTOCOL.md「配置参考」**：补 2 键说明（协议线格式零改动）。

### 作者中继配置建议（公式 + 示例）

公式：`A = 部署上行 ÷ 预期并发会话数`，且 **A ≥ 单流上限 16MiB/s**（否则压单接收者满速传输）。

示例（1Gbps ≈ 119MiB/s 上行、预期 4 并发会话）：A = 119÷4 ≈ 30 → 取 **32MiB/s**；B 取 32MiB/s（单接收者 2 个满速分享聚合上限）。具体值由作者按实际部署上行与监控调，风险4。

## pacer 机制设计（`library-squirrel-relay/pacer.go` 新增）

```go
// bytesPacer 线性逐字节限速器：累计字节按速率换算目标时刻，超前则等待。
// 对齐主仓 streamPacer（session.go:824-846）形态；rate<=0 不限。
// 互斥保护：A 会话级虽单写者（每会话至多一条活隧道、一条 serve 读循环），
// B 每 IP 级跨隧道共享，须互斥；统一内置互斥简单一致。
type bytesPacer struct {
    rate  int64
    mu    sync.Mutex
    start time.Time
    sent  int64
}
func newBytesPacer(rate int64) *bytesPacer
func (p *bytesPacer) wait(n int64) // 浮点换算目标时刻（对齐主仓，防超大文件溢出 int64）
```

- **A 会话级**：`sessionRT`（`session.go:38-45`）增 `pacer *bytesPacer` 惰性创建字段（对齐 `ensureRT` 模式，`session.go:48-53`；运行时态不持久化，重启重置——与 traffic 计数一致）。`serve()` DATA 分支按 `st.session.rt` 取 pacer。
- **B 每 IP 级**：`Relay` 结构体（`relay.go:16-33`）增 `ipPacers map[string]*bytesPacer` + 互斥。`tunnelStream`（`tunnel.go:208-218`）增 `recipientIP string` 字段，流开启时从拨号连接推导（复用 `relay.go:52-54` 同源函数）存入；`serve()` 投递该流帧时据此取/建 IP pacer。
- **清理**：`sweepLoop` 小时级清理处（`relay.go:505-509` 同位置）删除长时间无字节更新的 IP 键，防注册表膨胀。
- **接入顺序**（`tunnel.go:143-154` DATA 分支）：`accountTraffic`（总量硬杀）→ 会话 pacer wait(len) → 该流接收方 IP pacer wait(len) → `deliver`。仅下行方向（隧道→接收方）限速；反向（接收方→隧道）为控制帧，量可忽略。
