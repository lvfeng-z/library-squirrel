# 通知中心通用化方案

## 审查摘要

**关键声明（抽查项）**
- 声明1：`NotificationItem` 现状为 `{id,title,description,render}`，其中 `description` 从未被任何生产者赋值（仅模型与组件引用）—— `frontend/src/model/util/NotificationItem.ts:1-30`
- 声明2：通知 store 仅有 `add/get/getRange/remove/count`，**无 update**（无法原地变更）—— `frontend/src/store/UseNotificationStore.ts:18-79`
- 声明3：一套缓冲式 Toast（模块顶层可变状态 `positon`（拼写错误，实为 `boolean[2]` 双槽位）+ `notificationBuffer` + "N+"合并），由 `remove()` 触发入口—— `frontend/src/store/UseNotificationStore.ts:83-147`
- 声明4：仅两个生产者文件：任务 store `UseTaskStore`（`createNotificationItem` 硬编码"下载中"，调用点在 updateTask 与 loadSnapshot 两处）、建任务 `TaskManage`—— `frontend/src/store/UseTaskStore.ts:83-141,200-235,250-255`、`frontend/src/views/TaskManage.vue:88-105`
- 声明5：`custom-notify` IPC 监听为死代码，后端零 emit（`grep custom-notify backend/` 无命中）；`NotifyConfig` 仅此处引用—— `frontend/src/MainIpcListener.ts:110-129`
- 声明6：路由用 `name` 定位（`taskManage` 等），`WorkDetail` 是对话框非路由—— `frontend/src/router/routes.ts:46-50`
- 声明7：任务进度数据 `total/finished` 经 `updateTaskSchedule` 到达 store（面板可消费）—— `frontend/src/store/UseTaskStore.ts:148-164`
- 声明8：通知中心纯前端；后端事件已走 `Events.On`（任务增量 `task-events`:20、任务快照 `task-snapshot`:69、fsmonitor `fsmonitor:change`:82、死通道 `custom-notify`:110），本方案无后端改动—— `frontend/src/MainIpcListener.ts:20,69,82,110`

**待决策（已拍板）**
- 决策1（已定·接受）：`remove()` 解耦 toast，终态提示改由生产者用 `ElMessage` 触发（与全局 ~50 处一致）；删除 `positon/recursiveNotify` 缓冲合并系统，接受丢失"多任务同时完成的 N+ 合并提示"。
- 决策2（已定·仅活跃）：角标 count = 仅活跃（非终态）条目数。据此在模型加 `terminal` 标记（见 3.1）、store 加 `activeCount` getter（见 3.2）。

**自曝风险**
- 风险1：终态保留 + 不持久化，长会话下列表无限增长，无自动淘汰——本方案未设上限，可能需后补
- 风险2：`route` 仅能跳到路由页，非路由入口（如 `WorkDetailDialog`、合并进度所在处）无法精确落点；精确选中需各页支持定位协议，本方案不做
- 风险3：任务终态由 `remove` 改为 `update`（保留）后，终态通知须**脱离任务 store 生命周期**（`update` 置 `terminal:true` 时一并清空 `taskStoreObj.notificationId`）。否则 `loadSnapshot` 全量清理（`UseTaskStore.ts:204-208`，task-snapshot 主路径，每次快照推送都执行）会连同样终态回看条目一起清空——这是审查挖出的核心冲突。脱离后，`loadSnapshot`/`removeTask` 只 remove 仍被 `notificationId` 跟踪的活跃通知，终态条目留存至会话结束；`removeTask` 删活跃任务时仍正常 `remove` 其通知，避免僵尸残留

## 一、背景与现状

右侧侧边栏的 `NotificationList`（通知中心面板）本是为"通用通知系统"而建，但当前实现被任务领域硬编码污染、能力残缺：

- **模型太薄**：`NotificationItem` 只有 `{id,title,description,render}`，`description` 从不用，`render` 是唯一动态手段且被 `createNotificationItem` 写死成"下载中"。
- **无变更能力**：store 只有 `add/remove`，任务从"下载中 30%"到"完成"只能 remove 旧条目再 add 新条目，无法原地刷新。
- **无跳转能力**：模型无 route，点通知不能跳到相关页。
- **耦合 baggage**：`remove()` 内嵌一套脆弱的缓冲式 Toast（全局 `positon` 可变状态、双槽位、"N+"合并）；`custom-notify` 通道是死的预留。
- **不通用**：仅 `UseTaskStore`/`TaskManage` 两处用，且都写死任务语义。

详见审查摘要声明1–5。

## 二、目标

把 `NotificationList` 升级为**通用、外部可控的通知中心**，支持：
1. 跳转到消息关联页面（如有的话）
2. 动态消息数据（进度/异常/状态描述，可原地变更）
3. 外部可控的创建、变更、移除

约束（已与用户确认）：纯会话内、不持久化（刷新即清）；终态保留（update 成终态并标记，留列表供回看，由外部决定何时 remove）。

## 三、设计

### 3.1 模型（`NotificationItem`）

由纯 `{title,description,render}` 扩为**半结构化**——常见场景零代码，特殊场景仍可 `render` 兜底：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | store 分配，外部持有以做后续变更 |
| `level` | `'info'\|'success'\|'warning'\|'error'` | 严重度，驱动颜色/图标（走状态 tone，见下） |
| `category` | string? | 业务分类（`'task'`/`'merge'`/`'fsmonitor'`…），供未来过滤 |
| `title` | string | 标题 |
| `statusText` | string? | 状态描述（"下载中"/"完成"/"失败"） |
| `terminal` | boolean? | 是否终态（默认 false）；角标按此过滤活跃条目（决策2）。置 true 后该通知**脱离任务 store 生命周期**（见 3.2） |
| `progress` | `{current?:number,total?:number,percent?:number}`? | 动态进度；`percent` 可显式给（无 total 的 indeterminate 进度） |
| `exception` | string? | 异常/错误描述（失败时展示） |
| `route` | `{name:string,params?,query?}`? | 跳转目标（vue-router location，`name` 如 `'taskManage'`） |
| `render` | `(() => VNode)?` | 兜底自绘，存在则覆盖默认渲染 |
| `createTime` | number | 创建时间戳（ms），排序/展示用 |

删除 `description`（声明1，从未使用）。

### 3.2 Store API（`useNotificationStore`）

```
add(item): string           // 赋 id+createTime，入 map+list，返回 id
update(id, partial): void   // 原地合并（progress 整体替换，非深合并）
remove(id): void            // 出 map+list；不再触发 toast
get(id) / getRange(...) / count   // 保留；count=总数（分页 total 用）
activeCount                       // 新增 getter：非终态（!terminal）条目数（角标用，决策2）
```

`update` 是新增核心能力：外部持有 `add` 返回的 id，按事件流持续 `update(id, {...})` 刷新进度/状态/终态。

**终态脱离不变量**：生产者把通知 `update` 成终态（`terminal:true`）后，须同时放弃持有的 id 引用（任务 store 置 `taskStoreObj.notificationId=undefined`）。此后该通知仅存于通知 store，不被任何全量清理路径（`loadSnapshot`/`removeTask`，二者都只 remove 仍被 `notificationId` 跟踪的通知）触碰，直到会话结束或外部显式 `remove`。这解决快照刷新清空终态回看条目的冲突（见风险3）。

### 3.3 UI（`NotificationList.vue`）

每条通知默认渲染：level 图标/色（状态 tone）+ title + statusText + 进度条（`progress` 存在则 `el-progress`）+ exception（错误样式）；`render` 存在则覆盖默认。点击条目（或有跳转指示时）→ `router.push(item.route)`（route 存在才跳）。

保留右侧 `CollapsePanel` + 分页；角标值用 `activeCount`（仅活跃，决策2），`enable-badge` 按 `activeCount!==0`（分页 total 仍用 `count` 总数）。颜色遵循 `THEME_TOKEN_USAGE`/`STATUS_TOKEN_USAGE`：level → 状态 tone（active/done/fail/warn），用 `StatusTag` 或 tone class，禁硬编码色。

### 3.4 与后端事件的关系（无后端改动）

通知 API 是前端的，任何前端模块都能调。后端事件（任务状态/进度/fsmonitor）经现有 `Events.On` 监听器（`MainIpcListener.ts`）转成 `add/update`——不新建 IPC 通道，废弃死的 `custom-notify`。

## 四、实施步骤

1. **模型**：改 `NotificationItem.ts` 为 3.1 字段（删 `description`，加 `level/category/statusText/progress/exception/route/createTime`）。
2. **Store**：加 `update`；`remove` 去除 toast 耦合；删除 `positon/recursiveNotify`/`notificationBuffer`/`startNotify`（决策1 通过后）。
3. **UI**：`NotificationList.vue` 按 3.3 渲染结构化字段 + 点击跳转；接 `useRouter`。
4. **生产者迁移**：
   - `UseTaskStore`：
     - Processing/Waiting 时 `add`（带 `category:'task'`、`route:{name:'taskManage'}`、初始 `progress`）并持有 id；`updateTaskSchedule` 时 `update` 进度。
     - Finished/Failed/PartlyFinished 时 `update` 成终态（`terminal:true`+`level`+`statusText`+`exception`），**随即置 `taskStoreObj.notificationId=undefined`（脱离任务 store）**，不再 remove；终态 toast 改 `ElMessage`。
     - **`loadSnapshot`（`:200-235`，task-snapshot 主路径）**：其全量清理（`:204-208` 遍历 `tasks` remove 各 `notificationId`）天然跳过已脱离的终态通知（其 `notificationId` 已 undefined）——故终态回看条目不会被快照刷新清空；重建时对快照内 Processing/Waiting 任务照常 `add`。
     - **`setTask`（`:71-89`，后端当前未发射、保留备用）**：一并迁移到新模型（Processing/Waiting → `add`）保持一致，不删。
     - `removeTask` 仍 `remove` 其（未脱离的活跃）通知（风险3）。
   - `TaskManage::createTaskFromSource`：`add` "正在创建" → `update` 成功/失败终态（带 `route`、`terminal:true`），不再 remove。
5. **清理**：删 `MainIpcListener` 的 `custom-notify` 监听 + `NotifyConfig.ts`；删 `NotificationItem.description` 字段（`NotificationList.vue:44-48` 的引用在步骤3 UI 重写时一并移除）；删 `positon/notificationBuffer/startNotify/recursiveNotify` 顶层 Toast 系统。

## 五、范围边界

- **本次只做**"右侧消息列表"这个通用载体本身（模型/API/UI + 现有两处生产者迁移 + 死代码清理）。
- **暂不做**：`ElMessage`、`useChangeConfirmStore` 等其他通知机制并入（延后评估）；未读/已读状态；持久化；列表上限/自动淘汰（风险1）；精确落点定位协议（风险2）。
