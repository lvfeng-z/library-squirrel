# 作品软删除与回收站重构方案（work 单表软删）

> 状态：期一已实施（2026-08-18，编译+全量测试通过） · 四决策已裁决 2026-08-18 · 创建：2026-08-18 · 同日按 plan-reviewer 审查修订 + 用户裁决补全（并存策略节 3.9） · 前置背景：回收站查询功能（2026-08-18 当日实施）暴露快照模式成本天花板

## 审查摘要

**关键声明（抽查项）**

- 声明1：删除作品时 work 及关联行被**物理级联删除**（`backend/work/service.go:553` `DeleteWorkAndSurroundingData`：事务内删 re_work_tag / re_work_work_set / re_work_author / resource / work，`:576-590`；persistent_store 记录在**事务后**尽力删除且错误仅告警，`:596-600`，非原子）——但 **resource_store 关联行全后端无删除路径**（`backend/resource/repository.go:62-67` `DeleteByWorkId` 只删 resource 行；`backend/persistentStore/service.go:692` `Delete` 只删 persistent_store 记录；resource_store 实体无 FK 级联），现行删除链遗留 resource_store 孤儿行（既有缺陷，本方案新彻底删除链顺带修复，见 3.4）。数据只活在 recycle_bin.snapshot JSON——作品搜索链（原生 SQL EXISTS 体系）与回收站数据是两个世界，查询无法复用。
- 声明2：作品搜索的条件体系是 `backend/search/repository.go:386` `buildWhereClauseWithAlias`（作者/标签走 EXISTS 子查询、站点 eq 见 `:497-503` 的 Site 条件分支、作品集 EXISTS），但**时间条件只有精确匹配**（`WorksUploadTime` eq/ne，`search/repository.go:466`），无范围条件——复用后需补 gte/lte 条件类型。
- 声明3：原生 SQL 查 work 的点共 3 处（`search/repository.go:207`、`:296`、`:549`），其中 `:549` 是作品集页 EXISTS（不过滤则已删作品仍出现在作品集）；其余模块经 BaseRepository 结构化查询（`backend/database/base_repository.go:207` List / `:279` Page，GORM scope 可自动覆盖）。
- 声明4：work 业务键唯一索引 `idx_work_site_site_work`（`backend/base/model/entity/work.go:12`，UNIQUE(site_id, site_work_id)）由 AutoMigrate 管理；AutoMigrate 不删旧索引、不管部分索引，手写索引迁移（drop 旧 + 建新）有现成先例（`backend/migration/migrate.go:38-54` re_work_author 唯一索引升级）。
- 声明5：彻底删除的物理级联链已存在且为生产删除链（`work/service.go:553`，完整性缺口见声明1 的 resource_store 孤儿）——新彻底删除链以其为基座**并补 resource_store 删除**。存量 recycle_bin 条目按决策3 直接清空、不做快照展开，`work/service.go:792` `RestoreWorkFromSnapshot`（从快照重建 work+关联+resource+store）随两阶段退役。
- 声明6：现软删入口 `work/service.go:614` `SoftDeleteWork`（采集快照 → 文件移入 backup → 物理级联删）与复原链 `recycleBin/service.go:288` `RestoreWork`（快照重建 + backup 文件还原）、彻底删除 `recycleBin/service.go:387` `Purge`（删 backup 文件+记录+recycle_bin 行）为重构替换对象。
- 声明7：`gorm.io/plugin/soft_delete` v1.2.1 **无独立的 `DeletedAtMilli` 类型**（期一实施核验，源码 `soft_delete.go:13`）——正确用法为 `DeletedAt`（uint 基类型）+ tag `softDelete:milli`：Query/Update 自动 `WHERE deleted_at = 0`（`:38/:97`）、Delete 改写为 `UPDATE deleted_at = UnixNano()/1e6` 毫秒（`:143/:178`）、`Unscoped` 逃逸（`:39/:98/:121`）；Delete 与 Update 均只作用于活行（DeleteClause 尾部追加 `deleted_at = 0`，`:167`）。
- 声明8：search 服务面已有 `QueryWorkPage`（`backend/search/service.go:131`，分页查询作品、返回 WorkFullDTO），回收站列表可经此形态扩展复用。

**待决策（已全部裁决 2026-08-18）**

- 决策1 ✅ **乙：沿用移入 backup/**——软删期间文件移 backup/（保留文件移动链与抑制登记；复原需文件还原）。裁决后影响：删除/复原不再零文件 IO（收益相应下调，见第一节修正）；但「重新下载撞已删条目」场景因文件物理隔离而天然自洽（见 3.9 节并存策略）。
- 决策2 ✅ **插件**：引入 `gorm.io/plugin/soft_delete` 官方插件。
- 决策3 ✅ **存量 recycle_bin 不迁移，直接删除**——启动迁移位改为一次性清空全部存量条目（按现有 Purge 语义：删 backup 文件+backup 记录+recycle_bin 行）。**用户已接受数据丢失语义：现存回收站内的条目不可恢复**。
- 决策4 ✅ **甲：两阶段退役**——期三先停用快照链路（代码保留不接），稳定一个版本后再删除。

**自曝风险**

- 风险1：**漏过滤**是最大回归面——GORM 软删 scope 只保护主表标准 finisher（Find/Count/Update/Delete），不覆盖原生 SQL、Joins 子表、聚合子查询。search 3 处已识别（声明3），但各模块**绕过 BaseRepository 的自定义仓储查询**（含从 resource/re_work_* 出发不锚定 work 的聚合）需逐一审计，漏一处即已删作品泄漏进正常列表。
- 风险2：部分唯一索引与 AutoMigrate 交互——须先把实体 tag 上的 `uniqueIndex` 移除（否则 AutoMigrate 重建全量唯一索引），drop 旧索引与建部分索引全手写；SQLite 部分索引语法 `CREATE UNIQUE INDEX ... WHERE deleted_at = 0` 支持无虞（<未核验当前 SQLite 驱动版本行为，实施时验证>）。
- 风险3：复原（清标志）与彻底删除后的行为差异需全页面回归——尤其作品集列表/封面（EXISTS `:549`）、历史任务详情指向已删作品 resource（行保留 vs 现状悬空）。决策1=乙下已删作品文件在 backup/，fsmonitor 扫描白名单仅 store/ 子树、backup/ 变更为噪声丢弃（`backend/storeRegistry/registry.go:49`）。
- 风险4：存量清空幂等性（决策3）——逐条删除中途失败产生部分清空态，需幂等（backup 记录与 recycle_bin 行存在性为标记）。
- 风险5：删除时间从 recycle_bin.delete_time 列切换为 work.deleted_at 列，WorkFullDTO 需加 deleteTime 字段并重生成 bindings；前端回收站页（2026-08-18 当日刚改造的查询条件版）需切换数据源，当日实现的混合过滤/快照 createTime/名字组装/冗余列全部退役。
- 风险6：决策1=乙下，已删作品的 backup 文件被用户手动删除/损坏时，**复原会得到「无文件的活作品」**——缓解：复原链在文件还原步做存在性检测（缺失→警告后允许继续，部分复原语义；3.4 复原行的文件还原逻辑内含）。
- 风险7：**已删行/活行的写路径语义**——GORM 软删插件对 Update/Delete 均自动追加 `WHERE deleted_at = 0`。已核验 work 的 `repo.Delete` 共 3 处调用点（`work/service.go:548` 死入口 / `:589` 级联链 / `:755` 快照链，2026-08-18 grep 全量）：写已删行的 Updates 两处（复原清标志、迁移打标志）必须走 Unscoped 变体，普通 Updates 表现为「无效果但不报错」；**最高危是 `:589` 的语义反转**——该行同时服务复原覆盖分支（HardDeleteWork 物理删**活的新作品行**）与新彻底删除链（物理删已删行），若保持普通 Delete 会被静默改写为软删 UPDATE，覆盖复原后新作品带 deleted_at>0 出现在回收站列表——`:589` 必须显式 `Unscoped().Delete()`，三处写路径以测试覆盖。

## 一、背景与动机

回收站现为「快照模式」：逻辑删除 = 采集作品全量关联为 JSON 快照存 recycle_bin 表 + 资源文件移入 backup/ 目录 + work 谱系 7 类表物理级联删除；复原 = 从快照重建整个世界 + 文件还原。该设计让回收站数据脱离作品数据世界，导致：

1. 回收站查询无法复用作品搜索（EXISTS 体系锚定 work 表，而 work 行已删）——2026-08-18 的查询功能只能走「快照 JSON 内存过滤」的混合方案，且为支持创建时间筛选被迫引入快照结构演进（WorkSnapshot.CreateTime）+ recycle_bin 冗余列（work_create_time），存量条目永久缺失该数据。
2. 复原链复杂（重建 5 类实体 + 引用校验 + 文件还原 + 快照格式 v0/v1 兼容），删除/复原均有文件 IO 与跨存储一致性问题。
3. 每个新的搜索维度都是一次快照模式补丁。

**重构方向**：删除的作品留在原数据世界——work 单表打软删标志，查询复用、复原一行、快照体系退役。

## 二、方案总览

三个核心决定：

1. **软删标志只打在聚合根 work 上**。resource / resource_store / persistent_store / re_work_author / re_work_tag / re_work_work_set 从属行**原地不动**——业务查询均从 work 出发（主表过滤天然遮蔽从属行；search 的 EXISTS 子查询锚定 t1.id，主查询过滤即安全）。不给「所有 BaseRepository 泛型表」加列：site/task/plugin 等的删除语义本就是物理删，加列是纯成本。
2. **软删列兼作删除时间**：`deleted_at int64`（毫秒时间戳，0=活，删除时写当下）——回收站的删除时间展示、TTL 过期判定（`deleted_at > 0 AND deleted_at < expire`）、删除时间排序直接用这一列。
3. **查询复用而非重建**：回收站列表 = 作品搜索入口 + `deleted_at > 0` 附加条件，作者/标签/站点/作品集过滤白得；作品搜索补时间范围条件类型后创建时间筛选白得。

## 三、详细设计

### 3.1 软删机制（work 实体）

- work 实体加字段 `DeletedAt soft_delete.DeletedAtMilli`（或自写等价类型，决策2）：`gorm:"column:deleted_at;index"`；json 序列化暴露为 `deleteTime`（DTO 层映射，实体列名保持 gorm 惯例）。
- 机制行为（由类型实现/GORM 插件提供）：`Delete()` 自动改写为 `UPDATE work SET deleted_at = 当前毫秒`；`Find/Count/Get/Update` 自动追加 `WHERE deleted_at = 0`；显式 `Unscoped()` 逃逸。
- **复原 = `Unscoped().Update(deleted_at = 0)`**（一条 SQL）。

### 3.2 唯一索引迁移（部分唯一索引）

逻辑删行仍占 `idx_work_site_site_work`——用户删除作品后重新下载同作品会插入冲突。改造：

1. work 实体 tag 移除 `uniqueIndex:idx_work_site_site_work`（`work.go:12-13`）。
2. `migration/migrate.go` 新增命名迁移（照 `:38-54` 先例）：
   - `DROP INDEX IF EXISTS idx_work_site_site_work`
   - `CREATE UNIQUE INDEX IF NOT EXISTS idx_work_site_site_work ON work(site_id, site_work_id) WHERE deleted_at = 0`
3. 语义：删除（软删后 deleted_at>0）即释放业务键 → 重新下载合法插入新行；复原时若存在活的同键行即冲突（现有「放弃/覆盖」流程语义不变：覆盖 = `work/service.go:770` HardDeleteWork 物理删新行 + 清旧行标志）。
4. 冲突检测 `GetBySiteAndSiteWorkID`（`work/service.go` WorkRestorer 接口）依赖 GORM 自动过滤（只看见活行），无需改动。

### 3.3 BaseRepository 查询开关（期一实施定稿：bool 而非三态）

`database.QueryOption` 加字段（期一已实施）：

```go
// IncludeDeleted 查询是否包含软删行（Unscoped；仅对带软删列的实体有效，其余实体等价于普通查询）
// 「仅已删」场景由调用方以 IncludeDeleted=true + 自组 deleted_at>0 条件表达
IncludeDeleted bool
```

设计偏离原方案的三态 `DeletedFilter`：三态的「仅已删」态在 applyQueryOption 通用层生成 `deleted_at>0` 条件，对无软删列的实体会产生非法 SQL；bool + 调用方自组条件把该风险收敛到唯一带软删列的 work 消费方。另 BaseRepository 新增 `DeleteUnscoped(ctx, id)`（物理删，对无软删列实体与 Delete 等价）。

### 3.4 三条链重写

| 链 | 现实现 | 新实现（决策1=乙） |
| --- | --- | --- |
| 删除 | `SoftDeleteWork`（`work/service.go:614`：采集快照→逐 store 移 backup→写 recycle_bin→物理级联删 7 表） | 停关联任务（沿用）→ 事务外逐 store 走 `DeleteWithBackup` 移文件进 backup/ + 建 backup 记录（沿用现有 best-effort 哲学与 fsmonitor 抑制登记）→ 事务内 work 软删一条 UPDATE |
| 复原 | `recycleBin/service.go:288`（Unmarshal 快照→引用校验→重建 work/关联/resource/store→backup 文件还原→删 recycle_bin 行） | 冲突检测（活行存在且非自身→冲突；覆盖分支先 HardDeleteWork——其级联链 `work/service.go:589` 的 work 删除须显式 `Unscoped().Delete()`，防 GORM 软删改写令新作品幽灵进回收站）→ 事务外 backup 文件还原回 store/ 原路径（文件还原逻辑自现有 restoreStore 迁入，best-effort）→ `Unscoped().Update(deleted_at=0)` |
| 彻底删除 | `Purge`（`recycleBin/service.go:387`：删 backup 文件+记录+recycle_bin 行） | 收集 backup 引用 → 事务内物理级联删：以 `work/service.go:553` 现链为基座，**补删 resource_store 行**（现链全后端无 resource_store 删除路径，遗留孤儿——既删作品复现，新链修复）；对已删行的物理删除必须走 Unscoped 变体（GORM 软删 scope 会挡住普通 Delete，见风险7）→ 事务后删 backup 文件与记录（沿用现有 purgeBackup 语义） |
| TTL 清理 | `ListExpired`（recycle_bin.delete_time）→ Purge | 查 `deleted_at > 0 AND deleted_at < expire` 的 work（DeletedFilter=2）→ 逐条彻底删除。TTL 设置读取沿用 |

work 模块的 `RecycleItemSaver` 接口退役；**快照体系**（`recycleBin.WorkSnapshot/AuthorSnapshot/TagSnapshot/WorkSetSnapshot/ResourceSnapshot` 及序列化）退役；**文件移动/还原链保留**（`DeleteWithBackup`、backup 记录、文件还原逻辑——决策1=乙）。

### 3.5 回收站查询链（search 复用）

1. **search 模块新增** `QueryRecycleWorkPage`（或 QueryWorkPage 加 deleted 维度参数，实施时择一）：
   - 主查询复用 `QueryWorkPage` 的 SQL 骨架（`search/repository.go:214-301`，含 resource/tags/authors JSON 聚合子查询），`WHERE t1.deleted_at > 0` 为基线条件，与 `buildWhereClause` 条件 AND 组合；
   - 排序支持 `deleted_at` / `create_time`（时间范围条件类型见下条）；
   - `QueryWorkPage` / `QueryWorkSetPageByConditions`（`:207`/`:296`/`:549`）正常列表三处补 `AND t1.deleted_at = 0`（或 w 别名）。
2. **条件体系补范围类型**：`dto2.SearchCondition` 时间类条件（WorksUploadTime，另加 WorksCreateTime/WorksDeleteTime）支持 gte/lte 操作符（buildWhereClause 分支扩展）——回收站与作品搜索同时受益。
3. **模块依赖方向**：recycleBin（调用方）定义 `RecycleWorkQuerier` 接口，search（提供方）实现；recycleBin handler/service 收缩为薄层（列表转发查询、复原、彻底删除、TTL）。
4. **DTO**：WorkFullDTO 加 `deleteTime` 字段（deleted_at 映射），bindings 重生成；回收站列表前端复用 WorkFullDTO（站点名/作者名经现有聚合子查询白得，替代 2026-08-18 实现的三个名字批量查询接口）。

### 3.6 存量清空（决策3：不迁移，直接删除）

启动时（AutoMigrate 后、业务服务初始化前）执行一次幂等清空：

1. 遍历 recycle_bin 全部存量条目，逐条按现有 Purge 语义删除（backup 文件 + backup 记录 + recycle_bin 行），复用 `recycleBin/service.go:387` 现链；
2. **数据丢失语义用户已裁决接受**：现存回收站内条目连同其备份文件一并清除，不可恢复；
3. 幂等性：以 recycle_bin 行存在性为标记，逐条独立执行，中断可重入。

（原「快照展开迁移」方案随决策3 作废——`RestoreWorkFromSnapshot` 仅在清空链路中不再被调用，其代码按决策4 甲两阶段退役。）

### 3.9 重新下载与已删条目的并存策略（决策1=乙下天然自洽）

场景：删除作品 A（软删行 + 文件移 backup/）后重新下载同作品（siteId+siteWorkId 相同）：

- **任务创建**：查重走 GORM 自动过滤（看不见已删行）→ 任务正常创建；新 work 行插入被部分唯一索引放行（已删行 deleted_at>0 不占索引）；
- **新作品落盘**：旧文件已在 backup/、store/ 目标路径空闲，无覆盖——**乙的物理隔离使并存无文件冲突**（若当初选甲「文件留 store/」，下载器会覆盖旧文件、旧条目彻底删除时还会误删新作品文件）；
- **并存期**：活的新作品与回收站旧条目互不可见、互不干扰——文件分居 store/ 与 backup/，DB 从属行（resource/re_work_* 等）按各自 workId 隔离；彻底删除旧条目只动 backup/ 文件与旧 workId 从属行，新作品无感；同一作品多代删除（删→重下→再删）同理各自独立；
- **裁决点后移到复原**：复原旧条目时冲突检测发现活的新作品 → 现有「放弃/覆盖」流程；覆盖分支时序自洽（先物理删新作品、其文件随之移 backup/ 让出 store/ 路径 → 旧文件还原 → 清标志）；
- 可选增强（不阻塞）：任务创建时检测到同键已删行，给非阻塞提示「回收站已有该作品旧条目」。

### 3.7 漏过滤审计清单（实施时逐项核验）

- search 原生 SQL 3 处（声明3）——本方案已列；
- 各模块自定义 repository（非 BaseRepository 透传）中 FROM/JOIN work 的查询：`grep -rn "FROM work\|JOIN work" backend --include="*.go"` 全量核对（实施时执行并记录清单）；
- 从 re_work_* / resource 出发、不锚定 work 的聚合查询（如标签使用统计）：核对「已删作品是否应计入」——默认计入即视为需过滤；
- 插件链：SDK `GetWorkSetBySiteWorkSetId` 查 work_set（不涉 work，无影响）；`GetStoreRelPath` 经 task→resource（从属行保留，无影响）；
- fsmonitor：决策1=乙下删除即把文件移出 store/（监控白名单内），store/ 内不滞留已删作品文件；删除移动的抑制登记沿用现有内部写入登记机制，无新增场景。

### 3.8 行为差异清单（需回归确认）

| 场景 | 现状 | 新模式 |
| --- | --- | --- |
| 删除后重新下载同作品 | 业务键已释放，正常下载 | 相同（部分唯一索引释放键） |
| 复原时同键新作品存在 | 冲突→放弃/覆盖 | 相同（语义不变） |
| 历史任务详情指向已删作品 | resource 行已删，悬空/报错 | resource 行保留，仍可查看 |
| 删除后文件位置 | 移入 backup/，store/ 消失 | 不变（决策1=乙） |
| 已删作品的作者/标签关联行 | 物理删除 | 保留至彻底删除（从 work 出发的查询不可见） |
| 彻底删除后的 resource_store 行 | 遗留孤儿行（现链无删除路径，声明1） | 随级联物理删除（顺带修复既有缺陷） |
| 回收站条目创建时间 | 存量条目 NULL（快照缺） | 存量条目随决策3 清空消失；**新删除的作品保留原始 create_time** |

## 四、退役清单（净删代码面）

- `backend/recycleBin/snapshot.go` 全文件（快照结构与序列化）；
- work 前端直删死入口 `Handler.Delete`（`backend/work/handler.go:36` → `service.go:548`，前端 wrapper 无消费者、全项目 grep 证实）——随重构移除（软删后其语义会静默变为「进回收站」，与 SoftDelete 重复）；
- `work/service.go` 软删除的快照采集段（:614 起大段）、`RestoreWorkFromSnapshot` 及引用校验辅助（:792 起，存量清空后按决策4 甲两阶段退役）；
- `recycleBin` 的快照过滤 repository 路径（2026-08-18 实现的 RecycleSnapshotFilter/sortRecycleItems/matchSnapshotFilter）；

- 冗余列 work_create_time（work.create_time 本尊在场）与 2026-08-18 的 fillDisplayNames 三接口注入。

决策1=乙下**保留**的链路：`persistentStore.DeleteWithBackup`（删除移文件进 backup）、backup 记录体系、`recycleBin.restoreStore`（复原文件还原）、`purgeBackup`（彻底删除清 backup）——仅其「快照」耦合剥离。

## 五、实施分期

1. **期一（机制层，已实施 2026-08-18）**：work 加 deleted_at 列 + 部分唯一索引迁移（新名 idx_work_site_site_work_active 幂等）+ BaseRepository IncludeDeleted/DeleteUnscoped + search 基线条件（buildWhereClauseWithAlias 恒含 `deleted_at = 0`，QueryWorkSetPage 调用处的空条件门槛保留原语义）+ **work 三处 `repo.Delete` 同步改 `DeleteUnscoped`**（插件加列即生效，不改则期一当日就破坏现删除链——原「纯加列零行为变化」表述不准，加列+三处 Unscoped 化后才零行为变化）。全量编译+测试通过。**实机回归揪出迁移缺陷已修**：AutoMigrate 加列无默认值，存量行 deleted_at=NULL 而 `deleted_at = 0` 对 NULL 不命中，94 个存量作品全部从查询消失——迁移补 `UPDATE work SET deleted_at = 0 WHERE deleted_at IS NULL` 回填（幂等）。
2. **期二（链路切换，已实施 2026-08-18）**：删除/复原/彻底删除/TTL 四链重写 + recycleBin 模块收缩（快照体系断链，Repository 仅存存量清空能力）+ search 复用入口（`QueryRecycleWorkPage`：基线参数化 `buildWhereClauseWithBaseline`、精简投影、`RecycleWorkDTO`）+ 条件范围类型（WorksCreateTime/WorksDeleteTime + 既有 Gte/Lte 操作符）+ bindings + 前端回收站页切 SearchCondition 体系。**实施中的四项发现**：①fsmonitor 全量对账会把「已删作品 store 行（文件已移 backup/）」误报缺失——`persistentStore` 三个 StoreReader 方法统一加 NOT EXISTS 排除已删作品行的 join 条件；②覆盖分支由「物理删新作品」升级为「新作品软删入回收站」（`HardDeleteWork` 删除，WorkRestorer 直接引用 `SoftDeleteWork`，反悔可救、路径让出语义不变）；③文件还原弃 `StoreFromExternal`（会建多余新 store 记录）改用 `backup.RestoreFile`（纯文件移动，从属行本就保留）+ 调用方登记抑制；④删除链从属行与 persistent_store 记录**全部原地保留**（方案总览既定），事务体缩为一条软删 UPDATE。**实机首启即崩已修**：recycleBin 装配位置先于 SearchService 创建（接口 nil 注入编译期不可见，运行时 `s.repo` 空指针）——recycleBin 块移至 search 之后；教训：跨服务构造注入前先核目标服务的创建顺序。编译+全量测试+前端构建通过。
3. **期三（清空与停用，已实施 2026-08-18）**：存量 recycle_bin 一次性清空（解快照收集 backupId → 删 backup 文件与记录 → 删 recycle_bin 行）——**实机执行完毕后（85 条全清），迁移代码按用户裁决移除**（软件未发布，无需保留迁移逻辑）。**快照体系随之整体删除（决策4 甲提前执行，用户按未发布口径裁决）**：snapshot.go / recycleBin repository.go / RecycleItem 实体与表注册 / work 的 RestoreWorkFromSnapshot + 引用校验 + 九个快照专用构造参数（NewService 从 39 参收缩至 30 参）/ work handler Delete 死入口——净删约 500 行，全部零调用代码。清空实测顺带暴露既有问题（任务板块重执行备份与插件备份无清理路径持续膨胀）→ 任务树 reveal 为独立节点。编译+全量测试+前端构建通过。
4. **回归**：删除→列表不可见→复原（含冲突三态）→彻底删除；作品集/搜索/任务详情页已删作品不可见性；fsmonitor 文件事件。

## 六、非目标
