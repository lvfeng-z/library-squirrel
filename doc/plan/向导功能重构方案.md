# 向导功能重构方案

> 状态：评审中（关键决策已确认，待最终评审）
> 日期：2026-06-15
> 范围：前端为主（向导框架），后端仅持久化字段微调

## 一、背景与目标

### 1.1 现有诉求
当前存在一个**半成品向导雏形**，能力非常有限：
- 只能在单一页面内做几步 `el-tour` 高亮；
- 向导开关是**硬编码**的几个 boolean，新增向导必须改 store；
- `el-tour` 组件**分散写在 3 个页面**（MainLayout ×2、TaskManage ×1、Settings ×1），没有统一控制；
- 缺少"控制中心"：无法统一查看有哪些向导、当前进行到哪、如何手动开关；
- 缺少"跳转到某页面 + 定位某条数据"的标准化数据通道。

### 1.2 目标
重构为一个**声明式 + 集中式**的向导框架，满足：

1. **实际功能页面上的指引**：高亮真实 DOM 元素、分步讲解，且**支持跨页面编排**（一个向导的若干步可分布在不同页面）；
2. **统一控制中心**：集中注册所有向导、查看状态、手动启动/重置、控制开关；
3. **额外数据通道**：向导步可携带"目标数据"（如"跳到本地标签页，定位到 ID=123 的标签"），目标页面据此加载/定位，定位完成后再推进下一步；
4. **清理旧残留**：统一渲染层取代分散的 `el-tour`，修复 `goto-page` 半成品 bug。

### 2.2 现有问题清单

1. **开关硬编码，扩展性差**：每加一个向导需同时改 `TourStates` 字段、mitt 事件类型、`TourEvents` 类型、Settings 持久化结构（4 处）。
2. **el-tour 分散**：4 处独立 `el-tour`，无法跨页面编排、无法统一控制可见性。
3. **持久化分裂**：`Settings.tour`（3 字段）与 `TourStates`（4 字段）不对齐，存在隐性不一致。
4. **`askGotoPage` bug**：
   - `GotoPageConfig` 接口字段是 `page: PageEnum`，但 `askGotoPage` 里读的是 `config.path`（**接口中不存在该字段**）；
   - `switch` 分支写的是 `'\settings'`（**反斜杠 + 字符串字面量错误**），实际应为路由 path 或 name；
   - `gotoPath` 用字符串 path 跳转，而项目路由普遍用 `name` 跳转（见 `routes.ts`）。
5. **没有目标数据通道**：`extraData` 是 `unknown`，目标页面无标准方式接收并据此定位数据。
6. **`TourStates.getCallback` 命名误导**：实际作用是 emit finish 事件唤醒等待者，并非"取回调"。

## 三、整体架构

### 3.1 设计原则
1. **声明式定义**：向导 = 一组有序 step 的数据描述（写在集中文件里），引擎消费它；
2. **集中渲染**：全局只有一个 `<TourOverlay>` 渲染当前 step，页面不再各自写 `el-tour`；
3. **页面无关的元素定位**：step 用"路由 + targetKey"声明要高亮的元素，目标页面通过 composable 注册 targetKey→DOM；
4. **就绪协议**：跨页面切换后，引擎等待目标页面"加载完数据 + 挂载完元素"再显示 step；
5. **数据通道标准化**：step 携带强类型的 `TourStepData`，目标页面据此定位；
6. **持久化按向导 id**：用 `Map<tourId, completed>` 替代固定 boolean 字段。

### 3.2 概念与数据流

```
┌──────────────────────────────────────────────────────────────┐
│                    向导控制中心 useTourCenterStore            │
│  registry: Map<tourId, TourDefinition>                        │
│  activeTourId / activeStepIndex / status / context            │
│  completed: Map<tourId, boolean>（持久化）                    │
│                                                              │
│  start(tourId, context?) → next() → ... → finish()/skip()    │
└───────────────┬──────────────────────────────┬───────────────┘
                │ 读 step                       │ 注册/读取
   ┌────────────▼────────────┐      ┌───────────▼────────────┐
   │  TourOverlay（全局组件） │      │ 目标元素注册表           │
   │  放在 MainLayout         │      │ useTourTargets（每页面）│
   │  渲染当前 step 气泡       │      │ targetKey → DOM ref     │
   └──────────────────────────┘      └───────────┬────────────┘
                                                 │
                ┌────────────────────────────────▼───────────┐
                │ 就绪协议 useTourReady / useTourContext        │
                │ 页面进入时读取 context，加载数据、定位元素、   │
                │ 调用 reportReady() 通知引擎可显示             │
                └─────────────────────────────────────────────┘
```

### 3.3 步进引擎核心时序（跨页面）

```
start(tourId, ctx)
  ├─ activeTourId = tourId; activeStepIndex = 0; status = running
  ├─ 调用 step 的渲染前回调（可选）
  ├─ resolveStep(0):
  │     读 step.target.route → router.push(route)
  │     读 step.target.targetKey → 等待该 targetKey 的 DOM 出现
  │       （nextTick + 轮询，超时报错）
  │     若 step.data → 等待目标页面 reportReady()（页面已据 ctx 定位）
  │     → OK，status 步进可见
  ├─ next() → activeStepIndex++ → resolveStep(i) …（可能再跳路由）
  └─ finish() → completed[tourId]=true → 持久化 → 清空 active
```

## 四、详细设计

### 4.1 向导定义模型（`frontend/src/model/tour/TourDefinition.ts`，新建）

```ts
/** 向导步的目标定位（路由 + 可选元素 key） */
export interface TourStepTarget {
  /** 目标路由 name（与 routes.ts / SlotRegistry 的 name/viewId 对齐） */
  route: string
  /** 该页面内可被高亮的元素 key（页面通过 useTourTargets 注册）；不填则高亮页面整体 */
  targetKey?: string
}

/** 向导步需要的目标数据（强类型，按业务扩展） */
export type TourStepData =
  | { kind: 'work'; workId: number }
  | { kind: 'tag'; tagId: number; scope?: 'local' | 'site' }
  | { kind: 'author'; authorId: number; scope?: 'local' | 'site' }
  | { kind: 'task'; taskId: number }
  | { kind: 'none' }

/** 单步向导 */
export interface TourStep {
  target: TourStepTarget
  title?: string
  description: string
  placement?: 'top' | 'right' | 'bottom' | 'left' | 'center'
  /** 该步需要的目标数据（引擎写入 context.data，目标页面读取并定位） */
  data?: TourStepData
  /** 进入该步前在页面侧执行的钩子（如打开某个对话框） */
  onEnterPage?: (ctx: TourContext) => void | Promise<void>
}

/** 向导定义 */
export interface TourDefinition {
  id: string
  name: string
  description: string
  /** 仅在这些路由下才允许从控制中心启动（可选） */
  startRoute?: string
  steps: TourStep[]
}

/** 运行期上下文（控制中心 → 目标页面 的数据载体） */
export interface TourContext {
  tourId: string
  stepIndex: number
  data?: TourStepData
  /** 调用方自定义载荷（保留扩展位） */
  payload?: Record<string, unknown>
}
```

### 4.2 向导控制中心（`frontend/src/store/UseTourCenterStore.ts`，新建，替代 `UseTourStatesStore`）

```ts
export const useTourCenterStore = defineStore('tourCenter', {
  state: () => ({
    registry: new Map<string, TourDefinition>(),   // 已注册向导
    activeTourId: null as string | null,
    activeStepIndex: 0,
    status: 'idle' as 'idle' | 'running' | 'paused' | 'finished',
    context: null as TourContext | null,
    completed: new Map<string, boolean>(),         // 持久化（启动时从 Settings 读）
  }),
  getters: {
    activeTour: (s) => (s.activeTourId ? s.registry.get(s.activeTourId) : null),
    activeStep: (s) => {
      const t = s.activeTourId ? s.registry.get(s.activeTourId) : null
      return t ? t.steps[s.activeStepIndex] : null
    },
    isLastStep: (s) => {
      const t = s.activeTourId ? s.registry.get(s.activeTourId) : null
      return !!t && s.activeStepIndex >= t.steps.length - 1
    },
    tourList: (s) => [...s.registry.values()],
  },
  actions: {
    registerTour(def: TourDefinition) { this.registry.set(def.id, def) },
    isCompleted(id: string) { return !!this.completed.get(id) },
    markCompleted(id: string) { this.completed.set(id, true); this.persist() },

    async start(tourId: string, ctx?: Partial<TourContext>) {
      const def = this.registry.get(tourId)
      if (!def) throw new Error(`向导不存在: ${tourId}`)
      this.activeTourId = tourId
      this.activeStepIndex = 0
      this.status = 'running'
      await this.resolveStep(0, ctx)
    },
    async next() { /* activeStepIndex++ → resolveStep；越界则 finish */ },
    prev() { /* activeStepIndex--，不重新跳路由（仅回退气泡） */ },
    skip() { this.finish() },
    async finish() {
      if (this.activeTourId) this.markCompleted(this.activeTourId)
      this.reset()
    },
    reset() { this.activeTourId = null; this.activeStepIndex = 0; this.status = 'idle'; this.context = null },
    resetCompleted(id: string) { this.completed.delete(id); this.persist() },

    /** 核心：跳路由 + 等元素 + 等就绪，然后写 context */
    async resolveStep(index: number, baseCtx?: Partial<TourContext>) {
      const def = this.activeTour ? this.activeTour : null
      const step = def?.steps[index]
      if (!step) return
      this.context = { tourId: def!.id, stepIndex: index, data: step.data, ...(baseCtx ?? {}) }
      if (step.onEnterPage) await step.onEnterPage(this.context)
      await ensureRoute(step.target.route)          // 已在同路由则跳过
      await waitTargetReady(step.target)            // 等元素挂载 + 页面 reportReady
    },

    persist() { /* 调 settingsSaveSettings，写 tour.completed */ },
  },
})
```

> **注**：`waitTargetReady` 内部：`router.push` → `nextTick` → 轮询 `useTourTargets` 注册表取 DOM（超时 ~3s）；若 step 带 `data`，则同时 await 目标页面的 `reportReady` 信号（由 `useTourReady` 经 store 内置的一个 deferred 队列传递）。

### 4.3 页面侧协议（两个 composable，新建 `frontend/src/composables/`）

**`useTourTargets.ts`** — 注册可被高亮元素
```ts
// 页面内：
const workdirInput = ref()
useTourTargets().register('settings.workdirInput', workdirInput)
// 引擎/computed 通过 getEl('settings.workdirInput') 取 DOM
```

**`useTourReady.ts`** — 报告"数据已加载、元素已就位"
```ts
// 页面进入时：
const ctx = useTourContext()           // 读 store.context（若与当前路由相关）
onMounted(async () => {
  if (ctx.value?.data?.kind === 'tag') {
    await loadAndLocateTag(ctx.value.data.tagId)  // 业务定位（滚动/选中/打开详情）
  }
  useTourReady().reportReady(ctx.value)           // 通知引擎可显示 step
})
```

> 两个 composable 底层都读写 store 内部的 `targets: Map<string, Ref>` 与一个 `readySignal`（用 `Promise` + resolver 或 mitt）。目标 key 采用 `{viewId}.{element}` 命名空间，避免跨页面冲突。

### 4.4 全局渲染层（`frontend/src/components/tour/TourOverlay.vue`，新建）

- 挂载于 `MainLayout.vue`（替换原 2 个内嵌 `el-tour`）；
- 读取 `useTourCenterStore.activeStep`，用 computed 解析出当前 step 的 target DOM（经 `useTourTargets.getEl`）；
- 渲染**单个** `el-tour`（`v-model` 绑定 `status==='running'`），内部只渲染当前这一个 `el-tour-step`；
- 导航按钮（上一步/下一步/跳过）调用 store 的 `prev/next/skip`，**不使用 el-tour 自带的步进**（因为要跨页面、要走引擎）；
- 当 target DOM 尚未就绪时显示一个居中的"加载中"气泡占位。

## 七、风险与取舍

1. **el-tour 单步托管 vs 多步托管**：el-tour 原生支持多 step，但跨页面切换会破坏其内部 step 状态。**取舍**：自管步进，TourOverlay 每步只渲染一个 `el-tour-step`，导航按钮自定义。代价是放弃 el-tour 自带的进度条（可在按钮区自绘）。
2. **target 就绪等待的稳健性**：DOM 未挂载/数据加载慢时需超时兜底，避免向导卡死。**取舍**：3s 超时 + 降级为"居中气泡 + 提示元素未找到"。
3. **与动态路由（SlotRegistry）的 name 对齐**：step.target.route 需用统一的标识。**取舍**：统一用 viewId/route name；若两套路由体系并存，提供 `resolveRouteName(viewId)` 适配函数。
4. **插件向导（未来）**：插件若要贡献向导，可通过 SlotRegistry 扩展一个 `tourSlots`（本次不做，仅预留 `registerTour` 入口）。

## 八、已确认的关键决策（评审 2026-06-15）

1. **控制中心入口**：复用现有"向导"菜单，改造 `Guide.vue`（左精简说明 + 右控制中心面板），**不新增菜单**。
2. **旧持久化状态**：**不迁移**，新 `completed` Map 从空开始（老用户可能再被引导一次，可接受）。删除旧 `Settings.tour` 的 boolean 字段时**无需写迁移逻辑**。
3. **插件向导**：本次不做，仅保留 `registerTour()` 开放入口，未来扩展再设计 `tourSlots`。
4. **`goto-page`**：修复 bug 后保留，作为"跳转 + 启动向导"的统一前端入口（IPC 触发场景）。
