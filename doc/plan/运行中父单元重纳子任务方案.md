# 运行中父单元重纳子任务方案

## 审查摘要

> 术语速查（首现于此，正文不再括注）：`loadAndStartTaskTrees`＝从 DB 加载任务树并启动的总入口；`isUnitLoaded`＝检查某任务单元是否已加载到内存的快路径守卫；`classifyTaskUnit`＝据 Pid/HasChild 判定单元类型的函数，产出 unitLeaf（叶子：有父无子）/unitParent（父：有子）/unitStandalone（独立：无父无子）；`processParentUnit`＝处理一个父单元并构建其子任务的方法；`claimParent`/`claimTask`＝原子 insert-or-get 父/子任务到 parentMap/taskMap；`ManagedTask`＝内存中的任务运行控制对象；`ParentTask`＝父任务的内存聚合对象；`actorLoop`＝每任务一条常驻 goroutine 串行处理命令；`cmdCh`＝actor 的命令通道；drain goroutine＝actor 退出后吞掉 `cmdCh` 残留命令防投递方阻塞的协程；`actorStarted`＝dispatch 首派 CAS 守卫位；`dispatch`＝投 cmdStart/cmdResume 启动 actor 的入口；`cleanupFinishedTask`＝终态子任务的内存清理方法；`buildOrReuseChild`＝构建/复用子任务 ManagedTask 的方法；`onStateChange`＝子任务状态变更回调；skipTerminal＝是否跳过终态子任务的参数；recordMode＝执行模式记录参数（含 `runMode`：板块执行模式 workInfo+storeRoles）；`batchCheckDuplicates`＝派发前批量查重的方法。

### 关键声明（抽查项）

- 声明1（根因·吞掉点）：父任务运行中对子任务发起 Start/Retry 时，`loadAndStartTaskTrees` 的 `isUnitLoaded` 守卫对 unitLeaf 一律 `continue` 跳过、返回 nil 无错误。`backend/taskManager/manager.go:214-217`。
- 声明2（吞掉的另一面）：`processParentUnit` 在 `claimParent` 输者分支直接 `return nil`，故即使绕过 isUnitLoaded，父已 claim 时仍不处理叶子。`backend/taskManager/manager.go:277-280`。
- 声明3（unitLeaf 本会进 processParentUnit）：`loadAndStartTaskTrees` 循环的 `else` 分支把 unitLeaf 的 `unitId`（=父 ID）也 append 到 `parentUnits`，随后 `processParentUnit(parentId, leafIdsPerParent[parentId])` 处理——即设计上 unitLeaf 经此路径调度，仅被声明1的前置守卫拦截。`backend/taskManager/manager.go:243-245`、`251-253`。
- 声明4（终态子任务旧对象仍驻留 children）：`cleanupFinishedTask` 仅 `delete(m.taskMap, taskId)`，不从 `parent.children` 删除——终态子任务的旧 `ManagedTask` 对象留在父单元 children 内继续参与 `RefreshState`/`AllChildrenTerminal` 聚合。`backend/taskManager/manager.go:951-953`。
- 声明5（终态子任务 actor 已死、postCmd 无效）：`actorLoop` 遇终态 `return` 退出，退出前 defer 启动 drain goroutine 吞掉后续 `cmdCh` 命令；`actorStarted` 一旦由 dispatch CAS 置 true 后**从不重置**。故对终态旧对象 `postCmd` 命令被 drain 丢弃、无法重启，必须**重建 ManagedTask 对象**。`backend/taskManager/model.go:475-479`、`498-500`、`backend/taskManager/manager.go:486`（dispatch 的 CAS `task.actorStarted.CompareAndSwap(false, true)`）。
- 声明6（重建对象可正常 dispatch）：新建对象的 `actorStarted` 零值为 false，`dispatch` 的 CAS(false→true) 成功并投 `cmdStart`。`backend/taskManager/manager.go:485-494`。
- 声明7（父状态聚合自动跟随）：`newManagedTask` 注册的 `onStateChange` 回调在子任务 `setState` 时持 `m.mu.RLock` 调 `parent.RefreshState` 并推送父状态/进度——重建子任务进入 Processing 后，父状态自动从 PartlyFinished/Failed 拉回 Processing，无需额外处理。`backend/taskManager/manager.go:1187-1207`。
- 声明8（claimTask 对终态子任务创建新对象）：终态子任务已从 taskMap 删除，`claimTask` 的 insert-or-get 命中失败→`newManagedTask` 创建新对象并 insert。`backend/taskManager/manager.go:893-913`。
- 声明9（Start/Retry 与 Resume 的路径分野）：Start(`:111-113`)、Retry(`:711-714`) 均汇入 `loadAndStartTaskTrees`；Resume 经 `ResumeTaskTrees`(`:576`) 对内存命中的目标直接投 cmdResume，**仅当目标不在内存（!ok）时**才收集走 `resumeTaskTrees`→`loadAndStartTaskTrees`。故 isUnitLoaded 吞掉的是：Start/Retry 对父运行中子任务、以及 Resume 对**不在内存的终态子任务**。`backend/taskManager/manager.go:111/576-611/714`。
- 声明10（AddChild 覆盖即替换）：`ParentTask.AddChild` 为 `children[taskId]=child`，对已存在的终态旧对象是覆盖替换。`backend/taskManager/model.go:2043-2047`。
- 声明11（Paused 子任务的 Resume 本就正常·核验澄清）：父运行中的 Paused 子任务仍在 taskMap（cleanupFinishedTask 不删 Paused），`ResumeTaskTrees`→`resolveTargets` 命中→对 Paused/Pausing 投 cmdResume，**不经 loadAndStartTaskTrees、不被 isUnitLoaded 吞**。故本方案无需为"非终态子任务的 Resume"做任何改动。`backend/taskManager/manager.go:583-605`。
- 声明12（batchCheckDuplicates 对运行中任务的破坏性副作用）：查重命中会把对象 `setState(TaskStateWaitingForInput)`、写 `existingWorkId`、塞入 `waitingForInputMap` 并推重复弹窗。故 reinject **不得**把非终态（仍在 taskMap）子任务送入查重，否则正在 Processing/Waiting 的任务会被其自身作品命中、状态被强行改写。`backend/taskManager/manager.go:459-471`。

### 待决策（需用户拍板）

- 决策1（是否阻塞实施：否）：reinject 路径下，`recordMode`（仅 Start/Redownload 入口非 nil）当前会 `UpdateRedownloadSections` 写入 ListTaskTree 查出的**全部成员**（含其他正在运行的兄弟子任务），将其持久化 `StoreRoles` 置 NULL、`IncludeWorkInfo=true`（`backend/taskManager/manager.go:159-178`）。正在运行的兄弟 runMode 已派生不受影响，但其持久化字段被改→影响其未来"暂停→重启→resumeTaskTrees"恢复时的模式。选项 A（默认·简单）：保持现状，reinject 不改 recordMode 范围；选项 B（精确）：reinject 路径仅写用户请求的子任务，不波及兄弟。
- 决策2（回滚策略·是否阻塞实施：否）：三处改动（声明对应的两处 + reinjectLeaves）同提交、无渐进灰度。上线后若现 resource_store 孤儿/父状态聚合错乱，策略为整体 `git revert` 该提交（回退到"静默吞掉"的既有行为，不引入新故障），而非热修 reinjectLeaves。是否认可此回滚策略？

### 自曝风险

- 风险1（drain goroutine 累积泄漏·既有问题加剧）：每次 actor 终态退出，`actorLoop` defer 启动的 drain goroutine（`for range m.cmdCh`）因 `cmdCh` 从不关闭而永久阻塞、且闭包捕获旧 `ManagedTask` 致其无法 GC。反复重跑同一终态子任务会累积此类 goroutine。此为既有设计，reinject 会加剧但非本次新引入；本次不处理，仅记录基线（验证场景7）。
- 风险2（recordMode 副作用）：见决策1，选 A 时其他运行中兄弟的持久化执行模式被改写。
- 风险3（竞态：父单元恰在被清理的瞬间）：若父任务所有子任务恰好同时终态→`cleanupFinishedTask` 删除 `parentMap`(`manager.go:976`)，此刻 reinject 的 `processParentUnit` 调 `claimParent` 会 created=true 走正常整树路径而非 reinject 分支——语义自洽，但实现须确认 `!created` 分支仅依赖"父在 parentMap"这一实时判定，不缓存父对象。
- 风险4（重跑终态子任务必然命中查重→弹窗）：终态子任务（尤其 Finished）的作品已存在，reinject 重建后送 `batchCheckDuplicates` 必然命中→WaitingForInput→推"作品已存在"弹窗，用户确认替换后才重下。此为预期交互（与 Redownload/替换语义一致），但须在测试中确认备份/还原/resource_store 重挂在"父运行中并发"下无孤儿。
- 风险5（已化解·记录排查过程）：初版曾拟"一并修复非终态子任务（Paused）的 Start/Resume"，经声明11/12 核验撤销——Paused 的 Resume 走 resolveTargets 本就工作；且非终态子任务送查重会触发声明12 的破坏性副作用。故 reinject 严格限定只纳入终态子任务，非终态跳过（幂等）。

## 一、现状与根因

用户现象：父任务处于运行状态时，对其内部已终态（Finished/Failed）的子任务发起"开始/重试"操作，子任务不进入运行状态，且前端无任何提示；对终态子任务发起"恢复"同样无效（终态子任务不在内存，Resume 走 dbIds→loadAndStartTaskTrees 被同一守卫吞）。

完整数据流（终态子任务 C、父任务 P 运行中）：

1. Start/Retry 入口汇入 `loadAndStartTaskTrees`（声明9）；Resume 因 C 不在内存走 `resumeTaskTrees`→`loadAndStartTaskTrees`。
2. `classifyTaskUnit(C)` 判定 C 为 unitLeaf，`unitId = C.Pid = P.ID`（`manager.go:207-208`）。
3. `isUnitLoaded(P.ID, false)` 查 `parentMap[P.ID]` 命中→`continue`（声明1）。
4. 循环结束，`allToCheck` 为空，无 dispatch，`return nil`（`manager.go:263`）→ Handler 返回成功响应，前端无提示。

设计意图辨析：`isUnitLoaded` 的本意是"防同一单元重复加载整树"（`manager.go:213` 注释），而 `processParentUnit` 的 `leafSet` 机制（`manager.go:306-314`）证明设计上认可"对父单元内特定叶子单独执行"。把"运行中父单元"视为不可分割、连带吞掉对其终态子任务的执行请求，是守卫粒度过粗的副作用，非明确的"禁止此操作"决策。

## 二、方案：开放运行中父单元被外部调度内部终态子任务的能力

按用户拍板的方向：既不静默拒绝，也不让子任务脱离父单元单独成树，而是**复用已 claim 的运行中父单元，把请求的终态子任务重新纳入并 dispatch**。

两处改动 + 一个新方法，落在现有 unitLeaf→processParentUnit 调度链上，最小侵入：

### 改动1：`loadAndStartTaskTrees` 放行 unitLeaf 的 isUnitLoaded 检查

`backend/taskManager/manager.go:214`，把"isUnitLoaded 命中即跳过"收窄为"仅独立/父单元已 loaded 时跳过"，unitLeaf 不在此跳过（其父 loaded 由改动2 处理，重复由既有 `processedUnits`/`leafIdsPerParent` 去重保证）：

```go
// 重复执行保护:独立/父单元已 loaded 则跳过;unitLeaf 不跳过(父 loaded 时由 processParentUnit 的 !created 分支重新纳入)
if kind != unitLeaf && m.isUnitLoaded(unitId, kind == unitStandalone) {
    logger.Log.Infof("loadAndStartTaskTrees: 单元 %d 已在运行，跳过", unitId)
    continue
}
```

注意：unitLeaf 的 `leafIdsPerParent` 累积逻辑（`manager.go:219-224`）须在此检查**之前**执行（当前顺序已满足），确保父 loaded 时叶子仍累积进 leafSet。

### 改动2：`processParentUnit` 的 `!created` 分支改为重新纳入

`backend/taskManager/manager.go:277-280`，父已 claim（`claimParent` 输者）时不再 `return nil`，而是对 leafSet 内的叶子调用新方法重新纳入：

```go
parentTask, created := m.claimParent(actualParentId, parentTaskName)
if !created {
    // 父单元已在运行:复用 parentTask,把请求的终态叶子重新纳入(重建 actor 重跑)
    if len(leafSet) == 0 {
        return nil // 整树 Start 但树已在运行,不重复
    }
    return m.reinjectLeaves(parentTask, taskById, leafSet)
}
```

### 新方法：`reinjectLeaves`（仅纳入终态子任务）

复用现有 `buildOrReuseChild`（封装 claimTask + 跨重启续传标记）+ `AddChild`（覆盖替换）。**严格只纳入终态子任务**，非终态跳过（理由见声明11/12 与风险5）：

```go
// reinjectLeaves 把请求的终态叶子重新纳入已运行的父单元(claimParent 输者路径)。
// 仅纳入终态子任务(Finished/Failed,已从 taskMap 清理、actor 已退出):buildOrReuseChild 重建新对象,
// AddChild 覆盖 children 中的旧终态对象,返回者统一交 batchCheckDuplicates + dispatch 重跑。
// 非终态子任务(Paused/Processing/Waiting 等,仍在 taskMap)一律跳过:
//   1) Paused 的恢复由 ResumeTaskTrees 经 resolveTargets 内存路径直接投 cmdResume,不经本路径(声明11);
//   2) 把它们送入 batchCheckDuplicates 会因自身作品命中→误置 WaitingForInput,破坏运行中任务(声明12);
//   3) 对 Processing/Waiting "开始"属幂等/语义模糊,跳过最安全。
func (m *Manager) reinjectLeaves(parent *ParentTask, taskById map[int64]*domain.Task, leafSet map[int64]struct{}) []*ManagedTask {
    out := make([]*ManagedTask, 0, len(leafSet))
    for leafId := range leafSet {
        t := taskById[leafId]
        if t == nil {
            continue
        }
        if !isTerminalState(TaskState(t.Status)) {
            continue // 非终态不纳入,理由见方法注释
        }
        child, _ := m.buildOrReuseChild(t, false) // 终态已删 taskMap→claimTask 重建新对象;skipTerminal=false 不跳过
        if child == nil {
            continue
        }
        parent.AddChild(child) // 终态:覆盖旧对象(actor 已退出,无在途命令,无交错)
        out = append(out, child)
    }
    return out
}
```

返回值汇入既有 step5 的 `batchCheckDuplicates` + `dispatch`（`manager.go:256-261`），无需改动调度/查重/信号量逻辑。

### 语义保证（由现有机制天然成立，无需新增代码）

- 父状态聚合：声明7，重建子任务 setState 触发 onStateChange→RefreshState→推送。
- 一任务一 actor：声明5/6，终态旧对象 actor 已死，新对象新 actor，不并存两个活跃 actor；且终态旧对象无在途命令（actor 已 return），故不存在 reinject 与 Pausing/watcher 命令交错问题（化解审查担忧）。
- 查重/替换/进度：终态重建对象走 `batchCheckDuplicates` 命中→弹窗→确认替换，与 Redownload 同链路（风险4 为预期交互）。

## 四、验证场景

- 场景1（核心）：父任务运行中（至少一个子任务在跑），对其中一个 Failed 子任务点"开始/重试"→ 子任务重建、进入 Processing、跑到 Finished/Failed；父状态正确聚合；无 panic、无重复 actor。
- 场景2：父运行中对 Finished 子任务点"恢复"→ 终态子任务不在内存，经 dbIds→loadAndStartTaskTrees→reinject 重跑（验证 Resume 对终态子任务也生效）。
- 场景3（回归·须不破坏）：父运行中对 Paused 子任务点"恢复"→ 经 resolveTargets 内存路径正常恢复（声明11，不走 reinject，确认未被改动1/2 影响）。
- 场景4（幂等）：父运行中对正在 Processing 的子任务点"开始"→ reinject 判定非终态跳过，dispatch 不触发，无副作用（声明12 规避）。
- 场景5：父运行中同时选多个终态子任务批量"开始"→ 各自重建、并发受信号量控制、父进度正确。
- 场景6：重跑的终态子任务命中查重→ WaitingForInput→确认替换→备份/还原/resource_store 无孤儿（风险4）。
- 场景7：连续多次重跑同一终态子任务→观察 drain goroutine 数量（风险1，记录基线，不在本次修复范围）。
