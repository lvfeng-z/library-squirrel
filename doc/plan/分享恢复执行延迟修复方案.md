## 审查摘要

**关键声明（抽查项）**
- 声明1：share-receive 子任务每次执行（含暂停恢复、终态重跑）都完整重跑 `planReplace → stageFiles → Ingest`；成功后 `os.RemoveAll(staging)` 清理暂存（锚 `backend/share/task_execution.go:64/110/123/142`）。
- 声明2：`stageFile` 仅当「暂存文件大小 == 声明大小」才跳过拉取（锚 `task_execution.go:568`）；`0<暂存<声明` 走断点续传（`:574-576`）。**全量重拉仅对「暂存从未填充 / 已被清理」成立**（重跑 from 终态、暂停在确认弹窗期）；mid-download 暂停恢复走断点续传，非缺陷。
- 声明3：宿主单会话并发流上限 `defaultMaxStreams = 8`，超限关流（锚 `backend/share/session.go:49` 与 `:574`）；收件方 `stageFile` 对可重试错误退避重试（锚 `task_execution.go:583-604`，常量 `receiveMaxAttempts=4`/`receiveBackoffStart=1s`/`receiveBackoffMax=8s` 在 `:42-44`）——**实际退避 1→2→4s 三次（共 4 次尝试），8s 从不实际退避**。并发重拉撞流上限 → 退避放大 → 45-87s 无进度。
- 声明4：分享 manifest 的 `FileEntry` 含 `Size` 但分享路径**不填**内容哈希——宿主导出面「sha256 不预计算」（锚 `backend/share/service.go:428`）；`FileEntry.Sha256` 字段已存在（锚 `backend/export/manifest.go:199-200`）但仅 zip 导出打包时填充（锚 `backend/export/packer.go:126`），分享路径走 `Planner.Plan`（`service.go:408`）不填。
- 声明5：本地库 `persistent_store.ContentFingerprint` 为「size + 头部 64KB SHA256」指纹，落盘完成时同步计算、毫秒级（锚 `backend/base/model/entity/persistent_store.go:24-26`、`backend/fsmonitor/README.md:34`）；计算器复用 `backend/util/fingerprint.NewHeadComputer`（锚 `backend/util/fingerprint/fingerprint.go:36-41`），digest 格式 `<size>:<hex>` 落库口径不可变（锚 `backend/util/fingerprint/fingerprint_test.go:12`）。
- 声明6：查重命中作品由 `duplicate` 服务经 `StoreRoleSetProvider.ListStoreTypeSetsByWorkIds` 定位并读取其活行 store 角色集合（锚 `backend/duplicate/service.go:44-47`，实现 `backend/resource/service.go:138`）——该接口返回 `map[workID]map[storeType]`（按 store_type 去重，**无 store_seq、无 content_fingerprint、无 file_path**），A2 的指纹比对需**新增查询接口**。
- 声明7：`stageFiles` 的拉取集由 `fileSkipSet(sub, plan.skipWorks)` 决定（锚 `task_execution.go:123`），与 `confirmedWorks` **无关**（skipWorks 语义「整作品跳过，文件不拉」，锚 `:251`）；且 `stageFile` 对「暂存==声明」的文件自动跳过（`:568`）——**逐文件跳过可用「匹配文件先拷入暂存」实现，stageFiles 零改动**；共享文件由 `fileSkipSet`「全部引用作品均跳过才不拉」语义兜底（锚 `:453-487`）。
- 声明8：Ingest 落盘**边写边算全量 sha256 并校验** `entry.Sha256`（锚 `backend/import/ingest.go:353-364`：`io.TeeReader(src, hasher)` + `entry.Sha256 != ""` 即比对）——**分享 manifest 填 Sha256 即免费解锁分享下载校验**（todo#54 分享侧零新增收件方代码）。
- 声明9：分享宿主在 `hostSessionBody` 中 `s.planner.Plan(...)`（`service.go:408`）之后、`model.Manifest.Serialize()`（`service.go:429`）之前，可插入逐文件哈希填充。

**待决策（均已裁决 2026-08-31，用户拍板）**
- 决策1（**已裁决：选项 A**）：修复范围——宿主在 manifest 预填每文件内容哈希（分享由分享功能开发者控制，**强制**），收件方据哈希逐文件判定「内容相同跳过拉取」。否决仅按尺寸弱匹配（不安全）与仅优化调度退避（不治本）。
- 决策2（**已裁决：逐文件 + range**）：跳过粒度=**逐文件**——某文件哈希匹配则不拉网络（本地文件拷入暂存供导入），不匹配才拉（复用既有流协议 per-file + offset range 断点续传）。
- 决策3（**已裁决：3a**）：**全部文件**哈希匹配的作品整作品跳过——不软删/不拉取/不导入，保留现状（元数据不刷新），瞬时完成。
- 决策4（**已裁决：双哈希 + 预下载参考**）：manifest 填 `ContentFingerprint`（头部，供快路径）+ `Sha256`（全量，供强校验）双字段；`Sha256` 即「文件期望哈希」的**预下载参考**——同时供 ⑤ 跳过判定与分享下载校验（Ingest 免费验），是 todo#54 下载校验功能的先导落点（插件侧校验为独立后续设计，仅共享 `fingerprint.Computer` 能力）。

**自曝风险**
- 风险1：决策3（3a 整作品跳过）用头部指纹快路径（比对存储的 `content_fingerprint`，零读盘瞬时）——存在「size + 头 64KB 相同但尾部不同」的碰撞误跳过。重跑未变内容时头匹配即内容相同（本地文件即本会话导入），碰撞仅当宿主导出面改动尾部且保持同尺寸同头，概率低、影响小（文件滞留旧版非损坏）；若需消除可升级为全量哈希确认（读本地文件，秒级），列为可选增强。
- 风险2：宿主会话开始对每个文件算全量 sha256（L2 3GB ≈ 6-10s 延迟「分享进行中」）——分享校验为强制（决策4），此成本不可避免且由分享校验承担；头部指纹从同一读流免费顺带。
- 风险3：本地活 store 缺 `content_fingerprint`（存量未回填，`BackfillFingerprints` 未跑）→ 视为不匹配 → 走替换重拉（安全回退，不误跳过）。
- 风险4：逐文件 PARTIAL 场景（部分文件匹配）——匹配文件拷入暂存为本地磁盘 I/O（读+写），比网络重拉快但非零成本；且该作品仍走整作品替换（匹配文件的 store 也软删重建，内容相同但 store 行轮换）。
- 风险5：决策3 语义——「确认替换」对全部匹配作品不实际执行（保留现状、元数据不刷新）；内容未变通常元数据未变，判定可接受。

## 问题与用户决策

**现象**（测试报告「问题 ⑤」）：share-receive 子任务 task 6/8/11 在 11:49:24 恢复后**静默卡 45-87s**（11:50:09/16/51 才「导入完成：替换 1 增补 1」），期间零状态变更；trace 显示恢复后每秒 2-3 个拨号、80s 内 100+ 次（`lL3ZKy47` 会话）——恢复任务重新执行 share-receive（重新拨号拉取）而非本地续传。

**用户决策 B**（测试报告「用户决策记录」）：恢复执行延迟**必须深挖**——已深挖至执行模型层面（恢复=重新拉取 + 排队退避），修复范围待定。

**本版决策落地**（2026-08-31 用户多轮拍板）：决策1=选项 A（宿主预填哈希，分享强制校验）；决策2=逐文件 + range；决策3=3a（全部匹配整作品跳过）；决策4=manifest 填双哈希、Sha256 作为「文件期望哈希」预下载参考，为 todo#54 下载校验功能的前置。

## 机制（已核码）

1. **重跑/恢复 = 全量重拉**：`Execute` 每次执行重跑 `planReplace→stageFiles→Ingest`（声明1）。成功后 `os.RemoveAll(staging)`（`task_execution.go:142`）清暂存；暂停在确认弹窗期（WaitingForInput）的任务暂存从未填充。这两种情形（终态重跑、弹窗期暂停恢复）暂存为空 → `stageFile` 的「暂存==声明才跳过」不命中（声明2）→ 全量重新拉取。**注意**：mid-download 暂停恢复走断点续传（声明2），非本缺陷。
2. **慢因 = 并发重拉撞流上限退避**：高频启停测试同时恢复 10 个子任务 → 并发全量重拉 → 宿主单会话 `defaultMaxStreams=8` 超限关流（声明3）→ 收件方退避重试 1→2→4s×3 → 45-87s 无进度；宿主多个 active 会话竞争放大。
3. **核心浪费**：重拉的内容收件方**早已拥有**——作品在先前执行（如 L2 11:20 导入）已完整落库；重跑时 `planReplace` 先软删旧 store（文件移入备份），再从宿主重拉同样内容回灌。若内容未变，重拉纯属浪费。

## 修复障碍

安全的「跳过已拥有文件」需要**内容身份比对**：确认宿主当前文件 == 收件方本地已有文件。但：

- 分享 manifest 不含哈希（声明4）——收件方无法在下载前确认身份。
- 收件方本地有 `content_fingerprint`（声明5），但缺宿主侧可比对的同口径值。

**结论**：安全跳过必须由宿主导出面在 manifest 携带每文件哈希（加法字段，向后兼容），或放弃安全跳过。分享由分享功能开发者控制，**强制**携带（决策1/4）。

## 方案设计

### 概念：文件期望哈希（预下载参考，对齐 todo#54）

每个文件携带一个「期望哈希」（全量 sha256），贯穿下载流、两个消费点：
- **预下载**（manifest 携带）→ 收件方逐文件判定「本地已有文件是否已通过校验」→ 通过则跳过拉取（省网络，本方案核心）；未通过才拉。
- **下载后**（Ingest 落盘边写边算）→ 校验下载文件与期望哈希一致（`ingest.go:363`）——分享下载校验**免费解锁**（声明8）。

分享路径的期望哈希在宿主会话开始时填入 manifest，成为「预下载参考」。todo#54 插件侧校验为独立后续设计（站点多不提供哈希，通用形态=插件下载中边写边算、下载后比对），与分享仅共享 `fingerprint.Computer` 能力。

### A1. 宿主：manifest 补双哈希（`ContentFingerprint` + `Sha256`）

- `export.FileEntry`（`backend/export/manifest.go:191-203`）新增 `ContentFingerprint` 字段（`Sha256` 字段已存在）：
  ```go
  // ContentFingerprint 文件内容头部指纹（size + 头部 64KB SHA256，`<size>:<hex>`，与库内
  // persistent_store.content_fingerprint 同口径）；分享会话开始时计算供收件方快速判定。
  ContentFingerprint string `json:"contentFingerprint,omitempty"`
  // Sha256 既有字段：zip 导出打包时填全量哈希；分享路径本次起填全量哈希，作「文件期望哈希」
  // 预下载参考（⑤跳过判定 + Ingest 下载后校验共用）。
  ```
  SchemaVersion 不变（加法字段，向后兼容；旧收件端忽略、旧宿主不填则收件方走原路径）。
- 分享宿主在 `hostSessionBody` 中 `s.planner.Plan(...)`（`service.go:408`）之后、`model.Manifest.Serialize()`（`service.go:429`）之前，遍历非 Missing 的 `manifest.Files`，**一次读流双哈希**：读文件头 64KB 算头部指纹（顺带）+ 全量流式算 sha256（主成本），分别写 `entry.ContentFingerprint` 与 `entry.Sha256`。`entry.StorePath` 为 workDir 相对路径（absPath 域，现场 Join，遵守路径纪律）。

### A2. 收件方：`planReplace` 逐文件内容判定（决策2/3）

- **新增查询接口**（声明6——既有 `ListStoreTypeSetsByWorkIds` 无 seq/指纹/路径，须新接口）：
  ```go
  // StoreMountReader 按作品查活行 store 挂载键、头部指纹与文件路径（A2 内容判定与暂存拷贝用）。
  // 实现归 resource.Service：work→resource→resource_store（活行）→ persistent_store 两跳批量拼接。
  type StoreMountReader interface {
      ListMountsByWorkIds(ctx context.Context, workIds []int64) (map[int64][]StoreMountInfo, error)
  }
  type StoreMountInfo struct {
      StoreType          string // store_type 角色
      StoreSeq           int64  // store_seq 挂载序
      ContentFingerprint string // content_fingerprint（缺指纹为空串，视为不匹配）
      StorePath          string // workDir 相对路径（暂存拷贝源，absPath 域现场 Join）
  }
  ```
  注入 `ReceiveExecution`（`task_execution.go:47-53` 构造注入，对齐既有 `replaceOps`/`checker` 注入位）。
- 在 `planReplace` **决策应用之后、软删段之前**（现 `task_execution.go:357` 与 `:361` 之间）插入「逐文件内容判定」。`planReplace` 增加 `staging`/`workDir` 入参（Execute 已有，`task_execution.go:71/103`）：
  1. 对每个确认替换目标（`confirmTargets`，含 conflict 命中的本地作品）：由 `sub` manifest 该作品 `Resources[].Stores[]`（`StoreMount`：store 挂载，含 `StoreType`/`StoreSeq`/`StoreID`）建 `(StoreType, StoreSeq) → FileEntry` 映射；经 `StoreMountReader` 取本地活行 store 的 `(StoreType, StoreSeq) → StoreMountInfo`。
  2. **逐文件分类**：对每个 manifest store——
     - 快路径：manifest `ContentFingerprint` vs 本地 `ContentFingerprint` 直比（零读盘）。不匹配 → MISMATCHED。
     - 匹配 → **全量确认**：读本地活文件，算全量 sha256 与 manifest `Sha256` 比对（秒级、消除风险1）。匹配 → MATCHED；不匹配 → MISMATCHED。
  3. 按作品聚合：
     - **全部 MATCHED**（且文件数非零）→ **3a（决策3）**：`delete(plan.confirmedWorks, manifestID)` + `plan.skipWorks[manifestID]=∅` + 从 `confirmTargets` 过滤移除——不软删、不拉取、不导入，保留现状。
     - **部分 MATCHED** → **逐文件（决策2）**：作品留在 `confirmedWorks`（整作品替换），对每个 MATCHED 文件把本地活文件**拷入暂存**（`stagingPath(staging, entry.Path)`，`MkdirAll` 父目录；拷贝读流可 tee 全量哈希二次确认，不一致则放弃拷贝改拉取）。
     - 无 MATCHED → 原样整作品替换。
  4. 安全回退：本地缺指纹 / manifest 缺指纹 / 无本地对应 store / 文件数 0 → 视为 MISMATCHED，走原替换，不误跳过。
- **软删段（`:361-381`）不变**：确认作品软删全部角色（含 MATCHED 的 store——内容已拷入暂存，软删后 Ingest 从暂存重建）。
- **stageFiles 零改动**：MATCHED 文件已拷入暂存（满尺寸）→ 既有「暂存==声明」跳过（`:568`）；MISMATCHED 文件正常拉取（per-file + offset range 断点续传）。共享文件由 `fileSkipSet` 兜底（声明7）。
- **Ingest 零改动**：从暂存读全部文件（`extractFiles`），落盘时边写边算 sha256 校验 `entry.Sha256`（声明8）——**顺带完成分享下载校验**。

#### 逐文件粒度 + range 的能力依据

收件方「只拉某作品某文件」与「range 断点续传」由既有流协议承载，零协议改动：`streamRequest{Type:"file", Path, Offset}`（`backend/share/session.go:68-72`），宿主 `io.NewSectionReader(f, req.Offset, size)` 从偏移服务到 EOF（`:674-699`）。逐文件判定只决定「拉哪些文件」，不改变拉取机制。

### A3. 与缺陷④（确认记忆）的协同

高频场景 = 恢复重弹确认（④，已修）+ 确认后全量重拉（⑤）。④ 修复消除重复弹窗；⑤ 修复使确认后的替换在内容未变时**零网络流量**（3a 直接完成）。两者叠加后，重跑内容未变的分享从「每轮确认 + 45-87s 重拉」变为「单次确认 + 瞬时完成」。
