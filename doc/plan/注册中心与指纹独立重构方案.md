# 注册中心与指纹独立重构方案

## 审查摘要

> 本方案为**纯重构**（零行为变化）：①把内容指纹计算从 `fsmonitor` 抽成独立 util 工具，消除 persistentStore→fsmonitor 的横向借调耦合；②新建「store 域注册中心」承接白名单单一源，消除 `persistentStore/dir.go` 与 `fsmonitor/scanner.go` 的双份镜像。`StoreReader`（fsmonitor 经接口读 persistentStore DB）经确认**保留不动**；suppression（内部操作抑制）**不在本次**，作为注册中心就位后的下一阶段。下列现状声明均带代码锚点，无锚点的「零改动」论断视为未核验。

### 关键声明（带锚点）

1. **指纹耦合的唯一实体是 app 适配器**：`app.go:1112 fingerprinterAdapter` 将 `fsmonitor.ContentFingerprinter`（返回 `Fingerprint` 结构体，`event.go:30`）适配为 `persistentStore.Fingerprinter`（返回 `string`，`service.go:196`），取 `.Digest`（`app.go:1118-1123`）；装配点 `app.go:938-939`。统一返回类型后此适配器可删。
2. **指纹实现本体在 fsmonitor**：`fsmonitor/fingerprint.go`（`headFingerprinter` + `NewHeadFingerprinter` + `ComputeFingerprint`），纯 `crypto/sha256`+`os`+`io`，无领域依赖——满足工具独立前提。
3. **fsmonitor 侧指纹消费点**：`deps.go:30 ContentFingerprinter` 接口 + `deps.go:39 Deps.Fingerprinter` 字段 + `deps.go:48 NewPlatformDeps` 自建注入 + `correlator.go:64/74`（持有与构造）+ `correlator` 内用 `fp.Digest` 匹配。
4. **persistentStore 侧指纹消费点**：`service.go:196 Fingerprinter` 接口 + `service.go:219 SetFingerprinter` + `service.go:75 storeWriter.fingerprinter` 字段 + 落库点 `service.go:119-126(Complete)` / `service.go:302-312(computeFingerprint)` / `service.go:315-320(fillFingerprint)` / `service.go:284(runBackfillFingerprints)`；落库值取 digest 串入 `ContentFingerprint` 列。
5. **白名单权威源在 persistentStore**：`persistentStore/dir.go:18 registeredDirs` + `dir.go:12 StoreDir` 结构 + `dir.go:28 validatePath`（正斜杠 + 按分隔符前缀匹配，`dir.go:30-31`），被 `service.go:340 / 460 / 701` 三处 `Store`/`StoreStream`/`StoreFromExternal` 调用做落盘前路径校验。
6. **白名单镜像是 fsmonitor 抄写**：`fsmonitor/scanner.go:14 scanDirs`（注释自承「与 persistentStore/dir.go 白名单一致」）+ `scanner.go:24 inScanDirs` 谓词。`scanDirs` 被 `scanner.go:85 collectDiskFiles` 遍历使用；`inScanDirs` 当前**非测试代码 0 调用**（仅 `usn_windows_test.go:285` 测试覆盖，`scanner.go:22-23` 注释标明其为 USN 路径过滤预留、C-2/C-4 将接线），属死代码预留。两份白名单内容**当前一致**，但双源无机制约束，是漂移风险源；`inScanDirs` 迁 storeRegistry 的必要性在于"趁统一源一并迁、供 USN 后续用"，而非当前已有调用方。
7. **无第三方引用**：全局 grep 确认 `registeredDirs/validatePath` 仅 persistentStore 内 + plan 文档引用；`scanDirs/inScanDirs` 仅 fsmonitor 内 + 测试；`ContentFingerprinter` 仅 fsmonitor + app 适配器 + plan 文档。迁移影响面封闭。

### 待决策

- **D1 注册中心包名与归属**：①独立包 `backend/storeRegistry`（推荐，语义中性、未来承接 suppression 不违和）vs ②`backend/base/storeRegistry`（归「公共基础」）。推荐①——注册中心是 store 域协作中介（非 logger/model 级纯基础），独立包边界更清晰。
- **D2 util/fingerprint 的 API 形态**：①接口 + 实现（`Computer` 接口 + `NewHeadComputer()`，推荐，便于测试 mock 与未来全文件哈希实现）vs ②纯函数（`Compute(absPath) (Fingerprint,error)`）。推荐①。
- **D3 persistentStore/fsmonitor 是否保留各自指纹接口**：①两模块都直接依赖 `util/fingerprint.Computer`，删除各自接口（推荐，彻底消除借调）vs ②保留消费方自定义接口（鸭子类型满足，但 persistentStore 返回 `string` 的接口与 util 返回 `Fingerprint` 不兼容，仍需适配器——违背初衷）。推荐①。
- **D4 `dir.go` 去留**：①删除 `dir.go`，三处调用点直接 `storeRegistry.ValidatePath`（推荐，无意义转发层）vs ②保留 `dir.go` 作 thin wrapper。推荐①——`dir.go`/`registeredDirs` 被 `persistentStore/README.md:41` 引用，删后须同步 README（已纳入 S6）。
- **D5 `ComputeFingerprint` 便捷函数删 vs 迁**：`fsmonitor/fingerprint.go:48 ComputeFingerprint` 当前**无调用方**（Grep 仅命中定义 + plan 文档），按 `DEAD_CODE_CLEANUP`(P2) 倾向**删除**而非迁入 util；若未来 util 调用方需要便捷函数再加。推荐删。

### 自曝风险

- **R1 循环依赖**：`util/fingerprint` 与 `storeRegistry` 被 persistentStore + fsmonitor 共同向下依赖，二者**禁止反向 import** 任一业务模块。须审计两新包 import 列表仅含标准库/基础（fingerprint：`crypto/sha256`+`os`+`io`+`fmt`+`context`；storeRegistry：`path/filepath`+`strings`+`fmt`）。`go build ./...` 编译期即检出循环。
- **R2 指纹 digest 口径须不变**：当前 digest 格式为 `"<size>:<hex>"`（`fingerprint.go:43`），persistentStore `ContentFingerprint` 列存量数据与 fsmonitor correlator 匹配均依赖此格式。迁移后须**保持同一格式串**，否则存量指纹失效、移动匹配断裂。属不可逆数据兼容约束。
- **R3 白名单迁移须逐调用点验证**：`validatePath` 3 处 + `collectDiskFiles` 1 处 + `inScanDirs` 测试 1 处，行为须与迁前**位等价**（含 `store/avatar` 只认 `local`/`site` 的叶子目录语义、按 `d+"/"` 分隔符前缀匹配）。现有 `TestInScanDirs`（`usn_windows_test.go`）+ persistentStore 路径校验行为作回归基线。
- **R4 装配顺序**：指纹独立后 persistentStore 不再等 `fsmonitorDeps` 即可注入 Computer（`app.go:938` 条件块简化），`BackfillFingerprints` 触发时机不变。须确认 persistentStore 构造（`app.go:821`）与指纹注入的时序不引入 nil 解引用。
- **R5 测试归属迁移**：`TestInScanDirs` 当前在 `usn_windows_test.go`（fsmonitor 包内、windows-only build tag），迁移到 storeRegistry 后应改为 storeRegistry 包的跨平台测试（`storeRegistry_test.go`），原 fsmonitor 处删除，避免测试逻辑双份。

## 一、背景与目标

### 1.1 要消除的两个不健康耦合

**耦合 A：persistentStore → fsmonitor 横向借调指纹算器。**
`HeadFingerprinter` 是领域无关的纯文件能力（size + 头部 64KB SHA256），却挂在 `fsmonitor` 业务包下，由 persistentStore 经 `Fingerprinter` 接口 + app 适配器反向借调。违反 `MODULE_BOUNDARY_PURITY`（能力包只提供领域无关纯能力——指纹本就是领域无关纯能力，却错置于业务模块），且制造了两个业务模块间的横向依赖 + 一个只为弥合返回类型差异的适配器。

**耦合 B：白名单双份镜像，无单一事实源。**
同一套 store 子目录规则（`store/resource`、`store/thumbnail`、`store/avatar/{local,site}`）在 `persistentStore/dir.go`（写入校验权威）与 `fsmonitor/scanner.go`（读取过滤镜像）各抄一份，仅靠注释「保持一致」约束。任一侧增改目录（如未来新增性能 store 角色）须手动同步两处，漏改即致「写入允许落盘、监控却不看」或反过来的范围漂移。

### 1.2 目标（本次范围）

1. 指纹计算独立成 `util/fingerprint` 工具包，persistentStore 与 fsmonitor 都向下依赖它，删除 app 适配器与两模块各自指纹接口。
2. 新建 `storeRegistry` 注册中心，承接白名单单一源（`StoreDir` 清单 + `ValidatePath` + `InScanDirs`），persistentStore 与 fsmonitor 都引用它，删除两处镜像定义。
3. **零行为变化**：路径校验、指纹格式、监控过滤范围、落库口径全部位等价。`StoreReader`（fsmonitor→persistentStore 读 DB）保留。

### 1.3 非目标

- **suppression（内部操作抑制）不在本次**：注册中心本次只承接白名单。suppression 中介（写方注册进行中操作、读方查询跳过，修复「内部写入被误报为外部操作」缺口）作为注册中心就位后的**独立下一阶段**（见 §六）。
- 不改 `StoreReader`/`StoreRepairer` 接口与 app 的 `storeReaderAdapter`/`storeRepairerAdapter`。
- 不改指纹算法（仍是头部哈希，非全文件）、不改白名单目录集合。

## 六、与 suppression 的关系（下一阶段预告，本次不做）

注册中心就位后，suppression 落点天然清晰——它正是「写方(persistentStore 各写入点)注册进行中操作、读方(fsmonitor 事件源)查询命中即丢弃」的中介者，本次新建的 `storeRegistry` 即其载体。下一阶段将在此基础上加：

- `storeRegistry.Suppress(relPath)` / `Release(relPath)`（或 `WithSuppression(ctx, func())` 回调式），写方在 `Store`/`StoreStream`/`Complete`/`Delete`/`StoreFromExternal` 前后注册/注销。
- `fsnotifySource.handleEvent` 推送前查抑制集，命中即丢弃；配合「写后宽限期」处理 fsnotify 异步延迟的时序竞态。
- 此举把上轮发现的「内部写入被误报为外部操作（SemanticUntracked/SemanticDelete）」缺口根治，同时不破坏本次的单向依赖架构（suppression 是 storeRegistry 内的状态，两模块仍只依赖 storeRegistry，不直接互认）。

> 该阶段属新功能（改写入点 + 事件源行为），体量与回归面大于本次纯重构，故明确分阶段——本次先把中介者与共享工具就位、稳态落地。
