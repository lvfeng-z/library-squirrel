**自曝风险（作者没把握 / 可能错的地方）**
- 风险1　persistentStore 入口分散（StoreStream/读/删/merge 落盘/复原），「所有写路径都过 taskManager 前置拦截」未确认（探索代理明示未确认）——阶段2 须 grep 复核入口全集，拒绝点选服务层入口而非散在各拼路径处，避免漏点与重复判据（单一判据规则）。
- 风险2　fsmonitor 懒启动（决策2 半热更基线）引入「服务可二次启动」的新生命周期语义，与现有一启一停模型可能有状态机摩擦（Stop/stopOnce 语义）——实施时需核对 Start 幂等性。
- 风险3　USN provider 对空 workDir 行为未核（探索代理未读 `usn_provider_windows.go` 实现）——fsmonitor Start 空值短路后其构造点同被跳过，理论不触达，但需在阶段1 验证构造序确在其后。
- 风险4　「曾配置后清空」场景下 backup 清单行内已落空串 Workdir 的历史行（若存在）行为未定义——无历史包袱裁决下不迁移，仅保证新写入不再产生（未发布期，当前库已重建，预期零存量）。

## 背景

昨日 dev 启动挂死事故暴露：settings.json 缺失时 `WorkDir` 静默为空串，下游各模块把空串当合法路径（CWD 相对化），最恶劣形态是 fsmonitor 递归监控整个进程工作目录。用户裁决：**移除该隐式机制**——workdir 未配置是合法且显式的状态，各依赖模块必须自行处理该状态，最低要求是拒绝提供服务并引导用户去配置，而非静默产出错误行为。

「未配置」语义自此单一化：`GetWorkDir()` 返回空串 = 未配置（空串不是路径，不 Trim 后放行空白串——保存侧 Trim，读取侧判空串）。

## 设计

### 一、统一错误与判定（后端）

- `backend/settings` 新增哨兵错误 `ErrWorkDirNotConfigured`（文案：「工作目录未配置，请先在设置页配置工作目录」）——错误归概念拥有方（settings），消费方 `errors.Is` 判定。既有守卫（声明2 各方）**保留各自领域错误不动**，不做统一改写（它们已带领域上下文，改写属无收益扰动）；但拒绝原因属「workdir 未配置」时，这些守卫点同样经统一发射口发 `workdir:unconfigured`（裁决1「任何模块…都可调用」的完整兑现——**事件统一、文案不统一**）。
- 判定点归各消费模块**服务层入口**（单一判据规则：每个语义一个判定点，不散落到拼路径处）。

### 二、启动期服务（空串不启动 + info 日志）

- fsmonitor：`Service.Start` 判空 → 记 info「工作目录未配置，文件监控与启动对账未启动」并返回（live source、USN provider（基于 NTFS USN 变更日志的离线追溯能力）、离线对账整体不启动——声明8 误报路径随之关闭）。`NewPlatformDeps`/`NewFsnotifySource` 不加第二道判据。
- recycleBin：`StartCleanup` 判空跳过（app.go:1077 调用点或服务内，取调用链更内聚侧）。
- `NormalizeFilePaths`（app.go:993 调用）为纯 DB 操作无需守卫——实现为单条 `UPDATE persistent_store SET file_path = REPLACE(...)`（`backend/persistentStore/repository.go:115-120`），无文件系统访问。
- assetserver `SetWorkDir("")` 快照保留现状（消费侧 404 已显式）。

### 三、请求期拒绝点（新增 `ErrWorkDirNotConfigured` 拒绝）

- persistentStore：落盘/读/删/复原等**服务层入口**统一前置检查（入口全集阶段2 grep 复核，见风险1）。
- backup：`storeFile` 与还原路径入口拒绝；清单行不再落空串 Workdir。
- recycleBin：还原入口拒绝。
- appLauncher：`OpenPath` 拒绝（返回错误经 ApiResponse，前端 ElMessage 呈现哨兵文案）。
- resource：替换回滚路径入口拒绝（该路径仅在曾有落盘时可达，属防御性，判据仍归一）。

### 四、未配置通知接口与前端策略（裁决1）

- **后端统一发射口**：`backend/settings` 提供 `NotifyWorkDirUnconfigured(source string)` 包级函数——内部经注入的 emitter 闭包发射 Wails 事件 `workdir:unconfigured`（payload `{source}`），闭包在 app.go `SetEventEmitter` 之后接线（循插件推送器 LAZY_EMITTER_CLOSURE 既有模式，避免初始化时序问题）。**唯一调用方=请求期拒绝**：各拒绝点在返回错误的同时发射（`source=模块名`，既有守卫点与新增哨兵点同权接入）——判定+拒绝+发射收口进一个辅助函数（如 `settings.RefuseIfUnconfigured(workdir, source) error`），调用点一行，避免每点两行与漏发射。**后端不做启动期发射**：未配置的初始判定走前端拉取（下条），规避「发射早于前端 `Events.On` 注册即丢失」的时序缺口（与分享深链「缓存+消费式拉取」同构）。
- **前端策略层**（轻量 Pinia store + 事件监听枢纽）双通道：
  - **初始判定（拉取式）**：MainLayout 挂载时水合（`GetSettings`）——workdir 为空且 first-time 向导未完成 → 直接打开向导（复用 `tour/definitions.ts` 既有定义，target `settings.workdirInput`）；向导已关/已完成 → 常驻横幅「工作目录未配置，点击前往设置」；
  - **运行期事件（推送式）**：监听 `workdir:unconfigured` → 升横幅（若未展示）；同源去重，会话内向导不重复弹。API 错误文案（哨兵/领域错误经 ApiResponse 到 ElMessage）与事件双轨互补：错误管「当次操作为何失败」，事件管「主动引导去配置」。
- `Settings.Initialized` 死字段删除（声明6，DEAD_CODE_CLEANUP）。

### 五、未配置→已配置的转换（裁决2：热更新优先）

- **半热更基线**：settings `afterSave` 回调联动 `StoreFileHandler.SetWorkDir`（既有方法，一行接线）；fsmonitor 提供「因未配置未启动」场景的懒启动——保存事件触发 `Service.Start`（若未启动过），已启动态改目录仍提示重启；`fsmonitor:workdir-changed`（既有事件 `fsmonitor/service.go:454`）补前端监听与提示。
- **降级通道（已预授权）**：若懒启动与既有启停状态机（Stop/stopOnce 语义、启动期对账一次性）摩擦坐实（风险2），降级为「保存成功后提示重启生效」，仅保留 afterSave 快照联动（无状态机风险的部分）；降级与理由记入阶段3 交接摘要。
- 保存侧 workdir Trim（空白串不落库）。

### 六、文档同步

- `backend/settings`、`backend/fsmonitor`、`backend/workdirGuard`（README:19 注入方式表述修正）README + `.claude/rules/backend.md` 相应概念行。
- 本方案落地的「未配置=空串、拒绝语义」写入 workdirGuard 或 settings README 的关键设计节。

## 验收标准

1. 删除 settings.json 启动：无任何模块以空串路径静默操作（日志无相对路径落盘、无 CWD 监控），fsmonitor/recycleBin 清扫不启动且有 info 日志，`workdir:unconfigured` 事件触发前端向导/横幅。
2. 各请求期功能（下载落盘/导出/分享/备份/回收站还原/打开目录/替换）在未配置态拒绝：新增拒绝点返回哨兵文案，既有守卫点（下载/导出/分享）保留领域文案——所有拒绝均触发 `workdir:unconfigured` 通知。
3. 配置后按裁决2 形态生效（热更或预授权降级）；重启后监控/文件服务正常。
4. `Initialized` 死字段消失；workdirGuard README 与实现一致。
