## 审查摘要

**关键声明（抽查项）**
- 声明1：share-receive 子任务每次执行（含暂停恢复）都重跑 `Execute`，内部 `planReplace`（查重→确认→软删）从零开始（锚 `backend/share/task_execution.go:64` 与 `:110`）。
- 声明2：`planReplace` 命中冲突即调 `h.WaitReplaceConfirm(conflicts)` 阻塞等待用户整体答复（锚 `task_execution.go:345`）；暂停时执行上下文 `runCtx` 取消使该等待返回 `canceled=true`（锚 `backend/taskManager/execution_strategy.go:192-194` 外层取消分支）。
- 声明3：确认决策（`confirmedWorks`/`skipWorks`）是 `planReplace` 局部变量（锚 `task_execution.go:274-278`），暂停后无跨执行载体——恢复重跑重新弹窗。
- 声明4：任务级内存态跨暂停/恢复保留已有先例：`terminalRollback`（终态回滚登记）存于 `ManagedTask`，暂停不清、终态清空（锚 `backend/taskManager/model.go:410-412`，清空点 `execution_strategy.go:124-131` `Finish` 与 `model.go:1852-1867` `triggerTerminalRollback`）。
- 声明5：`PauseTaskTrees` 暂停时把任务从等待确认表移除（锚 `backend/taskManager/manager.go:661-666`），`ConfirmReplace` 答复后亦从表移除（锚 `manager.go:911`）——确认答复与任务状态由 taskManager 控制面管理。
- 声明6：`WaitReplaceConfirm` 存在**两个取消返回点**：外层取消分支（`execution_strategy.go:192-194`，答复未消费）与**内层取消分支**（`:186-188`，答复已被 confirmCh 消费、仅信号量取槽被打断，返回 `(res.decision, true)`）——方案须两处都覆盖，否则竞态答复仍丢。
- 声明7：暂停在确认等待期**实际可达**：`cmdPause` 在 setup 阶段（`inDownload=false`）立即 `runCancel`（锚 `model.go:718-723`），planReplace 在 downloadLoop 之前故 `inDownload` 恒 false——`execution_strategy.go:97-98` 与 `:178-179`「模态弹窗期间暂停/停止实际不可达」注释为**陈旧**，需修正。
- 声明8：`conflictWorkIds` 助手为「保序去重」（锚 `execution_strategy.go:58-59`）——记忆键复用同一函数，比对按**集合相等**（顺序无关）。
- 声明9：既有 `skipped` 字段（插件路径确认跳过标记）为**单 bool**、注释「Resume 不读」（锚 `model.go:424`）、设置点 `model.go:565`/`manager.go:1013`、用于父聚合判定 `model.go:2279`——与确认记忆（携带冲突集+决策、必须跨 Resume 存活）语义与生命周期不同，**不复用**，理由见「skipped 先例说明」。

**待决策（均已裁决 2026-08-31，用户拍板）**
- 决策1（**已裁决：采用**）：记忆匹配粒度——仅当「当前冲突本地作品 ID 集」与记忆一致（集合相等）时才复用决策（子集/超集变化均重新弹窗）。
- 决策2（**已裁决：采用**）：答复与暂停竞态——`WaitReplaceConfirm` 内统一记录：答复已消费（正常/内层取消）即记入记忆，外层取消时有残留答复也消费记入——用户点过确认不白点，符合决策 A「确认决策保留」。

**自曝风险**
- 风险1：记忆仅存内存（`ManagedTask`），应用重启后任务从 DB 重载 → 记忆丢失 → 重新弹窗。符合决策 A「单次会话内保留」，判定为预期行为。
- 风险2：决策记忆以「冲突作品 ID 集」为键，未纳入冲突角色集——同一作品角色冲突面变化（如 1 角色变 2 角色）而 ID 集不变，记忆仍复用旧决策。对「替换」语义影响小（替换角色按当次交集角色计算），判定可接受，需测试暴露。
- 风险3：`StrategyHandle` 接口新增 `ConfirmMemo` 方法只波及 **share 测试的 `fakeStrategyHandle`**（`backend/share/share_test.go:768`）——taskManager 自身测试用真实 `strategyHandle`（如 `confirmation_loop_test.go:180` 直接 `newStrategyHandle`），不实现该接口，故不受接口新增影响；但它们受 `WaitReplaceConfirm` **行为变更**（取消路径记录记忆）影响，需同步断言。
- 风险4：`WaitReplaceConfirm` 正常答复路径也记录记忆——若答复后软删失败任务落 Failed，`setFailed` 清记忆，无残留；若暂停在答复后、软删前，记忆已记 → 恢复复用决策并软删。判定一致。

## 问题与用户决策

**现象**（测试报告「新发现④」）：share-receive 子任务在高频「暂停→恢复」下，每次 `Paused→Processing`（恢复续传）都重新进入 `Processing→WaitingForInput` 弹覆盖确认；task 6/8/11 在 80s 内被「批量确认替换」12 次——用户对同一任务重复确认。

**用户决策 A**（测试报告「用户决策记录」）：覆盖确认**在单次会话中保留**——同一任务执行生命周期内，确认决策跨暂停/恢复保留（恢复续传不重新弹确认）；**终态重跑仍重新确认**（Finished/Failed 后重跑要重弹）。

## 机制（已核码）

1. 收件人子任务执行面 `ReceiveExecution.Execute`（`task_execution.go:64`）每次执行都完整走 `planReplace → stageFiles → Ingest`。暂停（`runCtx` 取消）时 Execute 提前返回不上报终态，恢复时**从零重跑 Execute**。
2. `planReplace`（`task_execution.go:272`）查重后，命中冲突即 `h.WaitReplaceConfirm(conflicts)`（`task_execution.go:345`）整体决策。
3. `WaitReplaceConfirm`（`execution_strategy.go:154`）置任务 `WaitingForInput` 后阻塞在 `select { confirmCh / runCtx.Done() }`。暂停 → `runCtx` 取消 → 两个取消返回点之一（声明6）：外层分支答复未消费、内层分支答复已被消费但取槽被打断。**两种情形下用户此前对本次执行作出的确认决策都随 Execute 返回丢失**——恢复重跑后 `planReplace` 重新查重、重新命中冲突、重新弹窗。
4. 用户决策产物 `confirmedWorks`/`skipWorks` 是 `planReplace` 栈上局部变量（`task_execution.go:274-278`），无任何跨执行载体。

## 方案设计

**核心**：把「用户对某冲突集作出的整体决策」提升为任务级内存记忆（`ManagedTask` 字段），与 `terminalRollback` 同生命周期——暂停/恢复保留、终态清空。**记忆记录统一收敛在 `WaitReplaceConfirm` 内部**（答复只在三处到达：正常答复、内层取消、外层取消竞态），`planReplace` 每次执行先查记忆，命中则复用决策不弹窗。

### 1. taskManager 侧：确认决策记忆

新增类型与字段（`backend/taskManager`）：

```go
// ReplaceConfirmMemo 覆盖确认决策记忆：用户对某冲突作品集作出的整体答复（任务粒度）。
// 跨暂停/恢复保留（同一任务执行生命周期内不重复弹窗）；终态清空，重跑重新确认。
type ReplaceConfirmMemo struct {
    ConflictWorkIds []int64         // 决策适用的冲突本地作品 ID 集（conflictWorkIds 保序去重输出）
    Decision        ReplaceDecision // ReplaceDecisionReplace / ReplaceDecisionSkip
}
```

`ManagedTask` 新增字段 `confirmMemo *ReplaceConfirmMemo`（放在 `terminalRollback` 旁，`model.go:410-412`），注释言明生命周期。

`StrategyHandle` 接口（`execution_strategy.go:83-105`）新增**只读**方法：

```go
// ConfirmMemo 返回已记住的确认决策记忆（无则 nil；仅策略任务用）
ConfirmMemo() *ReplaceConfirmMemo
```

实现放 `strategyHandle`：读 `h.m.confirmMemo`。**不新增写方法**——记忆写入收敛在 `WaitReplaceConfirm` 内部（见下）。

### 2. `WaitReplaceConfirm` 内部统一记录记忆（覆盖三条答复路径）

`execution_strategy.go:154` 的 `select` 两分支重构：

```go
select {
case res := <-m.confirmCh:
    // 答复已到达：先记记忆（决策 A——确认决策保留，供后续恢复复用）
    m.confirmMemo = &ReplaceConfirmMemo{
        ConflictWorkIds: conflictWorkIds(conflicts),
        Decision:        res.decision,
    }
    // 答复后重新排队取槽（阻塞取槽可被取消打断；取消时槽位保持释放）
    select {
    case m.semaphore <- struct{}{}:
        m.slotHeld = true
    case <-m.runCtx.Done():
        // 内层取消：答复已被 confirmCh 消费、仅取槽被打断——记忆已记，交恢复复用
        m.manager.removeWaitingForInput(m.taskId)
        return res.decision, true
    }
    m.setState(TaskStateProcessing)
    return res.decision, false
case <-m.runCtx.Done():
    m.manager.removeWaitingForInput(m.taskId)
    // 外层取消竞态：用户已答复但被暂停打断——非阻塞读残留答复记入记忆
    select {
    case res := <-m.confirmCh:
        m.confirmMemo = &ReplaceConfirmMemo{
            ConflictWorkIds: conflictWorkIds(conflicts),
            Decision:        res.decision,
        }
    default:
    }
    return ReplaceDecisionSkip, true
}
```

- **正常路径**：答复到达即记记忆（先于取槽/软删）；若软删失败任务落 Failed，`setFailed` 清记忆（见 §3），无残留。
- **内层取消**：答复已在 `res`，记忆已记——方案不留坑（审查遗漏1）。
- **外层取消**：竞态残留答复被消费记入记忆（原方案 §3 保留），无答复则不记（用户确实未答）。
- 进入等待时的「排空历史残留答复」（原 `:156-160`）**移除**——取消路径已消费残留，排空反而可能丢弃竞态答复；防御由各取消分支的消费承担。

### 3. 记忆清空点（终态）

- `strategyHandle.Finish`（`execution_strategy.go:124-131`）：置终态处 `h.m.confirmMemo = nil`。
- `ManagedTask.setFailed`（`model.go:1833`）：置失败态处 `m.confirmMemo = nil`（须在 `triggerTerminalRollback` 早退分支之前——该函数在 `terminalRollback == nil` 时提前返回，若只在那清会漏清）。

覆盖全部终态路径：`h.Fail` → `setFailed`；`h.Finish` → 直接清。暂停（非终态）不清。

### 4. 修正陈旧注释

`execution_strategy.go:97-98`（接口文档）与 `:178-179`（实现文档）的「模态弹窗期间暂停/停止实际不可达」与实测不符（声明7：`cmdPause` 在 setup 阶段立即 `runCancel`，弹窗期可达）——改为言明「确认等待期可被暂停打断（setup 阶段 `inDownload=false` 时 `cmdPause` 立即取消 runCtx），返回 canceled 交控制面接管；`setFailed` 单点仍收口确认之后的中断窗口」。

### 5. share 侧 `planReplace` 记忆复用

`task_execution.go` 的冲突整体决策段（现 `:343-359`）重构：

```go
if len(conflicts) > 0 {
    conflictIDs := conflictWorkIds(conflicts) // 复用既有助手（保序去重）
    if memo := h.ConfirmMemo(); memo != nil && sameIDSet(memo.ConflictWorkIds, conflictIDs) {
        // 记忆命中：复用决策，不弹窗（决策 A：单次会话内确认保留）
        applyConfirmDecision(plan, confirmTargets, memo.Decision)
    } else {
        decision, canceled := h.WaitReplaceConfirm(conflicts) // 内部已记记忆（决策2）
        if canceled {
            return nil, true, nil // 记忆已由 WaitReplaceConfirm 记录，恢复复用
        }
        applyConfirmDecision(plan, confirmTargets, decision)
    }
}
```

`applyConfirmDecision` 封装现有 switch（skip → `plan.skipWorks`；replace → `plan.confirmedWorks`），两处共用。**记忆键与比对**：`sameIDSet` 按**集合相等**（顺序无关）——两运行间 `conflictWorkIds` 输出保序但理论可因查重顺序漂移，集合比对消除顺序依赖（声明8）。

**软删段（`:363-383`）不变**：记忆复用路径下对已软删的旧 store 行，`SoftDeleteWorkStoreRoles` 只作用活行（GORM 软删 scope）→ no-op；`SetTerminalRollback` 按 StoreID 去重累积（`execution_strategy.go:198-220`）→ 幂等。

### 6. skipped 先例说明（为何不复用）

`ManagedTask.skipped`（`model.go:424`）是**插件路径**的「用户选跳过」标记：单 bool（仅 skip、无 replace）、注释「Resume 不读」（`:424`）——即它**明确不跨恢复存活**，与决策 A「确认决策跨暂停/恢复保留」**直接冲突**；且其职责是供父聚合 `AllChildrenTerminal` 判定子任务终态（`model.go:2279`），非「避免重弹确认」。确认记忆需携带**冲突集 + 决策二元组**且必须跨 Resume 存活，语义与生命周期都与 `skipped` 不同，故**独立字段**。插件路径不适用记忆（插件 ConfirmReplace 走 `cmdConfirmReplace` 命令、`skipped` 语义已足），两路径不混用。

### 7. 语义边界

| 场景 | 行为 |
|---|---|
| 暂停在确认弹窗前（未答复） | 无记忆 → 恢复重新弹窗（用户确实未答） |
| 答复正常到达后暂停（软删前/stageFiles 中） | 记忆已记 → 恢复复用决策不重弹；软删对活行 no-op、回滚并集去重 |
| 答复与暂停竞态（外层取消残留） | 取消路径消费答复入记忆 → 恢复复用 |
| 答复已消费仅取槽被打断（内层取消） | 记忆已记 → 恢复复用 |
| 确认后软删完成暂停，恢复 | 重新查库落零交集分类 → 不重弹（既有延续机制，`TestReceiveExecutionPauseResumeContinuation` 已锚） |
| 终态（Finished/Failed）后重跑 | 记忆清空 → 重新弹窗（决策 A「终态重跑仍重新确认」） |
| Stop（非暂停） | `cmdStop` → `runCancel` → 取消返回 → 控制面 `setFailed` → 记忆清空 → 重试重新弹窗（既有 `TestReceiveExecutionRetryReconfirm` 语义保持） |
| 应用重启 | 记忆随 ManagedTask 重载丢失 → 重新弹窗（单次会话语义） |
