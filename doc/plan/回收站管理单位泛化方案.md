## 一、背景与定位

J 的定位（TREE.md J 节点裁决）：回收站从「作品级最小单位」泛化为「已删实体通用管理器」（work | store | 未来 workSet——B 分支，任务树上延后的「作品集逻辑删除与回收站」推广任务，对齐）。查询方向已裁决：

- **work 条目** = `work.deleted_at > 0`，挂载链软删 store 聚合其内，条目单位=作品（现状即此，零改动）。
- **store 条目** = `persistent_store.deleted_at > 0` ∧ (work 不可达 ∨ work 存活)——条目单位是 store 行非作品，TTL/过期按行自身 deleted_at，作品仅分组展示；离链孤儿（挂载链不存在的软删行）自动落入 store 条目自愈，无需额外清扫。
- 挂载态不作判别（J' 残留崩溃时序两态皆有）；backup_id 有无降为条目状态（有备份=潜在可复原，无备份=仅清理）。

**定调（如实）**：J 是接管历史残迹 + 预铺 J' 例行态，非堵现行泄漏——dev 库 32 行残迹归因全部是开发期事故形态（中间版本实验/复原误耗/手动删表），现行链路中「work 删除→purge 幸存」窄路径零命中。但本次调研发现 purge 链存在**结构性残留产道**（声明4，每次 Purge 必触发，与 TREE 考古的「窄路径」不同层面），建议随 J 一并修复（决策4）。

**J 与 J' 的关系（红线1）**：J 是 J'（替换/merge 备份软删化，吞并 E——E 为原「替换场景备份还原点持久化」分支，已裁决并入 J' 不独立立项）的前置——J' 落地后替换/merge 残留以软删 store 行入回收站由 TTL 收尾，依赖 J 的 store 条目承载；J 的数据模型须预铺 J' 例行态（软删行带 backup_id、可挂载可离链两态、按行自身 deleted_at 计 TTL）。

## 二、条目数据模型与判定谓词

### store 条目判定谓词（核心）

```sql
-- 记 ps 为 persistent_store 别名
ps.deleted_at > 0
AND NOT EXISTS (            -- 排除「挂载链指向已软删作品」形态（该形态聚合进 work 条目）
    SELECT 1 FROM resource_store rs
    JOIN resource r ON rs.resource_id = r.id
    JOIN work w ON r.work_id = w.id
    WHERE rs.store_id = ps.id AND w.deleted_at > 0
)
```

谓词语义三态全覆盖：

| 形态 | 谓词结果 | 归属 |
| --- | --- | --- |
| work 已软删（挂载链在，store 随软删） | NOT EXISTS 不成立 → 排除 | work 条目聚合（复原走 RestoreWork） |
| work 活（挂载链在）——MarkInvalid 形态、J' 后替换残留（关联保留形态） | 纳入 | store 条目，有主链 |
| 挂载链断（resource_store/resource/work 行不存在）——purge 残留（若不修复）、开发期残迹、J' 前替换现行不留（HardDelete 直清） | 子查询无行 → 纳入 | store 条目，离链 |

谓词用 EXISTS 集合语义（非 JOIN 假设唯一），天然兼容 J' 关联保留形态下「同 (resource,role) 双关联」（软删行与活行各挂一条 resource_store）。

### 条目状态（backup_id 降级为状态而非判别）

- `HasBackup` = `backup_id > 0`（行内引用 backup 保管清单行，entity/persistent_store.go:31-34）——文件在 backup/ 可还原。
- `CanRestore`（可复原性）= `HasBackup` ∧ 挂载链可达（work 活）。仅呈现状态列（决策5：操作延后 J'）。
- MarkInvalid 行（外部裁决失效）= backup_id=0 的软删行（persistentStore/service.go:253-257 经记录级软删实现）→ 仅清理态。

## 三、查询设计（分轨）

### 查询模型按条目类型分轨（裁决原文落地）

- **work 条目**：沿用 SearchCondition 标签体系，`QueryRecycleWorkPage` 零改动（声明2）。
- **store 条目**：条件体系=文件域平铺字段（裁决原文：「离链只剩文件域条件（文件名/路径模糊、扩展名→资源类型、backup_id 状态、deleted_at 时间）」）+ 作品名模糊（有主链联作品元数据）。**不进 SearchCondition 体系**——store 条目条件域与作品标签体系正交，硬塞一个枚举会令两族语义混居（架构一致性：不为局部便利扩统一体系）。search 现有 `buildWhereClauseWithBaseline` 参数化形态不动（红线2 自动满足：不触碰即不破坏）；若未来给 store 条目扩作品域全套条件（J' 落地后按作品找替换残留），按红线2 手法经 `buildWhereClauseWithAlias(conditions, "w")` 嵌 EXISTS（声明3 先例）。

### 查询落点：search 模块（与 work 条目同构）

新增 `QueryRecycleStorePage`（search/repository.go，与 QueryRecycleWorkPage 并列）：原生 SQL，谓词经提取函数 `buildRecycleStoreWhere` 生成（列表与 TTL 圈定共用同一函数，风险3 防漂移）。recycleBin 经新接口转发（同 `RecycleWorkQuerier` 模式，recycleBin/service.go:59-63）：

### SQL 形态（草案）

```sql
SELECT ps.id, ps.file_name, ps.file_path, ps.filename_extension, ps.deleted_at, ps.backup_id
FROM persistent_store ps
WHERE ps.deleted_at > 0
  AND NOT EXISTS ( ...同第二节谓词... )
  [AND ps.file_name LIKE ?]            -- FileName 非空
  [AND ps.file_path LIKE ?]            -- FilePath 非空
  [AND ps.filename_extension IN (...)] -- MediaType 映射扩展名集
  [AND ps.backup_id > 0 / = 0]         -- HasBackup
  [AND ps.deleted_at >= ? / <= ?]      -- 时间范围
  [AND EXISTS (                        -- WorkName 非空：挂载链活作品名模糊
      SELECT 1 FROM resource_store rs2
      JOIN resource r2 ON rs2.resource_id = r2.id
      JOIN work w2 ON r2.work_id = w2.id
      WHERE rs2.store_id = ps.id AND w2.deleted_at = 0 AND w2.site_work_name LIKE ?)]
ORDER BY ps.deleted_at DESC|ASC, ps.id DESC
LIMIT ? OFFSET ?
```

计数查询同 WHERE。**作品上下文二段批查**（ELIMINATE_N_PLUS_1：分页行 ≤pageSize，收集 store ID 集一次查挂载链）：

```sql
SELECT rs.store_id, w.id, w.site_work_name, w.site_id, s.site_name, w.deleted_at
FROM resource_store rs
JOIN resource r ON rs.resource_id = r.id
JOIN work w ON r.work_id = w.id
LEFT JOIN site s ON w.site_id = s.id
WHERE rs.store_id IN (分页行 ID 集)
```

Go 侧构建 `map[storeID]上下文` 组装 DTO；`CanRestore` = `BackupID>0 ∧ map 命中 ∧ w.deleted_at=0`（map 命中即挂载存在；防御式再判活，谓词已排除但批查结果独立判定不受列表谓词影响）。

### PurgeStore（store 条目清理，J 的操作面核心）

```go
// PurgeStore 彻底删除文件条目（物理删行 + 按行内 backup_id 消费式删备份）
func (s *Service) PurgeStore(ctx context.Context, storeId int64) error
```

流程：
1. 行校验：含已删查行（`GetByIdUnscoped` 形态），非软删行返回 ErrRecycleItemNotFound。
2. 尽力删 file_path 文件（`os.Remove` 容忍 NotExist，操作前 `storeRegistry.Suppress` 登记——与 persistentStore 各落盘点同款）：正常软删行文件已移 backup/ 或已离场、扑空无害；backup/ 域残迹行（风险6）文件随行清除。
3. 物理删行（`DeleteUnscopedByIds([]{storeId})`，见第五节 persistentStore 新增）。
4. 行内 `backup_id > 0` 时 `DeleteBackup(backupId)`（消费式终态清理，红线3——与 `PurgeWork` 的备份清理义务同款（recycleBin/service.go:229-233）；行删+备份删同拍完成，失败模式=无主备份由治理兜底，与 PurgeWork 同族）。

MarkInvalid 行（backup_id=0）走同一入口：仅物理删行，无备份可清——该类死行由此获得终态。

### RestoreStore 延后（决策5）

版本回滚置换（软删占位活行+复活本行+文件还原+关联重挂）延至 J'：J' 前无可复原对象的例行产道，且关联重挂处置依赖 J' 关联保留设计题裁决（现行唯一关联形态下需 UPDATE resource_store.store_id 改指；J' 双关联形态下对偶替换不动关联）。J 侧 `CanRestore` 状态列照常计算与呈现（数据模型预铺完整，J' 落地即接通操作）。

### TTL 自动清理扩展（决策3：共享保留期）

`runCleanup`（recycleBin/service.go:269）扩为两轮：
1. 现行 work 条目轮：`ListDeletedBefore` → `PurgeWork`（零改动）。
2. 新增 store 条目轮：`ListRecycleStoreIdsDeletedBefore(expireBefore)`（与列表同谓词，**保护 work 条目聚合行不被提前清**——work 已删行被 NOT EXISTS 排除，否则破坏 work 复原能力）→ 逐行 `PurgeStore`。

保留期读同一 `GetRecycleBinSettings()`（决策3 共享）。

## 五、purge 残留产道修复（决策4）

**问题**（声明4）：`DeleteWorkAndSurroundingData` 事务后 `HardDelete(storeId, false)` 对已软删 store 行被 GetById 软删 scope 挡住提前返回 → 行残留成离链孤儿。「彻底删除」名不副实。

**修复**：
1. persistentStore 新增（Repository 接口 + 实现，单条 SQL，BATCH_UPDATE_OPTIMIZATION）：
   ```go
   // DeleteUnscopedByIds 批量物理删行（单条 DELETE IN；purge 链行删除——HardDelete 的 GetById
   // 受软删 scope 保护会跳过已删行，purge 目标行全是软删行故须 Unscoped 直删）
   DeleteUnscopedByIds(ctx context.Context, ids []int64) error
   ```
2. work/service.go `DeleteWorkAndSurroundingData`：事务内（resource_store 级联删除之后）加 `storeDeleter.DeleteUnscopedByIds(storeIds)`（StoreDeleter 接口扩展，声明10）；事务后的 `HardDelete` 循环**移除**（该调用对已删行恒空转——行已在事务内物理删，保留即死代码）。
3. 文件侧无需补删：purge 场景 store 行全为软删（work 软删链保证），原路径文件早已在 backup/，由外层按 backup_id 清备份（recycleBin/service.go:229-233）承担；万一存在活行异常态（work 已删而 store 未软删，构造上不可达），行删后残留文件由 fsmonitor 对账按 Untracked 暴露——不为不可达态加代码。

修复后 purge 链不再产生 store 残留，store 条目持续产道收敛为：MarkInvalid 行（零散）+ J' 例行态（软删化后）。

## 六、J' 预铺与延后项

- **数据模型预铺**（红线1）：store 条目谓词 EXISTS 集合语义兼容 J' 双关联形态；`CanRestore` 含挂载可达判定；TTL 按行自身 deleted_at——J' 落地后新增的软删残留行（替换/merge 场景 `SoftDeleteWithBackup` 产物）自动落入 store 条目、按行 TTL 收尾，无需 J' 再动回收站。
- **延后 J'**（决策5/6）：RestoreStore 操作与关联重挂设计；关联保留消费面审计（ResolvePrimaryStore/recomputeComplete/任务查重按行活性过滤与按 role 去重）。J' 方案落笔时一并收口。
