## 审查摘要

本方案解决「主题切换导致任务状态色互相撞色」的架构问题。根因：状态语义色与主题主色共用同一套色族变量，主题为融入基调把多个色族染成相近色相。解耦方式：新增一套**固定色相**的状态语义 tone 色板（HSL 表达，hue 锁死、S/L 主题微调），所有状态别名改引用它，主题主色不再污染状态语义。

- 风险1：HSL 表达与现有 hex + EP 派生档体系并存，令牌体系认知成本上升；StatusTag 底色观感需对齐原 `*-light-9`（EP 派生档命名，指与白色混合 90% 的浅色底）浅底（HSL `L=90%` 近似但非完全等同，可能略有色差）。
- 风险2：forest 主色 hue≈140（绿）与 done tone hue=120（绿）仍同色域，forest 下"完成"状态标签会融入绿主题（单色融入，非多状态撞色）——符合"主题微调深浅"预期，但若希望 done 在森林下也跳脱则需另选 done 色相（会偏离"绿=完成"的通用认知）。
- 风险3（暖色侧压缩）：fail 红 hue=0、active 橙 hue=30、warn 黄 hue=55、pending 洋红 hue=325 四个暖色 tone 挤在色轮约 90° 弧内（325°→0°→55°），相邻色相差仅 25°~35°；任务列表横向并列不同状态时辨识压力较大（冷色侧仅 done 绿、idle 灰）。S/L 不同可辅助区分，且同一任务不会同时处多态，但色弱用户可能仍难辨——这是交通灯语义体系（红/橙/黄/洋红）的固有压缩，落地后须重点肉眼校准。
- 风险4：tone 的 hue 值由 EP 默认色换算得出，可能与设计偏好存在偏差，首次落地后大概率需要肉眼校准一轮。
- 风险5：迁移步骤1撤销本次注入的 indigo 后，task-created 不可裸回落到 info（会与 task-waiting 重新撞色，正是用户原始痛点），必须直接改指 pending tone；步骤1与步骤3须连续执行，不保留"indigo 已删、task-created 指向已失效变量"的中间态。
- 风险6（source 视觉风格切换）：source-local/source-site 当前经 `--app-tag-*` 用半透明底（rgba），解耦后改用 hue 锁死的 tone 浅底（hsl 实色，L=90%），从"半透明 tag"变为"实色浅底"，与仍用 `--app-tag-*` 的彩色分类标签（MainView/WorkQueryView 的 green/blue/red/purple 标签）产生质感差异。可接受（StatusTag 全类目统一为实色浅底，内部一致），但需知晓。

## 1. 问题与根因

### 1.1 现象与验证口径

任务管理页面状态标签在 default 主题下区分良好，在其他主题下出现混淆。forest 为用户实际报告（进行中与已完成都是绿色、难辨）；ocean/sakura 为据色值推断的潜在风险，须运行实测确认。色相（HSL 的 H，0~360）换算：

| 主题 | 混淆对 | 主色 → hue | 状态色 → hue | hue 差 | 感知 |
|---|---|---|---|---|---|
| forest | 进行中 / 已完成 | primary `#007038` ≈150° | success `#5fa83a` ≈100° | ~50° | 同属绿色域（黄绿 vs 青绿），饱和度/明度相近，肉眼判为"都是绿" |
| ocean | 进行中 / 已完成 | primary `#1ab7c7` ≈186° | success `#3eb58e` ≈160° | ~26° | 青 vs 青绿，邻近 |
| sakura | 进行中 / 失败 | primary `#ec6d8e` ≈344° | danger `#e8637a` ≈350° | ~6° | 粉 vs 红粉，极近 |

**口径澄清**：撞色不能靠单一 hue 阈值判定——forest 的 hue 差高达 50° 却仍被感知为同色（同绿色域 + 相近饱和度/明度），而 sakura hue 差仅 6°。故本方案不设机械 hue 阈值，凡称"撞色/偏近"均指"同色域归属 + 饱和度/明度相近 + 人眼感知"的综合判断，最终以肉眼实测为准。default 主题各状态色相分散（蓝 210 / 绿 120 / 红 0 / 橙 34），不撞。

### 1.2 根因

`task-processing` 复用 `--app-color-primary`（主题主色），`task-completed` 复用 `--app-color-success`。**主题主色的色相由主题决定，不可控**；一旦主题主色色相与某个状态语义色色相重叠（forest 选绿≈success 的绿），两者必然撞色。

这是**"状态语义"与"主题主色"共用同一套色族变量**的架构耦合，非单点色值可修。

## 2. 解耦思路：两条独立轨道

把当前混用的色族拆成职责分离的两条轨道：

- **主题主色轨道 `--app-color-*`**：继续随主题切换（forest 绿、ocean 青、sakura 粉），驱动 EP 组件（按钮/链接/选中态等 UI 装饰）。**这条轨道保持现状不动。**
- **状态语义轨道（新）**：一套**色相固定、跨主题不变**的语义 tone，所有 `--app-status-*` 别名改引用它，主题**不覆盖色相**、仅微调饱和度/明度以融入氛围。

无论什么主题，状态色相稳定可辨；主题只决定页面氛围，不污染状态语义。这是 Material/Ant Design 等设计系统的主流做法（status color 不随品牌色变）。

## 3. 技术方案：HSL 固定色相 tone 体系

用 HSL 色彩空间天然分离色相（H）与饱和度/明度（S/L）：H 锁死保证可辨，S/L 开放给主题微调。

### 3.1 令牌结构（新增于 `tokens.css`）

第一层：**色相常量**（主题不覆盖，固定）：
```
--app-status-hue-active: 30;    /* 进行中·橙 */
--app-status-hue-done: 120;     /* 完成·绿 */
--app-status-hue-fail: 0;       /* 失败·红 */
--app-status-hue-warn: 55;      /* 警示·黄 */
--app-status-hue-pending: 325;  /* 待激活·洋红 */
--app-status-hue-idle: 220;     /* 空闲·灰（靠低饱和实现，色相不参与辨识） */
/* source 类目专属色相（不复用 tone，决策2） */
--app-status-hue-source-local: 170;  /* 本地来源·青绿 */
--app-status-hue-source-site: 275;   /* 站点来源·紫 */
```

第二层：**S/L 基准**（主题可整体覆盖微调）：
```
--app-status-sat-text: 65%;   /* 文字实色饱和度 */
--app-status-sat-soft: 55%;   /* 底色/边框柔和饱和度 */
--app-status-lit-text: 45%;   /* 文字明度 */
--app-status-lit-bg: 90%;     /* 底色明度（浅底，近似原 light-9） */
--app-status-lit-border: 84%; /* 边框明度 */
--app-status-sat-idle: 8%;    /* idle 灰专用低饱和 */
```

第三层：**tone 三分量**（hue + S/L 组合，每 tone 三个变量 bg/text/border）：
```
--app-status-active-text: hsl(var(--app-status-hue-active) var(--app-status-sat-text) var(--app-status-lit-text));
--app-status-active-bg:   hsl(var(--app-status-hue-active) var(--app-status-sat-soft) var(--app-status-lit-bg));
--app-status-active-border: hsl(var(--app-status-hue-active) var(--app-status-sat-soft) var(--app-status-lit-border));
/* done / fail / warn / pending 同理；idle 用 --app-status-sat-idle */
```

> 语法说明：现代 CSS `hsl(H S L)` 空格分隔形式，WebView2（Chromium）与 WebKit 均支持，无需相对颜色（`hsl(from …)`）等新特性。

### 3.2 别名改引用

`--app-status-{类目}-{语义}-{bg|text|border}` 别名从引用 `--app-color-*` 改为引用对应 tone，例如：
```
--app-status-task-processing-bg:   var(--app-status-active-bg);
--app-status-task-completed-bg:    var(--app-status-done-bg);
--app-status-task-failed-bg:       var(--app-status-fail-bg);
```
StatusTag 仍按 `var(--app-status-${status}-bg)` 消费（声明1），组件无感。

## 4. 色相选择与类目映射

### 4.1 6 个 tone 的色相选择

色相采用**交通灯语义体系**（红停/橙行/黄注意/绿完成），由用户拍板；done/fail/idle 为给定值，active/warn/pending 的橙/黄/洋红 hue 为建议值：

| tone | hue | 服务语义 |
|---|---|---|
| active | 30（橙） | 进行中、活跃 |
| done | 120（绿） | 完成、成功、启用 |
| fail | 0（红） | 失败、错误、损坏 |
| warn | 55（黄） | 警示、过渡、部分完成、缺失 |
| pending | 325（洋红） | 待激活（已创建） |
| idle | 220 + 低饱和（灰） | 空闲、等待、暂停、禁用 |
| source-local（专属） | 170（青绿） | 本地来源 |
| source-site（专属） | 275（紫） | 站点来源 |

### 4.2 17 个状态 → tone 映射

语义归类完全继承现状，仅替换色源：

| 类目 | 状态 | tone |
|---|---|---|
| task | created（已创建） | pending（洋红） |
| task | processing（进行中） | active（橙） |
| task | waiting（等待中） | idle（灰） |
| task | paused（已暂停） | idle（灰） |
| task | pausing / stopping（暂停中/停止中） | warn（黄） |
| task | completed（完成） | done（绿） |
| task | partly-finished（部分完成） | warn（黄） |
| task | failed（失败） | fail（红） |
| task | waiting-input（等待确认） | warn（黄） |
| source | local（本地） | source-local 专属（青绿 hue=170） |
| source | site（站点） | source-site 专属（紫 hue=275） |
| toggle | enabled（启用） | done（绿） |
| toggle | disabled（禁用） | idle（灰） |
| resource | downloaded（已下载） | done（绿） |
| resource | missing（缺失） | warn（黄） |
| resource | damaged（损坏） | fail（红） |

## 5. 主题微调（S/L）

主题只覆盖第二层 S/L 基准（3~4 个变量），所有 tone 自动「同色相、调深浅」跟随，无需逐 tone 重算：

| 主题 | 建议微调 | 效果 |
|---|---|---|
| default-light | 不覆盖（用基准） | 标准状态色 |
| forest-light | sat 降至 ~55%/48%、lit-text 降至 ~40% | 整体调沉，融入深绿基调 |
| ocean-light | sat 降至 ~60%、lit-text ~42% | 偏清冷 |
| sakura-light | sat 降至 ~58%、lit-text ~45% | 偏柔和 |

> 建议值须运行后肉眼校准（决策3）。

## 8. 待决策与风险详述

见审查摘要的「待决策」「自曝风险」。补充几点：

- **风险2**（forest 下 done 绿融入绿主题）是「主题微调深浅」方案的固有代价——状态间可辨（绿/红/橙/黄/洋红互相区分）已达成，单色与主题主色同域属预期；若不可接受，唯一出路是 done 改非绿色相，但会破坏「绿=完成」的通用认知，不建议。
- **决策4**（EP 组件色与 StatusTag 业务色分家）：解耦后 forest 下 EP 的 success 按钮（随主题深绿）与 StatusTag「完成」（固定 hue 绿）会是两种绿。这是"状态语义固定、主题主色随主题"的必然结果——EP 组件属 UI 装饰应随主题，业务状态色应稳定，分家合理；若强求两者一致则解耦不成立。**例外（后续演进）**：破坏性操作按钮（`type="danger"` + `tone-fail`）为与危险状态语义同源、统一随主题调色，改走 fail tone 轨道（见顶部演进 note），其余 EP 按钮仍遵循本分家。
- **风险5**（task-created 回落）：步骤1 删 indigo 与步骤3 改指 pending 须连续执行，禁止出现"indigo 已删、task-created 裸指失效变量"或"回落 info 与 waiting 重新撞色"的中间态。
