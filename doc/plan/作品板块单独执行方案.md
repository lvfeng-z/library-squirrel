# 作品板块单独执行方案

## Context

当前任务执行入口 `ManagedTask.run()`（`backend/taskManager/model.go:285`）是一条不可拆分的整体流水线：查重 → 拉作品元数据 → 保存作品信息 → 打开下载流 → 建资源记录 → 写文件 → 取封面。用户无法对**已存在作品**单独重做某个方面：

- 作品元数据过期或上次拉取不全 → 单独**重新下载作品信息**（板块 A）
- 封面损坏或当时未生成 → 单独**重新下载封面**（板块 C）
- 资源文件损坏或不完整 → 单独**重新下载资源文件**（板块 B）

**目标**：把作品执行流程拆成三个可独立调度的板块。用户选定一个任务记录（同一作品可能有多个关联任务，由用户自行选择），**以此作为一次与原始下载任务执行等价的操作**，复用任务模块的现有执行管线完成该板块的单独执行。

## 关键约束与本方案的覆盖

| 约束 | 内容 | 本方案如何覆盖 |
|------|------|---------------|
| 1. 需从作品定位到任务记录 | 执行所需的 `PluginPublicID/PluginContributionID/PluginData/URL` 在 `entity.Task`（`backend/base/model/entity/task.go:21`），不在 work | 复用 work 与 task 既有的 `(site_id, site_work_id)` 复合业务键关联（查重即用此键，`model.go:327`），前端列出关联任务供用户选定具体 taskId；执行直接以该 taskId 发起，无需后端选取策略 |
| 2. saveThumbnail 耦合下载流 | `saveThumbnail` 用 `task.PendingResourceID` 定位 Resource（`model.go:1050`），下载完成后该字段被清空（`model.go:565`） | 改造为按 workId → `Resource.WorkID` 定位，与下载流解耦 |
| 3. 资源覆盖需备份还原 | 重新下载资源文件会覆盖磁盘文件，需备份 + 失败还原 | 板块 B 复用 `StoreBackupOrchestrator`（`model.go:344` + `run()` defer 还原） |
| 4. 步骤间状态耦合 | `run()` 步骤读 `ManagedTask` 实例字段，无法脱离完整流程单独调用 | 引入 `runMode`，`run()` 内部按模式分流到不同板块；模式分流即步骤解耦 |

## 设计原则

1. **唯二执行入口**：所有任务执行只经"开始"和"恢复"两个入口，二者均改造为**支持多根**。完整下载、重试、板块 A/B/C 执行全部统一为 `taskIds + runMode` 走这两个入口，无任何专用调度路径。

2. **等价于原始任务执行**：板块执行不是寄生在源任务上的特殊操作，而是**一次任务执行**——通过唯二入口，依据用户选定的任务记录**新建 `ManagedTask`**，走与原始下载任务完全相同的调度/状态机/cleanup 管线，用 `runMode` 区分行为。输入即 taskId，与 `StartTaskTree`/`RetryTaskTree` 同构。不另建轻量同步路径、不引入虚拟父任务。

3. **依据任务记录执行，不新建任务行**：板块执行依据用户选定的任务记录，不向 task 表插入新记录。该任务记录上次执行完已被 `cleanupFinishedTask` 移出 `taskMap`，板块执行时新建 `ManagedTask`（以该 taskId）执行本次操作，完成后照常移除——与普通任务执行新建 `ManagedTask` 完全等价。

4. **A/C 为非终态操作，B 为终态操作**：更新作品元数据（A）或封面（C）不改变作品的下载完成状态，因此 A/C 执行**不产生任务终态**——任务在执行期间处于瞬态 Processing，结束后保持执行前状态、不写库。板块 B（重新下载资源文件）等价于原始下载执行，产生终态（Finished/Failed）并持久化。

5. **内存树结构正确**：多根入口按传入 taskId 的 DB 真实父子关系构建内存树，同 `pid` 归同一真实 `ParentTask`，`pid=0` 为独立任务。不发明虚拟聚合节点。

6. **任务由用户选定**：同一作品可能关联多个任务记录，由用户在前端自行选择执行依据，后端不做任何自动选取。

7. **板块隔离**：各板块只备份和操作自身负责的 Store，互不影响——A 不动文件；B 只动资源文件并保留旧缩略图；C 只动缩略图并保留资源。详见 §5.3。

## 总体架构

```
前端：作品 → 经 (site_id, site_work_id) 列出关联任务 → 用户选定 taskId(s)
                                                              │
                                                              ▼
┌──────────── 唯二执行入口（均支持多根）────────────┐
│  开始入口 startTaskTrees(taskIds, opts)          │
│    opts.runMode ∈ {Full, ResourceOnly,           │
│                     WorkInfo, Thumbnail}         │
│  恢复入口 resumeTaskTrees(taskIds, opts)         │
└──────────────────────────────────────────────────┘
        │
        ├─ 按 DB 真实 pid 分组：同 pid → 同一 ParentTask；pid=0 → 独立
        ├─ 共享一次 ListTaskTree 查询 + 一次批量查重 + 批量调度
        └─ 为每个任务记录新建 ManagedTask（注入 runMode）→ run() 分流：
              Full         → 完整流程（现有）
              ResourceOnly → 板块 B：跳过查重+作品信息，从 Start 开始（终态，持久化）
              WorkInfo     → 板块 A：CreateWorkInfo + SaveWorkInfo（非终态）
              Thumbnail    → 板块 C：saveThumbnail 改造版（非终态）

ConfirmReplace / ConfirmReplaceBatch 作为例外，保留现有实现（操作内存 waitingForInputMap，不经过两入口）
```

## 详细设计

### 1. work → task 关联（复用既有键，不改表）

work 与 task 通过 `(site_id, site_work_id)` 复合业务键关联，两表均有这两个字段（`work` 表该键为联合唯一索引 `idx_work_site_site_work`）。任务执行前的查重（`model.go:327` `WorkChecker.GetBySiteAndSiteWorkID`）即沿此键从 task 侧查 work。本方案沿同一键**反向**使用：从 work 侧列出关联的任务记录，供用户选择。

**无需修改 work 表、无需迁移。**

task 表对该键无唯一约束，同一作品可能匹配多条任务记录——全部列出，由用户选定，后端不选取。

### 2. 唯二执行入口（多根改造）

现有 `loadAndStartTaskTree`（`manager.go:114`）是单根：以单个 taskId 为根、靠 DB Pid 关联子任务、`ParentTask.id = actualParentId`。改造为多根：

```go
type startOpts struct {
    skipTerminal bool
    runMode      runMode // Full / ResourceOnly / WorkInfo / Thumbnail
}

// 开始入口（覆盖 Start / Retry / 板块执行）
func (m *Manager) startTaskTrees(ctx context.Context, taskIds []int64, opts startOpts) error {
    tasks, err := m.repo.ListTaskTree(ctx, taskIds) // SQL 已支持 []int64（repository.go:247）

    // 按 DB 真实父子关系分组构建（核心：内存树结构正确）
    //   - 传入 taskId 为独立任务（pid=0, has_child=0）→ 独立 ManagedTask（parentId=0）
    //   - 传入 taskId 为父任务（has_child=1）→ ParentTask + 其 Pid==id 的子任务
    //   - 传入 taskId 为叶子（pid>0）→ 归到其真实 pid 的 ParentTask
    //   - 同 pid 的多个入口 taskId 共享同一个 ParentTask（去重）
    // 为每个任务记录新建 ManagedTask，注入 opts.runMode
    // 共享一次 batchCheckDuplicates（A/C runMode 跳过查重）
    // 跨根批量 tryDispatch
}
```

恢复入口 `resumeTaskTrees(taskIds, opts)` 同理，`skipTerminal=true`。

**多根构建依赖 `ListTaskTree` 的 SQL 特性**（`repository.go:247`）：传入多个 id 时，`children`（has_child=0）回溯各自 pid，`parent`（has_child=1）展开各自子任务。返回的任务集合足以按真实 pid 分组。该 SQL 非 `WITH RECURSIVE`，仅回溯/展开一层，但配合"入口 taskId 既是叶子可回溯父、既是父可展开子"已覆盖现有任务结构（父→子一层）。

**改造方式（最小侵入）**：把现有单根判定（standalone / leaf / parent + 收 `Pid==actualParentId` 子任务）抽取为按 taskId 可复用的处理逻辑，外层对多根循环调用，仅共享 `ListTaskTree` 查询和 `batchCheckDuplicates`。

**重复执行保护**：入口在为某 taskId 新建 `ManagedTask` 前，需检查 `taskMap` 中是否已有该 taskId 的运行实例；若存在则拒绝（或按业务排队）。这是任务执行管线的固有约束，对普通任务执行和板块执行同等适用（当前 `addTask` 是 map 覆盖，需补存在性检查）。

### 3. runMode 与 run() 分流

```go
type runMode int
const (
    runModeFull         runMode = iota // 完整下载（现有）
    runModeResourceOnly                // 板块 B
    runModeWorkInfo                    // 板块 A
    runModeThumbnail                   // 板块 C
)
```

`ManagedTask` 新增 `runMode runMode` 字段。`run()`（`model.go:285`）入口按模式分流：

| runMode | 0.0 查重 | 0.1 备份 | 1 CreateWorkInfo | 2 SaveWorkInfo | 3~8 资源下载 | 终态性质 |
|---------|:---:|:---:|:---:|:---:|:---:|------|
| Full | 执行 | 替换场景 | 执行 | 执行 | 执行 | 终态，持久化（现有） |
| ResourceOnly | 跳过 | 仅 Work（isReplace=true，`BackupStores(Work)`） | 跳过 | 跳过 | 执行（仅 Work：`saveResource` 不清缩略图、`downloadLoop` 跳过 saveThumbnail，见 §5.3） | 终态，持久化（B 是真实下载） |
| WorkInfo | 跳过 | 不需要 | 执行 | 执行（upsert） | 跳过 | **非终态**，任务保持执行前状态 |
| Thumbnail | 跳过 | 不需要 | 跳过 | 跳过 | 跳过（仅 saveThumbnailByWorkId） | **非终态**，任务保持执行前状态 |

**workId 的获取**：Full/WorkInfo 模式由 `SaveWorkInfo` 返回 workId（现有流程）；ResourceOnly/Thumbnail 模式跳过 `SaveWorkInfo`，由任务记录的 `(site_id, site_work_id)` 经 `WorkChecker.GetBySiteAndSiteWorkID`（`model.go:327` 已有依赖）查出 workId。板块 B 用该 workId 走 `saveResource` 替换分支（`model.go:446`），板块 C 用该 workId 走 `saveThumbnailByWorkId`。

### 4. 状态机调整（A/C 非终态操作）

板块执行通过唯二入口新建 `ManagedTask` 执行，走与原始下载任务完全相同的状态机管线。A/C 与 B 的区别仅在于终态性质：

**A/C 为非终态操作**：更新元数据/封面不改变作品的下载完成状态，执行不产生任务终态：

- **执行期间**：任务进入瞬态 Processing（瞬态本就不持久化，现有机制仅稳定态 `addToPending`，见 `manager.go:975`）。
- **执行结束（成功/失败均然）**：任务不落入 Finished/Failed 终态，保持执行前状态。`onStateChange` 内对 A/C runMode 跳过 `addToPending`，全程不写库。
- **失败处理**：A/C 失败**不走 `setFailed`**（避免落入 Failed 终态），仅记录错误信息并推送失败通知；任务状态保持执行前。成败一视同仁——都不产生终态，无需单独定义"失败语义"。

**板块 B 为终态操作**：资源文件重新下载等价于原始下载执行，走完整终态流转——成功 `setState(Finished)`、失败 `setState(Failed)` + 备份还原（`model.go:288` defer），均持久化。

**cleanup**：所有板块执行结束后（A/C 保持执行前状态 / B 进入终态），由 `executeTask` 走标准 `cleanupFinishedTask`（`manager.go:801`）。A/C 作为根（parentId=0）→ 从 `taskMap` 移除实例 + `PushTaskRemove` 通知前端移除卡片。这是任务执行完成的固有行为，无特殊处理。前端表现为：板块执行期间任务卡片短暂可见（Processing），结束（成功/失败）后移除。

**A/C runMode 的状态变更实现**：现有 `setState`（`model.go:820`）→ `onStateChange`（`manager.go:975`）对稳定态调 `addToPending`。A/C 需零写库，故在 `onStateChange` 内按 `mt.runMode` 判断：A/C runMode 一律跳过 `addToPending`（但仍推送前端状态变化，让前端可见 Processing）；A/C 失败路径不调 `setFailed`，改用只记录错误 + 推送通知、不改状态的路径。

### 5. saveThumbnail 改造（约束 2）

#### 5.1 定位：PendingResourceID → workId

`saveThumbnail`（`model.go:1043`）改造为按 workId 查 Resource（走已有 `Resource.WorkID` 关联）：

```go
// 板块 C 直接调用；下载完成路径（Full/ResourceOnly）也可复用
func (m *ManagedTask) saveThumbnailByWorkId(ctx context.Context, workId int64, force bool) error {
    resources, err := m.deps.ResourceReader.GetEnabledByWorkId(ctx, workId)
    if err != nil || len(resources) == 0 {
        return err
    }
    return m.doSaveThumbnail(ctx, m.task, resources[0], force)
}
```

`downloadLoop` 完成路径（`model.go:563`）改为 `saveThumbnailByWorkId(ctx, m.workId, force=false)`，行为不变（不覆盖已有缩略图）。

#### 5.2 覆盖语义：板块 C 强制覆盖 + 备份还原

当前 `resource.ThumbnailStoreID.Valid` 时直接 return（`model.go:1056`）。重新下载封面必须覆盖旧缩略图，且**必须走备份-还原机制**（与板块 B / Full 替换一致），避免新缩略图下载失败时旧封面永久丢失：

- **备份**：旧 ThumbnailStore 经备份机制移到 `workdir/backup/` + 建 Backup 记录（而非直接删除）。
- **下载新缩略图** → 更新 `Resource.ThumbnailStoreID`。
- **失败还原**：从 backup 移回旧缩略图 + 重建 PersistentStore + 恢复 `Resource.ThumbnailStoreID`。

为支持按单 Store 类型备份/还原（C 仅 Thumbnail，不应像 Full 那样全量备份把资源文件也移走再搬回），`StoreBackupOrchestrator`（`model.go:147`）扩展按 StoreType 的方法：

```go
type StoreBackupOrchestrator interface {
    BackupAllStores(ctx context.Context, workId int64) []*StoreBackupItem                         // 现有：全量（Work + Thumbnail）
    BackupStores(ctx context.Context, workId int64, types ...backup.StoreType) []*StoreBackupItem // 新增：按类型
    RestoreAllStores(ctx context.Context, items []*StoreBackupItem)                               // 现有：部分还原（BackupID>0）
}
```

`doSaveThumbnail(force=true)` 内部包"备份 → 下载 → 失败还原"逻辑（仿 `run()` defer 模式，panic/error 时还原）；板块 C 用 `BackupStores(workId, backup.StoreTypeThumbnail)` 备份。TaskDeps 无需新增依赖（`StoreBackupOrchestrator` 已在 `TaskDeps`，`model.go:197`）。

#### 5.3 备份范围在板块拆分下的归属（板块隔离）

**原则：各板块只备份/操作自身负责的 Store，互不影响。** 原始 Full 替换流程的 `BackupAllStores` 一次性备份 Work + Thumbnail（因 `run()` 下载资源后经 `saveResource` 替换分支清除 `ThumbnailStoreID` → `saveThumbnail` 重新生成）。板块拆分后各板块收敛到只备份自己的 Store：

| 板块 | 覆盖范围 | 备份 | 失败还原 |
|------|---------|------|---------|
| A 作品信息 | 无文件 | 无 | 无 |
| B 资源文件 | 仅 Work（保留旧缩略图） | `BackupStores(Work)` | `RestoreAllStores`（Work 项） |
| C 封面 | 仅 Thumbnail | `BackupStores(Thumbnail)` | `RestoreAllStores`（Thumbnail 项） |
| Full（完整下载） | Work + Thumbnail | `BackupAllStores`（全量，现有） | `RestoreAllStores`（全量） |

**B 的隔离实现**：B（ResourceOnly）只重新下载资源文件，不触及缩略图——

- `saveResource` 替换分支**不清除 `ThumbnailStoreID`**（区别于 Full 替换的清除行为，`model.go:475` 按 runMode 判断），保留旧缩略图引用。
- `downloadLoop` 完成时**按 runMode 跳过 `saveThumbnail`**（`model.go:563`），不重新生成缩略图。
- 备份仅 Work（`BackupStores(Work)`），失败仅还原 Work；缩略图全程不受 B 影响。

由此 B 和 C 都用按类型备份（`BackupStores`），各自只备份自己的 Store；只有 Full 用全量 `BackupAllStores`。`RestoreAllStores` 已支持部分还原（按传入的 `storeBackupItems` 条目），B/C 各传入自身类型的备份项即可。

#### 6.3 并发互斥

任务执行管线以 taskId 为 key 管理 `taskMap`。板块执行与普通任务执行一样遵循"同一 taskId 不重复执行"的固有约束（见 §2 重复执行保护）：若某 taskId 已有运行中的 `ManagedTask`，新的执行请求被拒绝或排队。板块执行不引入额外并发规则，也不需要为 A/C 的插件/站点请求并发额外设闸——进入状态机即受信号量 `m.semaphore` 约束。

## 注意点与风险

1. **板块 A 的"全量替换"语义**：板块 A 沿用 `SaveWorkInfo` 的全量替换（`DeleteByWorkId` 后重建作者/标签关联，`work/service.go:749`），会清掉用户在 UI 手动添加的本地作者/标签。本方案**保持全量覆盖**，并**保留合并模式作为后续增强 TODO**（`work/service.go:739` 已有 TODO）。

2. **板块 C 必须强制覆盖**：见 §5.2，否则 `saveThumbnail` 永远跳过已有缩略图。

3. **任务记录信息时效性（插件契约层面）**：用户选定的任务记录存的是创建时刻的 `PluginData`/`URL`。重新执行时插件能否凭过期值再次拉流/取封面（带时效 token、已失效 URL），取决于各插件实现。架构层已尽力（沿既有键确定性列出任务供用户选），剩余属插件契约。建议插件契约约定：`CreateWorkInfo`/`GetThumbnail`/`Start` 需能基于持久化的 task 上下文重放。

4. **多任务记录由用户选定**：同一 `(site_id, site_work_id)` 可能匹配多条任务记录。后端不做选取，全部列出由用户选择；用户若选错（如选了 `PluginData`/`URL` 已失效的旧任务），板块执行会失败，需重新选择。前端列表应展示足够信息（创建时间、状态）帮助辨识。

5. **多根构建的分组正确性**：多根入口必须严格按 DB 真实 pid 分组，同父叶子归同一 `ParentTask`、去重。若分组错误会导致内存树与 DB 不一致、进度聚合错乱。实施时需针对"同父多叶子""混合根""独立+父子混合"补充测试。

6. **A/C 卡片短暂可见**：A/C 执行期间任务卡片在任务列表短暂出现（Processing），结束（成功/失败）后移除。此为接入状态机的必然呈现，与板块 B 一致。

## 不涉及的部分

- **板块 B 的下载/暂停/恢复/崩溃恢复内部机制**不变，仅新增"从资源步骤开始"的 runMode
- **`resumeFromPersistedState`**（跨重启续传）不变
- **前端任务进度推送协议**不变（板块执行复用现有推送）

1. **多根入口改造**：`loadAndStartTaskTree` 抽取单根处理逻辑 → 外层多根化 + 共享查询/查重 → `startTaskTrees`/`resumeTaskTrees`；补"taskId 已有运行实例"的重复执行保护

## 验证方式

1. `task dev` 启动应用
2. **关联任务列举**：对一个有多条关联任务记录的作品，调用 `ListTasksBySiteAndSiteWorkID`，验证返回全部关联任务（含创建时间/状态），用户可据此选择
3. **多根构建**：批量传入多个 taskId（含同父叶子、跨父叶子、混合独立+父子），验证内存树结构与 DB 真实关系一致、同父聚合 N/M 正确
4. **重复执行保护**：对同一 taskId 连续发起两次执行，验证第二次被拒绝/排队而非覆盖
5. **板块 A**：选定任务执行"重新下载作品信息"，验证元数据更新（覆盖语义下手动改动被替换）、任务终态不变（零写库）、任务卡片执行后移除
6. **板块 C**：无封面作品生成缩略图；已有封面作品旧缩略图被替换（验证 §5.2 强制覆盖）；模拟封面下载失败，验证旧缩略图从备份还原、资源文件未被搬运
7. **板块 B**：对已完成作品重新下载资源 → 任务 Processing → 旧文件备份（查 `workdir/backup/`）→ 完成 Finished；中途暂停/恢复/停止验证控制流；失败时验证备份还原
8. **并发约束**：批量板块执行受信号量控制，不冲击插件/站点
9. **用户选择**：同一作品多条关联任务时，验证用户可选定其中任一执行；选定过期任务导致失败时，验证可重新选择
10. **A/C 非终态**：板块 A/C 执行成功与失败，验证任务终态均不变（零写库）、失败仅推送失败通知、任务卡片移除；板块 B 执行成功落 Finished、失败落 Failed 并持久化
11. `go vet ./backend/taskManager/...`、`go vet ./backend/task/...`、`go vet ./backend/work/...` 无警告
