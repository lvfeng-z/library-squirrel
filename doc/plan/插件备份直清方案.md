# 插件备份直清方案（plugin 侧引用终态清理）

## 审查摘要

**关键声明（抽查项）**：

- 声明1：`installCore`（安装核心，所有安装/重装/升级形态共用）在重装路径上以 `Save` 全字段覆盖复用行（旧 BackupID 此刻落 NULL）→ `CreateBackup` 建新备份 → `Updates` 写新 BackupID——**旧备份在重装瞬间即失引用变无主**。锚点：`backend/plugin/service.go:519-541`。
- 声明2：所有重装形态共用 installCore——`Reinstall`（`backend/plugin/service.go:579`）、`ReinstallFromPath`（`service.go:616`）、`InstallBundled` 的三个 installCore 入口（`service.go:389` 强制重装、`service.go:415` 静默升级重装、`service.go:436` 全新安装兜底——对已卸载 existing 行经 `service.go:470-475` 等效复用重装）、`ApplyPendingUpgrade`（`backend/plugin/upgrade.go:135` 经 ReinstallFromPath）、`InstallFromPath` 对已卸载行的复用（`service.go:470-475`）。
- 声明3：**「自动修复」的安装源就是行内 BackupID 指向的备份文件**（`Reinstall` 直查备份取路径后以该文件为源走 `ReinstallFromPath`，`backend/plugin/service.go:588-612`）；「选择安装包修复」分支由用户提供本地包、升级（ApplyPendingUpgrade）用捆绑 zip——均不用备份。
- 声明4：治理兜底已就位——无主备份超保留期（默认 7 天）由正向对账删除（`backend/backupGovernance/service.go:294-317`，启动即跑+24h 巡检 `service.go:116-128`）；备份管理页另有无主可视化（分页与引用态标注 `backend/backupGovernance/manage.go:20-65`）与手动清理（`manage.go:71-95`）。
- 声明5：卸载语义现状——`uninstall` = 停运行时+删插件文件+标记 `Uninstalled=true`（`backend/plugin/service.go:699-724`，停用链 `backend/plugin/lifecycle.go:48-67`），**行与 BackupID 均保留**；治理引用集含已卸载行（`backend/plugin/repository.go:56-65`）；监视哨 90 天只 Warn 不清（`backend/backupGovernance/service.go:230-246`）。
- 声明6：**plugin 行物理删通路现状为零**——`Service.Delete`（`backend/plugin/service.go:211-213`）存在但 Handler 未暴露；`Handler.SetUninstalled`（`backend/plugin/handler.go:110-112`）仅被 wrapper `pluginDelete` 调用而该 wrapper 全项目无调用方（死链）；`pluginSave`/`pluginUpdate`（`frontend/src/apis/http/wrappers/plugin.ts:19-26`）同样无调用方。
- 声明7：已卸载行在 UI 完全不可见——`Service.Page` 默认过滤已卸载（`backend/plugin/service.go:216-227`），管理页无 uninstalled 查询入口（`frontend/src/views/PluginManage.vue` 全文无 uninstalled 参数）。
- 声明8：**bundled 已卸载行重启自动重装**——`InstallBundled`（pre-Run 检测入口）对已卸载行不进升级判定分支、直接 `installCore(reinstall=false)`（`backend/plugin/service.go:383` 条件不满足已卸载行 → `service.go:436`），后者对已卸载 existing 复用行重装并重置 Uninstalled（`service.go:470-475`）——重装源是捆绑 zip（`resources/bundled-plugins/`），**不依赖备份**。
- 声明9：`backup.Service.DeleteBackup`（删磁盘文件+清单行，文件缺失容忍）现成可用（`backend/backup/service.go:196-210`；recycleBin 消费式先例接口 `backend/recycleBin/service.go:57-66`）；plugin 侧 `BackupProvider` 接口现只有 `CreateBackup`/`GetById`（`backend/plugin/service.go:99-104`），增补 `DeleteBackup` 后 `backup.Service` 零改动适配（装配处 `app.go:979` 直接传 `app.BackupService`）。
- 声明10：`plugin_storage`（插件自存 KV，含用户设置）按 `plugin_id` 挂行（`backend/plugin/plugin_storage_repository.go:23-54`）；重装复用行时行 ID 不变，storage 自然延续（本方案不删行，storage 永不动）。
- 声明11：备份管理页的有主守卫与治理对账共用同源引用集 `collectReferencedStrict`（`backend/backupGovernance/manage.go:164-181`，枚举 `ListReferencedBackupIDs`）——plugin 行清列后引用集自然收缩、守卫自动解除，**备份管理页与治理均零改动**。
- 声明12：dev 库 `plugin` 表 4 行全部 `uninstalled=0` 且 backup_id 均有效指向（可复现：`sqlite3 database/database.db "SELECT id,public_id,uninstalled,backup_id FROM plugin"`）——**无历史已卸载行，无存量迁移需求**；项目未发布，不写迁移代码。
- 声明13：GORM 结构体 `Updates` 跳零值字段；清 NULL 列的既有确定形态是显式列更新（治理悬空清列先例 `Update("backup_id", nil)`，`backend/plugin/repository.go:68-75`）——卸载清列采用同形态（map Updates，零值安全）。

**待决策（需用户拍板）**：无——四项岔路已由用户 2026-08-22 裁决（记录见第三节裁决记录）。

**自曝风险**：

- 风险1：**第三方插件卸载后失去备份重装源**——卸载即清备份，此后重装须用户自备原安装包（「自动修复」对该行报 `ErrBackupNotFound`，`service.go:588-590`）；bundled 插件不受影响（重启自动重装用捆绑 zip，声明8）。用户裁决明示接受（备份只用作自动修复）。
- 风险2：**换代清旧备份后无法回退旧版本**——旧版本安装包随换代直清，回退须自备旧包。与风险1 同源，用户裁决接受。
- 风险3：installCore 失败窗口（`Save` 落 NULL 后 `CreateBackup` 前失败）留「行内无引用+旧备份无主」形态——**系现状既有**（Save 全字段覆盖早已存在，`service.go:519-523`），本次不引入不恶化；新增加的删除动作只发生在成功路径，失败路径不补偿（治理保留期兜底）。
- 风险4：plugin 模块既有测试的 fake BackupProvider 须同步补 `DeleteBackup` 方法，否则编译失败（影响面：`plugin_bundled_upgrade_test.go` 等，实施时按编译报错清单补齐）。
- 风险5：注释与文档同步面——`ListReferencedBackupIds` 的「含已卸载行——卸载行持有重装能力引用，合法有主」注释（`repository.go:56-57`）与 app.go 装配处「含已卸载行引用」注释（`app.go:1008`）在本方案后语义过时（卸载即清列，已卸载行不再持有引用），须同步改写，防误导后来者。
- 风险6：卸载链是「标记成功才清备份」的顺序依赖——若清列 map Updates 成功而 DeleteBackup 失败（磁盘错误），留无主备份（Warn+治理兜底）；若清列本身失败，卸载整体报错（备份保留、行未标记，用户可重试）——两个失败出口的行为差异须测试锚定。
- 风险7：**卸载与换版/修复的并发竞态**——uninstall（捕获旧 BackupID → 清列 → DeleteBackup）与重装链（installCore 覆写新 BackupID）之间无服务端互斥。不加行级锁（用户节奏操作、前端按钮串行），处置分两层：①清列 UPDATE 带 `AND backup_id = ?旧ID` 条件（CAS 形态）——若重装已并发写入新引用，条件不中（0 行受影响）即报错引导重试，**防清列抹掉新引用**；②文件级交错（DeleteBackup 删文件时并发重装链正读该文件）终态有界——至多一次失败的重装尝试或一份无主备份（治理兜底），无半损库态。

## 一、背景与范围

本方案属任务派生谱系（`.claude/workflow` 派生图）中「发起方直清补齐」分支（2026-08-21 裁决收窄为仅 plugin 侧三项）。上游的「backup 无主治理」任务建立了「引用方枚举 + 双向对账 + 终态清理义务」体系：`backend.md` MODULE_BOUNDARY_PURITY 规定——凡业务行内嵌 `backup_id` 引用保管清单行的模块，登记进 `app.go` 装配处引用方枚举时，**必须自带终态清理路径**，否则引用永不释放、备份永不清（监视哨按引用年龄暴露）。

persistentStore 方的终态路径已齐（回收站复原消费式删备份、purge 物理删联动、回收站 TTL）；plugin 方的终态路径缺失——引用的两类长寿命形态均无出口：换版后被覆盖的旧备份（只能等治理保留期）、已卸载行的备份（引用永不释放、监视哨只 Warn）。

### 2.2 两类长寿命引用的缺口

**换版链**：每次重装（升级/修复/对已卸载行重装）经 installCore 复用行覆盖，行内 BackupID 指向新备份，旧备份即时失引用变无主——只能等治理保留期（默认 7 天）清理。现状膨胀有界但存在；本方案改为换代直清。

**卸载链**：`Uninstall` → `deactivate`（停运行时+删插件文件）→ 标记 `Uninstalled=true`，行与 BackupID 保留。缺口：已卸载行 UI 不可见（声明7）、引用永不释放、备份永不入无主集、监视哨只 Warn。本方案改为卸载即清引用+清备份。

### 2.3 备份的真实用途（用户裁决的依据，已核验）

备份的唯一运行期消费方是「自动修复」（Reinstall，声明3）。升级用捆绑 zip、新装/选择包修复用用户提供路径、bundled 已卸载行重启重装用捆绑 zip（声明8）——**均不依赖备份**。因此备份的生命周期可以收紧到「当前安装版本的存在期间」：换版本即旧备份无用、卸载即备份无用。

## 三、设计

### 3.1 裁决记录（用户 2026-08-22）

1. **plugin 行永不物理删**——卸载仅标记，行只增不减的负担可接受（不删行的附带红利：重装复用行时 `plugin_storage` 按 ID 延续，设置不丢）。原设想的物理删行通路、已卸载行查询开关、彻底删除按钮全部**不做**。
2. **备份只用作自动修复**（已核验为现状唯一用途，声明3/2.3 节），因此**卸载或更新换代后备份即可删**——两条链各内嵌直清。
3. **死链删除**（决策4 原项，用户确认）。
4. 2026-08-21 收窄裁决注记「膨胀由治理保留期兜底」由本方案升级为直清+兜底双层（直清为主、治理兜底失败窗口）。

### 3.2 卸载链：清引用 + 清备份

`uninstall()`（`backend/plugin/service.go:699-724`）改造，标记与清列合成一条 SQL：

1. 现有 `deactivate`（停运行时+删插件文件，参与者否决链）不变；
2. 标记步骤改为仓储单条更新：`UPDATE plugin SET uninstalled = 1, backup_id = NULL WHERE public_id = ? AND backup_id = ?旧ID`（map Updates 形态，零值安全——声明13；`AND backup_id` 条件为 CAS 守卫，防并发重装写入的新引用被抹掉——风险7；0 行受影响时报错「插件状态已变化，请重试」）；
3. 标记成功后 → `backupProvider.DeleteBackup(ctx, 旧ID)`（删磁盘文件+清单行）；**失败仅 Warn**（此时引用已清，残留备份即无主，治理保留期兜底）——风险6 的两个失败出口：标记失败则卸载整体报错可重试（备份未动），删备份失败仅留无主文件；
4. `removePending`（内存更新待办清理函数，卸载时清残留可操作项）不变。

卸载后的重装通路自洽性：已卸载行 UI 不可见无「自动修复」入口；bundled 行重启自动重装（捆绑 zip 源）；第三方行重装走 `InstallFromPath` 用户提供包（`service.go:470-475` 复用行）——均不依赖已清的备份（风险1 明示代价）。

### 3.3 换版链：成功路径直清旧备份

`installCore`（`backend/plugin/service.go:456-559`）改造，仅在重装路径（`reusePlugin != nil`）：

1. `Save` 前捕获 `reusePlugin.BackupID`（reusePlugin 为重装时复用的原记录，此时行内还是旧值）；
2. 现有链不变：`Save`（全字段覆盖）→ `CreateBackup`（新备份）→ `Updates`（写新 BackupID）；
3. **成功路径末尾**（`Updates` 返回 nil 后、清理旧安装目录之前或之后均可，两者无数据依赖）：旧 ID 有效且 ≠ 新 `backup.ID` → `backupProvider.DeleteBackup(ctx, 旧ID)`，失败仅 Warn（留无主，治理兜底）。

时序约束满足：「修复」场景下旧备份文件既是本次安装源也是删除对象——删除安全的依据是 `CreateBackup`（把源文件复制成新备份，`service.go:534`）先于 DeleteBackup 执行，此后旧文件是否在世不再影响任何在途读取（`loadPluginPackage` 读源与 `ExtractZip` 解压解源都发生在删除点之前）。失败窗口（风险3）不补偿：`Save` 后链中断时行内已无旧 ID 的引用，旧备份成无主由治理兜底——与现状行为一致。

`BackupProvider` 接口增补 `DeleteBackup(ctx context.Context, id int64) error`（`backend/plugin/service.go:99-104`）——3.2/3.3 两处消费；`backup.Service` 已有同名实现零改动适配（声明9）。

### 3.4 死链清理（用户确认）

- 删 `Handler.Save`/`Handler.Update`/`Handler.SetUninstalled`（`backend/plugin/handler.go:24-41,110-112`）；
- 随之删失去调用方的 `Service.Save`（`service.go:200-203`，经 repo.Create 新建——与安装链无关的旧通用 CRUD 遗留）与 `Service.Update`（`service.go:205-208`）；
- 删 `Service.Delete`（`service.go:211-213`，死代码不重写——行永不物理删）与 `Service.SetUninstalled`（`service.go:747-759`）；`Service.Delete` 删除后 `Repository` 接口的 `Delete` 方法项（`service.go:84-85`）同失调用方，一并从接口删除；
- 删 wrapper `pluginSave`/`pluginUpdate`/`pluginDelete`（`frontend/src/apis/http/wrappers/plugin.ts:19-31`，全项目无调用方）；
- `wails3 generate bindings -ts` 再生成（三个方法从 bindings 消失）；前端管理页零改动。

### 3.5 治理与管理页守卫关系（零改动确认）

两条直清链均走 `backup.DeleteBackup` 消费式删除（「消费式」= 引用方在终态时按行内引用主动删除对应备份的形态，同 recycleBin PurgeStore 先例），**不产生绕过引用集守卫的形态**：清列（卸载）/覆写引用（换代）先于删备份，引用集即时收缩——备份管理页的有主守卫与引用态标注在清列后自动视该备份为无主（声明11），无悬空引用产生。app.go 装配处引用方枚举注释的「终态清理路径」义务由两条链补齐——**plugin 方从此满足登记时的终态确认条款**；监视哨对「长寿命已卸载引用」的周期性 Warn 噪音（`backupGovernance/service.go:231` 注释明示接受过）随之消失。

7. **引用集收缩回归**：卸载/换版后 `ListReferencedBackupIDs` 相应收缩（治理/管理页守卫消费面）；
8. **换版失败窗口**：CreateBackup 注入失败——行内 BackupID 已 NULL、旧备份行仍在（成无主，不补偿不删除）；
9. **卸载 CAS 竞态防御**：清列执行前并发将行内 backup_id 改为新值（模拟重装交错）——CAS 条件不中（0 行受影响）、报错「状态已变化」、新引用与备份均未动（风险7 ①层锚定）。
