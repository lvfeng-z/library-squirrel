# 任务-插件版本绑定方案

> 范围：插件升级后，旧任务的 `plugin_data`（任务表里插件自定义的不透明数据）如何在新版本插件下正确执行。属发布前「完善插件约定」的一部分。定位为**约定收拢**，非重型基建。

## 审查摘要

**关键声明（抽查项）**：
- 声明1：`task.plugin_data`（任务表里插件自定义的不透明字符串，主程序不解析其内容）— `backend/base/model/entity/task.go:23`（`sql.NullString`）
- 声明2：`plugin_data` 在每次执行（CreateWorkInfo / Start / Resume）都随整个 `task` 实体回传给插件，无单独参数位 — 转换 `backend/plugin/extension/convert.go:38`、写入 proto `backend/plugin/extension/task_handler_proxy.go:441`
- 声明3：`contractVersion`（host↔plugin 协议代际号，整数，当前=3）是 host 侧**单向**校验插件 manifest 声明的依据，**未**经任何 RPC 透传给插件运行时 — 定义 `library-squirrel-sdk/transport/contract.go:15`、校验 `backend/plugin/extension/loader.go:46-57`
- 声明4：`plugin_data` 是 opaque string，其内部格式变化**不触发** `contractVersion` bump（即不递增协议版本号；bump 仅限 proto/DTO/RPC 签名、render.Context（SDK 插件前端渲染契约类型）的破坏性变更）— bump 规则 `library-squirrel-sdk/transport/contract.go:5-7`
- 声明5：`plugin.version`（插件自声明 semver，如 "1.0.0"）为"展示用、加载不比较"——加载期仅校验 `contractVersion`（`ValidateContractVersion` 签名只吃协议版本号、无 version 比对参数）`backend/plugin/extension/loader.go:46-57`、`:240-243`、设计文档 `doc/plan/插件契约稳定性与版本化.md:11`；升级时同主键整字段覆盖（GORM `Save`）`backend/plugin/service.go:388-448`；DB 无版本历史表（`service.go:459-466` 的 `CreatePluginBackup` 是安装包 zip 归档、非版本历史；全仓无 `version_history` 类表）
- 声明6：任务路由全链路仅按 publicId（插件公开唯一标识符）索引、无 version 维度 — `TaskHandlerRegistry`（按 publicId+extensionId 索引的运行时扩展点注册表）键 `backend/plugin/extension/task_handler_registry.go:30`、`Loader.processes`（publicId→激活插件进程的内存映射）`backend/plugin/extension/loader.go:197`

**决策已定**：
- 决策1 → **途径①**：`plugin_data` 格式版本由插件自管（JSON 内嵌 `schemaVersion`），主程序零改动；途径②（主程序透传 `plugin.version`）代价高且版本语义错配、途径③（复用 `contractVersion`）经声明3/4 论证概念不适用，均不采用
- 决策2 → **不提供 SDK 解析便利**：插件自行 `json.Unmarshal`，SDK 不增加插件未必需要的抽象
- 决策3 → **fail-fast（报错拒绝执行）**：插件读到不认识的高 `schemaVersion` 时报错而非尽力解析；**此为插件自决的约定、主程序无法强制**（主程序不解析 `plugin_data` 内容，见声明1），覆盖用户从高版本回滚低版本插件的场景

**自曝风险**：
- 风险1：途径①依赖插件自觉自存版本，旧任务的 `plugin_data` 无版本字段——须文档明确"无字段=默认旧格式"兜底约定，否则旧数据无分支可走
- 风险2：本方案假设 `plugin_data` 渐进演进（加字段/改结构）；若插件某版完全重写数据模型，仅靠版本号仍需插件手写迁移逻辑，版本号只解决"识别"不解决"迁移"
- 风险3：若未来需主程序侧强制（如禁止跨大版本执行旧任务），途径①无主程序介入点——当前方案定位"插件自判"，不预设此能力，留作未来需求触发
- 风险4：`schemaVersion` 递增并写入新任务后，旧版本插件无法解析这些任务的 `plugin_data`（风险1 的反向场景；含用户主动从高版本回滚到低版本插件）——已落库数据的兼容性不可逆，依赖用户维持插件版本或重建任务

---

## 1. 背景与痛点

插件升级（`ReinstallFromPath`）后，publicId（插件公开唯一标识符）复用、同主键记录整字段覆盖（声明5），新版本插件的 TaskHandler 代码接管旧版本创建的任务。旧任务的 `task.plugin_data` 由旧版本插件按当时的格式写入；新版本 TaskHandler 执行（Start/Resume/Retry）这些旧任务时，需要**识别**这份 `plugin_data` 是哪个格式版本，才能正确解析——否则可能按新格式误解析旧数据。

严重性：低。当前不兼容的兜底是"重建任务"（成本可接受）。但发布前应把"plugin_data 格式演化的兼容性责任"确立为明确约定，让插件作者有章可循——这正是 epic A「完善插件约定」的题中之义。

## 2. 现状事实

### 2.1 plugin_data 的产生与回传
- **产生**：插件在 `Create` RPC 的 `TaskCreateResponse.pluginData`（及子任务 `TaskCreateChildResponse.pluginData`）返回，主程序读出以 `sql.NullString` 写入 `task` 表（声明1）。
- **回传**：执行时主程序把**整个 task 实体**（含 plugin_data）经 `entity.Task → SDK TaskDTO → proto gen.Task` 链路回传——CreateWorkInfo、Start、Resume 三类调用**全部携带**（声明2）。即插件在每次执行时都能拿到完整的 plugin_data 原文。

### 2.2 现有协议层无版本字段
SDK `TaskHandler` 接口（`library-squirrel-sdk/dto/task_handler.go:7-26`）及 proto `gen.Task`（field 13/14/15 = pluginPublicId/pluginExtensionId/pluginData）均**无任何插件版本或数据版本字段**。要做"主程序透传版本"，需新增字段并改 proto + 转换链。

### 2.3 两个独立的版本轴
| 版本轴 | 载体 | 语义 | 当前是否到插件 |
|---|---|---|---|
| `contractVersion` | 整数，编译期锁定 | host↔plugin **协议**代际（proto/RPC/render.Context 兼容性） | 否（声明3，host 单向校验） |
| `plugin.version` | semver 字符串 | 插件**整体**发布版本（展示用、不参与加载比对） | 否（仅落库与资源 URL，声明5） |
| `plugin_data` 格式 | opaque string 内部结构 | 插件任务数据的 schema | **是**（声明2，每次执行回传） |

## 3. 关键判定

### 3.1 为何 contractVersion（途径③）不适用
`contractVersion` 描述的是 host↔plugin **协议**代际，而 `plugin_data` 是该协议里的一个 opaque string 字段——它的内部格式演进**不改变**协议本身（声明4：opaque string 内部变化不触发 bump）。插件完全可能在同一个 `contractVersion=3` 内多次重构 `plugin_data` 结构。因此 `contractVersion` 与 `plugin_data` 格式是**两条独立演进轴**，用前者标识后者是概念混淆、粒度严重错配。排除。

### 3.2 为何 plugin_data 自管版本（途径①）更优
声明2 证明：`plugin_data` 每次**执行都完整回传给插件**。这意味着——**版本信息与它所描述的数据天然同处一处、且已有传输通道**。插件只需在写入 `plugin_data` 时自声明一个版本字段，读取时按版本分支即可，**主程序零改动、零协议变更**。

相比之下，途径②（主程序记 `plugin.version` 透传）需新增 task 字段 + proto 字段 + 转换链，且 `plugin.version` 是"插件整体版本"——插件可能改了 UI（version bump）但 `plugin_data` 格式没变，造成**版本与数据格式非严格对应**的误判。途径①的版本直接描述数据本身，语义最精确。

### 3.3 结论
推荐**途径①**：`plugin_data` 格式版本由插件自管（内嵌声明），主程序不解析、不裁决、不透传。L 的交付物收敛为**约定文档化**（+ 可选 SDK 便利），与 L 的已定方向"由插件自判兼容性、主程序不替插件裁决"完全一致，且是最轻量实现。

## 4. 方案（途径①·推荐）

### 4.1 约定（落 `doc/plugin-dev-guide.md` 新增节）
1. 插件写入 `plugin_data` 时，应在 JSON 顶层携带版本字段（命名建议 `schemaVersion`，整数，初值 1）。
2. 插件读取 `plugin_data` 时按 `schemaVersion` 分支解析；**缺失该字段（旧数据）按默认旧格式（v0）兜底**，不抛错（风险1）。
3. 读到**高于自身支持的 `schemaVersion`**（数据由更新版本插件写入）时 fail-fast——返回明确错误（如"任务数据由更高版本插件创建，请升级插件或重建任务"），禁止尽力解析以防静默数据损坏；此分支覆盖用户从高版本回滚到低版本插件的场景（决策3）。**此为插件自决的约定，主程序无法强制**——主程序不解析 `plugin_data` 内容（声明1），是否 fail-fast 完全由插件实现负责。
4. `schemaVersion` 仅在 `plugin_data` 结构**破坏性变更**（删字段/改字段语义/改类型）时递增；加可选字段不必递增（向前兼容）。
5. 责任声明：`plugin_data` 的格式兼容性与跨版本迁移由**插件自负**，主程序不解析其内容、不裁决版本、不强制迁移。

### 4.2 SDK 便利
不提供（决策2）。插件自行 `json.Unmarshal` 解析 `plugin_data`，SDK 不增加插件未必需要的抽象。

### 4.3 插件适配
pixiv / local 各自审查 `plugin_data` 结构：若已写入业务数据，补 `schemaVersion` 字段 + 读取分支与 v0 兜底。

### 4.4 主程序改动
**无**（声明2 已证明回传通道就位）。无需数据库迁移（新约定仅约束未来写入，旧数据按 v0 兜底）。

## 5. 实现步骤

1. **约定文档化**：`doc/plugin-dev-guide.md` 新增「plugin_data 格式版本约定」节（内容见 4.1），并在 `.claude/rules/plugin.md` 能力边界表「插件自存信息」一行补指针。
2. **插件适配**（仅当插件实际使用 plugin_data 时）：pixiv / local 各自按约定补 `schemaVersion` 字段 + 读取分支 + v0 兜底 + 高版本 fail-fast。
3. **同步树**：完成后回任务树标 `[完成]` 并外链本方案。

## 6. 验证
- 编译：若有插件改动，相关插件 `go build` 通过。
- 约定自检：文档"无字段=旧格式兜底 / 高版本 fail-fast"可独立执行、无歧义（风险1 闭环）。
- 插件侧（若适配）：构造旧格式（无 `schemaVersion`）`plugin_data` + 读取，验证走 v0 兜底不报错；构造高版本数据，验证 fail-fast 报错。

## 7. 备选途径（若决策1 选②）
若用户选途径②：task 实体加 `PluginVersion` 列（`sql.NullString`，创建时落 `plugin.version`）→ proto `gen.Task` 加 `pluginVersion` field（**需 bump `contractVersion`→4**，破坏性 proto 变更）→ `convert.go` / `task_dto.go` 转换链透传 → 插件 TaskHandler 据传入的创建时版本自判。代价显著高于途径①，且版本语义为"插件整体版本"非"数据格式版本"，精度更差。仅当未来出现"必须主程序侧强制版本"的硬需求时再启。
