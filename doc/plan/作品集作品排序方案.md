# 作品集作品排序方案（原站序 / 本地序双轨）

## 审查摘要

### 关键声明（抽查项，每条挂锚点）
- **声明1**：现状 `buildWorkSetLinks`（构造 work→作品集关联记录的函数）用「该 work 关联的第几个作品集」的下标填 `sort_order`，单集时下标为 0，集内 `sort_order` 塌 0（多集时为 0,1,2…，但语义仍是「第几个集」非「集内位置」，维度错位）。`backend/work/service.go:1867-1877`、调用点 `:1379`
- **声明2**：`sort_order` 现语义是「作品在作品集内的位置」，展示按 `sort_order ASC`、封面兜底取最小者。`backend/reWorkWorkSet/repository.go:65`、`backend/workSet/README.md:42`
- **声明3**：主程序经 `TaskHandlerProxy`（持有插件 gRPC client 的代理对象）反向调用插件的 `TaskHandlerService`（插件侧 RPC 服务），新拉取方法加在此 service + proxy 上。`backend/plugin/extension/task_handler_proxy.go:25-31`、`library-squirrel-sdk/proto/plugin.proto:175-183`
- **声明4**：插件身份固化在 `task.PluginPublicID`，`work_set` 实体不携带插件信息，无「站点→插件」映射表；入库钩子处主程序手里即有该字段可路由插件。`backend/task/service.go:612-613`、`backend/base/model/entity/work_set.go:10-22`
- **声明5**：站点侧 ID→内部 ID 映射均已存在：作品集 `GetBySiteAndSiteWorkSetID`、作品批量 `ListBySiteAndSiteWorkIDs`。`backend/workSet/service.go:325`、`backend/work/service.go:1003`
- **声明6**：作品入库完成钩子——父任务所有子任务终态（`AllChildrenTerminal`，判定父任务下全部子任务是否终态的方法）；单作品任务转 `Finished` 处。`backend/taskManager/manager.go:997-1004`、`backend/taskManager/model.go:2118-2130`、`:1285`
- **声明7**：回收站快照 `WorkSetSnapshot` 现仅含 `SortOrder`，采集（`work/service.go:668-673`）与恢复（`:895`）只读写本地序；物理纳入 `MergeWorkSetInto`（把源作品集及其后代的 work 关联复制到目标作品集的操作）复制关联行写 `sort_order`（`workSet/service.go:251-262`）。

### 决策（均已确认）
- **决策1**：拉取 RPC 复用 `TaskHandlerService`（不新建独立 service）。
- **决策2（核心·重构）**：原站序 / 本地序**双轨**——`re_work_work_set` 新增 `site_sort_order`（原站序，插件写），`sort_order` 明确为本地序（用户写），两字段互不覆盖。
- **决策3**：默认展示本地序（`sort_order`）；原站序（`site_sort_order`）作可选视图与「应用原站序」操作。
- **决策4**：原站序**入库时强制写入**——`SaveWorkInfo` 事务提交后主程序强制异步调插件拉取写 `site_sort_order`（不碰 `sort_order`，零副作用）；编排归 work 模块（入库发起方，`ORCHESTRATION_BY_CALLER`），不经 taskManager 终态钩子。
- **决策5**：`buildWorkSetLinks` 默认值修正为续排（修维度错位 bug）。
- **决策6**：**完全不处理存量**——已入库作品的 `site_sort_order` 保持 NULL，不回填、不提供手动入口；仅新入库作品有原站序。

### 自曝风险
- **风险1**：插件 `QueryWorkSetOrder`（主程序调插件查询集内原站全序的 RPC）可能回源站点（网络），入库钩子里须异步派发 + 超时保护，不阻塞 taskManager。
- **风险2**：失败的作品不入库（不触发 `SaveWorkInfo`），其 `site_sort_order` 不被本次拉取写入；同集其他成功作品拉取全序时，若插件返回含该失败作品 siteWorkId，因映射不到 work.id 会跳过——失败作品无原站序（不影响本地序展示）。
- **风险3**：`SaveWorkInfo` 是单作品入库，拉取的是该 workSet 全序但仅能映射到已入库的 work；同集其他作品各自入库时再次拉取覆盖，最终收敛。
- **风险4**：跨站点物理纳入的成员属他站，`site_sort_order` 写入须限定本站点成员；物理纳入复制时 `site_sort_order` 留空（NULL）。
- **风险5**：用户手动添加作品（`LinkWorkToWorkSet`，建立单个 work→作品集关联的方法）不触发拉取，其 `site_sort_order` 为空、仅本地序——符合预期，前端须容错空 `site_sort_order`。
- **风险6**：回收站恢复路径不触发入库钩子，`site_sort_order` 必须由快照字段保全（实施步骤 1、8 覆盖），否则恢复后丢失原站序。
- **风险7**：存量作品 `site_sort_order` 为 NULL（决策6），其「应用原站序」无效——可接受取舍。

## 一、问题与目标

### 现状缺陷
`buildWorkSetLinks`（`backend/work/service.go:1867`）给 `sort_order` 写的是「该 work 关联的第几个作品集」下标，而 `sort_order` 语义是「作品在集内位置」——维度错位致集内塌 0，原站顺序丢失。更深层：`sort_order` 单字段同时承载「原站顺序」「用户手动序」「入库默认序」三个来源，无优先级，插件拉取会覆盖用户手动序。

### 目标
**原站序 / 本地序双轨**：插件提供的原站顺序存独立字段 `site_sort_order`，用户的本地排序存 `sort_order`，两者物理隔离、互不覆盖。插件无需了解主程序状态（是否入库、用户是否改过），可随时刷新原站序而不破坏用户序。

> 设计类比：项目已有「站点作者 / 本地作者」「站点标签 / 本地标签」双实体双轨（站点数据与本地数据分离存储、各自由不同来源维护）。排序双轨同此哲学。

## 二、双轨模型

### 2.1 数据层（`re_work_work_set`）
| 字段 | 含义 | 写入者 | 用途 |
| --- | --- | --- | --- |
| `sort_order`（现有） | **本地序** | 用户拖拽 / 入库默认续排 / 物理纳入续排 | 默认展示、封面兜底（语义不变） |
| `site_sort_order`（新增，`sql.NullInt64`） | **原站序** | 插件拉取写入 | 「按原站序」视图 / 「应用原站序」源 |

### 2.2 写入规则（互不交叉）
- **入库**（`buildWorkSetLinks`）：`sort_order` 续排（本地序初始）；`site_sort_order` 留空待插件填。
- **插件拉取**（`QueryWorkSetOrder`）：**只写 `site_sort_order`，绝不碰 `sort_order`**。
- **用户拖拽**（`UpdateSortOrders`，批量更新集内本地排序的方法，CASE 单 SQL）：只写 `sort_order`（现有逻辑不变）。
- **物理纳入**（`MergeWorkSetInto`）：`sort_order` 续排（现有 `max+1+i`，`workSet/service.go:251-262`）；`site_sort_order` 留空（NULL）——纳入到目标集的成员原站序应由目标集上下文决定，跨站纳入源值无意义（风险4）。
- **「应用原站序」**：把 `site_sort_order` 拷进 `sort_order`（用户主动恢复原站序到本地序）。

### 2.3 主程序→插件：拉取 RPC（`TaskHandlerService.QueryWorkSetOrder`）
在 `TaskHandlerService`（`library-squirrel-sdk/proto/plugin.proto:175-183`）新增可选 RPC：

```proto
rpc QueryWorkSetOrder(QueryWorkSetOrderRequest) returns (QueryWorkSetOrderResponse);

message QueryWorkSetOrderRequest {
  int64 site_id = 1;           // 站点内部 ID（主程序已知）
  string site_work_set_id = 2; // 站点作品集 ID（插件原生 ID）
}
message QueryWorkSetOrderResponse {
  repeated WorkOrderEntry entries = 1; // 集内全序；空=插件不掌握
}
message WorkOrderEntry {
  string site_work_id = 1; // 站点作品 ID
  int64 sort_order = 2;    // 该作品在此集内的原站序号（从 0 起）
}
```

可选实现：插件不实现则 gRPC 返回 `Unimplemented`，主程序跳过（`site_sort_order` 保持空）。代理方法加在 `TaskHandlerProxy`，范式同 `Create`/`Retry`，client 入口 `getTaskClient()`（`task_handler_proxy.go:25-31`）。

### 2.4 入库时强制写入（决策4）
主程序在作品入库流程（`SaveWorkInfo`，`backend/work/service.go:1289`）事务提交后触发拉取——对 `workResp.WorkSets` 声明的每个 workSet，异步调插件拉取原站全序。事务后异步避免事务内网络调用（`MaxOpenConns=1` 死锁，风险1）。编排归 work 模块（入库发起方，`ORCHESTRATION_BY_CALLER`），注入 plugin 提供的 `WorkSetOrderFetcher` 接口，不经 taskManager 终态钩子。

每个 work 入库拉取其所属 workSet 的全序，多次拉取覆盖更新 `site_sort_order` 最终收敛（风险3）。插件返回空则跳过。

### 2.5 映射与写入 `site_sort_order`
插件返回 `[(site_work_id, sort_order)]` → 主程序：

1. 批量映射 `site_work_id → work.id`：`ListBySiteAndSiteWorkIDs`（`backend/work/service.go:1003`）。
2. 构造 `siteSortOrders map[int64]int`（work.id → 原站序），**仅取本站点成员**（风险4）。
3. 新增 `reWorkWorkSet.Repository.UpdateSiteSortOrders(workSetId, siteSortOrders)`（范式同现有 `UpdateSortOrders` 的 CASE 单 SQL，`backend/reWorkWorkSet/repository.go:157`，但写 `site_sort_order` 列）。

### 2.6 `buildWorkSetLinks` 默认值修正（决策5）
`buildWorkSetLinks`（`backend/work/service.go:1867`）的 `sort_order` 从「作品集下标 `i`」改为「该作品集当前最大 sort_order + 1」续排（参照 `MergeWorkSetInto` 的 `MaxSortOrderByWorkSetId + 1 + i`，`backend/workSet/service.go:251-262`）。修正后集内本地序稳定递增（按入库顺序），不再塌 0。`site_sort_order` 此处不写（留空待插件）。

### 2.7 前端（决策3）
- 默认按 `sort_order`（本地序）展示，逻辑不变。
- 新增「按原站序」视图：临时按 `site_sort_order` 排序展示（不改 `sort_order`）；`site_sort_order` 为空的成员容错（风险5，排末尾或按本地序补位）。
- 新增「应用原站序」操作：调主程序 `ApplySiteOrder(workSetId)`（新增，把该集 `site_sort_order` 拷进 `sort_order`），用户主动把原站序固化为本地序；该集 `site_sort_order` 为空时此操作无效（风险7）。

### 2.8 回收站快照与历史数据
- **回收站**（风险6）：`WorkSetSnapshot`（`backend/recycleBin/snapshot.go:43`）加 `SiteSortOrder` 字段，软删除采集快照（`work/service.go:668-673`）与恢复重建（`:895`）均带上 `site_sort_order`。因恢复路径不触发入库钩子，原站序须由快照保全而非重拉。
- **历史数据**（决策6）：存量 `re_work_work_set` 行 `site_sort_order` 保持 NULL，不回填、无手动入口；仅新入库作品有原站序。

## 三、与上一版（提示+拉取）的差异
本版**去掉**了上一版的 `NotifyWorkSetOrderReady` 提示 RPC、待拉取标记、用户排序脏标记——双轨字段隔离后，插件无需了解主程序状态、无需提示时机，主程序在入库钩子（自带 `task.PluginPublicID`）直接拉取。新增成本仅 `site_sort_order` 一个字段 + 前端一个视图/操作 + 回收站快照字段同步。盲区（插件不知用户改过、主程序不知是否需要排序）由「字段物理隔离 + 插件答空即跳过」消解。

## 四、排序路径边界
| 路径 | 写入字段 | 触发 |
| --- | --- | --- |
| 入库默认 | `sort_order`（续排） | 作品入库 |
| 插件原站序 | `site_sort_order` | 入库钩子自动拉取 |
| 物理纳入 | `sort_order`（续排）；`site_sort_order` 留空 | `MergeWorkSetInto` |
| 用户拖拽 | `sort_order` | 用户 UI 操作 |
| 应用原站序 | `sort_order`（拷自 site） | 用户主动操作 |
| 回收站恢复 | 两个字段均从快照还原 | 软删除恢复 |

`sort_order` 与 `site_sort_order` 独立，无覆盖冲突。

## 五、实施步骤
1. 实体 + 迁移：`re_work_work_set` 加 `site_sort_order`（`sql.NullInt64`）；`WorkSetSnapshot` 加 `SiteSortOrder`。`backend/migration/migrate.go` 自动迁移。
2. SDK proto：`TaskHandlerService` 加 `QueryWorkSetOrder` + 消息；生成 Go bindings。
3. SDK：独立 `WorkOrderQuerier` 可选接口（非 `TaskHandler` 主接口，避免破坏现有插件实现）+ transport 类型断言（未实现返回空，与 proto `Unimplemented` 语义一致）。
4. 主程序：`TaskHandlerProxy` 加 `QueryWorkSetOrder` 代理。
5. 主程序：`reWorkWorkSet` repo 加 `UpdateSiteSortOrders`；`workSet` service 加 `ApplySiteOrder`（site→sort 拷贝）。
6. 主程序：`work.SaveWorkInfo` 事务提交后异步编排——对 `workResp.WorkSets` 每个 workSet 调 `WorkSetOrderFetcher`（plugin 实现，包装 proxy+registry）拉取 → `ListBySiteAndSiteWorkIDs` 映射 → `UpdateSiteSortOrders`；work 注入 `WorkSetOrderFetcher`。
7. 主程序：修正 `buildWorkSetLinks` 默认值为续排。
8. 主程序：回收站快照采集（`work/service.go:668-673`）与恢复（`:895`）同步 `SiteSortOrder`；`MergeWorkSetInto`（`workSet/service.go:251-262`）复制关联时 `site_sort_order` 留空。
9. 前端：作品集页默认按 `sort_order`；加「按原站序」视图 + 「应用原站序」操作 + handler/wrapper。
10. 插件（pixiv/bilibili 等）：实现 `WorkOrderQuerier` 接口的 `QueryWorkSetOrder`（回源查集内全序）；不实现的插件自动跳过。
11. 前端 bindings 生成、模块文档同步。

## 六、影响面
- SDK（proto + `TaskHandler` 接口）、主程序（实体迁移 / proxy / repo / taskManager 钩子 / `work.buildWorkSetLinks` / `workSet` 新增 `ApplySiteOrder` / 回收站快照 / 物理纳入）、前端（作品集页视图与操作）、各运行时插件（实现拉取）。
