# 插件构建身份（buildId）与捆绑升级判据机制

## 审查摘要

**关键声明（抽查项）**

- 声明1：zip 容器哈希在「源码不变、仅重新构建」时必变——实证：同内容文件 mtime 更新后各 Compress-Archive 一次，哈希 `CF4E1784…` ≠ `C5AD2F3E…`（复现：`Set-Content a.txt "hello"; Compress-Archive …; 改 mtime 后再 Compress-Archive; Get-FileHash 对比`）；主因是 zip 条目记录文件 mtime，重构建必产生新 mtime。
- 声明2：插件 exe 字节在同机同路径同源码下可复现——实证：同一 main.go 连续两次 `go build`，哈希均为 `7067516d…`；但 Go 未加 `-trimpath` 时二进制嵌入构建路径，跨机器/路径构建会变（通识推断，未跨机核验）。
- 声明3：版本号判据已实证失效——2026-08-14 事故时点，生产已装插件与捆绑 zip 同为 `1.0.0` 但内容不同物：当日 15:39 启动（旧版主程序）按旧 `slots` 格式注册前端扩展（生产 `server.log:229/244`），15:44 启动（新版主程序）零前端扩展注册（`server.log:313-325`），而捆绑 zip 内 plugin.json 为新 `frontendExtensions` 格式（2026-08-15 会话解包核对）。注：本声明锚定时间戳日志；生产已装磁盘文件在会话期间已被更新为新格式（生产环境被更新过），可变文件不作证据。
- 声明4：当前判据实现为 `needBundledUpgrade`（`backend/plugin/service.go:386`，比对 IntegrityHash），实体字段 `backend/base/model/entity/plugin.go:30`（注释语义「纯追溯存档」，本方案将其复位为纯存证）。
- 声明5：构建管线存在统一收口——`task build:plugins`（`Taskfile.yml:57`）调 `build/plugins.ps1`，逐仓库调用各自 `build.ps1`（`build/plugins.ps1:72`）后复制 dist zip（`:98`）；各仓库脚本把 plugin.json 原样复制进包（`library-squirrel-plugin-local/build.ps1:40`）再 Compress-Archive（`:50`）——打标（构建时把 buildId 写入包内 plugin.json）的插入点明确。
- 声明6：三版本轴（contractVersion / configSchemaVersion / plugin_data schemaVersion）已独立存在（`.claude/rules/plugin.md`「插件 SDK 能力边界」）；本方案新增第四轴 buildId，不与前三轴耦合。
- 声明7：插件静态资产 URL 以 version 为缓存段并声明一年不可变缓存——URL 构建于 `app.go:646`（resolveSourceURLs）与 `app.go:665`（resolveIconURL），响应头 `Cache-Control: public, max-age=31536000, immutable` 与含 version 的 ETag 于 `backend/plugin/extension/static_resource_service.go:108-111`。叠加声明3（version 不可靠）→ 同版本升级重装后 URL/ETag 不变，前端将持续命中旧缓存（代码路径已确认，未实机复现）。
- 声明8：publicId 构造为 `author + "/" + id`（`backend/base/model/dto/plugin_types.go:58`），而 id 本身已含反域名（如 `com.lvfeng.`）与 UUID 后缀——同一身份三重唯一性冗余；author（展示字段）进身份键意味着作者改名即身份裂变。
- 声明9：IntegrityHash 无判据性读取方——实体注释定位「纯追溯存档」（`backend/base/model/entity/plugin.go:30`），判据借用（`backend/plugin/service.go:386`）是 2026-08-15 修复引入的权宜；仅存的前端透传为 `backend/base/model/dto/plugin_dto.go:25`（DTO 字段）、`:52`（组装）与 `frontend/src/components/plugin/PluginStatusPanel.vue:94-97`（状态面板展示）。
- 声明10：升级重装保留插件用户数据——`plugin_storage` 按 `(plugin_id, key)` 唯一索引（`backend/base/model/entity/plugin_storage.go:13-14`），重装路径复用原记录 ID（`backend/plugin/service.go:461`）且 installCore 全段（`service.go:396` 起）无 plugin_storage 写操作，用户设置与凭据在升级重装中保留。

**待决策（已全部裁决，2026-08-15 用户追认）**

- 决策1 → 按默认 fail-fast。已实现：build.ps1 中 git describe 失败即构建失败，不产出无身份包。
- 决策2 → 按默认暂不展示。buildId 未进 PluginDTO/前端。
- 决策3 → scope 划分确认。判据 + 构建身份统一已落地；升级提示流为独立后续方案（未启动，当前生效行为为静默升级）。
- 决策4 → 按默认移除。实体字段/安装写入/DTO 透传/前端展示/回填补算已全链路删除；DB `integrity_hash` 旧列与存量数据保留（AutoMigrate 不删列），回退窗口在。
- 决策5 → 随本方案执行。cacheKey = buildId（未打标回落 version）已贯穿 URL 构建/ETag/资源注册。
- 决策6 → 用户拍板尽快独立立项实施（2026-08-15），方案另行编写；本方案不涉及。

**自曝风险**

- 风险1：git 历史改写（rebase 重建分支）使同源码对应不同 SHA → buildId 变 → 触发一次无害重装。
- 风险2：`--dirty` 只区分有无未提交改动、不区分改动内容——同 commit 不同未提交内容得到相同 buildId（仅本地开发场景，不进发布流）。
- 风险3：`git describe` 依赖 tag 才有版本前缀；仓库不打 tag 时 buildId 为裸 SHA——判据（相等性比较）不受影响，但失去人读语义与排序线索。建议各仓库发版时打 tag。
- 风险4：四个插件仓库各自打标存在「改一处漏三处」风险——主任务事后校验兜底；单独运行某仓库 build.ps1 时若 git 缺失将按决策1 报错，不静默。
- 风险5：PowerShell 写回 plugin.json 若带 BOM，Go `encoding/json` 解析失败——打标必须 UTF-8 无 BOM 写回，校验步骤实际解包验证可覆盖此风险。
- 风险6：URL 缓存段切换为 buildId 后，每次重构建（新 buildId）使前端资产 URL 全量更换——语义正确但升级后首启全量重取插件资产（本地服务开销可忽略）；未打标包回落 version，仍带陈旧缓存隐患（与今天一致，无恶化）。
- 风险7：回退判据改用 version 后，未打标 zip 且 version 未变但内容变 → 漏升级（正是 2026-08-14 事故的形态，但仅限绕过构建管线的手工包）；第一方插件由 build:plugins 强制打标校验兜底（风险4）。

## 一、背景：判据两难的实证

捆绑插件升级检测需要回答「已装版本与随主程序发布的 zip 是否同一个构建」。现有两个信号都不合格：

- **zip 哈希（IntegrityHash，当前判据）**：重构建必变（声明1）——即使插件源码一字未动，主程序每次发版重新 `task build:plugins` 都会产生新哈希。静默升级流可容忍（幂等重装便宜），提示流不可用（每次发版必弹，提示疲劳）。
- **版本号**：人工维护不可信（声明3：事故实证同号不同物），且无法用机器纪律强制（开发者忘记 bump 即失效）。

结论：需要一个「源码状态的函数」而非「构建产物的函数」的身份标识。

## 二、目标与非目标

**目标**

1. 构建身份 buildId：同源码状态（同 commit + 同干净度）→ 永远同 id；源码状态变化 → id 必变。
2. 与构建环境（机器/路径/时间/工具链）完全解耦——这是「永久可用」的核心承诺。
3. 与既有三版本轴正交，不混用职责。
4. 一次性迁移，此后进入稳态，不再需要数据迁移。

**非目标**：升级提示流（何时问用户、拒绝状态持久化、聚合提示、契约不兼容强制升级）——独立后续方案。可复现构建——不追求 zip/exe 字节可复现。

## 三、身份分层：各轴只回答一个问题

| 轴 | 载体 | 回答的问题 | 谁维护 | 变更时机 |
| --- | --- | --- | --- | --- |
| publicId | `author/id`（id 含反域名+UUID，声明8） | 这是哪个插件 | 插件作者 | 几乎不变（但 author 进键致改名裂变） |
| version | plugin.json `version` | 语义版本（人读/排序） | 插件作者 | 有意发布新版本 |
| **buildId（本方案新增）** | plugin.json `buildId` | 这是哪次构建（机器判同+缓存失效） | 构建管线自动 | 每次源码状态变化 |
| contractVersion | plugin.json | host↔plugin 协议边界 | 插件作者 | 协议不兼容变更 |
| configSchemaVersion | plugin.json | 插件配置结构版本 | 插件作者 | 配置结构变更 |
| plugin_data schemaVersion | task PluginData JSON 顶层 | 插件任务数据格式 | 插件自管 | 数据格式变更 |

分工示例（提示流消费时）：判「变没变」用 buildId（相等性）；判「升还是降」用 version（语义排序）；判「能否允许拒绝升级」用 contractVersion（协议边界）。三个问题三个信号，不混用。

**分散度判定**（对「身份机制是否过于分散」的回答）：四条版本轴各答一问、职责清晰，不属分散；真正的病是**「构建身份」槽位空缺**引发的连锁错位——(a) 升级判据先后用「已装即跳过」、权宜借用 IntegrityHash（声明9），判据一直在漂移；(b) version 被拉去兼任静态资产 URL 缓存段与 ETag（声明7），把一年不可变缓存挂在不可靠信号上；(c) IntegrityHash 写而不读，属无效机制。本方案以 buildId 填上该槽位（判据 + 缓存失效统一消费），同时让 IntegrityHash 退役——分散与无效一并收敛。publicId 的三重冗余（声明8）是另一处分散，但与判据正交，按决策6 延后独立处理。

## 四、机制设计

### 4.1 buildId 定义

`git describe --tags --always --dirty` 的输出：

| 输出 | 含义 |
| --- | --- |
| `v1.0.0` | 正好在 tag 上（正式发布构建） |
| `v1.0.0-3-ga1b2c3d` | tag 后第 3 个提交 |
| `a1b2c3d` | 无可达 tag（裸 SHA） |
| `v1.0.0-dirty` | 工作区有未提交改动 |

性质：**源码状态的函数**——SHA 不可变，同状态重构建永远同 buildId（区别于 zip 哈希的重建必变）；commit 前进或干净度变化必变；与构建机器、路径、时间、Go 版本全部无关。

### 4.2 生成与注入（构建管线）

- 各插件仓库 `build.ps1`：在 plugin.json 复制进 dist 之后、Compress-Archive 之前，把 buildId 写入 `dist/plugin.json`（源 plugin.json 不动，仓库工作树保持干净）。写回必须 UTF-8 无 BOM。
- 主仓库 `build/plugins.ps1`：每个仓库构建完成后校验产物 zip 内 plugin.json 含非空 buildId（解包读取），缺失即整体构建失败——集中兜底「改一处漏三处」（风险4）。
- 无 git 元数据时按决策1 处理（默认报错中止）。

### 4.3 存储（主程序）

- DTO：`PluginManifest`（`backend/base/model/dto/plugin_types.go:23`）与 `PluginInstallDTO`（`:39`）增加 `BuildID string json:"buildId,omitempty"`。
- 实体：`Plugin`（`backend/base/model/entity/plugin.go:10`）增加 `BuildID sql.NullString gorm:"column:build_id"`，经 GORM AutoMigrate 自动加列，无需手写迁移。
- `installCore` 写入 `plugin.BuildID`（与 Version 同排写入）。

### 4.4 升级判据（替换现哈希判据）

`needBundledUpgrade`（`backend/plugin/service.go:386`）改为：

```
zip 侧 buildId 非空？
  是 → 已装 buildId 非空且相等 → 不升级
       否（缺失或不同）→ 升级        // 缺失 = 升级前存量记录，一次性对齐
  否（未打标 zip）→ 比较 version：不同 → 升级；相同 → 跳过
```

回退判据不用哈希：IntegrityHash 按决策4 移除后不可比。未打标包的残余盲区（同 version + 内容变 → 漏升级）由构建管线强制打标兜底（见风险7）。

IntegrityHash 按 决策4 处置（默认移除实体字段与写入，回退判据随之改用 version，见 4.4）。

### 4.5 构建身份统一消费：静态资产 URL 与 ETag（决策5）

现状把 version 拼进所有插件资产 URL 并声明一年不可变缓存（声明7）。切换为：

- URL 构建链（`app.go:646` resolveSourceURLs、`app.go:665` resolveIconURL）与注册（`app.go:418` RegisterPlugin）的版本段参数改为**缓存键**：取 buildId，未打标包回落 version。
- `StaticResourceService.ServeHTTP` 的 ETag（`static_resource_service.go:109`）以注册时的缓存键组成——重构建必换 buildId → URL 与 ETag 必变 → 不可变缓存策略才真正安全。
- URL 版本段只用于缓存失效，不参与文件路径解析（`static_resource_service.go:75` 既有注释），磁盘目录 `{publicId}/{version}/` 布局不动。
- 前端无感：资产 URL 全部由后端构建下发，前端纯消费。

### 4.6 为什么能永久用

1. **声明式身份**：id 是构建时写进 plugin.json 的字符串，不依赖任何环境属性的可复现性。声明1/2 表明「驯服字节哈希」需同时保证 exe 与 zip 容器两层可复现——把永久性押在环境属性上方向就错了；声明式身份没有这个包袱。
2. **比较语义只有相等性，无格式耦合**：buildId 未来演变（追加 CI 构建号、日期段）不破坏机制；第三方/市场插件用任何唯一字符串（如 CI run id）都合法。
3. **git describe 是数十年稳定的核心命令**，SHA 不可变，无时间衰减。
4. **轴独立**：其余各轴各自演进不动摇本轴（同 contractVersion 三轴独立的既有原则）。
5. **迁移一次性**：存量记录 `build_id` 为 NULL → 首次判定「不等」→ 升级对齐 → 稳态；此后无迁移。

## 六、被否决的替代方案

- **可复现构建**（`-trimpath` + 固定 zip 时间戳）：需长期维护构建纪律，任何环境差异（机器/路径/工具链）破坏稳定性；声明1/2 表明要同时驯服两层字节；「永久」不可押在环境属性上。
- **解压后内容哈希**：同机稳定但跨机器/路径变（无 `-trimpath` 时 exe 嵌路径，声明2），仍依赖构建环境；且无语义信息、无法支撑排序。
- **读 exe 内嵌 VCS 信息**（`go version -m`）：要求运行时解析外部 exe 的 buildinfo，纯 UI 插件（无 exe）不覆盖；plugin.json 打标更通用、语言无关。
- **纯版本号 + 构建纪律强制 bump**：纪律无法机器强制（忘 bump 即失效），声明3 即纪律失守的实证。

## 七、迁移与稳态

发布带 buildId 的主程序后首个启动：存量插件记录 build_id 为 NULL → 判定「不等」→ 按 InstallBundled 现行升级路径重装对齐 → DB 记录与磁盘 plugin.json 均带上 buildId。此后进入稳态：源码不变 → buildId 不变 → 永不触发；源码变化 → 必触发（升级后首启因 URL 版本段更换会全量重取插件资产，见风险6）。唯一会再次出现「一次性对齐」的场景是风险1（历史改写）与新增未打标包，均无害。
