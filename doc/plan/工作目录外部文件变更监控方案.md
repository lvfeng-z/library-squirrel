> **状态**：设计阶段（5 项决策已拍板，待审查）。方案经多轮讨论收敛为"事件驱动 + 能力接口 + 按平台降级"。

**自曝风险（作者没把握 / 可能错的地方）**：

- **风险3. Linux 大目录受 `fs.inotify.max_user_watches` 限制**（inotify 不递归、逐目录加 watch），需捕获错误降级

- **风险5. 外部删除不经回收站**（声明6），复原唯一数据源是 backup；无备份则不可复原，UI 须诚实表达
- **风险6. backup repository 需新增按 `original_file_path` 反查方法**（声明5缺口）
- **风险7. 监控 goroutine 生命周期须与 Wails shutdown 协调**，须在 `shutdownPlugins` 之前停止（声明7）
- **风险8. 指纹头部哈希的精度边界**：size + 头部 64KB 检测 size 变化或头部字节变化；中间字节改且 size 不变的极端情况漏检（罕见，配合 size 已覆盖大多数场景）。若未来需全字节精确，改全文件哈希（届时变耗时，复活 longops 分支 F）
- **风险9.（审查补充）Linux inotify 逐目录加 watch 的工程复杂性**：fsnotify 在 Linux 不递归，workDir 文件多时 watch 数量爆炸（消耗 fd/内存，与风险3 的 `max_user_watches` 上限正交）；新建子目录需监听 Create 事件动态补 watch。Windows(`ReadDirectoryChangesW`)/macOS(`FSEvents`) 原生递归无此问题，Linux 实现须自维护 watch 树
- **风险10.（审查补充）离线对账与实时写入的并发窗口**：对账扫描期间发生 store 写入（如对账中触发下载），扫描快照与实时写入有瞬态语义差异；SQLite WAL 单写者不脏读，但"扫到一半文件被改"可能瞬态不一致——由运行时事件或下次对账收敛（对账是尽力而为快照）

## 一、问题与范围

软件外部（用户手动、其他程序）对 workDir 的文件操作，当前完全无感知，导致 DB 记录（`persistent_store.file_path`）与磁盘实际文件不一致：文件被**移动/重命名** → DB 路径指向旧位置；文件被**删除** → DB 孤儿记录。

本功能目标：检测这两类不一致（运行时 + 启动时），通知用户，提供一键修复。**核心是"监控 + 修复"，不是溯源。**

**首版范围**（决策2/3 收窄）：仅路径类变更（移动/重命名/删除）；外部新增文件仅提示不导入；内容修改延后。

## 二、总体架构：事件驱动 + 能力接口 + 按平台降级

按"能力"切接口，每个能力可独立注入/缺失，**能力缺失 = 不注入（nil），上层走降级路径**。

| 能力 | 首版 | 性质 | 降级后果 |
|---|---|---|---|
| `LiveEventSource`（实时事件流） | ✅ 实现 | 运行时主路径，三平台 fsnotify 封装 | 环境不可用 → 运行时无监控 |
| `ReconciliationScanner`（全量对账） | ✅ 实现 | **首版离线主实现**（三平台统一） | — |
| `ContentFingerprinter`（内容指纹） | ✅ 实现 | 离线对账匹配键 + 运行时配对丢失兜底 + **落库计算**（决策4） | 降级为仅 size |
| `OfflineChangeProvider`（USN 离线追溯） | ⏸️ 接口预留 | Windows 独有增强 | 不注入 → 离线退化为全量对账 |

**演进**：首版离线三平台都走对账；未来 Windows 接入 USN 后，对账降级为 Linux/macOS 离线手段 + Windows 兜底。

> 运行时是**事件驱动**（fsnotify 推送），非定时轮询——轮询在设计讨论中作为简化退路出现，与"OS 原生监控"目标冲突，已否决。

## 三、事件模型（平台无关语义）

```go
package fsmonitor

type ChangeKind int
const (
    ChangeCreate ChangeKind = iota // 文件或目录出现
    ChangeRemove                   // 文件或目录消失
    ChangeMove                     // 移动或重命名(From→To 配对)
)

// FileChange 一次文件变更,所有路径相对 workDir,与 persistent_store.file_path 同基准
type FileChange struct {
    Kind       ChangeKind
    Path       string // 相对 workDir;Move 时为旧路径(From)
    ToPath     string // 仅 Move 有值:新路径
    IsDir      bool
    DetectedAt int64  // 毫秒时间戳
}
```

> 首版去掉 `ChangeModify`（决策3）。`ChangeMove` 是关联层产出的已配对语义事件。fsnotify 在 source 层无法可靠配对，原因有二：① 不暴露 inotify 的 cookie；② **Windows 后端对 rename 只发一个 `Create`(新名) 事件**——`renamedFrom`=旧名信息存在但字段未导出（`fsnotify@v1.10.1/fsnotify.go:194`，无 getter），旧名（`FILE_ACTION_RENAMED_OLD_NAME`）mask=0 不发事件（`backend_windows.go:605-606`）。故 `LiveEventSource` 忠实推送 Create/Remove（Windows rename 在事件流里只产 Create 新名），移动配对全部在关联层（阶段3）用**落库指纹**匹配（Create 新名 → 算指纹 → 匹配 DB 落库指纹 → 旧名记录）。配不上的（跨边界移出，风险1）退化为 `ChangeRemove`。

## 四、能力接口定义

### 接口一：实时事件流（首版核心）

```go
// LiveEventSource 运行期文件变更事件源
// 三平台均由 fsnotify 封装(Windows ReadDirectoryChangesW / Linux inotify / macOS FSEvents)
// 降级:网络盘 / watches 耗尽 / 内核限制 → 不注入,运行时退化为仅启动对账
type LiveEventSource interface {
    Start(ctx context.Context) (events <-chan FileChange, errs <-chan error, error)
    Stop()
}
```

**两条降级路径须分清**：构造期失败（`Start` 返回 error）→ 不注入；运行期失效（`errs` 推致命错误后关闭 `events`）→ 标记下线、其余流程继续。

### 接口二：离线变更追溯（延后，接口预留）

```go
// OfflineChangeProvider 离线变更追溯(基于持久日志)
// Windows(USN Journal，NTFS 卷级持久变更日志，记录文件增删改/重命名，可从 USN 游标续读)可实现;Linux/macOS 无原生等价 → 不注入,退化为全量对账
type OfflineChangeProvider interface {
    ChangesSince(ctx context.Context, cursor OfflineCursor) (changes []FileChange, next OfflineCursor, err error)
}
type OfflineCursor []byte // 不透明游标,上层仅持有/持久化/回传
```

### 接口三：全量对账（首版离线主实现）

```go
// ReconciliationScanner 比对 workDir 实际文件与 persistent_store 记录,产出差异集
type ReconciliationScanner interface {
    Scan(ctx context.Context) (DiffSet, error)
}
type DiffSet struct {
    Missing   []MissingRecord   // DB 有 file_path、磁盘无(被删或移走)
    Untracked []UntrackedFile   // 磁盘有、DB 无(外部新增或移入)——首版仅提示(决策2)
}
```

### 接口四：内容指纹（匹配键 + 兜底 + 落库计算）

```go
// ContentFingerprinter 内容指纹(size + 头部 N 字节哈希,避免大视频全量哈希)
// 用途:① store 落盘时算并落库(决策4);② 离线对账 Missing×Untracked 移动匹配键;③ 运行时配对丢失兜底
type ContentFingerprinter interface {
    Fingerprint(ctx context.Context, absPath string) (Fingerprint, error)
}
type Fingerprint struct {
    Size   int64
    Digest string
}
```

## 五、检测-关联-修复 三层流水线

### 检测层（两个输入源）
- **运行时**：`LiveEventSource` 推 `FileChange` 事件流
- **离线**：`ReconciliationScanner.Scan()` 产 `DiffSet`

### 关联层（技术心脏）

**运行时关联**（输入：FileChange 流）：
- 配对 rename 信号 → 直接 `ChangeMove`
- 独立 Remove + 短窗口 Create → 指纹匹配 → 命中 `ChangeMove`，否则各自归删除/新增
- 跨边界移出（只有 Remove）→ `ChangeRemove`（标记"可能移出"）

**离线关联**（输入：DiffSet，**强依赖落库指纹**）：
- `Missing × Untracked` 按指纹配对 → `ChangeMove`
- 剩余 `Missing` → 删除
- `Untracked` → 仅提示（决策2，不自动导入）

> 关联层是纯函数式逻辑（输入事件/差异，输出语义变更），无平台依赖、无副作用，易单测。

### 离线对账的指纹必要性（决策4 的关键依据）

离线移动匹配要把"Missing（DB 有磁盘无）"与"Untracked（磁盘有 DB 无）"按内容配对。**Missing 的文件已不在磁盘，无法现场算指纹**；而 `persistent_store` 连 `Size` 都没有（声明2），无任何内容线索。唯一解：**指纹落库**——Missing 文件的指纹从 DB 读，Untracked 现场算，二者匹配。不落库则离线无法自动判定移动（详见决策4）。

### 修复层

每条语义变更对应修复动作，更新 `persistent_store`。**首版修复矩阵**（决策3 去内容修改、决策2 外部新增仅提示）：

| 语义变更 | 复原（恢复原状） | 同步（接受现状改 DB） |
|---|---|---|
| 移动/重命名（workDir 内） | 文件移回原路径 ✅ | DB `FilePath` 指向新位置 ✅（核心场景） |
| 移动到 workDir 外 | 找不回 ❌（物理限制） | 不知新位置 ❌ → 标记记录失效（语义见决策6） |
| 删除 | 从 backup 恢复 ⚠️（若有备份） | 标记 `persistent_store` 记录失效（语义见决策6） |
| 外部新增 | —（不自动处理） | 仅提示，不导入（决策2） |

⚠️ = 依赖 backup；❌ = 物理不可能。UI 诚实表达。修复走事务（`database.WithTransaction`，事务内 repository 方法必须 `dbFromCtx(ctx)`，见数据库规则 `TRANSACTION_INTERNAL_USE_DBFROMCTX`）。

## 六、指纹落库设计（决策4 落地）

**字段**：`persistent_store` 加 `ContentFingerprint string` 列（size + 头部 64KB SHA256）。

**算法**（只读头部，几毫秒）：打开文件读前 64KB 算 SHA256，与 size 拼接成指纹串。相比下载/拷贝耗时可忽略，故**同步算**（无需异步 goroutine、不接 longops）。

**落库时机**（挂 4 个完成点，仿 `fillImageDimensions` 同处调用）：
- `storeWriter.Complete()`（`service.go:92`，流式写入完成）
- `Store` existing 分支（`:385`）/ 新建分支（`:401`）
- `StoreFromExternal`（`:571`）

每个完成点在设 `Status=Complete` + `fillImageDimensions` 后，调指纹函数算出指纹，与 width/height 一同 `Updates`/`Create` 落库。

**接口注入**（仿 `FileMover` 先例，`service.go:170-179`）：persistentStore 定义本地 `Fingerprinter` 接口（由 fsmonitor 实现、构造注入）；persistentStore 不反向依赖 fsmonitor 具体类型，只依赖本地接口。nil 时不算指纹（降级）。

**存量回填**：启动时扫仍存在的 persistent_store 记录算指纹填入；磁盘已无的记录留空（交对账处理）。

| 指纹计算（注入 persistentStore） | `ContentFingerprinter`（fsmonitor 实现） | 仿 `FileMover` `service.go:170-179` |

路径校验复用 `validatePath`（`dir.go:28`）；扫描遇白名单外目录（如 `backup/`）另行处理。

**模块边界纪律**（`MODULE_BOUNDARY_PURITY` + `ORCHESTRATION_BY_CALLER`）：fsmonitor 是发起方/编排方，通过注入接口串联流程；不把多模块能力揉进单一"集成器"接口，不反向侵入现有 service（指纹计算经本地接口注入 persistentStore，而非 fsmonitor 直接写 persistent_store）。

## 八、降级路径

```
LiveEventSource 不可用 → 运行时无监控，仅靠启动对账
OfflineChangeProvider 不可用（首版全部平台） → 离线走 ReconciliationScanner 全量对账
指纹未落库/计算未完成的记录 → Missing 时不参与移动匹配，降级为"删除"报告
workDir 运行期切换（决策5） → Stop watcher + 通知前端提示重启
```
