# 插件约定发布前审计与任务规划

> 本文档是「完善插件约定，为正式发布做准备」epic 的发布前契约空白审计，并据此规划任务图结构。
> 审计方法：两轮代码核查（Explore agent 核验实现层 7 项 + tag 模型 6 项）+ 自查（任务创建参数流、作品集层级契约）。

## 审查摘要

**关键声明（抽查项，均经代码核查）**：

- 声明1：版本协商仅 go-plugin 的 `ProtocolVersion=1`+MagicCookie，**无** min-host/min-sdk 校验；插件 manifest 的 version 仅展示、加载时不比较 — `library-squirrel-sdk/transport/handshake.go:11`、`backend/plugin/extension/loader.go:154`
- 声明2：插件信任/安全零校验、零沙箱、零权限模型；任意 ZIP 解压即跑，子进程 `os.Environ()` 继承全部环境+完整文件系统/网络访问权 — `backend/plugin/extension/service.go:217-230`、`loader.go:146-162`
- 声明3：能力探测隐式——仅 `WorkOrderQuerier`（作品集原站序查询，插件可选实现的接口）一个「实现即启用」可选能力，gRPC 空响应兜底；其余能力靠插件 Activate（插件启动回调）运行时 `ctx.RegisterXxx()` 注册，`plugin.json` 不声明能力 — `library-squirrel-sdk/transport/plugin_server.go:179`、`loader.go:118-120`
- 声明4：SDK dto 完全独立（不 import 主程序），但与主程序 entity 的映射靠 `convert.go` 手工逐字段、**无契约校验**，存在静默漂移风险 — `backend/plugin/extension/convert.go:44-64`
- 声明5：插件子进程崩溃**无 respawn**；崩溃→清理扩展点注册 + 任务转 Failed 终态 + 回滚本次 store 产物 — `loader.go:326-340`、`backend/taskManager/model.go:780-784`
- 声明6：资源类型封闭——`ResourceTypeRegistry`（资源类型中央注册表）是预定义 5 类 map，**无运行时注册 API**；`ValidateResourceType` 拒绝非注册值 — `backend/base/model/entity/resource_type.go:50-56,215-223`
- 声明7：配置无迁移——`plugin_storage`（插件 KV 存储）无版本字段；插件升级保留 KV，settings（用户设置）key 变动时旧 key 成孤儿、新 key 取默认值 — `backend/plugin/extension/plugin_storage_service.go:87-103`、`service.go:440-472`
- 声明8：作品集层级契约缺失——插件声明作品集的 `TaskWorkSetDTO` **扁平、无 parent 字段**；父子层级表 `re_work_set_work_set` 当前仅用户手动 merge 可建，插件无入口 — `library-squirrel-sdk/dto/handler_dto.go:135-139`
- 声明9：任务创建纯 URL、无参数通道——`CreateTaskByURL(url)` → 插件 `Create(url)`，`CreateTaskRequest` 无「用户选择/下载模式」字段；audio（纯音频）无对应 ResourceType，video 强制 videoMain — `backend/task/service.go:521`、`task_handler_proxy.go:33`、`task_dto.go:43-51`、`doc/resource-type-spec.md`
- 声明10：tag 模型三表（`local_tag`/`site_tag`/`re_work_tag`）无 category/kind/synonym；`local_tag` 已有 `base_local_tag_id` 树状层级；作者与 tag 是两套并行体系；`re_work_tag.tag_type` 值在「插件导入路径」(1/2) 与「用户 UI 路径」(0/1) 间不一致（latent，查询不读该列故未爆）— `entity/local_tag.go:10-16`、`work/service.go:1935,1962`、`reWorkTag/service.go`
- 声明11：local 插件已实现「创建任务时弹 dialog 收集用户元数据」——`Create` 调 classifier，无法自动分类时经 PublishToFrontend 弹 ClassifyPanel dialog，用户填写后经 SubscribeFrontend 回收；此模式即「按任务用户选择」的成熟实现，无需 host 参数通道 — `library-squirrel-plugin-local/activate.go:42-60`、`task_handler.go:43,70`、`views/classify/ClassifyPanel.vue`

**待决策（需用户拍板）**：

- 决策1（已决）：tag 演化方向 = 扩展现有模型，且 **namespace 作为 work↔tag 关联级属性**（非 tag 身份）：local_tag 保持扁平不变，site_tag/re_work_tag 加 nullable namespace 列，local/site 关联通用，无 namespace 时 null。e-hentai 用 namespace:tag 复合身份但属单站点，本项目多站点故不照搬。完整方案见 doc/plan/tag体系演化方案.md。
- 决策2：信任模型最小集边界——仅「安装信任提示 + 哈希/来源记录」vs 含「权限声明 UI」。阻塞节点 D（插件信任模型最小集）的实施。
- 决策3（已决）：任务创建参数化（原节点 J）**取消**——local 插件 Create→dialog（PublishToFrontend/SubscribeFrontend）模式已实现「按任务用户选择」（声明11），无需 host 参数通道。S4 仅余 audio 资源类型前置（节点 G）。
- 决策4：起步节点——C（契约稳定性，地基）还是 I（tag 演化设计，你要尽快讨论）。不阻塞大盘。

**自曝风险**：

- 风险1：节点 D 的信任最小集（提示+哈希）对真实恶意插件防护有限，完整沙箱（reveal 延后）才是实质隔离——发布给第三方生态前需明确「最小集非安全边界」的定位。
- 风险2：节点 C 的 DTO 漂移防护若用契约测试，需长期维护 SDK dto 与主程序 entity 的同步断言，有维护成本；若用代码生成则引入构建复杂度。
- 风险3：节点 G 开放 ResourceTypeRegistry 会动摇「封闭枚举 + 严格识别」根基——渲染分发、完整性校验（ValidateResourceStructure）、PrimaryRoles 派生如何跟随自定义类型扩展，设计需谨慎，否则破坏声明6 的不变量。
- 风险4：声明10 的 tag_type 值不一致是 latent 隐患，节点 I 演化前必须先统一 + 数据迁移，否则踩雷。
- 风险5：9 节点大盘挂在单 epic A 下偏大，跨会话焦点易散（已由 task-graph 结构化 mitigate）。

## 一、审计范围与方法

正式发布后，软件将面对**更多需支持的站点**与**第三方开发者**，带来资源类型、作品集结构、tag 语义、契约稳定性、安全等扩展压力。本审计从 `doc/todo.md` 筛选相关待办 + 两轮代码核查 + 自查，定位发布前应处理的契约空白。

核查手段：Explore agent 核验实现层 7 项（版本协商/信任安全/能力探测/DTO 耦合/崩溃恢复/资源类型可扩展性/设置迁移）+ Explore agent 核验 tag 模型 6 项；自查任务创建参数流与作品集层级契约。

## 三、三个已澄清项

### 3.1 tag 体系演化（节点 I）

现状：`local_tag`（带 `base_local_tag_id` 树状层级）+ `site_tag`（`local_tag_id` 外键桥接）+ `re_work_tag`（work 挂点，带 TagType）；无 category/kind/synonym；作者与 tag 两套并行体系；插件声明面 `TaskSiteTagDTO` 仅 name+id+description；site→local 绑定全靠用户手动（插件导入不自动建）。

**e-hentai 驱动（用户提供，节点 I 的核心担忧来源）**：e-hentai 的类-tag 体系含**命名空间**——语言（language）、作者（artist）、角色（character，作品中出现的角色）、原作（parody，二创作品所基于的原作），以及 tag 的**性别属性**（标识 tag 含义作用于作品中哪个性别，如 `female:`/`male:` 命名空间）。当前扁平 tag 模型（无 namespace/category）无法承载这些维度，导入即**丢信息**。此例倾向「tag 加 namespace 维度」方向（A 路线扩展），但 artist/author 命名空间与现有独立 author 体系的归属须在设计中厘清（合并进 tag namespace 还是保持 author 独立体系）。

演化张力（对应 todo#37）：A 路线扩展现有模型（加 namespace 字段，复用层级，较轻，契合 e-hentai 命名空间观察）vs B 路线新增类-tag 分立体系（仿 author，每个语义种类一套表，适合语义差异大但表数膨胀）。两路线共同前置：声明面 `TaskSiteTagDTO` 要能表达 namespace/性别等更多语义；site→local 绑定当前全靠用户手动，富语义下需考虑自动或半自动映射。演化前必清声明10 的 tag_type 不一致 + 修正 glossary.md 把 local↔site 关联表误写为 re_work_tag 的文档错误。

**方向已决（b·namespace 关联级属性）**：经 e-hentai 核实（其用 `namespace:tag` 复合身份，但属单站点、namespace 体系一致）+ 多站点现实（多数站点无 namespace）权衡，选定 namespace 为 **work↔tag 关联级属性**而非 tag 身份——local_tag 保持扁平不变，site_tag/re_work_tag 加 nullable namespace 列，local/site 关联通用。完整 schema/迁移/搜索方案见 doc/plan/tag体系演化方案.md。

### 3.2 S4 可行性（bilibili 封面/音频/完整 → 不同任务）

S4 本体是 bilibili 插件功能，不入本 epic。其主程序前置经补充信息澄清后**仅余一项**：
- audio 资源类型：当前无，属节点 G（资源类型扩展）的子集。
- 原「按任务用户选择参数通道」前置**取消**——local 插件已证明 Create→dialog（PublishToFrontend/SubscribeFrontend）模式可成熟实现「创建期用户每次选择」（声明11），无需 host 参数通道；bilibili 的封面/音频/完整选择复用同一 dialog 模式即可（插件弹自己的选择 UI）。

封面(image)、完整视频(video) 当前已支持；audio-only 受阻于无 audio 类型（G）。

### 3.3 能力探测声明化（并入节点 C）

当前能力分四类机制（必选 TaskHandler / nil 检查可选 SiteBrowser 与生命周期回调 / 可选接口 WorkOrderQuerier / Activate 运行时注册）。主程序不读 `plugin.json` 探测能力。声明化（manifest 声明能力清单）的价值：静态可知、前端徽标、懒激活、兼容校验——随 S1/S2 等新能力加入而升值，故并入 C（与版本协商共用 manifest 载体）。

## 四、任务图结构（单 epic A，9 节点）

```text
A [进行中] 完善插件约定，为正式发布做准备
├─ [完成] B 作品集作品排序（原站序/本地序双轨）
├─ [未开始] C 插件契约稳定性与版本化 — 版本协商 + 能力声明化 + DTO 漂移防护（地基，建议最先）
├─ [未开始] D 插件信任模型最小集 — 安装信任提示 + 哈希/来源记录
│  └─ [延后] D' 完整沙箱隔离（reveal，体量大，独立 epic）
├─ [未开始] E 配置升级迁移 — schema_version + 迁移钩子
├─ [未开始] F 崩溃自动恢复 — respawn/restart + 状态恢复
├─ [未开始] G 资源类型扩展 T3 — 开放 ResourceTypeRegistry + 渲染分发/完整性校验扩展（内含 audio）
├─ [未开始] H 插件作品集父子关系与子集排序 — TaskWorkSetDTO 加层级 + 子集序能力（对齐 B 的 QueryWorkSetOrder 模式）
├─ [未开始] I tag 体系演化设计 — 方向决策 + 声明面扩展 + 清 tag_type 隐患
│  └─ [延后] I' tag 演化实施（reveal）
└─ [延后] J 任务创建参数化（reveal）— S4 的 (b) 前置
```

合并理由：C 揉合版本协商/能力声明/漂移防护三者（共用 manifest + 契约测试基建，作为一个交付更连贯，内部拆分归其 plan）；D 拆「最小集(derive) + 完整沙箱(reveal)」；S4 不入 epic 但其两个前置（audio→G、参数通道→J）已挂树。

## 五、决策与约束

- **单 epic 统揽**：9 节点挂 A 下不拆分（用户决策），焦点在节点级，由 task-graph 结构化防散。
- **C 为地基**：版本协商与能力声明化先行，为 G/H 提供能力声明载体、为 D2 提供兼容校验基础。
- **封闭枚举根基不可轻动**：G 开放 ResourceTypeRegistry 须同步设计渲染分发与完整性校验的扩展点，不可破坏声明6 的严格识别不变量（风险3）。
- **演化前清障**：I 实施前必须统一 tag_type 值并做数据迁移（风险4）；本文档登记的 latent 隐患（声明10、glossary 文档错误）随对应节点修复。
- **最小集非安全边界**：D 的信任最小集定位为「信任 signaling + 来源追溯」，非实质隔离；完整沙箱（D'）是发布给不可信第三方前的实质安全项，延后但需在发布说明中明确。
