# 作品删除方案

## Context

当前程序没有"逻辑删除/可复原"能力。代码层存在一个**纯物理级联删除**方法 `work.Service.DeleteWorkAndSurroundingData`（`backend/work/service.go:376`）：

- 事务内删 `re_work_tag` / `re_work_work_set` / `re_work_author` / `resource` / `work`；
- 事务后删磁盘文件，**硬编码 `backup=false`**（`service.go:415`），资源文件直接物理删除，不可恢复；
- 不处理关联 Task。

并且该方法**已通过 `WorkHandler.DeleteWorkAndSurroundingData`（`handler.go:50`）暴露给前端**，`WorkDialog.vue:350 deleteWork()` 直接调用——也就是说当前前端的"删除"就是**不可恢复的物理删除**。项目**无任何软删除机制**（`BaseEntity` 仅 `ID/CreateTime/UpdateTime`，GORM 未启用软删除）。

**目标**：

1. **逻辑删除**：作品及其全部周边数据从正常视图中消失，但可通过"回收站"**100% 复原**（含作者/标签/作品集关联信息及资源文件），资源文件复用现有 Backup 模块。
2. **回收站 TTL**：回收站条目超过保留天数自动彻底清理。
3. **物理删除**：作为后端内部能力保留（复原冲突的"覆盖"分支需要），**按决策不提供用户入口**——现有前端物理删除入口改造为逻辑删除。

## 删除范围界定（核心约束）

**原则：删除作品时，只删除"作品自身的记录"和"作品与外部的关联记录"，绝不删除被关联的独立实体本身（资源除外——资源属于作品自身）。**

| 数据 | 类别 | 逻辑删除 | 物理删除 | 复原 |
|------|------|---------|---------|------|
| `work` 主记录 | 作品自身 | 删（进快照） | 删 | 从快照重建 |
| `re_work_author` | 关联 | 删（进快照） | 删 | 重建 |
| `re_work_tag` | 关联 | 删（进快照） | 删 | 重建 |
| `re_work_work_set` | 关联 | 删（进快照） | 删 | 重建 |
| `resource` | 资源（作品自身） | 删（进快照） | 删 | 重建 |
| `persistent_store` | 资源登记 | 删（进快照） | 删 | 重建（新 id） |
| 资源文件（磁盘） | 文件 | 移动到 `backup/` | 物理删除 | 从 `backup/` 还原 |
| `local_author` / `site_author` | 作者实体 | **保留** | **保留** | — |
| `local_tag` / `site_tag` | 标签实体 | **保留** | **保留** | — |
| `work_set` | 作品集实体 | **保留** | **保留** | — |
| `site` | 站点实体 | **保留** | **保留** | — |
| `task` | 下载任务（独立软关联） | **不在删除范围**：仅停止运行中实例，记录保留 | 同左 | — |

> 逻辑删除与物理删除的"删除范围"完全相同（删 `work` + 三个关联表 + `resource` + `persistent_store` + 处理资源文件）。区别仅在于：逻辑删除把"关联元数据"序列化为快照、把"资源文件"移入 Backup，保留可复原副本；物理删除直接丢弃。

## 设计原则

1. **逻辑删除 = 快照 + 文件备份 + 物理删除原记录**：逻辑删除后 `work` 及其关联、`resource`、`persistent_store` 在 DB 中**物理消失**（不引入软删除字段、不改造任何查询）。可复原副本分两处：关联元数据进新增 `recycle_bin` 快照表，资源文件进现有 Backup 模块的 `backup/` 目录。
2. **职责分离，复用现有模块**：Backup 模块只负责"文件级"备份与还原（`MoveToBackup` / `StoreFromExternal`），本方案不改其语义；`recycle_bin` 只负责"作品关联元数据级"快照与重建。两层通过 `backup_id` 衔接。
3. **资源文件用"移动"而非"复制"**：逻辑删除时 `os.Rename` 移入 `backup/`（O(1)、省空间），复原时移回原位。
4. **被关联实体一律保留**：作者/标签/作品集/站点是可被多作品复用的独立实体，删除作品仅清关联行。
5. **物理删除内部化**：`HardDeleteWork` 作为 `work.Service` 内部方法，不经 handler、不生成前端 binding，仅供复原"覆盖"分支调用。
6. **task 不在删除范围**：删除/复原均不改动 `task` 记录，仅停止运行中的关联任务实例。

## 总体架构

```
┌──────────────────── 逻辑删除（SoftDelete，对前端暴露）────────────────────┐
│ 1. 收集 resource(work_store_id, thumbnail_store_id) + 三类关联             │
│ 2. [事务外] 资源文件 MoveToBackup → Backup 记录(含 original_file_path)      │
│            + 得 backupId；persistent_store 记录保留                         │
│ 3. 构建 recycle_bin 快照 JSON（work + authors + tags + workSets             │
│            + resources[含 backupId 映射]）                                  │
│ 4. [事务内] 写 recycle_bin → 删 persistent_store → 删三类关联                │
│            → 删 resource → 删 work                                          │
│ 5. [Task] 停止运行中关联任务实例（记录保留）                                 │
└─────────────────────────────────────────────────────────────────────────────┘
                              │ 删除后：work/关联/resource 在 DB 物理消失，资源文件在 backup/，元数据在 recycle_bin
                              ▼
┌──────────────────── 复原（Restore，对前端暴露）────────────────────────────┐
│ 1. 读 recycle_bin 快照                                                      │
│ 2. 冲突检查：(site_id, site_work_id) 是否已被新作品占用                     │
│ 3. [事务外] 逐 backupId：从 backup 还原文件到原位 + 建新 persistent_store    │
│            → 得 storeId 映射 → 删 backup 记录                               │
│ 4. [事务内] 引用校验 → 重建 work → 重建 resource(填新 storeId)               │
│            → 重建三类关联 → 删 recycle_bin                                   │
└─────────────────────────────────────────────────────────────────────────────┘

┌────────── 彻底删除（Purge，对前端暴露，回收站界面）─────────────────────────┐
│ 删 recycle_bin 快照 + 删对应 backup 记录与 backup/ 磁盘文件                 │
└─────────────────────────────────────────────────────────────────────────────┘

┌──── 物理删除（HardDeleteWork，后端内部、不暴露，复原"覆盖"分支调用）──────┐
│ 1. [Task] 停止运行中关联任务实例（记录保留）                                 │
│ 2. 复用现有 DeleteWorkAndSurroundingData（backup=false，物理删文件）         │
└─────────────────────────────────────────────────────────────────────────────┘

┌──────────────── 自动清理（TTL，后台 goroutine）────────────────────────────┐
│ 每 24h（启动时立即一次）：ListExpired(retentionDays) → 逐条 Purge           │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 详细设计

### 1. 新增数据模型：`recycle_bin`（回收站快照表）

**实体** `backend/base/model/entity/recycle_bin.go`：

```go
type RecycleItem struct {
    *model.BaseEntity
    WorkID     sql.NullInt64  `gorm:"column:work_id"`            // 原作品 ID（溯源，不参与复原）
    SiteID     sql.NullInt64  `gorm:"column:site_id;index"`      // 冗余，列表筛选
    SiteWorkID sql.NullString `gorm:"column:site_work_id"`       // 冗余，列表展示
    WorkName   sql.NullString `gorm:"column:work_name"`          // 冗余，列表展示
    Thumbnail  sql.NullString `gorm:"column:thumbnail"`          // 冗余缩略图 backup 路径，列表展示（可选）
    DeleteTime int64          `gorm:"column:delete_time;index"`  // 逻辑删除时间（TTL 依据）
    Snapshot   string         `gorm:"column:snapshot;type:text"` // 完整快照 JSON
}
```

> 冗余字段仅为回收站列表展示/筛选/TTL 服务，**复原只依赖 `Snapshot`**。`recycle_bin` 注册到 `backend/migration/migrate.go`。

**快照 JSON 结构**（保存"无法从 Backup 表还原"的全部关联元数据）：

```jsonc
{
  "work": {
    // work 表全部业务字段（site_id/site_work_id/site_work_name/site_author_id/
    //   site_work_description/site_upload_time/site_update_time/nick_name/
    //   local_author_id/last_view/create_time/update_time）
  },
  "authors": [
    { "authorType": 1, "localAuthorId": 2, "siteAuthorId": null, "roleName": "画师", "sortOrder": 1 }
  ],
  "tags": [
    { "tagType": 1, "localTagId": 3, "siteTagId": null }
  ],
  "workSets": [
    { "workSetId": 5, "isCover": true, "sortOrder": 0 }
  ],
  "resources": [
    {
      "taskId": 10, "enabled": true, "suggestName": "...", "resourceComplete": 100,
      "workStoreBackupId": 1001,      // 主资源 Backup 记录 ID（0 = 删除时无主资源文件）
      "thumbnailStoreBackupId": 1002  // 缩略图 Backup 记录 ID（0 = 无缩略图）
    }
  ]
}
```

**关键设计点**：
- 快照存 `backupId`（Backup 表主键，持久稳定）而非 `persistent_store.id`（复原后会变）。
- Backup 记录自身的 `original_file_path`/`original_file_name`/`file_path` 已承载文件级信息（`backend/backup/service.go:248-250`），快照不重复。
- `resource` 的业务字段（`task_id`/`enabled`/`suggest_name`/`resource_complete`）必须进快照，Backup 不保存。

### 2. 逻辑删除流程（`SoftDeleteWork`）

```
1. 校验 work 存在
2. 收集：
   - resources = resourceDeleter.ListByWorkId(workId)            // 含 work_store_id/thumbnail_store_id
   - authors   = reWorkAuthorReader.ListByWorkId(workId)          // 含 author_type/role_name/sort_order
   - tags      = reWorkTagReader.ListByWorkId(workId)
   - workSets  = reWorkWorkSetReader.ListByWorkId(workId)         // 含 is_cover/sort_order
3. [事务外] 资源文件备份：
   对每个 resource 的 work_store_id / thumbnail_store_id（Valid 的）：
     先 StoreReader.GetById 取 store 的 FilePath/FileName/FilenameExtension
     backupId = backup.Service.MoveToBackup(
         sourceId = store.id,
         absFilePath = filepath.Join(workDir, store.FilePath),
         originalFilePath = store.FilePath,        // 复原依据
         originalFileName = store.FileName,
         originalFilenameExtension = store.FilenameExtension)
     // MoveToBackup 仅：移动文件到 backup/ + 建 Backup 记录，【不删 persistent_store 记录】
     收集 backupId 映射（store id → backupId）
4. 构建 recycle_bin.Snapshot（work 字段 + authors + tags + workSets +
   resources[填 backupId]）
5. [事务内 ExecInTransaction]：
   - recycleBinRepo.Save(recycleItem)
   - 对每个 store id：persistentStoreRepo.Delete(storeId)        // 文件已在 backup，删记录安全
   - reWorkAuthorWriter.DeleteByWorkId / reWorkTagWriter.DeleteByWorkId /
     reWorkWorkSetWriter.DeleteByWorkId
   - resourceDeleter.DeleteByWorkId
   - workRepo.Delete
6. [Task] 见 §6
```

> **事务一致性（best-effort）**：文件移动（步骤 3）在事务外，文件 IO 不可回滚。若事务（步骤 5）失败回滚，DB 记录完整恢复，但资源文件已移入 `backup/`（Backup 记录也已写）——作品表现为"资源文件暂不可用"，文件本身未丢失。这是本地 SQLite + 文件系统固有的跨存储一致性窗口，与现有 `DeleteWorkAndSurroundingData`（事务后 best-effort 删文件）同属一类哲学。**刻意让 `MoveToBackup` 不删 `persistent_store` 记录**，使事务失败时 DB 侧完整回滚，不一致面收敛到"文件已在 backup"这一可恢复状态（见 §风险 1）。
>
> **为何不用 `persistentStore.Delete(id, backup=true)`**：该方法（`persistentStore/service.go:425`）把"移动文件 + 建 Backup 记录 + 删 persistent_store 记录"打包且删记录在事务外，事务失败时无法回滚 → `resource` 悬空。拆分的 `MoveToBackup` + 事务内删记录更可控。

### 3. 复原流程（`RestoreWork`）

```
1. recycleItem = recycleBinRepo.GetById(id)
2. 冲突检查：snapshot.work 的 (site_id, site_work_id) 经 WorkChecker 查是否已存在 work
   - 已存在（删除后用户又下载了同一作品）→ 返回冲突，前端让用户在两选项中决策：
     a) 放弃复原（保留新作品）
     b) 覆盖（内部 HardDeleteWork 删除新作品，再复原）
     默认提示，不静默覆盖。无第三选项（决策 2）。
3. [事务外] 文件还原：
   对 resources 中每个 backupId > 0：
     backup = backupReader.GetById(backupId)
     newStoreId = persistentStore.StoreFromExternal(
         srcAbsPath = backupReader.GetBackupPath(backup),
         relPath     = backup.OriginalFilePath,
         fileName    = backup.OriginalFileName)
     // StoreFromExternal：校验 relPath（store/resource|thumbnail 前缀）→ os.Rename 移回原位 → 建新 persistent_store
     backupReader.Delete(backupId)            // 清理 Backup 记录（文件已被移走）
     记录 backupId → newStoreId 映射
4. [事务内 ExecInTransaction]：
   - 引用校验：authors/tags/workSets 引用的 local_author_id/site_author_id/local_tag_id/site_tag_id/work_set_id
     是否仍存在；不存在的关联行跳过（部分复原，见 §风险 4）
   - 重建 work（新自增 id，写快照字段；关联都用新 work id 重建）
   - 重建 resource：work_id=新workId, work_store_id/thumbnail_store_id 取自步骤 3 映射，
     其余字段(task_id/enabled/suggest_name/resource_complete)取自快照
   - 重建 re_work_author / re_work_tag / re_work_work_set（work_id=新workId）
   - recycleBinRepo.Delete(recycleItem.id)
```

> 复原的文件还原复用 `StoreFromExternal` + Backup 记录清理，与 `RestoreAllStores`（`store_backup_orchestrator.go:185-211`）同源；区别是复原是"resource 全部新建"，不需其"更新已存在 resource.store_id"那步。

### 4. 物理删除流程（`HardDeleteWork`，后端内部、不暴露）

> 按决策 3，对正常状态作品的物理删除**不提供用户入口**。`HardDeleteWork` 作为 `work.Service` 的内部方法（**不经 WorkHandler、不生成前端 binding**），仅服务于复原"覆盖"分支（§3 步骤 2-b）。

```
1. [Task] 停止运行中关联任务实例（保留记录，见 §6）
2. workService.DeleteWorkAndSurroundingData(workId)   // 现有方法，backup=false 物理删文件
```

直接复用现有级联方法（删除范围与本方案界定一致），仅前置 Task 停止。无需改动 `DeleteWorkAndSurroundingData` 的实现。

### 5. 回收站彻底删除（`Purge`，对前端暴露）

针对**已逻辑删除、存在于回收站**的作品，彻底销毁（不可恢复）：

```
1. recycleItem = recycleBinRepo.GetById(id)
2. 解析快照，收集所有 backupId
3. [事务外] 删 backup 文件 + 记录：
   对每个 backupId：
     backup = backupReader.GetById(backupId)
     os.Remove(backupReader.GetBackupPath(backup))   // 删 backup/ 磁盘文件
     backupReader.Delete(backupId)                    // 删 Backup 记录
4. [事务内] recycleBinRepo.Delete(recycleItem.id)
```

> `Purge`（回收站内作品的彻底删除，暴露前端）与 `HardDeleteWork`（正常状态作品的物理删除，内部）针对的目标位置不同：前者 work 记录已删、文件在 `backup/`；后者 work 记录仍在、文件在 `store/`。

### 6. Task 处理（已定）

作品通过 `(site_id, site_work_id)` 与 `task` 软关联（`task` 无 `work_id` 外键）。**task 属独立下载凭证，不在作品删除范围**（决策 1）：删除/复原均**不改动 task 记录**。仅：

- **停止 `taskManager.Manager` 中正在运行的关联任务实例**（必须，否则任务完成后会重新创建 `work`/`resource`，破坏删除/复原）。
- **保留 task 记录**（含 `PluginData`/`URL`/`PluginPublicID` 等下载凭证）；复原 `work` 后，task 经 `(site_id, site_work_id)` 自动重新关联到复原的作品。

**实现**：`taskManager.Manager` 新增"按 `(site_id, site_work_id)` 停止运行中任务实例"的入口（复用 `StopTaskTree`，`manager.go:620`），仅停内存实例、不删 DB。`task.Repository.ListBySiteAndSiteWorkID`（`task/repository.go:327`，已存在）用于反查关联任务。

### 7. 自动清理（TTL）

回收站条目超过保留天数后自动 `Purge`，避免 `backup/` 文件无限累积（决策 4）。

**配置**（`config/settings.json` 运行时设置，用户可调）：

`settings.Settings` 结构体新增 `RecycleBinSettings`：

```go
type RecycleBinSettings struct {
    AutoCleanupEnabled bool `json:"autoCleanupEnabled"` // 默认 true
    RetentionDays      int  `json:"retentionDays"`      // 默认 30
}
```

`defaultSettings()`（`backend/settings/service.go:24`）提供默认值；用户经 `SettingsHandler` 调整（koanf path 如 `recycleBin.retentionDays`，沿用现有 `SaveSettings(changes)` 模式）。

**后台清理 goroutine**：

- 挂载点：`recycleBin.Service` 初始化时启动后台 goroutine，持有可取消 `context.Context`（应用关闭时取消，避免泄漏）。参考现有模式：`main.go:164` 的 `go func() + time.Sleep`、`manager.go:828` 的 `time.NewTicker`。
- 节奏：**启动时立即执行一次**（清理上次运行期间过期的条目），随后每 24h 检查一次（间隔常量 `24h`，不暴露配置，保持简单；如需可调再扩展）。
- 逻辑：
  1. 读 `RecycleBinSettings`，`AutoCleanupEnabled=false` 则跳过。
  2. `recycleBinRepo.ListExpired(retentionDays)`：查 `delete_time < (now - retentionDays*86400000)` 的记录（`delete_time` 为毫秒时间戳）。
  3. 逐条执行 `Purge`（§5）。
  4. 记录清理日志（logger），便于追溯。

> 自动清理即 `Purge`，被清理作品不可恢复。TTL 仅作用于回收站条目，不影响 Backup 模块原有的替换场景备份（那些由 `RestoreAllStores` 还原后清理）。

### 8. 模块划分与 Handler 暴露

新增模块 `backend/recycleBin/`（handler-service-repository）：

```go
// recycleBin/handler.go（对前端暴露）
func (h *Handler) Page(ctx, page, query) *ApiResponse[Page[RecycleItemDTO]]   // 回收站列表
func (h *Handler) Restore(ctx, id int64) *ApiResponse[any]                    // 复原
func (h *Handler) Purge(ctx, id int64) *ApiResponse[any]                      // 彻底删除

// work/handler.go（对前端暴露）
func (h *Handler) SoftDelete(ctx, id int64) *ApiResponse[any]                 // 逻辑删除（移入回收站）
```

**前端入口迁移（决策 3 的关键影响）**：现有 `WorkHandler.DeleteWorkAndSurroundingData`（`handler.go:50`）是已暴露前端的**物理删除**入口，`WorkDialog.vue:350 deleteWork()` 调用、wrapper `workDeleteWorkAndSurroundingData`（`frontend/src/apis/http/wrappers/work.ts:83`）。改造为：

- **移除** `WorkHandler.DeleteWorkAndSurroundingData`（handler 方法，遵循 DEAD_CODE_CLEANUP，移除后前端不再有物理删除入口）。其 service 实现 `work.Service.DeleteWorkAndSurroundingData`（`service.go:376`）**保留**，作为 `SoftDeleteWork`/`HardDeleteWork` 的内部复用。
- **新增** `WorkHandler.SoftDelete`（逻辑删除，暴露前端）。
- `work.Service.HardDeleteWork`（内部方法，**不经 handler**，复原覆盖分支通过注入的接口调用）。
- 前端 `WorkDialog.vue:350 deleteWork()` 改调 `workSoftDelete`；wrapper `workDeleteWorkAndSurroundingData` 替换为 `workSoftDelete`。

运行 `wails3 generate bindings -ts` 重新生成前端 bindings；前端新增回收站页面/入口（列表 + 复原 + 彻底删除）。

**前端入口**：作品卡片/详情的删除按钮执行**逻辑删除（移入回收站）**；回收站界面提供"复原"与"彻底删除（Purge）"。**无"永久删除"用户入口**。

### 9. work.Service 新增依赖（接口隔离，符合 SERVICE_DEPENDENCY_VIA_INTERFACE）

`SoftDeleteWork`/`RestoreWork` 需读取三类关联与 store（现有 service 仅持有 Writer/Deleter，需补 Reader）：

```go
ReWorkAuthorReader  { ListByWorkId(ctx, workId) ([]*entity.ReWorkAuthor, error) }
ReWorkTagReader     { ListByWorkId(ctx, workId) ([]*entity.ReWorkTag, error) }
ReWorkWorkSetReader { ListByWorkId(ctx, workId) ([]*entity.ReWorkWorkSet, error) }
StoreReader         { GetById(ctx, id) (*entity.PersistentStore, error) }   // 取 FilePath/FileName/Ext 喂给 MoveToBackup
```

各仓储补对应 `ListByWorkId`（复用 `BaseRepository`，符合 BASE_REPOSITORY_REUSE）。`recycleBin.Service` 通过接口注入 `work.Service`（复原覆盖调 `HardDeleteWork`）、`backup.Service`、`persistentStore.Service`、各关联仓储。

## 注意点与风险

1. **跨存储事务一致性（best-effort）**：文件移动在 DB 事务外，无法跨存储原子。逻辑删除刻意拆分"移动文件+建 Backup 记录"（事务外）与"删 persistent_store 记录"（事务内），使事务失败时 DB 完整回滚、文件留在 `backup/` 可恢复。极端失败下可能残留孤儿 Backup 文件/记录（文件已移但 recycle_bin 未建），属可接受的低频边界；TTL 清理与人工可兜底。

2. **复原时的唯一索引冲突**：`work` 表 `(site_id, site_work_id)` 为唯一索引（`idx_work_site_site_work`）。逻辑删除后该键释放，用户可能重新下载同一作品占据此键；复原时若冲突，由用户在"放弃/覆盖"两选项中决策，不静默覆盖（决策 2，无第三选项）。

3. **作品集封面失效**：被删作品若是某作品集封面（`re_work_work_set.is_cover=true`），删除后作品集封面悬空。逻辑删除复原可恢复；若该作品被 Purge/HardDelete，作品集封面兜底交由现有 `ListMinSortOrderWorkIdsByWorkSetIds`（`reWorkWorkSet/repository.go:187`）。本方案不主动改写封面（保持"原样复原"）。

4. **复原时被引用实体已被删除**：删除期间用户可能删掉了某 `local_author`/`local_tag`/`work_set`。复原重建关联时校验被引用实体仍存在，不存在的关联行跳过（部分复原），不可写入悬空外键。

5. **资源文件路径已被占用**：复原时 `StoreFromExternal` 把文件移回原 `store/resource/...` 路径，若该路径已被新文件占用，复原前应检测目标路径是否已存在并处理。

6. **多 Resource 作品**：业务上通常一 `work` 对一 `resource`，但实体允许一对多。快照 `resources` 为数组，逻辑删除/复原按数组逐条处理，兼容多 Resource。

7. **Backup `source_id` 悬空无害**：Backup 记录 `source_id` 指向已删的 `persistent_store.id`，复原/Purge 依赖 `backup_id`（快照存）而非 `source_id`，悬空无影响。

8. **TTL 清理与复原/手动 Purge 的并发**：后台 TTL goroutine 与用户手动复原/Purge 可能并发操作同一回收站条目。`Purge`/`Restore` 操作以 `recycle_bin.id` 为准并删除该记录，需确保操作原子（事务内先锁定/校验记录存在再删），避免 TTL 与手动操作重复处理。

## 不涉及的部分

- **不引入软删除字段**：`work`/`resource`/关联表均不加 `deleted_at`，不改造任何现有查询。
- **不改动 Backup 模块语义**：`MoveToBackup`/`StoreFromExternal`/`RestoreAllStores` 保持原样，仅被复用。
- **不改动 `DeleteWorkAndSurroundingData` 的级联范围与实现**（SoftDelete/HardDelete 复用）。
- **不级联删除作者/标签/作品集/站点实体**（仅清关联）。
- **不改动 task 记录**（仅停止运行实例，task 不在删除范围）。
- **不提供物理删除用户入口**（决策 3，HardDelete 内部化）。
- **不通知插件**：当前 SDK 无作品删除扩展点（`TaskHandler` 仅 8 个 rpc），删除不通知插件。

## 已确认决策

1. **Task 处理**：停止运行中关联任务实例 + **保留 task 记录**。task 属独立下载凭证，**不在作品删除范围**，删除/复原均不改动 task 记录。
2. **复原冲突**：仅"放弃/覆盖"两选项，**无第三选项**。
3. **前端暴露范围**：仅暴露逻辑删除（`SoftDelete`）+ 回收站管理（`Page`/`Restore`/`Purge`）。**物理删除不提供用户入口**——现有 `WorkHandler.DeleteWorkAndSurroundingData` 前端入口移除，`deleteWork` 改调逻辑删除；`HardDeleteWork` 作为 `work.Service` 内部方法（不经 handler、不生成 binding），仅供复原"覆盖"分支调用。
4. **回收站 TTL**：启用自动清理，超过保留天数（默认 30，settings 可调）自动 Purge；后台 goroutine 启动时立即清理一次 + 每 24h 检查。
