**自曝风险：**

- 风险1：**收录窗口期**——插件独立发版后、主程序发版收录名单前，新版官方包不命中（保守显示本地，无危害增益）；dirty 构建/绕过管线的手工包同样不入名单。对照原现场比对设计（只能识别当前捆绑版本、盲区永久），名单累积机制把盲区收窄为窗口期，是裁决带来的覆盖增强。
- 风险2：同 buildId 不同 contentDigest 的冲突（跨机构建同源码、exe 嵌路径致字节不同）——官方管线应唯一；若发生，名单 upsert 以最新管线产出为准并在构建日志警示，另一字节形态的手装包不命中（保守方向，可接受）。
- 风险3：摘要算法跨语言分叉风险——名单生成统一走 Go 工具（PS 仅调用 `go run`），单一实现消除 PowerShell/Go 两套 sha256 聚合逻辑漂移的可能；Go 工具属 `build/` 脚手架域，`go build ./...` 全量须排除的既有纪律（PostToolUse 钩子）已覆盖。
- 风险4：`Official` 落库 true 后不随主程序升级翻转（证实的是历史事实），经重装换内容时随 `installCore` 重算覆盖；存量证实仅对 buildId 相等（双方非空）的行做目录摘要，未打标历史包不证实（保守，仅损失展示）。
- 风险5：开发库 id=2/3 存量行的 buildId（`e894386-dirty`/`1d7bd5e-dirty`，dirty 构建）与下次管线产出的 buildId 是否相等取决于插件仓库工作树状态——不相等则存量不纠正（显示维持本地），属预期而非缺陷，实机验证以实际比对结果为准。
- 风险6：**类别纪律风险**——未来往订死类别（`locked_config.yaml`）加新键时必须保持「不进 viper 合并链」：一旦误走 `MergeConfig`/磁盘合并，该键即获得磁盘覆盖路径、防篡改静默失效。类别入口单一（config 包独立加载函数）+ 文件名即语义可缓解，但属登记义务，需在 config 包注释与 `.claude/rules` 声明。
- 风险7：**名单误录的纠错路径**——「旧条目永不删除」策略下若构建管线误录指纹（人为失误或管线被篡改，把非官方产物的 digest 写入名单），该产物将被永久判官方；纠错只能下版删条目再发版（名单随 git 维护，发现即删）。危害面被决策2/3 隔离在展示层（不接运行门控/升级权），非安全语义，故可容忍此纠错延迟。

## 1. 背景与问题

插件信任模型（`.claude/rules/plugin.md`「插件信任模型」节）中 `plugin.Source` 按**安装入口**判定：`InstallBundled→bundled`、`InstallFromPath→local`。UI 消费侧方案（`doc/plan/插件管理页来源标识强化方案.md`，已实施）把 source 消费为官方性二分（bundled=绿「官方」、其余=灰渠道文案），达成 README「按官方/第三方区分」承诺。

缺口：用户手动安装官方插件包（如重新下载的 pixivSuite zip）被判 `local` → 显示灰「本地」+ 触发第三方免责提示，与承诺相悖（声明3 的存量行即此形态）；且升级判变对其静默跳过（该跳过系「尊重用户手动安装的版本」的刻意设计，决策2 已裁决维持）。

## 2. 语义分析：渠道与官方性是两个维度

`source` 的本义是**安装渠道**——「用户手动安装」这个渠道事实无论装的是谁的包都成立，渠道判定本身没有错。错在 UI 把渠道维度强解为官方性维度：两个维度只在 bundled 渠道上耦合（host 亲手装 → 通常官方），在「手动安装的官方包」上分裂。

更深的约束是 `source=bundled` 身上挂着的三个安全语义（声明2）：受限模式放行、升级自动重装资格、UI 官方标识（免责豁免）。若走「把手动装的官方包改判 bundled」的路线，三个语义同时被触动——尤其受限模式（安全救生圈）会被照抄 publicId 的伪造包击穿：publicId/buildId 都是 plugin.json 里的字符串，手写即可冒充。

结论：**拆维度**——`source` 保持纯渠道（入口判定、零伪造面），受限模式与升级资格继续挂它（决策2/3）；新增「官方身份」独立字段供展示消费，判定走主程序预记录的指纹名单（决策1）。

## 3. 官方身份（Official）定义

- **实体**：`Plugin` 增加 `Official sql.NullBool`（`gorm:"column:official"`），语义「本行已装内容经 host 证实为官方发布产物（内容摘要命中主程序携带的官方指纹名单）」；NULL/false = 未证实（未命中、窗口期新版、存量未迁移）。经 GORM AutoMigrate 自动加列，存量行为 NULL。
- **DTO**：`PluginDTO` 透传 `official`，bindings 再生成，前端 `plugin.official === true` 消费（与 `trusted === true` 同风格，NULL 保守视作非官方）。
- **与 Trusted 正交**：Trusted = 用户知情同意（运行门控，是否运行）；Official = 发布者身份（展示/免责指向，是谁产的）。互不推导、互不覆盖——手装官方包不自动 trusted（决策6）。bundled 渠道强制 trusted 的既有规则不变。
- **与渠道完全正交**：官方身份统一查名单（bundled 渠道不短路）——config.yaml 清单被换成自制 zip 时，装出的行 source=bundled 但 official=false，官方身份语义保持「内容命中官方产物」单一含义。

## 4. 判定机制：官方指纹名单（决策1 裁决形态）

### 4.1 双配置文件：可覆盖层与订死层

配置体系按「是否允许磁盘覆盖」拆为两个文件，类别即文件：

| 文件 | 层别 | 加载方式 | 磁盘覆盖 |
|---|---|---|---|
| `backend/config/default_config.yaml` | 可覆盖（默认层） | 现有两层合并：embed 基础层 + 磁盘 `config.yaml` 覆盖层（`config.go:105-131`） | **允许**（既有语义，零改动） |
| `backend/config/locked_config.yaml`（新） | **订死（locked）** | 独立 `go:embed` + 独立 `yaml.Unmarshal`，**不参与 viper 合并链** | **路径不存在**——磁盘无对应物、无合并步骤，防篡改由此保证 |

- **实现**：config 包新增 `lockedConfigFS`（`//go:embed locked_config.yaml`）与独立加载函数（如 `loadLocked()`），`yaml.Unmarshal` 到 `LockedConfig` 结构（纯 yaml tag，不走 viper）；`LoadFromDir` 内调用并挂到 `cfg.Locked`，plugin 模块经 `config.Get().Locked.OfficialPlugins` 消费。**调用方无感**——`Locked` 是 `Config` 上与 `Server`/`Database` 并列的普通字段，读取统一走 `config.Get()` 单一入口，双文件/双加载链的差异封装在 config 包内部；`Config.Locked` 字段标 `mapstructure:"-"` 显式排除出 viper 主链（防磁盘 `config.yaml` 手滑写 `locked:` 键时被主 Unmarshal 先填充弄脏单一来源，独立加载是唯一取值路径）。解析失败不拦启动（空名单保守降级，全不命中）。
- **文件形态**（整文件机器生成域，构建管线整体重写安全）：

```yaml
# 订死配置（locked）——随二进制分发的权威数据，不参与两层合并，磁盘无对应覆盖物；
# 由构建管线 task build:plugins 生成维护，勿手改（手改仅影响本地构建产物）
officialPlugins:
  - publicId: com.lvfeng.pixivSuite
    buildId: v1.0.0-394e66f
    contentDigest: sha256hex…
```

- **累积性**：官方插件每发一版，指纹条目由构建管线 upsert（同 publicId+buildId 覆盖 digest，新 buildId 追加），旧条目永不删除——主程序 git 历史跨版本维护，发版携带全量历史。这是覆盖「历届官方版本手装包」的关键（对照现场比对只能识别当前捆绑版本）。
- **类别扩展**：未来其他「随二进制分发的权威数据」加新顶层键进本文件即可，纪律是恒不进 viper 合并链（风险6）。

### 4.2 contentDigest（插件包内容摘要）算法

- **输入源两种形态产出同一摘要**：zip 包（`archive/zip` 读全部文件 entry）与已解压目录（walk 文件，供存量证实）。
- **步骤**：收集 (相对路径正斜杠, 文件内容 sha256hex) 对 → 按路径字典序排序 → 逐条拼接 `"{path}\n{sha256hex}\n"` → 对拼接全文再 sha256，得最终 hex。
- **排除 zip 容器元数据**（entry mtime、压缩参数）——同内容重打包摘要不变（zip 容器字节哈希重构建必变，`doc/plan/插件构建身份与升级判据机制.md` 声明1，故不可用容器哈希）；目录 entry 不参与（仅文件）。

### 4.3 生成管线

- **Go 工具** `build/tools/genofficial/main.go`：输入 zip 路径，读 plugin.json 取 publicId/buildId、按 4.2 算 contentDigest；upsert 进 `backend/config/locked_config.yaml`——整文件即机器生成域，**整体读-改-写**（解析→合并条目→固定文件头注释+marshal 重写），无段替换手术。单一实现，消除 PS/Go 算法分叉（风险3）。
- **接线**：`build/plugins.ps1` 在 `Assert-BuildId` 之后对每个成功构建的 zip 调 `go run ./build/tools/genofficial`（插入点见声明4）。
- **同 buildId 冲突**：digest 不同时以最新管线产出覆盖并日志警示（风险2）。

### 4.4 运行时判定

安装路径上（`InstallFromPath` 加载包得 `installDTO` 后）执行 `matchOfficial(installDTO) bool`（名单取 `config.Get().Locked.OfficialPlugins`，已随 `LoadFromDir` 载入）：

1. 该 `publicId` 无条目 → false。
2. **buildId 短路**：安装包 buildId 不在该 publicId 的条目集 → false（省 10MB 级摘要计算；buildId 不等则内容必不等，声明5）。
3. **终裁**：按 4.2 zip 源算安装包 contentDigest，与条目比对，相等 → true。

`installCore` 统一推导落库（单一推导点，重装链自动正确，声明7）：

```
plugin.Official = matchOfficial(installDTO)
```

### 4.5 伪造面分析（信任锚要求）

来源是信任锚（官方/第三方免责指向），判定不可被包自声明冒充：

| 信号 | 伪造面 | 裁定 |
|---|---|---|
| 包自声明字段（publicId/buildId/version） | 手写 plugin.json 照抄即冒充 | 不可作裁决，仅作定位与短路 |
| publicId/buildId 官方清单（不比内容） | 同上，照抄字符串即冒充 | 否决（第 7 节） |
| **contentDigest 名单命中** | **零伪造面**——摘要与官方发布产物一致意味着它就是官方产物字节本身，伪造成本=必须拥有官方产物 | **采纳（裁决）** |

判定权威源=编译进二进制的 `locked_config.yaml`（host 自带，随官方构建管线生成，不参与 viper 合并、磁盘无覆盖路径，声明8 与第 4.1 节）。防篡改边界外的残余面=替换二进制本身，不在讨论域。

### 4.6 能力极限（诚实声明）

窗口期外，仍有两类不命中（均保守方向、无危害增益）：自建官方源码的包（buildId 相同但 exe 跨机构建字节不同，digest 不等，风险2 的镜像场景）；名单未收录的手工/测试构建。彻底解法是插件签名体系（官方私钥签包、主程序内置公钥验签，任意版本可验），属独立大项延后——名单机制是其子集，未来验签落地后判定可平滑升级。

## 5. 升级维度与受限模式（决策2 裁决 / 决策3）

- **升级判变资格：维持现状（已裁决解耦）**——`needBundledUpgrade` 零改动，仅 `source=bundled` 参与。理由：(a) 「尊重用户手动安装的版本」语义成立——手动装了比捆绑新的官方版，判变会降级回捆绑旧版；(b) 官方身份是展示维度，不授予自动化写操作权（判变重装是自动换版）；(c) 手动装的行即使名单命中（与捆绑同构建），判变本就判「无变化」，零影响。
- **受限模式：维持按 `source` 判定（决策3 推荐）**——救生圈语义是「回到 host 亲手安装的最小集」，与包是谁产的无关；不把任何新维度接进安全语义是本方案的架构纪律。

## 6. 存量纠正（决策4）

历史手动安装的官方行（声明3 的 id=2/3）在启动 `InstallBundled` 扫描的「已装未卸载、判变不成立」跳过分支（`service.go:422-424`）顺带证实：

- 条件：`existing.Official` 非 true，且 `existing.BuildID` 与名单中该 publicId 的某条目 buildId 相等（双方非空）。
- 动作：对已装目录（`existing.RootPath`）按 4.2 目录源算 contentDigest，查名单比对，命中 → `Updates` 置 `official=true`。
- 幂等：证实后短路；未打标历史包不证实（风险5）。常态成本=每次启动一次字符串比较/行，无感。
- 开发库 id=2/3 能否纠正取决于其 dirty buildId 是否被管线名单收录（风险6），实机验证以实际结果为准。

## 7. 被否决/被修正的替代方案

- **（被裁决修正）安装时现场解包捆绑 zip 比对**：本方案初稿形态——每次安装解包主程序自带 zip 现场算摘要。被否决理由：计算浪费（捆绑 zip 摘要重复算）、覆盖仅限「与当前捆绑一致」的包（历届版本永久盲区）。裁决改为名单预记录：运行时只算被判定包一次摘要、查表即可，且名单累积收录历届官方版本（风险1 的对比）。
- **（被裁决修正）磁盘名单文件 `resources/bundled-plugins/official-manifest.json`**：中稿形态——独立 JSON 随捆绑 zip 分发。被否决理由：磁盘 artefact 可被本机用户改写自授官方标。裁决改为嵌入主程序内。
- **（被裁决修正）单文件 locked 段（`default_config.yaml` 内订死段 + 覆回填充）**：第三稿形态——locked 段进 `default_config.yaml`、`LoadFromDir` 磁盘 merge 后 embed 直读覆回。被否决理由：覆回依赖顺序不变量（需单测锚定）、构建工具重写 yaml 丢中文注释（需文本级段手术，脆）、同文件两种读取语义微妙。裁决改为**双配置文件**（`locked_config.yaml` 独立 embed、不进 viper 链，防篡改由「覆盖路径不存在」保证，第 4.1 节）——简单清晰即本轮裁决动机。
- **publicId/buildId 官方清单直接判官方（不比内容）**：照抄字符串无防御——伪造者获绿「官方」标 → 免责提示消失 → 付费纠纷指引错误，信任锚被架空。
- **手动装官方包改判 source=bundled**：渠道事实失真；受限模式、升级资格全被牵动，伪造 publicId 直接击穿救生圈，最不可取。
- **插件签名体系**：密码学彻底解，但需密钥管理、构建签名步骤、第三方签名申请通道设计，独立立项延后；名单机制是其子集，未来平滑升级。
