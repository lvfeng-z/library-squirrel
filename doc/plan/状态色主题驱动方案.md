# 状态色主题驱动方案

## 审查摘要

本方案是对《状态色与主题解耦方案》的**方向纠正**。前者把「解耦」误实施为「状态色固定 EP（Element Plus，前端 UI 组件库）hex、跨主题一致」，与用户最初意图（「状态色族与具体颜色解耦、由主题自行控制」）相反。本方案回归正确方向：**状态语义层抽象（固定映射）+ 颜色层由各主题定义（主题控制），主题自行保证各槽位色相分散以避免撞色**。

### 当前进度（2026-07-23）

- ✅ **脚手架已落地**：forest/ocean/sakura 三个 `theme-*-light.css` 各新增完整状态槽位覆盖（7 tone × text/bg/border = 21 变量——6 通用 + source-site；source-local 不覆盖、仍 `var(--app-color-primary)` 跟随主题主色；值暂同 default EP hex，**零视觉改动**），各文件头部注释与 `--app-color-*` 块注释同步修正。证据：`theme-forest-light.css:71`、`theme-ocean-light.css:71`、`theme-sakura-light.css:71`（状态槽位块）；`tokens.css` `:root` 未动（仍是 default 默认 + 全局 fallback）。StatusTag 零改动已验证（消费 `var(--app-status-${status}-*)`，经别名→tone 解析，主题只覆盖 tone 值）。
- ⏸️ **调色留后**：逐主题填色（含 forest/sakura 撞色修复）+ StatusPalette 改造，均未做（见下文「未做清单」）。文档同步（tokens.css 注释 + frontend.md/plugin-theme-tokens.md/status-color-tuning.md）已于 2026-07-23 完成。

### 关键声明（抽查项）

- 声明1：<未核验，证据为对话原话> 用户最初意图是「状态色族（语义槽位）与具体颜色解耦、主题自行控制每个槽位颜色」——即 done/fail 等槽位不绑死「绿/红」，各主题自行填色。
- 声明2：当前实现的 tone 段为固定 EP hex。**脚手架后**，forest/ocean/sakura 重新获得了对 `--app-status-{tone}-*` 的覆盖权（值暂同 default），主题重新能控制状态色；`--app-color-{success,warning,danger,info}` 色族覆盖仍服务 EP 组件（el-button/el-tag 经 ep-bridge），与状态槽位是**两条独立轨道、互不引用**。证据：`theme-forest-light.css:21`（EP 色族注释）、`:71`（状态槽位块）。
- 声明3：<已核验> **撞色是逐主题不同的，非统一模式**（这是对本方案原第3节"统一 sketch"的关键纠正）：
  - **forest**：done（绿 `#67c23a`，hue≈100°）↔ primary（绿 `#007038`，hue≈150°）同绿域。证据：`tokens.css:123`（done）、`theme-forest-light.css:5`（primary）。
  - **sakura**：fail（红 `#f56c6c`，hue≈0°）↔ primary（粉 `#ec6d8e`，hue≈344°）同红粉域，**最棘手**——搬 fail 伤"红=危险"通用语义。证据：`tokens.css:127`（fail）、`theme-sakura-light.css:5`（primary）。
  - **ocean**：primary（青 `#1ab7c7`，hue≈185°）与各槽基本不撞（最近 source-local 青绿≈173°、pending 蓝≈210°，但多属不同展示场景），**可能无需改**。证据：`theme-ocean-light.css:5`。
  - **default**：本就不撞（primary 蓝 vs 各状态色经典分配）。证据：`tokens.css:8`（primary）、`:119-141`（各 tone）。
- 声明4：<已核验> **active 槽位不锚定 primary**。default 自身 active=`#f97316`（橙，`tokens.css:119`）≠ primary=`#409eff`（蓝，`tokens.css:8`）；active 是独立的"进行中橙"，应跨主题保持。本方案原第3节"primary 驱动 active"的表述**错误，已弃**。（注：default 里是 pending 巧合等于 primary 蓝，与 active 无关。）
- 声明5：<设计推演> 调色**无法在文字里预演**，须在 StatusPalette 测试页上逐主题视觉迭代。原第3节的 forest 建议（active 橙 / warn 橙 / done 金）三色挤入暖域（橙≈25°/琥珀≈37°/金≈45°），本身即撞色——证明"统一 sketch"不可行。

- 决策4 ✅ 已定：**保留**「状态色板」测试页（改造留后，见风险5）。
- 决策5 ✅ 已定：**保留** forest/ocean/sakura 的 `--app-color-*` 色族覆盖（服务 EP 桥接）；EP 组件色与状态槽位色分家。
- 决策6 ✅ 已定（新增）：**active 保持橙、不锚定 primary**（跨主题一致的"进行中"信号，与 default 现状一致）。
- 决策7 ✅ 已定（新增）：本轮**只搭脚手架**（值=default，零视觉改动），逐主题调色留后单独会话。

### 自曝风险

- 风险1（通用语义认知被打破）：主题驱动下"绿=完成、红=失败"不再全局成立——forest 的完成可能是金、sakura 的失败若搬离红则更甚。需用户接受这是"主题控制"的代价。（用户已确认 forest 绿撞色是**实拍**、非推演，故回退方向正当。）
- 风险2（主题调色工作量大）：每主题需精心设计 6 槽位色相并保证两两分散；且因撞色逐主题不同（声明3），无法套模板，须逐个肉眼迭代。
- 风险3（与 EP 组件色的关系）：状态槽位独立定义，done 的颜色可能与同页面 `<el-button type="success">`（走 `--app-color-success`）不一致——两套"完成/成功"色并存。
- 风险4（回退当前实现）：本方案把已落地的"固定 EP hex"改为"主题可覆盖"，属对刚完成工作的回退；需同步文档。
- 风险5（测试页改造范围被低估）：StatusPalette 不止 hue 标注失真（pending 标 hue=325 实为 `#409eff` 蓝 hue≈210）——`section label`"主题仅微调饱和度/明度"是被删 S/L 方案的措辞，整页"Tone 原色——固定色相"框架在主题驱动下也不再成立。测试页改造比原先估计的大。
- 风险6（组件零改动的前提）：StatusTag 零改动依赖别名命名 `--app-status-{类目}-{语义}-*` 不变；只改 tone 的**值**、不改 tone 的**变量名**。**已验证**（脚手架仅加值覆盖、未改名）。

## 1. 意图纠正

| 维度 | 误解（已废弃实现） | 正确意图（本方案） |
|---|---|---|
| 语义层 | tone 固定 EP hex | 槽位抽象（done/fail 等语义），不绑颜色 |
| 颜色层 | 跨主题锁死一致 | 由各主题定义、随主题变化 |
| 撞色防治 | 固定色相回避 | 主题填色时保证槽位色相分散 |
| 主题控制权 | 无（主题无法影响状态色） | 完全（主题决定每个状态色） |

## 2. 方案：主题驱动的状态语义槽位

三层架构：

1. **语义别名层**（`tokens.css`，固定）：`--app-status-{类目}-{语义}-{bg|text|border}` → 引用语义槽位。状态→槽位的语义映射不变（如 `task-completed`→`done`、`task-processing`→`active`）。
2. **语义槽位层**（即现有 tone 色板，`tokens.css:113-148`）：变量名 `--app-status-{active/done/fail/warn/pending/idle}-{text/bg/border}`（**复用现有命名，不新增中间层、不加 `-tone-` 中缀**，否则 StatusTag 拼名失效，见风险6）。`tokens.css` 的 `:root` 给 default 主题的默认色（沿用当前 EP hex），forest/ocean/sakura 在各自 `theme-*.css` 覆盖这些变量的值。
3. **主题色定义**（`theme-*.css`）：每个主题给 6 个槽位填具体颜色，**自行保证槽位间色相分散**（决策2 定机制）。

> 与最早《主题状态色令牌方案》的区别：那个方案的状态别名引用 `--app-color-{success,warning,...}`（与 EP 组件共用色族），导致 forest 把 success 染绿与 primary 撞；本方案的槽位**独立于** `--app-color-*`（决策1），主题直接给槽位定义颜色，不与 EP 组件色耦合。

## 3. 撞色防治（已按"逐主题不同"重写）

### 3.1 关键事实：撞色逐主题不同

各主题 primary 与状态槽的实际色相关系（hue 为估算，结论可核验）：

| 主题 | primary 色相 | 与哪个状态槽同域 | 棘手度 |
|---|---|---|---|
| forest | 绿 `#007038` ≈150° | **done**（绿 `#67c23a` ≈100°）同绿域 | 中：done 须搬离绿，但落点（金/琥珀）又撞 warn（橙≈37°）/active（橙≈25°），**无处落脚** |
| sakura | 粉 `#ec6d8e` ≈344° | **fail**（红 `#f56c6c` ≈0°）同红粉域 | 高：搬 fail 伤"红=危险"通用语义；或调 primary 偏紫、或接受邻近，需单独裁决 |
| ocean | 青 `#1ab7c7` ≈185° | 最近 source-local（青绿≈173°）、pending（蓝≈210°） | 低：多属不同展示场景，**可能无需改** |
| default | 蓝 `#409eff` ≈210° | 无 | 无：本就不撞 |

结论：**不能套统一模板**。原第3节的 forest 建议（active 橙 / warn 橙 / done 金）三色挤暖域，本身撞色，已证不可行（声明5）。调色须逐主题在 StatusPalette 上视觉迭代。

### 3.2 active 槽位：保持橙、不锚定 primary（决策6）

原第3节"primary 驱动 active"是错误表述，已弃。理由：default 自身 active=`#f97316` 橙 ≠ primary 蓝（声明4），active 是独立的"进行中橙"。保持 active=橙跨主题一致，既与 default 现状对齐，也让 forest 不必把 active 染绿、减少一次碰撞。

### 3.3 撞色防治机制（决策2）

- 选项A「调色规范」：文档约束 + 每主题手调，灵活。（采用）
- 选项B「算法辅助」：槽位色相 = 主色色相 ± 固定偏移，自动分散但欠精细、可能产出难看的色。（不采用）
