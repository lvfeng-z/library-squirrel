# 插件信任模型最小集方案（任务 D）

> 关联：任务图 `plugin-convention-release-prep` 节点 D（TREE.md「最小集非安全边界」决策约束）。本方案是 D 的权威设计，实施步骤归此文档。经 plan-reviewer 对抗式审查修订（v2）。

## 审查摘要

**关键声明（抽查项，带锚点）**：
- 声明1：Plugin 实体无任何来源/哈希/信任字段，仅 15 业务字段（`backend/base/model/entity/plugin.go:12-26`）；工厂 `NewPlugin()` 仅初始化 BaseEntity（`:29-34`）。
- 声明2：installCore 写入字段集无来源/哈希/信任（`backend/plugin/service.go:379-394`）；`installType`（Manual=0/Auto=1，`backend/base/model/dto/plugin_types.go:8-15`）是调用链中的死参数——`installCore` 签名（`service.go:342`）本就无该参数，它只出现在外层 `install()` 包装（`service.go:301`）签名里且在该层即被丢弃，全程未落库。
- 声明3：三安装入口走同一 installCore，bundled 与用户插件 DB 层完全不可区分（InstallFromPath 声明 `service.go:218` 传 reinstall=false / InstallBundled 声明 `:319`（实际 installCore 调用在 `:336`）传 reinstall=false 且不 Activate / ReinstallFromPath 声明 `:462`（实际 install 调用在 `:493`）传 reinstall=true；InstallBundled 无任何 bundled 专属标记）。
- 声明4：loadPluginPackage 仅做 plugin.json 字段非空 + 契约版本范围校验，无签名/完整性（`service.go:273-291`）；LoadPluginProcess 仅校验契约版本范围后直接 `exec.Command` 启子进程，无完整性校验（`backend/plugin/extension/loader.go:171-215`）；HandshakeConfig 是 hashicorp/go-plugin 的 magic cookie 握手，非代码签名。
- 声明5：HostService（插件→宿主方向的 gRPC 服务，21 个方法）对所有激活插件全开、无任何裁剪（`library-squirrel-sdk/transport/host.go:30-188` 每方法直委托 deps）；capabilities（插件在 plugin.json 声明的能力数组）方向反——它门控主程序→插件的可选接口（`workset_order_fetcher.go:26` 声明 workOrderQuery 才调 QueryWorkSetOrder），**不门控插件→宿主 RPC**，故不能承载信任分级。
- 声明6：contractVersion（host↔plugin 协议版本）不在 proto，是 Go const（`library-squirrel-sdk/transport/contract.go:15`=2，加载期由 ValidateContractVersion `loader.go:44-55` 与 manifest 声明值比对）；本方案不改 proto/不改 manifest/不加 RPC，**不 bump contractVersion**（论证见 3.8）。
- 声明7：前端安装/卸载均无确认弹窗（`frontend/src/views/PluginManage.vue:195` 选完文件即装、`:172` 直接卸）；列表仅 name/author/version/createTime，无来源/信任列（`PluginManage.vue:43-86`），PluginDTO 无 source/trust 字段（`frontend/bindings/.../dto/models.ts:224-239`）；StatusRegistry 只有 task/source/toggle/resource 四类、无 plugin 类目（`frontend/src/constants/StatusRegistry.ts:5`）；可复用确认模式在同文件 `PluginManage.vue:144-149`。

**已决策（用户确认 2026-08-05/06）**：
- 决策1：来源枚举取 bundled/local/url/marketplace **四值**（预留，当前仅实现 bundled+local）。
- 决策2：哈希范围 = **包级 SHA256 必做**（安装时计算存档、纯追溯、重装即覆盖、不做比对 block）；entry 可执行文件加载时校验**先不做**（误伤 dev 迭代 + 基准不确定 + D 定位 signaling 非 gating，留 D' 评估）。
- 决策3：consent（用户知情同意）**服务端权威**——后端按安装入口判 source，trusted 由 UI 确认结果经参数透传，绕过 UI（直接调 wrapper）则 trusted=false。
- 决策4：**纳入**全局 Restricted Mode / kill switch（启动跳过所有非 bundled，作出问题时救生圈）。
- 决策5：卸载**顺带加确认弹窗**；死参数 `installType` **废弃**（DEAD_CODE_CLEANUP）。
- 决策6：trusted=false 的插件**不 Activate（不运行）**，需用户在管理页显式「信任」后才运行（Obsidian 式运行门控）。正常弹窗安装的插件 trusted=true 直接运行、不受影响。**这是「是否运行」的二值门控，非「裁剪 HostService 能力」**——插件一旦运行仍全开（能力裁剪属 D'）。

**自曝风险**：
- 风险1：plugin.json 是插件作者自声明，**不可作信任锚**——来源/完整性若放进 manifest 可被恶意作者伪造。本方案来源由 host 按安装入口判定、哈希由 host 计算，manifest 不承载任何信任信号（与 VS Code/JetBrains 有中央市场签名的场景本质不同：本项目无市场）。
- 风险2：加载时 exe 哈希校验（决策2）已决定**先不做**，故 D 阶段无法检测「安装后被篡改的磁盘文件」，只能保证「记录了安装时的包指纹」。该检测留 D' 评估时再定 warn/block 策略（block 会误伤 dev 迭代）。
- 风险3：`trusted` 在最小集承担两种作用——signaling（来源/信任展示）与运行门控（决策6：trusted=false 不运行）；但**不做能力门控**：trusted=true 一旦运行，HostService 仍对该插件全开（声明5）。即用户「信任」某第三方插件后，该插件仍能调用全部 21 个宿主方法——这是最小集接受的已知风险，真正的能力裁剪属 D'。
- 风险4：历史已安装插件经 AutoMigrate 加列后字段为 NULL，需迁移回填 source=bundled/trusted=true/补算哈希，否则前端状态展示异常、且 trusted=NULL 会被加载逻辑视作 false 导致 bundled 插件不运行（决策6）。**降级**：回填在启动时（LoadPlugins 之前）**幂等**执行，每次启动检查 source=NULL 的记录都补；加载逻辑对 source=NULL && trusted=NULL 的历史插件兜底视作 bundled trusted=true（向后兼容）；个别补算哈希失败不阻断启动，仅记日志、IntegrityHash 留 NULL。
- 风险5：若安装确认仅在前端 UI 层，则可被绕过（直接调 wrapper 安装）；故 trusted 写入须服务端权威（决策3），UI 弹窗只是 consent 的收集手段。**实现铁律**：handler 形参 trusted 必须显式传值，缺省/空值一律落 false（防「不传即信任」）。

## 1. 背景与定位

当前插件安装流程**没有信任概念**：任何来源的插件都能装、都能跑。插件是 Go 子进程，经 `PluginContext`（gRPC HostService）拥有**完整宿主能力**——数据读写、创建任务、网络、原生窗口等（见声明5）。在邀请第三方插件作者前，需要让用户「知情同意 + 来源可追溯」。

**D 的定位（TREE 决策约束）**：信任 signaling + 来源追溯的**最小集**，**非实质安全边界**。完整沙箱隔离（进程沙箱、HostService RPC 按信任裁剪、Marketplace 扫描）是 D 引出的延后 epic D'（完整沙箱隔离，发布给不可信第三方前的实质安全项），延后但需在发布说明中明确。

**最小集三件事**（用户需求）：
1. 来源记录：插件来源（bundled/本地/远程）+ 安装时哈希，供完整性校验与追溯；
2. 信任 signaling：标记插件是否受信任（bundled 默认信任、第三方需用户确认）；
3. 安装信任提示：安装第三方插件时弹窗（风险告知 + 来源 + 哈希），用户确认后安装。

**D 解决的「责任」问题**：发布初期即开放第三方插件，D 提供的是「事故归因 + 用户授权凭证」能力——出事时能查清是哪个插件、用户是否授权过、包有无篡改；并把「选择信任第三方」的责任明确交还用户（安装确认弹窗即知情凭证）。**D 不提供法律追责能力**（插件作者匿名、无市场实名），也**不事前阻止损害**（那是 D'）。

**明确不做（D' 延后）**：沙箱进程隔离、HostService RPC 按信任分级裁剪、Marketplace 恶意扫描与 block-list、代码签名 PKI。

## 2. 现状调研结论（四面）

### 2.1 安装与加载流程（后端）
- 安装三入口（声明3）共用 `installCore`（`service.go:342`），写入字段无来源/哈希/信任（声明2）。
- `installType` 是死参数（声明2）——定义了 Manual/Auto 却从未落库，是记录安装来源的天然挂载点，但语义是「触发方式」非「来源」，本方案新增独立 `Source` 字段而非复用它（决策5 废弃）。
- 前置任务 K「重装路径修复」（commit 77e7765）已落地 reinstall 标志：变量 `reusePlugin`（`service.go:350`），ReinstallFromPath 传 true 走 Save 覆盖、InstallFromPath/InstallBundled 传 false。
- `loadPluginPackage`（`service.go:234-298`）解 zip + 读 plugin.json，仅字段非空校验（声明4）。
- bundled 机制：`app.InstallBundledPlugins`（`app.go:227`）读 config 列表逐个 `InstallBundled`，在 `main.go:143`（窗口就绪前、`LoadPlugins` 之前）触发；bundled 与用户插件唯一行为差异是「已装则跳过 + 不立即 Activate」（纯时序，`service.go:317-318` 注释），DB 层无任何区分（声明3）。
- 加载侧 `LoadPluginProcess`（`loader.go:171`）仅 `ValidateContractVersion` 后 `exec.Command`（声明4），HostDeps（注入给插件的一组宿主能力 Provider）全量注入存储/任务/站点等高权限（`loader.go:178-207`），不因来源差异化。

### 2.2 entity 与契约与能力边界
- Plugin 实体 15 业务字段，无来源/哈希/信任（声明1）；运行态（PID/是否运行）在 Loader 内存对象 `RuntimeStatus`（`loader.go:380-406`）不入库。
- plugin.json 顶层（`backend/base/model/dto/plugin_types.go:33-45` 的 PluginManifest）无 source/signature/integrity/publisher；`author`（`:39`）是开发者名（拼入 PublicID），非信任信号。
- capabilities 是 `[]string` 封闭枚举，当前 2 值：`workOrderQuery`、`workSetRelationQuery`（`loader.go:72-75`）。**方向反**（声明5）：门控主程序→插件的可选接口，不门控插件→宿主 RPC。
- HostService 21 个方法（`library-squirrel-sdk/dto/context.go:4-53`）对全部激活插件全开，无 per-plugin 白名单/中间件（声明5）。
- contractVersion 是 Go const 不在 proto（声明6）；configSchemaVersion（插件配置结构版本）管 plugin_storage、与 contractVersion 正交。

### 2.3 前端管理页
- `PluginManage.vue`：本地 zip 文件选择安装（`selectPackage` `:183` 调系统文件选择器过滤 `*.zip`），**无远程/URL 安装入口**。
- 安装/卸载均无确认弹窗（声明7）；唯一一次 `ElMessageBox.confirm` 是重装的「修复方式」选择（`:143-159`），问的是修复方式非信任。
- 列表无来源/信任列；状态抽屉 `PluginStatusPanel.vue` 只展示运行时（在线/PID/扩展点/存储/URL），无来源/信任。
- wrapper `plugin.ts:54` 的 `pluginInstallFromPath(packagePath, installType?=0)` 形参 installType 已存在但前端从不传（声明7）。
- StatusRegistry 无 plugin 类目（声明7）；`source-local`/`source-site` 是**作者/标签的本地 vs 站点**来源，与插件来源无关，勿复用。

### 2.4 桌面应用参考（借鉴 vs 不做）
- **VS Code**：Extension Signature Verification（市场签名）+ Publisher Trust（v1.97+，首次装未知发布者弹信任框）+ Workspace Trust（`capabilities.untrustedWorkspaces` 声明，受限模式禁用未声明扩展）+ Marketplace 恶意扫描。
- **JetBrains**：双重签名（作者 RSA-4096 + 市场 AWS KMS 复签），IDE 内置 CA TrustStore 校验，未签名弹警告。
- **Obsidian**：默认 Restricted Mode + 首次启用第三方时**全屏警告**要求信任作者；启用后**无限制文件访问**（公认弱点，仅靠知情同意缓解）——与本项目「插件全能力 + 无市场」处境最接近。决策6 的「trusted=false 不运行、需手动信任」即借鉴此模式。
- **Chrome**：`_metadata/verified_contents.json` 存加密哈希、运行时逐文件校验；权限警告列表。
- **对照结论**：本项目无中央市场，故「市场签名/扫描」不可借鉴；可借鉴的是 **Obsidian 的知情同意提示 + 运行门控** + **Chrome/VS Code 的包哈希**；Workspace Trust 式的能力裁剪属 D'。

## 3. 设计方案

### 3.1 总体原则
1. **host 权威、插件透明**：来源由 host 按安装入口判定、哈希由 host 计算、信任由 host 落库；插件自身不知、不需知自己的信任态（插件若自报信任无意义——自声明不可信，见风险1）。
2. **manifest 不承载信任信号**：plugin.json 不加 source/integrity/trust 字段（与子代理参考建议不同——那假设有市场签名；本项目无市场，manifest 自声明可伪造，声明6/风险1）。
3. **signaling + 运行门控，非能力门控**：最小集让用户知情同意 + 来源可追溯，并对 trusted=false 做运行门控（决策6）；但不裁剪 HostService 能力、不做沙箱（D'，见风险3）。
4. **bundled 默认信任**：`resources/bundled-plugins/` 来源的插件 trusted=true，免提示（对齐 VS Code 预装扩展、Obsidian 官方插件）。

### 3.2 数据模型（Plugin entity 加 4 字段）
在 `backend/base/model/entity/plugin.go` 现有字段后新增（均 `sql.Null*`，符合零值合法字段规则；Trusted 的 false=未信任是合法值须 NullBool，与现有 `Uninstalled` 一致）：

| 字段 | 类型 | gorm column | 语义 |
|---|---|---|---|
| `Source` | `sql.NullString` | `source` | 来源枚举：`bundled`/`local`/`url`/`marketplace`（决策1） |
| `SourceDetail` | `sql.NullString` | `source_detail` | 来源详情：安装时的包路径或 URL，供追溯 |
| `IntegrityHash` | `sql.NullString` | `integrity_hash` | SHA256（hex），对象见决策2 |
| `Trusted` | `sql.NullBool` | `trusted` | 信任标记：bundled=true；第三方经 consent 后 true（决策3）；false 则不运行（决策6） |

AutoMigrate 自动加列（`backend/migration/migrate.go` 无需改，GORM 自动迁移 additive 列）。`NewPlugin()` 工厂无需改（字段默认 Null 零值，由 installCore 赋值）。

### 3.3 来源判定（source 由安装入口决定，服务端权威）
- `InstallBundled` → `source=bundled`，`SourceDetail`=config 配置的相对路径。
- `InstallFromPath` → `source=local`，`SourceDetail`=用户选择的本地绝对路径。
- （未来）URL/市场安装入口 → `source=url`/`marketplace`（决策1 预留）。
- 判定在 `installCore` 内按「调用入口」设定，**不由前端传入**（防伪造）。实现上由各入口在调 installCore 前传入 source 参数（替代废弃的 installType，见决策5）。

### 3.4 完整性哈希（决策2）
- **包级 SHA256（必做）**：安装时在 `loadPluginPackage` 解 zip 前对原始 zip 字节流计算 SHA256，存 `IntegrityHash`。纯追溯：装时指纹存档、可在弹窗/列表展示。零运行时成本、不误伤 dev。
- **纯追溯、不做比对 block**：包级哈希仅作存档指纹——**重装（ReinstallFromPath）时直接覆盖为新包哈希、不做新旧比对**（新包本就是新内容，比对无意义）；加载时也不校验。
- **entry exe 加载校验（留 D'）**：决策2 已定先不做。原因：① 误伤 dev 迭代（频繁替换 exe 触发 mismatch）；② 基准不确定（包级哈希无法直接比对解压后 exe）；③ D 定位 signaling 非 gating。该检测（warn/block 策略）留 D' 评估（风险2）。

### 3.5 信任标记与 consent（决策3）
- `Trusted` 写入规则（服务端权威，`installCore` 内）：
  - `source=bundled` → `trusted=true`（免提示，默认信任）。
  - `source=local`（及其他第三方来源）→ `trusted` 由「用户 consent 结果」决定。consent 经 **UI 弹窗收集 → 前端调 wrapper 时透传确认参数 → 后端写入**。弹窗取消则前端根本不发起安装；弹窗确认则透传 trusted=true。
  - 后端默认：未带确认参数的安装调用（绕过 UI）→ `trusted=false`（装了但标为未信任），保证服务端权威、UI 绕过不等于自动信任（风险5 实现铁律：handler 形参 trusted 缺省落 false）。
- `ReinstallFromPath`（重装/修复）：第三方包重装同样走 consent（重装即换包，是新一次代码执行，应重新确认）。
- **trusted=false 的运行门控（决策6）**：trusted=false 的插件**不 Activate（不启动进程）**。`loadInstalledPlugins`（`app.go:285`）激活前检查 trusted，false 则跳过激活、前端标记为「待信任」。用户在管理页点「信任」后置 trusted=true，下次启动或手动激活时运行。
  - 这是「是否运行」的二值门控，**不是能力门控**——一旦 trusted=true 运行，HostService 仍全开（声明5、风险3）。
  - 与 Restricted Mode（决策4）正交叠加，见 3.7。

### 3.6 安装流程改造
- `installCore`（`service.go:342`）签名增加 `source string` 与 `trusted bool`（或封装为一个小 struct），写入新 4 字段；`loadPluginPackage` 返回包级哈希一并带入。
- 三入口适配：
  - `InstallFromPath`：前端透传 consent → source=local、trusted=consent（缺省落 false）。
  - `InstallBundled`：source=bundled、trusted=true。
  - `ReinstallFromPath`：source 沿用原插件来源、trusted 经 consent（第三方）/true（bundled）；IntegrityHash 覆盖为新包哈希（3.4）。
- Handler/wrapper：`pluginInstallFromPath` 增加 consent 透传参数（trusted bool，缺省 false）；重新生成 bindings。

### 3.7 信任 UX（前端）
1. **安装确认弹窗**：在 `PluginManage.vue:195` 的 `selectPackage()` 与 `installFromPath()` 之间插 `ElMessageBox.confirm`（照搬 `:144-149` 模式，`type:'warning'`），文案含风险告知 + 来源 + 哈希（参考 Obsidian 全屏警告强度）：「此插件来自第三方（非官方捆绑），将获得完整宿主能力（读写资源库、创建任务、网络、原生窗口）。仅在你信任作者 {author} 时继续。来源：本地文件。校验：{hash 前 12 位}。」bundled 安装不经此 UI（默认信任）。
2. **来源/信任展示**：列表 thead（`PluginManage.vue:43-86`）加「来源」列用 `StatusTag` 渲染；`PluginStatusPanel.vue` 运行时区块上方加信任徽章（信任/未信任/待信任）+ 完整哈希（hover 展开）。
3. **StatusRegistry**：新增 `plugin` 类目 + key `plugin-trusted`/`plugin-unverified`/`plugin-bundled`，在 `tokens.css` 补对应 `--app-status-plugin-*-bg/text/border` 三档令牌（沿用现有 tone 派生机制，见 `.claude/rules/frontend.md` STATUS_TOKEN_USAGE）。
4. **手动信任入口（决策6 配套）**：管理页为 trusted=false 的插件提供「信任」操作（置 trusted=true 并激活）；trusted=true 的可选「取消信任」（置 false，下次启动不再运行）。
5. **Restricted Mode 开关（决策4）**：设置页加全局开关，启用时 `loadInstalledPlugins`（`app.go:285`）跳过所有 `source!=bundled` 的插件（不论 trusted），作出问题时安全启动。与决策6 的 trusted 门控正交：正常启动 + trusted=false → 不运行；Restricted Mode + 任何非 bundled → 不运行。
6. **卸载确认（决策5）**：在 `PluginManage.vue:172` 的 `unInstall` 前加 `ElMessageBox.confirm`（现状直接卸、无确认）。

### 3.8 契约面（不改 manifest、不 bump contractVersion）
**结论：本方案零 manifest 改动、零 contractVersion bump、零 configSchemaVersion bump。** 论证：
- 加的是 Plugin **DB 列**（host 侧）与 host 安装/加载逻辑，不碰 host↔plugin 的 gRPC 协议。
- 不新增/不修改 proto 消息，不动 `ActivateRequest`（`library-squirrel-sdk/proto/plugin.proto:166-172`），不加 RPC。
- plugin.json 不加字段（来源/哈希/信任全由 host 判定与存储，见 3.1 原则2）。
- contractVersion 管「协议破坏性变更」，本方案无协议变更 → 不 bump（声明6）。
- configSchemaVersion 管「插件配置结构」，本方案不动 plugin_storage → 不 bump。
- 故**插件侧零改动**（两个现有插件 local/pixiv 无需发版），符合「host 权威、插件透明」。

### 3.9 历史数据迁移
AutoMigrate 加列后，已安装插件的 4 个新字段为 NULL。需回填（启动时、LoadPlugins 之前**幂等**执行，每次启动检查 source=NULL 的记录都补）：
- 现有已安装插件（均为 bundled：pixiv/local/bilibili）→ `source=bundled`、`trusted=true`、`SourceDetail`=推断或留空、`IntegrityHash`=对当前 RootPath 下 zip 或 entry exe 补算。
- **加载兜底**：`loadInstalledPlugins` 对 `source=NULL && trusted=NULL` 的历史插件（回填未覆盖的极端情况）视作 bundled trusted=true 运行并记日志（向后兼容，避免升级后官方插件全不运行）。
- **降级**：个别插件补算哈希失败不阻断启动，仅记日志、IntegrityHash 留 NULL（前端容忍空值展示「未校验」）。回填在 LoadPlugins 之前同步完成，避免竞态。
- 风险4：遗漏回填会导致前端状态展示异常（NULL 渲染）+ trusted=NULL 被加载逻辑视作 false 导致 bundled 插件不运行（决策6），故需上述兜底。

## 4. 与 D' 的边界（延后清单，发布说明须明确）
D'（完整沙箱隔离 epic）**不做**以下各项：
- **HostService RPC 按信任裁剪**：需在 `host.go` 加 per-plugin 白名单/中间件层（当前完全缺失，声明5），是独立工程。最小集只做运行门控（决策6），不做能力门控（风险3）。
- **进程沙箱 / 文件 ACL / OS 级隔离**：Go 子进程当前是 RPC 客户端，OS 隔离需重新设计 transport。
- **代码签名 PKI**（VS Code/JetBrains 式）：无中央市场前无意义。
- **Marketplace 恶意扫描 + block-list 自动卸载**：无市场前不适用。
- **Workspace Trust 式能力声明裁剪**（capabilities.untrustedWorkspaces）：需逐 RPC 权限模型，且现有 capabilities 方向反（声明5），需先重构。
- **加载时完整性校验**（exe 哈希 warn/block）：决策2 已定先不做，留 D'（风险2）。

发布说明须写明：「当前插件信任模型为来源追溯 + 知情同意 + 运行门控的最小集，**不提供沙箱隔离与能力裁剪**；插件一旦被用户信任运行即获得完整宿主能力。完整的第三方插件沙箱隔离在后续版本提供（D'）。」
