**自曝风险**
- 风险1：方案A 自定义组件有视觉打磨成本，fixed 定位的 z 层级须对齐全局 `z-axis-layers` 体系（`frontend/src/styles/`）
- 风险2：聚合窗口使提醒最长延迟窗口时长到达（现为 300ms，含后端 50ms 防抖最坏 ~0.35s），与批量合并率有权衡——窗口再缩短会开始拆散跨快照批次
- 风险3：（已消解）瞬时任务与中间态（待确认/暂停）→终态的漏报曾因"prev 须活跃"判据发生；现判据为"prev 非终态"（见 5.2 迁移表），两场景均覆盖，live 通道 prev 缺席不提醒属刻意（DB 装载历史终态）
- 风险4：任务终态有两个接入点（loadSnapshot 快照路径 / updateTask 非快照路径），须保证同一任务终态只提醒一次——两路径由 useSnapshotMode 配置二选一，运行时天然互斥，但代码两处都要接入且风格一致

## 一、定位与机制地图

消息提醒系统是**通用瞬时醒目通道**：任何前端模块（含 IPC 监听器转译的后端事件）都能推一条提醒，负责在用户可能专注于其它页面时抓住注意力，数秒后自动消失。它与既有机制按交互模式四分，互不吞并：

| 轨道 | 交互模式 | 说明 |
|---|---|---|
| ElMessage | 同步操作反馈（瞬时） | 用户刚做的操作成败，~50 处，保留 |
| 通知中心（NotificationList） | 异步被动追踪（持久列表） | 进度/终态回看，已建 |
| ChangeConfirmDialog | 异步待办动作 | fsmonitor 修复确认，保留 |
| **消息提醒系统（本方案）** | **异步瞬时醒目提醒** | 后台事件结局/重要状态变化的一过性提示 |

用户已确认：批量堆叠优化必做（旧双槽位 + "N+"内联角标 + 300ms 释放等待的效果不满意，废弃该形态）。

## 二、API 设计（通用）

`frontend/src/store/UseReminderStore.ts`，单方法入口：

```ts
announce(input: ReminderInput): void

interface ReminderInput {
  level: 'info' | 'success' | 'warning' | 'error'  // 严重度，tone 着色
  title: string        // 卡片标题，兼做分组头，如「任务完成」「合并完成」
  message: string      // 单条详情一行，如「任务【A】完成」
  category?: string    // 业务分类 'task'/'merge'/…，参与分组键
  duration?: number    // 自动关闭毫秒数，缺省按 level（error 更长）
}
```

生产者示例：任务终态 → `announce({level:'success', title:'任务完成', message:'任务【A】完成', category:'task'})`。

## 三、聚合策略（新的堆叠设计）

合并发生在**卡片层**而非旧方案的"N+"内联角标：

1. `announce` 将提醒入队并开窗（窗口时长=决策3，300ms）；窗口到期统一 flush。
2. flush 按（category + level + title）分组，每组生成一张卡片：
   - 组内 1 条：`title` + `message` 原样展示；
   - 组内 N 条：`title` + 计数 + 条目列表（前 3 条 message + "等 N 条"）。
3. 效果上界：无论批量多大，同屏卡片数 ≤ 分组数（通常 ≤3，如成功/失败/警告各一张）。

与旧堆叠的本质差异：无槽位互等延迟；合并产出的是**可读的汇总卡片**（含具体条目名）而非视觉角标；条数与批量规模解耦。

## 四、UI 设计（决策1 的两个候选）

**方案A（推荐）：自定义堆叠卡片组件** `frontend/src/components/common/ReminderStack.vue`
- 挂 MainLayout，fixed 右上角，z 层级对齐 `z-axis-layers`。
- 同屏最多 3 张卡片；更多时第 3 张尾部显示"还有 N 条"（入队待展示）。
- 卡片结构：level 色条/图标 + title +（单条 message 或 条目列表）；level → 状态 tone 着色（与通知中心同映射：info→pending 蓝 / success→done 绿 / warning→warn 橙 / error→fail 红）。
- 自动关闭（duration），hover 暂停计时（增强项，可后补）；滑入/淡出动画。
- 不做点击跳转：留档与详情归通知中心，提醒保持纯注意力。

**方案B：ElNotification + 聚合层**——沿用 EP 原生右上角堆叠，聚合后的 title/message 直接喂给 ElNotification。零组件工作量，但视觉与交互受 EP 限制（无 hover 暂停、列表排版弱），且是旧方案同款载体。

## 五、任务模块接入（首个消费者，含失效修复）

### 5.1 根因（终态提醒为何失效）

快照模式（默认）下任务状态只经 `task-snapshot` 到达，`task-events` 从不发射；而终态提醒逻辑挂在 `updateTask`（增量死路径）上。终态实际到达点 `loadSnapshot` 无迁移检测，完成任务的活跃通知被静默 remove——提醒与终态保留双双未生效（声明1-4）。

### 5.2 loadSnapshot 迁移感知

diff 基线为替换前 `this.tasks`（id → {status, notificationId}），按下表处理：

| 旧态 | 快照新态 | 处理 |
|---|---|---|
| 中间态或活跃（有通知） | 仍活跃 | 保留通知，原地 `update(id, {progress})`（消除现有每次 flush 的 remove+re-add churn） |
| 中间态或活跃（有通知） | 终态（live 或 removedItems） | `update(id, {terminal:true, level, statusText})` + 脱离 + `announce(...)` |
| 中间态或活跃（无通知，如待确认 9、暂停 4） | 终态 | 新增 terminal 通知（供回看）+ `announce(...)` |
| 未见 | 活跃 | `add`（现状行为） |
| 未见 | 终态（live 通道） | 不提醒——用户 Start 会连 DB 历史终态子任务一起装载进 taskMap（`buildOrReuseChild` skipTerminal=false），live 快照携带它们，prev 缺席时提醒即误报 |
| 未见 | 终态（removedItems 通道） | 补终态条目 + `announce`——移除缓冲仅含本会话新近终止任务（`PushTaskRemove` 唯二调用方均为终止/停止清理），prev 缺席即瞬时任务（全生命周期落在后端 50ms 防抖窗内） |
| 已终态 | 终态 | 跳过（此前快照已处理过该迁移，防重复提醒） |
| 活跃 | 消失且不在 removedItems | remove 其通知（防御分支） |

> 判据核心：**prev 是否已终态**（而非"曾经活跃"）。prev 非终态 = 本会话尚未处理的迁移，到达终态即提醒；prev 已终态 = 已处理，跳过。live 与 removedItems 两通道对"prev 缺席"的语义不同（历史装载 vs 瞬时任务），故不对称。

清理段重构为逐任务按上表决定通知去留，不再"先全清再重建"；已脱离终态通知不受影响（延续终态脱离不变量）。

### 5.3 updateTask 路径对齐

非快照模式下 `updateTask` 终态分支的 ElMessage 替换为同样的 `announce(...)`（风险4：两接入点风格一致，运行时配置互斥不双弹）。

## 六、实施步骤

1. **UseReminderStore**：时间窗聚合 + 分组 + 卡片数据模型（载体按决策1）。
2. **ReminderStack.vue**（若决策1 选 A）：堆叠卡片组件，挂 MainLayout。
3. **loadSnapshot 重写**：按 5.2 迁移表实现 diff。
4. **updateTask 终态分支**：ElMessage → announce。
5. **验证**：单任务完成弹具体文案；批量并发完成弹汇总卡片；终态条目留在通知中心且不被快照清空；活跃任务通知进度原地刷新（id 不变）。

## 七、范围边界

- 做：通用提醒 store + 堆叠 UI、任务模块双路径接入（含 loadSnapshot 迁移感知，同时修复提醒/终态保留/churn 三缺陷）。
- 不做：提醒点击跳转；桌面级系统通知（声音/托盘，未来挂在 announce 内部）；ElMessage 与 ChangeConfirm 并入；非快照模式单独实测（默认配置不走，仅保持编译一致）。
