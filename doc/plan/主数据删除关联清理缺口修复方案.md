## 一、背景

删除链审计（外键方案 todo#48 讨论中完成）发现：八处「主数据物理删除」链路未清理指向被删行的子引用，全部属「删父行留悬空子引用」类。定稿时规划「本方案先行、外键执行阶段以本方案为硬前置」；实际推进中外键方案改为单轨直做——DSN 强制执行随批次一开启，八入口有子引用即报错为已接受的过渡代价（doc/plan/外键补充方案.md 裁决4、风险6），现已全量落地。本方案因此转为**外键落地后的编排收口**：外键是报错式验证器（已就位），本方案补齐令删除链合规的应用层编排；落地后八入口从「有子引用即报错不可用」恢复为可用。

| 2 | localAuthor.Delete | re_work_author.local_author_id、work.local_author_id（镜像列）、site_author.local_author_id（绑定列） | re_work_author 与 work 镜像面被 FK 拒绝（含软删 work 行）；绑定列无 FK 仍静默悬空 |

## 二、修复方案

统一模式：**编排归发起方**（ORCHESTRATION_BY_CALLER）——发起删除的模块注入提供方窄接口（SERVICE_DEPENDENCY_VIA_INTERFACE），删除编排在事务内完成（transactor 注入，事务内 repository 方法走 dbFromCtx——从 context 取事务连接的既有纪律，MaxOpenConns=1 下误用普通连接会死锁）。外键落地后，「先清子引用、后删父行」从推荐顺序变为**强制约束**——编排漏步即 FK 违约报错，运行期防线兜底。

### 2.1 localTag.Delete 编排化（缺口1、8）

事务内四步：
1. **子标签重挂**（缺口8）：读被删标签自身的 base_local_tag_id（`sql.NullInt64`，NULL=根）→ 原生 `UPDATE local_tag SET base_local_tag_id = ? WHERE base_local_tag_id = ?`——推荐上提祖父（孙变子，子树整体上移一层），置根形态传 NULL（已裁决 NULL 方向）；原生 UPDATE 覆盖全部行（local_tag 无软删无分行态顾虑）。兼解 base_local_tag_id 的 FK 拦截。
2. 解绑站点侧：`UPDATE site_tag SET local_tag_id = NULL WHERE local_tag_id = ?`（siteTag 模块新增 ClearLocalTagBinding）——绑定列无 FK，纯为清静默悬空面。
3. 删作品关联：reWorkTag 新增 `DeleteByLocalTagId(ctx, localTagId)`（对齐 reWorkAuthor 既有 DeleteByLocalAuthorId 命名；repository 层 `WHERE local_tag_id = ?` 删除，dbFromCtx 模式）。兼解 re_work_tag 的 FK 拦截。
4. 删 tag 行（现有 repo.Delete）。

### 2.2 localAuthor.Delete 编排化（缺口2）

事务内四步：
1. 解绑站点侧：siteAuthor 新增 ClearLocalAuthorBinding（置 NULL）——绑定列无 FK，纯为清静默悬空面。
2. 删作品关联：**接线既有死能力** reWorkAuthor.DeleteByLocalAuthorId（声明4——能力已存在，本方案接线即启用）。
3. 清作品镜像列：work 模块新增 `ClearLocalAuthorOnWorks(ctx, localAuthorId)`——原生 `UPDATE work SET local_author_id = NULL WHERE local_author_id = ?` **覆盖含软删行**（GORM 管线自动排除软删行，但 FK 拦截不看 deleted_at：软删行引用不清则删 author 行即违约；软删行置 NULL 语义亦正确——作者已删）。
4. 删 author 行。

### 2.3 siteTag.Delete / siteAuthor.Delete 编排化（缺口3、4）

事务内两步：删各自 re 关联（reWorkTag 新增 DeleteBySiteTagId / 接线 reWorkAuthor.DeleteBySiteAuthorId）→ 删自身行。先清子后删父，顺序即 FK 合规。

### 2.4 site.Delete 纯守卫（缺口5，已裁决1、2）

已裁决纯守卫形态：五类引用任一存在即拒绝删除，不做级联清理与历史置空。

1. **守卫（核心步）**：事务内聚合查询该站点的引用计数——
   - work：活行（`site_id = ? AND deleted_at = 0`）与**软删行**分别计数（裁决2 软删行同样拒绝；分开计数因清理指引不同——活行引导作品页删除、软删行引导回收站 purge；软删行计数须 Unscoped 查询，GORM 管线自动排除软删行）
   - task：行计数（task 无软删）
   - work_set：活行与软删行分别计数（同 work）
   - site_tag、site_author：行计数
2. **业务提示**：任一计数 > 0 → 返回聚合错误消息（示意：「无法删除站点：仍有作品 3（含回收站 1）、作品集 2、任务 5、站点标签 10、站点作者 4，请先清理后重试」）——错误变量 `ErrSiteHasReferences`（errors.Is 判别，消息文本带计数），前端 ElMessage 展示；守卫覆盖全部五类引用面后，FK 违约错误对该入口不再外露（守卫即业务语义层，FK 退为冗余兜底）。
3. **删除**：全部计数为零 → 删 site 行（此时无子引用，FK 天然放行）。

计数查询经 site 模块注入各提供方窄接口（work/task/workSet/siteTag/siteAuthor 各自暴露按站点计数方法，SERVICE_DEPENDENCY_VIA_INTERFACE）；守卫查询与删除同事务包裹（与全方案统一事务模式一致，单连接串行下无并发窗口）。

### 2.5 task.DeleteTask 补 resource.task_id 清理（缺口6，已裁决 NULL 方向）

删除任务后批量 `UPDATE resource SET task_id = NULL WHERE task_id IN (ids)`（resource.task_id 现 `sql.NullInt64`，NULL=非任务产——外键方案裁决3 已锁定，原「清 0」形态随列型 NULL 化作废）。GORM Updates 跳零值对 NULL 赋值不构成问题（Updates(map) 或原生 SQL 均可）；FK 下不清引用即删 task 被拒，本步从「推荐做」变为「必须做」，原备选「接受悬空」不可行、作废。resource 无软删，无行态顾虑。

### 2.6 PurgeStore 补关联清理（缺口7）

物理删行前摘除指向该行的 resource_store 关联：复用既有 `DeleteByStoreIds(ctx, storeIds)`（声明4）插入 DeleteUnscopedByIds 之前，同事务。摘除后行物理消亡，无中间态暴露；当前未修复时该入口对带关联条目 FK 报错，本步落地即恢复可用。

### 2.7 resource.Delete 死端点退役（已裁决3）

已裁决退役：删除 handler 方法 + frontend wrapper 对应函数 + `wails3 generate bindings -ts` 再生成。零调用方（声明7），按 DEAD_CODE_CLEANUP 直接删除。resource 行的物理删除归宿不受影响——work purge 链已物理删 resource（声明8），退役后无残留路径。

每处修复一个用例，测试库一律 `migration.OpenTestDB()`（`:memory:?_foreign_keys=on` + 完整迁移——声明6；装配对齐 backend/work/delete_purge_test.go:134 先例）：

- TestDeleteLocalTagCleansReferences：预置 work + local_tag + re_work_tag + site_tag(绑定) → 删 tag → re 行归零、site_tag 行保留且 local_tag_id 为 NULL
- TestDeleteLocalTagReparentsChildren（缺口8）：预置祖父-父-子三级标签 → 删父 → 子的 base_local_tag_id 指向祖父（上提形态）或为 NULL（置根形态）；删根级标签 → 子成为根（NULL）
- TestDeleteLocalAuthorCleansReferences：同构 + work.local_author_id 断言 NULL——**含软删 work 行**（软删行镜像列亦置 NULL，FK 下不清即删 author 违约）
- TestDeleteSiteTag/SiteAuthorCleansReferences：同构
- TestDeleteSiteGuard：分别预置五类引用（work 活行、work 软删行、task、work_set 活行/软删行、site_tag、site_author）→ 各自拒绝且 errors.Is(ErrSiteHasReferences) 成立、消息含对应计数与清理指引；全空 → 删除成功
- TestDeleteTaskClearsResourceTaskId：删任务 → resource.task_id=NULL、resource 行保留
- TestPurgeStoreRemovesAssociations：软删 store（带关联）→ PurgeStore → resource_store 行归零

FK 强制库的免费锚定：编排漏步（先删父后清子）在 OpenTestDB 下直接违约报错——上述用例对「删除成功」的断言本身即顺序正确性证明；预置数据裸建子行须带父行种子（FK 强制，外键方案风险2 同款注意点）。

前端行为不变（删除按钮交互照旧，site 删除拒绝场景由错误消息文本呈现），除阶段6 退役（删 bindings 函数）外无 bindings 形态变更，无 schema 变更（外键已落地，本方案纯行为编排）。

## 五、风险与边界

- **风险1（work.local_author_id 消费面）**：grep 核验无查询条件用法（声明4）；raw SQL 拼接盲区残余风险低。若实施中发现遗漏消费点，置 NULL 的语义仍正确（作者已删），最多影响某处展示需跟随兜底。
- **风险2（删除后重建交互）**：删除 site_tag 后再次下载同站点作品，插件入库流按 (site_id, site_tag_id) upsert 会重建 site_tag 行并重建 SITE 关联——「删掉的标签随新下载回来」是入库流的既定行为，非本方案引入的缺陷，用户感知点在此说明。
- **风险3（子标签上提的层级变化）**：上提祖父改变用户可见的标签树结构（孙变子）；实现先读被删标签的父值再批量改子行，读改两步间理论上有竞态窗口（单连接串行写之下实际封闭）。
- **风险4（守卫拒绝的操作面变化）**：软删作品/作品集未 purge 前站点不可删，用户须清空回收站后重试（裁决2 已接受）；2.2 镜像列覆盖软删行与守卫拦截面均基于「FK 不看 deleted_at」语义推导（未实机复现）——错误消息须含可操作的清理指引，测试锚定断言消息内容，阶段7 实机复核。
- **边界（不在本方案范围）**：运行中任务的删除时序（taskManager 内存态 vs DB 行）维持现状；poi 域死域无删除流（声明7）；外键已全量落地——本方案与其关系为「应用层编排满足 FK 约束」，原「两阶段、硬前置」依赖表述作废；两绑定列（site_tag.local_tag_id、site_author.local_author_id）未挂外键属 FK 登记面既有空隙，本方案以应用层清理覆盖，是否补挂外键归外键方案后续裁决。
