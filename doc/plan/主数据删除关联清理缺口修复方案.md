**自曝风险**：

## 一、背景

todo#48「补充外键」讨论中完成的删除链审计发现：八处「主数据物理删除」链路未清理指向被删行的子引用，全部属「删父行留悬空子引用」类。本方案以**应用层编排修复**收口（不依赖外键裁决；外键方案已重构为两阶段——声明阶段与本方案可并行、执行阶段以本方案为硬前置，见 doc/plan/外键补充方案.md 第六节）。CASCADE 数据库代行已讨论否决，不在本方案范围。

### 缺口全量清单

| # | 删除入口 | 遗留悬空引用 | 用户可见影响 |
|---|---|---|---|
| 1 | localTag.Delete | re_work_tag.local_tag_id、site_tag.local_tag_id（绑定列） | 作品的该标签关联静默失效；站点标签的本地绑定悬空 |
| 2 | localAuthor.Delete | re_work_author.local_author_id、work.local_author_id（镜像列）、site_author.local_author_id（绑定列） | 作品作者关联失效 |
| 3 | siteTag.Delete | re_work_tag.site_tag_id | 作品的该 SITE 标签关联静默失效 |
| 4 | siteAuthor.Delete | re_work_author.site_author_id | 作品的该 SITE 作者关联失效 |
| 5 | site.Delete | work.site_id、task.site_id、**work_set.site_id**、site_tag.site_id、site_author.site_id | 波及面最大：作品归属、任务/作品集历史归属、站点全部从属行悬空 |
| 6 | task.DeleteTask | resource.task_id（资源行长存） | 资源溯源键悬空（DTO 投影 JOIN miss 显示空） |
| 7 | recycleBin.PurgeStore | resource_store.store_id | 消费侧 liveness JOIN 天然滤掉（无可见 bug），垃圾关联行累积，突破「死行 0..N 按代次」文档形态 |
| 8 | localTag.Delete（树指针面） | local_tag.base_local_tag_id（子标签的父指针） | 删父标签后子标签成悬空树节点——从根出发的递归树查询（repository.go:77-81）丢失整个子树 |

> 缺口1 与缺口8 为同一删除入口的两个引用面（re 关联 + 树指针），修复在同一编排内。

## 二、修复方案

统一模式：**编排归发起方**（ORCHESTRATION_BY_CALLER）——发起删除的模块注入提供方窄接口（SERVICE_DEPENDENCY_VIA_INTERFACE），删除编排在事务内完成（transactor 注入，事务内 repository 方法走 dbFromCtx——从 context 取事务连接的既有纪律，MaxOpenConns=1 下误用普通连接会死锁）。

### 2.1 localTag.Delete 编排化（缺口1、8）

事务内四步：
1. **子标签重挂**（缺口8，形态待决策4）：读被删标签自身的 base_local_tag_id → `UPDATE local_tag SET base_local_tag_id = <该值或 0> WHERE base_local_tag_id = ?`——推荐上提祖父（孙变子，子树整体上移一层）；原生 UPDATE（覆盖全部行，local_tag 无软删无分行态顾虑）。
2. 解绑站点侧：`UPDATE site_tag SET local_tag_id = NULL WHERE local_tag_id = ?`（siteTag 模块新增 ClearLocalTagBinding）
3. 删作品关联：reWorkTag 新增 `DeleteByLocalTagId(ctx, localTagId)`（对齐 reWorkAuthor 既有 DeleteByLocalAuthorId 命名；repository 层 `WHERE local_tag_id = ?` 删除，dbFromCtx 模式）
4. 删 tag 行（现有 repo.Delete）

### 2.2 localAuthor.Delete 编排化（缺口2）

事务内四步：
1. 解绑站点侧：siteAuthor 新增 ClearLocalAuthorBinding（置 NULL）
2. 删作品关联：**接线既有死能力** reWorkAuthor.DeleteByLocalAuthorId（声明2——能力已存在，本方案接线即启用）
3. 清作品镜像列：work 模块新增 `ClearLocalAuthorOnWorks(ctx, localAuthorId)`（`UPDATE work SET local_author_id = NULL WHERE local_author_id = ?`；work 有软删，UPDATE 经 GORM 管线自动排除已删行——已删行的镜像列随作品 purge 物理消亡，无需处理）
4. 删 author 行

### 2.3 siteTag.Delete / siteAuthor.Delete 编排化（缺口3、4）

事务内两步：删各自 re 关联（reWorkTag 新增 DeleteBySiteTagId / 接线 reWorkAuthor.DeleteBySiteAuthorId）→ 删自身行。

### 2.4 site.Delete 三段式（缺口5，形态待决策1）

推荐形态（三段式）：
1. **守卫**：work 活行存在挂该站点（`site_id = ? AND deleted_at = 0`）→ 拒绝删除，错误消息指明作品数（作品是核心资产，删除站点不得令其失锚；已软删作品不拦——其行随 purge 物理消亡）
2. **级联**：列出该站点全部 site_tag / site_author 行 → 复用 2.3 的删除编排逐行清理（含各自 re 关联）
3. **置空**：`UPDATE task SET site_id = NULL WHERE site_id = ?` 与 **`UPDATE work_set SET site_id = NULL WHERE site_id = ?`**（B2 修订补入 work_set；work_set 置空须**原生 UPDATE 覆盖含软删行**——软删集行同样持有 site_id 引用，且三列唯一索引 (site_id, site_work_set_id, deleted_at) 中置 NULL 不参与唯一性、对软删行互异性无破坏；已软删集终将 purge 清行，置空为统一纪律而非消费需要）

备选形态（纯守卫）：五类引用（work/task/work_set/site_tag/site_author）任一存在即拒绝，用户先清从属再删站点。实现最简但用户操作繁琐。

### 2.5 task.DeleteTask 补 resource.task_id 清理（缺口6，形态待决策3）

推荐：删除任务后批量 `UPDATE resource SET task_id = 0 WHERE task_id IN (ids)`（0 是该列既定的「无」哨兵，resource.task_id 为 int64 非 Null）。注意 GORM Updates 跳零值——须用单列 Update 或原生 SQL。resource 无软删，无行态顾虑。
备选：接受悬空（resource.task_id 仅 DTO 投影消费，JOIN miss 显示空，无功能损坏）——但违反 RECORD_STATE_TRUTHFUL（记录指向不存在任务），不推荐。
联动：外键方案决策3 若将 resource.task_id NULL 化纳入批次四，本步改 `SET task_id = NULL`。

### 2.6 PurgeStore 补关联清理（缺口7）

物理删行前摘除指向该行的 resource_store 关联：复用既有 `DeleteByStoreIds(ctx, storeIds)`（声明5）插入 DeleteUnscopedByIds 之前，同事务。摘除后行物理消亡，无中间态暴露。

### 2.7 resource.Delete 死端点处置（待决策2）

推荐退役：删除 handler 方法 + frontend wrapper 对应函数 + `wails3 generate bindings -ts` 再生成。零调用方（声明4），按 DEAD_CODE_CLEANUP 直接删除。
备选：补编排保留（事务内删 resource_store 关联 + task.pending_resource_id 清空 + 删自身）——为可能的未来调用方保留，但当前无需求。

## 五、风险与边界

- **风险1（site 级联量级）**：单站点数千 site_tag 的级联删除在单连接 SQLite 下事务时长未实测；缓解：分批不可行（事务原子性），但桌面单机无并发写者，长事务只阻塞同进程写——可接受，实施后以实机验证收尾。
- **风险2（work.local_author_id 消费面）**：grep 核验无查询条件用法（声明3）；raw SQL 拼接盲区残余风险低。若实施中发现遗漏消费点，置 NULL 的语义仍正确（作者已删），最多影响某处展示需跟随兜底。
- **风险3（删除后重建交互）**：删除 site_tag 后再次下载同站点作品，插件入库流按 (site_id, site_tag_id) upsert 会重建 site_tag 行并重建 SITE 关联——「删掉的标签随新下载回来」是入库流的既定行为（reWorkAuthor README「SITE 关联删后重建」同族），非本方案引入的缺陷，用户感知点在此说明。
- **风险4（子标签上提的层级变化）**：上提祖父改变用户可见的标签树结构（孙变子）；实现先读被删标签的父值再批量改子行，读改两步间理论上有竞态窗口（单连接串行写之下实际封闭）。
- **边界（不在本方案范围）**：运行中任务的删除时序（taskManager 内存态 vs DB 行）维持现状；poi 域死域无删除流（声明8）；外键方案两阶段（声明/执行）独立推进——声明阶段与本方案并行无依赖，执行阶段以本方案落地为硬前置，决策3/决策4 两处取值互相联动（见各决策节）。
