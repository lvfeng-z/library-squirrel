# 代码误判防线固化方案

## 审查摘要

**关键声明（抽查项）**：
- 声明1：`runMode.hasAnyStore()`（`backend/taskManager/model.go:69`）命名与语义失配是本次误判首因——字面「存在任何 store」，实义「选择了任意资源板块」；误读发生在调用点（`model.go:927`），定义处注释不随调用传播
- 声明2：`storeRoles` 空集双义（全量 vs 仅作品信息，由 `fetchStores` 区分，`model.go:55` 注释自述）未被类型封装，裸谓词 `hasAnyStore()` 在定义上无法独立无歧义——`.claude/rules/backend.md` 现无命名/两义封装类规则（P0-P2 清单已核，`ENTITY_USE_NEW_FACTORY` 起的既有条目不含此项）
- 声明3：`.claude/skills/phase-executor/SKILL.md` 的交接摘要契约（≤5 行：文件/逻辑/遗留/验证）无锚点要求、无「主会话加工结论前核码」义务
- 声明4：`.claude/skills/live-test/SKILL.md` 的「失败与修复记录」节无「已断言事实 vs 根因推断」分级要求——本次错误修复建议（「hasAnyStore 纳入 fetchStores」）即推断未分级直接入树
- 声明5：`doc/plan/_CONVENTIONS.md` 审查摘要契约（无锚点视为未核验）已覆盖方案文档，但未覆盖子代理交接链

**待决策**：
- 决策A：两条新编码规则分级——建议 P1（命名失配 + 两义封装）、双标准并存 P2（评审信号级）
- 决策B：storeScope 三态化（治本重构，把 storeRoles+fetchStores 组合语义封装为 None/All/Selected）是否立独立小任务排 M 之后——建议立（小规模），但 M 已能修复缺陷本身，非阻塞
- 决策C：是否同步写一条 feedback 记忆（跨会话提醒「摘要加工为裁决依据前核码」）——建议写（规则管子代理链，记忆管主会话行为）

**自曝风险**：
- 三条新规则 + 两技能契约增补会加长规则文件，存在稀释注意力风险——条目文本须控制在既有规则条目密度内，不展开长案例
- 锚点要求增加子代理摘要负担，可能令 ≤5 行约束被挤爆——锚点以行内 `file:line` 形态计入，不单列

## 背景

2026-08-28 K 任务收尾时，live-test 发现的替换轨道缺陷（M 节点）其根因在三级传递链上被持续误判：live-test 子代理读码后摘要写「hasAnyStore()=false 不走守卫链」（被命名误导，修复建议「hasAnyStore 纳入 fetchStores」建立在错误语义上）→ 主会话转述时加工为「判定作品是否已有 store、数据源失真」的自洽叙事 → 用户核码（三个锚点）后纠正。复盘六层成因：命名丢主语、两义值未封装、同域双标准并存、交接链无锚点、推断与断言混排、编排模式未随输出性质切换。本方案把其中可项目级固化者落地为规则与技能契约。

## 修改面

### 一、`.claude/rules/backend.md` 新增三条编码规则

1. **PREDICATE_NAMING_SUBJECT** (P1)：布尔谓词方法命名必须自含主语与语义域，**调用点不依赖定义处注释即可无歧义解读**（名字是调用点唯一的语义载体，注释不随调用传播）。「存在性」与「选择域」字面易混的命名禁止。反例：`hasAnyStore()`（字面=存量存在，实义=用户选择集非空，`taskManager/model.go:69`）；正例：`hasSelectedStores()`。同类：`isXxx`/`hasXxx` 命名在写入口时自查「主语是谁、问的是哪个域」。
2. **AMBIGUOUS_VALUE_MUST_ENUM** (P1)：一个字段的空值/零值承载两种及以上业务含义时，必须封装为显式枚举/三态类型（如 None/All/Selected），禁止「靠伴随字段 + 注释区分」的隐式多义约定——歧义留在注释里必有一处调用点丢上下文。反例：`storeRoles` 空=「全量」或「仅作品信息」由 `fetchStores` 区分（`taskManager/model.go:55`）。
3. **SINGLE_CRITERION_PER_SEMANTIC** (P2)：同一语义判定（如「本次是否涉及资源板块」）在一条执行链内只允许一套判据；并存两套即缺陷信号，评审/自查遇到必质疑（反例先例：`model.go:909` 用 `fetchStores`、`model.go:927` 用 `hasAnyStore()` 判同一语义）。

### 二、`.claude/skills/phase-executor/SKILL.md` 交接契约增补（「核对与交接」节）

- 子代理交接摘要中引用的代码符号（方法/字段/常量/错误名）必须附 `file:line` 锚点——**符号名≠锚点**，无锚点的符号引用视为未核验（对齐 `_CONVENTIONS.md` 审查摘要契约精神，将覆盖面从方案文档扩展到交接链）。
- 主会话把交接摘要**加工为分析结论/裁决依据**输出前，必须核码（读锚点片段验证语义）或在输出中显式标注「未核码推断」；防上下文膨胀的编排纪律不豁免裁决支持的核码义务——执行编排与分析支持的可靠性要求不同档。

### 三、`.claude/skills/live-test/SKILL.md` 报告分级契约（「失败循环」节增补）

- 报告「失败与修复记录」「关键发现」类节必须两级显式标注：**已断言**（有证据采集落盘：SQL/DOM/日志/截图）与**推断**（解释性、未单独验证）。
- 推断级内容不得直接转化为修复方向/修复建议供下游采纳——修复方向须另经锚点核码定准（本条防的是：推断者的命名误读经「发现→建议」通道洗白为事实）。

### 四、（决策C 通过时）`memory/` 新增 feedback 记忆

`handoff-requires-anchor-before-analysis`：交接摘要加工为裁决依据前先核码；符号名≠锚点。Why/How 按 memory 模板。
