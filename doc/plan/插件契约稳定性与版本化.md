# 插件契约稳定性与版本化（任务图节点 C）

> 本文档是「完善插件约定，为正式发布做准备」epic（任务图节点 C）的设计方案。
> 范围：把插件↔主程序之间零散/不完整的契约收拢为稳定、可校验的发布标准。含四个关注面：版本协商 / 能力声明化 / 后端 gRPC 契约 / 前端 TS 契约。

- 风险1：类型别名（`type TaskDTO = gen.Task`）消灭 `host.go`/`client.go` 映射层，但 gen 与 dto 字段命名大小写不一致，需机械统一，触及热点文件（`search/repository.go` 59 处、两插件 `task_handler.go`）。
- 风险2：B 类移出 SDK dto 包涉及主程序多文件改 import（`WorkFullDTO` 15、`TaskProgressTreeDTO` 26、`WorkSetWithCoverDTO` 24、`SiteTagFullDTO` 24 等引用密集）；**且前端 TS bindings 路径 `@bindings/.../library-squirrel-sdk/dto` 中 B 类部分会失效**（B 类移出后 bindings 改从主程序 model 包生成），`ResourceViewer.vue:3`/`VideoRenderer.vue`/`UnknownRenderer.vue`/`WorkCardItem.ts`/`WorkSetDialog.vue`/`WorkGridForWorkSet.vue` 等前端 import 路径全要改。范围广但机械（只改 import 路径，字段/逻辑不变）。
- 风险3：`resourceViewer` 收紧 props 对**现有插件零影响**（声明10，无人用 resourceViewer），是纯主程序侧改进 + 为未来插件建稳定契约。风险落在未来插件需按新 props 契约开发。
- 风险4：`contractVersion` 整数代际依赖「破坏性变更才 bump（bump = 提升契约版本号）」纪律——proto 加字段（向前兼容）不能误 bump、删/改字段（破坏性）不能漏 bump。需建立变更判定规则（proto 字段编号机制为判据），否则误拒插件或漏拒致静默错乱。
- 风险5：四块改动有依赖顺序（契约版本机制是其余校验的基础），需按序迁移，不能并行。
- 风险6：proto 单源 + 别名是较大重构，首发前做有回归风险，需充分测试（尤其 TaskHandler 流式契约、`StoreSpec` reader 路径、Start/Resume bidi stream）。
- 风险7：契约版本/能力声明需同步更新两个现有插件（local/pixiv）的 manifest（补 `contractVersion`/`capabilities` 字段），首发前无兼容包袱、正合适。
- 风险8：未来 `contractVersion` bump 到 2 时无 deprecation 宽限期设计——首发立「硬拒绝」纪律，但主程序 bump 后已发布插件会立即失效。需在首次 bump 时定宽限策略（如主程序同时支持 N 与 N-1 一段时间）；首发可不定，但需知晓此债。
- 风险9：字符串常量若首发不根治、仅加契约测试断言三处相等，该测试只能覆盖主程序 entity 与 SDK dto 两处，**无法覆盖第三方插件用字面量字符串（非引用 SDK 常量）的场景**——第三方插件硬编码 `"image"` 仍可能漂移。唯有单一真相源（决策7）才能彻底防。

## 现状总览：三层类型 + 两处手工映射

```
主程序 entity（GORM tag / BaseEntity / sql.Null*）
   ⇄  映射层① 主程序 convert.go 手写
SDK dto   （纯 struct / json tag / *T pointer / io.ReadCloser）
   ⇄  映射层② SDK host.go · client.go 手写
proto gen.*  ⇄  gRPC 传输
```

- dto 包混了两类：**A 类插件契约**（走 gRPC，proto 已覆盖）+ **B 类前端展示**（`WorkFullDTO`/`ResourceFullDTO`/`TaskProgress*` 等，不走 gRPC、给前端 bindings 用）。
- dto 包因此背三种职责：gRPC 契约 + 插件 Go API 面 + 前端 TS bindings 源——演进节奏不同，是混乱根源。
- 字符串常量三处手写（声明5），运行时静默漂移、零编译期保护。

## ① 版本协商：A2 独立整数契约版本

**结论**：采用方案 **A2「独立整数契约版本」**（候选对比：A1=复用主程序 semver 做 min-host 校验、A3=用主程序 semver 的 major 当契约版本——经对比选 A2，理由见下文「为何整数而非 semver」）。引入独立于发布版本的「契约版本」整数，与 go-plugin `ProtocolVersion`（传输握手、编译期）形成两层分工——契约版本是业务契约、运行期校验。

**机制**：
- 主程序声明 `currentContractVersion`（首发 = 1）与 `minSupportedContractVersion`（首发 = 1）。
- 插件 manifest 声明 `contractVersion`（它编译时锁定的契约版本；SDK 导出一个常量供插件作者引用，但不强制编译期同符号——契约版本是「声明 + 比大小」，**不需要单一真相源**，故无字符串常量那样的依赖方向难题）。
- 校验：`plugin.contractVersion > host.current` → 插件太新，拒（提示升级主程序）；`< host.minSupported` → 插件太旧，拒（提示升级插件）。
- 失败行为：**硬拒绝 + 清晰提示**（指明该升级谁）。首发立「不兼容就明确拒」纪律，避免静默错乱。
- 时机：**安装期预检**（`loadPluginPackage`，阻止装不兼容插件）+ **加载期终检**（`LoadPluginProcess` 兜底）。

**为何整数而非 semver**：契约版本是「代际计数器」（仅破坏性变更 +1），不是「发布进度刻度」（semver 的 major.minor.patch 粒度）。proto 加字段（向前兼容）不 bump，故无 minor/patch 需求；整数比大小无歧义、无解析成本；与 go-plugin `ProtocolVersion` 同形；避免 semver 的 false precision（minor 误夹带破坏性变更会骗消费者）。Terraform `tfprotov5/v6` 即整数协议版本先例。

**bump 判定规则**（风控4）：proto 加字段 = 兼容（不 bump）；删字段 / 改字段类型 / 改 DTO 结构 / 改 RPC 签名 / 改前端 props 契约 = 破坏性（bump）。

**改动点**：
- 主程序：`backend/plugin/extension` 加 `currentContractVersion`/`minSupportedContractVersion` 常量；`loadPluginPackage` 加安装期校验；`LoadPluginProcess` 加加载期校验。
- SDK：导出 `ContractVersion` 常量（供插件 manifest 引用）。
- `PluginManifest`（`backend/base/model/dto/plugin_types.go`）加 `contractVersion` 字段。
- 两插件 manifest 补 `contractVersion`。

## ② 能力声明化：方案1（建机制 + WorkOrderQuerier 迁移）

**结论**：plugin.json 加 `capabilities` 封闭枚举字段；`WorkOrderQuerier` 从「类型断言盲调」（`plugin_server.go:179`）改为「声明驱动 + 运行时验证」。机制就位，未来任务图节点 G（资源类型扩展）/H（作品集父子关系）引入新能力 = 加 capabilities 枚举值，零机制改动。

**机制**：
- `capabilities` 为封闭枚举数组（主程序定义合法能力集，未知值拒绝/忽略——与 `ResourceType`/`StoreType` 严格识别哲学一致）。
- 能力**不单独版本化**：用全局 `contractVersion` 兜底（能力演进 = 契约演进）。
- `capabilities` 与 `extensions` **分离**：`extensions` 是扩展点实例（taskHandlers/siteBrowsers/frontendExtensions），`capabilities` 是可选接口特性（如 WorkOrderQuerier），各管各的。
- 首发枚举仅 1 值：`workOrderQuery`。
- WorkOrderQuerier 迁移后：插件声明 `"capabilities": ["workOrderQuery"]`，主程序查到才调（不盲调）；声明说有但运行时未实现 → 报契约错；声明说没有但实现了 → 忽略。

**首发收益诚实评估**：② 是四块里首发收益最小的（前瞻铺路）。WorkOrderQuerier 当前运行时探测本就干净；声明化边际收益在 G/H 引入新能力后才真正显现。但首发前改现有插件无兼容包袱，机制成本低（1 枚举值 + manifest 补字段），故建机制 + 迁移。

**改动点**：
- `PluginManifest` 加 `capabilities` 字段 + 主程序封闭枚举常量集。
- `plugin_server.go` 的 `QueryWorkSetOrder`：从类型断言兜底改为「主程序侧先查声明、声明无则不调」。
- 主程序加载时读 `capabilities` 存入 `PluginInfo`/registry。
- 两插件 manifest 补 `capabilities`（pixiv 实现 WorkOrderQuerier → `["workOrderQuery"]`；local 未实现 → `[]` 或省略）。

## ③ 后端 gRPC 契约：A 类 proto 单源 + B 类移出 SDK + 字符串常量待定

### A 类（插件契约）：proto 单源，类型别名消灭映射层

**结论**：proto 已是事实契约源（声明2）、且用 optional 与 dto 指针天然匹配（声明3）。用类型别名 `type TaskDTO = gen.Task`（留在 dto 包）让 dto 名字即 gen 类型，**消灭 `host.go`/`client.go` 的 `protoToWorkSet`/`workSetToProto`/`protoToSite` 等手工映射层**（漂移根源）。

**为何不裸替换、不代码生成**：
- 裸替换（dto 包消失、全用 gen）：1019 处引用全改，灾难级，否决。
- 别名（`type X = gen.Y`）：引用点零改动（dto.TaskDTO 仍是合法名），映射层可删；代价仅字段命名机械统一（决策5）。
- 代码生成（dto 从 proto 生成保持风格）：插件零改动但引入 buf+模板基建，首发不值当，留作演化项。

**破坏面**（声明9）：1019 处为裸替换上限；别名方案真实改动 = 映射层删除（`host.go`/`client.go` 十几个函数）+ 字段命名统一（`SiteID`→`SiteId` 类，触及热点文件，机械）。`io.ReadCloser`（`StoreSpec`）已有正解——proto 用 `StoreSpecMeta`（元数据）+ stream data 块（reader 数据）拆开（`plugin.proto:294-309`），`StoreSpec` 手写包装保留，不算新破坏。

**改动点**：
- dto 包 A 类类型改为 gen 别名（`type TaskDTO = gen.Task` 等）。
- 删 `host.go`/`client.go` 的 protoTo*/ToProto 映射函数。
- 字段命名统一（决策5）。
- 影响热点文件字段访问（机械改）。

### B 类（前端展示）：移出 SDK dto 包

**结论**：`WorkFullDTO`/`ResourceFullDTO`/`TaskProgressTreeDTO`/`WorkSetWithCoverDTO`/`SiteTagFullDTO` 等前端展示 DTO 不走 gRPC（proto `WorkResponse` 不含它们），不该待在 SDK dto 包（插件 Go API 面）。移出到主程序 model dto（决策6 定具体位置）。移出后插件 Go 侧看不到 B 类，堵住「插件误用主程序前端 DTO」的耦合。

**破坏面**（声明9）：B 类在主程序引用密集，移包涉及主程序多文件改 import（`WorkFullDTO` 15、`TaskProgressTreeDTO` 26、`WorkSetWithCoverDTO` 24 等）；**且前端 bindings 路径迁移**（`@bindings/.../library-squirrel-sdk/dto` 中 B 类部分改从主程序 model 包生成，`ResourceViewer`/`VideoRenderer`/`UnknownRenderer`/`WorkCardItem`/`WorkSetDialog`/`WorkGridForWorkSet` 等前端 import 路径全改，见风险2）。范围广但纯机械（只改 import 路径，字段/逻辑不变）。

### 字符串常量：真相源位置 open（决策7）

**结论**：store_type/resource_type/generation 三处手写（声明5），危害最大（运行时静默漂移、零编译保护）。根治需单一真相源，但位置 open：
- 源放主程序 entity → SDK 要引用主程序，**破坏 SDK 独立发布** ❌
- 源放 SDK contract 子包 → 主程序底层 entity 反向依赖 SDK，方向别扭（倾向，但顾虑 open）
- proto enum → 生成 int，与 string 场景绕，无明显优势
- 不根治 + 契约测试断言三处相等 → 最轻，但运行时仍无编译保护（保底方案）

实施时定；若首发不根治，至少加契约测试断言三处常量值相等作为兜底。

## ④ 前端 TS 契约：bindings 单源，收紧 resourceViewer props，不 proto 化

**结论**：前端 TS 是 Wails bindings 从 Go 生成（声明6，单源、非同步漂移），**不该 proto 化**（proto 是 gRPC 后端语言，前端 props 走 bindings+JSON，两套机制）。真问题不是 Go↔TS 不一致，而是 `resourceViewer` 把完整 B 类（易变展示 DTO）当插件前端契约面注入（声明7）——**用易变类型当稳定契约**，脆弱。

**机制**：
- 收紧 `resourceViewer` props 为**专为插件设计的稳定最小 props**（候选 `{resourceId, workId, resourceType, storeBaseUrl}`），插件按需调 RPC 取详情，而非主程序直接喂完整 `WorkFullDTO`。
- 主程序前端 B 类 DTO 随展示需求随便变，不再撼动插件契约面。
- 破坏性 props 变更走 ① 的 `contractVersion` bump（演进兼容归版本协商）。

**对现有插件影响**（声明10 + 风险3）：零——两插件均未声明 resourceViewer，收紧是纯主程序侧改进 + 为未来插件建稳定契约。

**改动点**：
- `ResourceViewer.vue` 注入 props 从 `{resource, work}` 改为稳定最小集。
- 提供插件按需取详情的 RPC（若最小 props 不够，插件调 HostService 查）。
- 决策8 定最小 props 字段集。

## 迁移步骤（按依赖顺序）

1. **契约版本机制（①）**——基础，其余校验的载体。建常量 + manifest 字段 + 安装/加载双校验 + 两插件 manifest 补字段。
2. **能力声明化（②）**——用 ① 的 manifest 载体。capabilities 枚举 + WorkOrderQuerier 迁移 + 两插件 manifest 补字段。
3. **B 类移出 SDK dto 包（③-B）**——为 ④ 明确 B 类归属、为 ③-A 清理 dto 包。机械改 import。
4. **A 类 proto 单源（③-A）**——依赖 3 清理后的 dto 包。类型别名 + 删映射层 + 字段命名统一。较大重构，需充分测试（风险6）。
5. **前端 TS props 收紧（④）**——依赖 3 的 B 类定位明确。`ResourceViewer.vue` 改注入 + 按需 RPC。
6. **字符串常量（③ 附带，决策7）**——相对独立，可与 3–4 并行；若首发不根治则加契约测试兜底。

> 1→2 是 manifest/校验基建（轻）；3→4 是 dto 架构重构（重，主体工作）；5 是前端（中）；6 独立。

## 决策与约束（守住勿回退）

- **契约版本整数代际**：仅破坏性变更 bump；proto 加字段（向前兼容）不 bump。bump 判定以 proto 字段编号机制为据。
- **proto 已是 gRPC 真相源**：A 类单源化是「消灭手写映射层」，非「从零建 proto」。类型别名方案优先于裸替换/代码生成。
- **A/B 类判据 = 是否跨 gRPC**：A 类（跨 gRPC）proto 单源；B 类（前端展示）移出 SDK、不 proto 化。判据不是「插件是否可见」。
- **前端 TS 不 proto 化**：TS 是 bindings 单源；前端 props 契约靠「收紧为稳定最小集 + 版本协商」，不靠 proto。
- **能力封闭枚举 + 不单独版本化**：与 ResourceType/StoreType 严格识别哲学一致；能力演进由 contractVersion 兜底。
- **首发前无兼容包袱**：两插件 manifest 改字段、dto 重构都可在首发前做，无需兼容迁移。
- **SDK 独立性是硬约束**：任何「真相源放主程序、SDK 引用主程序」的方案破坏 SDK 独立发布，否决。
