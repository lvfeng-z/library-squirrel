# 插件检查更新方案

## 审查摘要

**关键声明（抽查项）**

- 声明1：当前升级为静默流——`InstallBundled`（`backend/plugin/service.go:355`）判 `needBundledUpgrade`（`service.go:383`，buildId 不一致即升）后直接 `installCore` 重装（`service.go:368-371`），无任何用户交互。buildId 为构建管线注入 plugin.json 的源码状态标识（同源码状态永远同值）。
- 声明2：检测点在 pre-Run——`main.go:144` 调 `InstallBundledPlugins`（`app.go:232`），逐包调 `InstallBundled`（`app.go:251`），失败仅 error 日志后 continue（`app.go:252-254`）；此时插件进程未启动（`LoadPlugins` 延迟至窗口运行时就绪回调 `WindowRuntimeReady` 内执行，真证 `main.go:147-155`——LoadPlugins 于 `:153`，`app.go:226-229` 仅为方法定义本体），故 pre-Run 路径无运行中任务可拦。
- 声明3：契约校验双卡口已存在——`ValidateContractVersion`（`backend/plugin/extension/loader.go:46`：插件契约 > 主程序当前契约拒绝、< 最低兼容契约拒绝、0=未声明视为当前契约放行）；安装期预检挂 `loadPluginPackage`（`service.go:323-326`），加载期终检挂 `LoadPluginProcess`（`loader.go:251`）——已装插件契约不兼容时加载被拒，插件实际不可用。
- 声明4：热重载方案（`doc/plan/插件热重载体系完善方案.md`，2026-08-16 完成）的换版原语已就绪——`deactivate`（停用并删文件）= `stopRuntime`（参与者否决 → 停进程 → 清理；参与者即 LifecycleParticipant，持有插件运行时痕迹的模块在停用前收到 PrepareStop 否决询问、停后收到 OnStopped 清理回调）+ `removeFiles`（按插件 RootPath 删目录，不触运行时不改 DB，`backend/plugin/lifecycle.go:80-90`；组合见 `service.go:648-665`）；`ReinstallFromPath` = deactivate → `loadPluginPackage` → `install`（重装并 Activate，`service.go:539-571`）；否决标准=运行中任务（Paused 不拦——热重载方案决策5：拦截标准统一为「运行中」，Paused 任务随更新存活可续传）。
- 声明5：`GetActiveTaskCount(pluginPublicId)` 已存在（`backend/taskManager/handler.go:68-70`），运行中定义=Processing/Pausing/Stopping/WaitingForInput——与热重载方案否决标准同源，可作确认框代价计数。
- 声明6：「插件」菜单按钮存在且当前无徽标——builtin 菜单项 `builtin-plugin`（`frontend/src/composables/useBuiltinMenus.ts:113-120`，label「插件」、viewId pluginManage），由 `DynamicSideMenu.vue` 无子菜单顶层项分支渲染（`frontend/src/components/slot/DynamicSideMenu.vue:132-139`）；红点载体 el-badge 在应用内有使用先例（`frontend/src/components/common/CollapsePanel.vue:96-109`），侧边菜单项尚无 badge 先例（本方案为首例）。
- 声明7：`installCore` 重装为全字段覆盖——构造全新 `Plugin` 对象仅复制 ID 与 CreateTime（`service.go:433-471`），新增列在其中未赋值即写零值——「拒绝标记随任何重装自然清零」由该结构保证；且重装自带旧目录清理——RootPath 变化即 RemoveDir 旧安装目录并逐级回收空父目录（`service.go:483-495`），version 变化必使 RootPath 变化（安装路径含 version，`service.go:420-421`），故正常升级不残留旧 version 目录。
- 声明8：插件实体现有 `BuildID`（`backend/base/model/entity/plugin.go:30`），无任何「拒绝/跳过」类字段；新增列经 GORM AutoMigrate（启动时自动比照实体加列）自动加列，无手写迁移。
- 声明9：前端外壳挂载点存在——`MainLayout.vue` 为应用外壳（侧边菜单 + router-view + 通知中心等全局件，`frontend/src/MainLayout.vue:43-70`）；任务快照的既有数据通道是后端推送转译（`frontend/src/MainIpcListener.ts:66-68` 监听 `task-snapshot` 事件消费后端防抖快照）；页面级 onMounted 拉取是既有普遍模式（如 `frontend/src/views/PluginManage.vue:23-28` 挂载即 doSearch 拉插件列表），「MainLayout 外壳层全局数据拉取」为本方案首例——形态为 wrapper 调 bindings 查询，与既有查询类 wrapper 同构。
- 声明10：handler 层已有 `ReinstallFromPath(ctx, pluginPublicId, packagePath, trusted)`（`backend/plugin/handler.go:62-68`），但 bundled zip 路径属服务端权威信息（config.yaml `Plugins` 段解析，`app.go:240-244`），本方案不让前端回传路径（见决策记录）。

**待决策（已全部裁决 2026-08-17）**

- 决策1 → **不进**（用户裁决）：未打标 zip（buildId 为空，回落 version 判据）维持现状静默升级，不进检查更新流——不记待办、不亮红点、不提供跳过按钮；构建管线打标校验已兜底其盲区（`build/plugins.ps1:51-64` Assert-BuildId：zip 内 plugin.json 非空 buildId 且无 BOM，缺失即该插件构建失败）。
- 决策2 → **本期不关注**（用户裁决）：server 纯 HTTP 模式系 Wails 模板自带构建形态（`-tags server`），非本项目现役用法，作未来方向保留——本期不做判别分支、不承担其无 UI 消费面的行为；启用时的缺口记入第七节非目标。
- 决策3 → **加**（用户裁决，按推荐）：PluginDTO 透传 declined 值，插件管理页显示「已跳过构建 X」+ [重新提示]（`RestorePendingUpgrade` 清标记并立即重跑单插件检测重建待办）。

**自曝风险**

- 风险1：「pre-Run 无运行时故强制路径可绕过 stopRuntime」依赖调用时序不变——若未来 `InstallBundled` 被运行期复用，强制路径将跳过参与者否决。须在 `InstallBundled` 注释声明「仅 pre-Run 调用」并让运行期路径独走 `ApplyPendingUpgrade`。
- 风险2：拒绝标记与 buildId 等值比较依赖构建身份方案（`doc/plan/插件构建身份与升级判据机制.md`）的机制承诺（同源码同 buildId）；git 历史改写（其风险1）会使 declined 失配 → 重新提示一次，无害但需知晓。
- 风险3：待办列表为 service 内存态（进程生命周期），前端仅在 mounted 拉取与操作后刷新——会话中途磁盘/DB 被外部改变（如手动重装）后红点计数可能过期；`ApplyPendingUpgrade` 服务端重验（重读 zip + 重查 DB）兜底，过期项报错而非误操作。
- 风险4：红点数据无会话内轮询/推送——捆绑 zip 随主程序安装分发、运行期不变，偏差窗口为零；但未来非 bundled 网络源接入后（检查结果随网络变化）需引入刷新或事件推送机制，届时接口要预留演进。
- 风险5：降级场景（主程序回滚，zip version 低于已装）UI 按「降级」展示，跨版本 PluginData（插件写入任务的自管 JSON 数据）兼容性未实测——与热重载方案风险1 同源，由插件 schemaVersion fail-fast（格式版本超出支持即快速失败）兜底。
- 风险6：强制升级判定读 DB 记录的 `contract_version`，若 DB 值与磁盘 plugin.json 漂移（手工篡改）判定失真——加载终检（声明3）仍拒绝加载，不会放行坏插件，只是强制时机延迟。
- 风险7：换版执行中断的自愈依赖重启重检——`ApplyPendingUpgrade`（运行期换版）与 pre-Run 强制路径（installCore 直装）中途崩溃均会留下半解压或 DB 未写状态（执行中守卫为进程内存态，崩溃即失效）；待办项/判变条件未消除，下次启动重新检测后可重试，installCore 重解压覆盖可自愈，与现状 ReinstallFromPath 崩溃面同源。

## 一、背景与四要素

上游构建身份方案（`doc/plan/插件构建身份与升级判据机制.md`，下称**构建身份方案**）落地 buildId 判据后，「检测是否该升级」已可靠，但「检测到之后如何对待用户」留白（其「非目标」节、决策3）。当前生效行为：静默升级（bundled buildId 不一致即重装，声明1）+ 契约不兼容捆绑包静默失败仅记日志（声明2）。

**方向调整（2026-08-17 用户裁决）**：功能定名为**插件检查更新**——概念上不分 bundled/非 bundled（统一「检查更新 → 发现待更新 → 提示 → 用户答复」流），当前仅实现 bundled 生产者（本地 zip 判据，零网络依赖）；非 bundled 网络检查更新留接口不实现（第七节）。提醒面为**「插件」菜单按钮红点（带个数文本）**，不再使用 announce 聚合卡片（消息提醒系统，右上角堆叠卡片）——红点常驻可发现，替代一过性卡片的提醒职责。

本方案定稿四要素（第三项随方向调整由「聚合提示」改为「红点计数提示」）：**何时问用户、拒绝状态持久化、红点计数提示、契约不兼容强制升级**。已锁前提（前序会话裁决，派生图谱见 `.claude/workflow/active/plugin-identity-version-system/TREE.md`）：检测在 pre-Run（InstallBundled）；**答复当次生效**——用户答复后当次会话内立即换版，不等下次启动（依赖热重载方案（`doc/plan/插件热重载体系完善方案.md`，下称**热重载方案**）的换版基建，已就绪）；拦截语义=运行中任务否决、Paused 不拦。

三信号分工沿用构建身份方案第三节：判「变没变」用 buildId；判「升还是降」用 version（仅展示文案）；判「能否允许拒绝」用 contractVersion。

## 二、四要素定稿

### 2.1 何时问用户

**检测（后端，pre-Run）**：`InstallBundled` 判 `needBundledUpgrade` 为真时**不再静默重装**，改为记录一条待更新项（内存列表），保留旧版继续运行；仅在两情形下不经询问直接动库：全新安装（现状保留）与契约不兼容强制升级（见 2.4）。

**提醒（前端，mounted 后）**：`MainLayout` `onMounted` 拉取 `GetPendingUpgrades` 写入 Pinia store，「插件」菜单按钮渲染红点（个数 = 可升级项数，见 2.3）。旧版插件在 `LoadPlugins`（WindowRuntimeReady）正常加载运行——检测与提醒之间插件可用性不中断。

**答复（用户主动，当次生效）**：红点引导用户进入插件管理页——待更新条目带 [升级] / [跳过此构建] 按钮。用户点击 [升级] 即答复，`ApplyPendingUpgrade` 走热重载方案换版链（stopRuntime 否决 → removeFiles → installCore → Activate），当次会话内完成换版，无需重启。点击 [跳过此构建] 即拒绝，持久化（见 2.2）。

不采用启动模态对话框：升级非紧急决策（旧版可用），四轨消息机制（`doc/message-integration-guide.md`）中对话框留给「需用户决策/动作」的阻塞场景；红点常驻 + 管理页承接是提示疲劳与可发现性的折中。

### 2.2 拒绝状态持久化

- **载体**：`Plugin` 实体新列 `UpgradeDeclinedBuildID sql.NullString`（列 `upgrade_declined_build_id`，AutoMigrate 自动加列，声明8）。不用 `plugin_storage`（插件自管 KV 表）——主程序往插件命名空间写用户决策语义错位。
- **语义**：「跳过此构建」——记录用户拒绝的目标 buildId，非「永不再问」。
- **写入**：[跳过此构建] → `DeclinePendingUpgrade(publicId)` → service 从待更新项取目标 buildId 写入实体（目标 buildId 为空不提供该按钮，见决策1）。
- **消费**：`InstallBundled` 判 `needBundledUpgrade` 为真后，若 `existing.UpgradeDeclinedBuildID == zip.BuildID` → 静默跳过（不记待更新项、不亮红点），info 日志。
- **失效与清除**：新 buildId 到来（≠ declined 值）→ 重新提示；任何重装走 `installCore` 全字段覆盖（声明7），declined 自然清零——「升级后拒绝历史消失」由结构保证，无需清理代码。
- **豁免**：契约不兼容强制升级无视 declined（旧版无法加载，拒绝无意义）。优先级：**强制 > declined > 提示 > 跳过**。
- **反悔入口（决策3）**：declined 非空的 bundled 插件在管理页显示「已跳过构建 X」+ [重新提示]——`RestorePendingUpgrade` 清除标记并立即对该插件重跑检测（服务端自持 zip 路径，检测=读包+比较、无副作用）重建待更新项，不必等下次启动。

### 2.3 红点计数提示

- **载体**：「插件」菜单按钮（builtin 项 `builtin-plugin`，声明6）右上角红点，带个数文本（`el-badge :value`，0 时隐藏，≥100 显示 99+——Element Plus 默认溢出行为）。
- **计数口径**：仅 **available**（可升级、可答复）项计数——红点语义 =「有 N 个更新等你在管理页处理」；forced（已强制升级）/error（捆绑包安装失败）不计数，二者属告知性信息，在管理页待更新区块只读可见。
- **数据流**：新 Pinia store `usePluginUpdateStore`（`frontend/src/store/UsePluginUpdateStore.ts`）持有待更新列表（类型从 `@bindings/...` 引用，BINDING_TYPE_REUSE 规则）与 `badgeCount` 计算属性；`refresh()` action 调 wrapper 拉取。`MainLayout` `onMounted` 触发首次 `refresh()`；管理页操作（升级/跳过/重新提示）完成后由 store 内部或页面触发 `refresh()` 刷新红点。`DynamicSideMenu` 插件项外包 `el-badge` 读 `badgeCount`。
- **升级结果反馈**：`ApplyPendingUpgrade` 为用户点击后 await 的 IPC 调用，成功/失败用 ElMessage（四轨机制「同步操作反馈」判定）——不再使用 announce（方向调整，见决策记录）。
- **拉取时机说明**：无会话内轮询（风险4）——bundled 判据在会话内不变，mounted 一次 + 操作后刷新已完备。

### 2.4 契约不兼容强制升级

契约三信号问题的回答：「能否允许拒绝」。三子场景：

| 场景 | 判定 | 处置 |
|---|---|---|
| a. 已装不兼容 + zip 兼容 | `ValidateContractVersion(existing.ContractVersion)` 报错（`loader.go:46`；DB 值 NULL/0 按未声明=当前契约放行，与加载终检同语义）且 `loadPluginPackage` 通过（安装预检声明3） | **pre-Run 强制升级**：`installCore(reinstall=true)` 直接换，不经提示、无视 declined。此时无运行时（声明2），无需 stopRuntime；旧 version 目录由 installCore 自带清理收口（声明7，`service.go:483-495`）——与换版链磁盘行为天然对齐，差异仅剩无 stopRuntime（无进程可停，非能力缺失）。记录 forced 项供管理页展示 |
| b. zip 不兼容（已装兼容与否不论） | `loadPluginPackage` 契约校验报错 | 无法安装。记录 error 项（包路径+错误摘要）供管理页展示；保留现状 error 日志 |
| c. 双侧不兼容 | 同 b 叠加 a | 同 b——zip 装不进、已装加载不了，只能等修包，管理页 error 说明 |

场景 b/c 的 error 项记录范围：`InstallBundled` 内 `loadPluginPackage` 的一切失败（不止契约错——解压失败、manifest 非法同样值得让用户知晓捆绑插件没装上），`app.go:252-254` 现有日志保留。

## 三、接口与数据设计

### 3.1 后端（backend/plugin）

**待更新项（service 内存态）**：`map[publicId]*pendingUpgradeEntry` + 互斥锁，进程生命周期，重启重检（检测每启必跑，无需落库；落库的只有 declined）。

```go
// pendingUpgradeEntry 启动期检测出的插件更新待办（内存态，重启重检）
type pendingUpgradeEntry struct {
    PublicID         string
    PluginName       string
    InstalledVersion string
    TargetVersion    string
    TargetBuildID    string  // zip 侧 buildId；未打标包为空（决策1：不进检查更新流则不会出现）
    Direction        string  // up/down/none（version 语义排序，仅展示用）
    Kind             string  // available/forced/error
    PackagePath      string  // bundled zip 绝对路径（服务端权威持有，不下发前端作操作参数）
    Message          string  // error 类的错误摘要
    Executing        bool    // 执行中守卫：Apply 运行期置位，拦截重复触发与 Decline/Restore 竞态
}
```

**新 handler 方法（backend/plugin/handler.go，命名不带 Bundled——「检查更新」统一概念，为非 bundled 网络源接入预留同一待办流）**：

| 方法 | 行为 |
|---|---|
| `GetPendingUpgrades() → []PendingUpgradeDTO` | 返回全部待办项（三类 kind 混合；DTO 放 `backend/base/model/dto/plugin_dto.go`） |
| `ApplyPendingUpgrade(publicId) → *PluginDTO` | 从待办项取 zip 路径 → 走 `ReinstallFromPath` 内部链（deactivate(PluginStopOpUpdate) → loadPluginPackage 重验 → install）。服务端自持路径，不复用 `ReinstallFromPath` handler 入口（声明10：避免路径 IPC 往返）。成功后移除待办项 |
| `DeclinePendingUpgrade(publicId) → *PluginDTO` | 从待办项取目标 buildId 写入 `UpgradeDeclinedBuildID`，移除待办项；目标 buildId 为空则报错 |
| `RestorePendingUpgrade(publicId) → *PluginDTO` | 清除 `UpgradeDeclinedBuildID` 并对该插件立即重跑检测（决策3 反悔入口）：判真则重建待办项，判假则无事可提示 |

**执行守卫（并发）**：待办列表互斥锁内原子完成「取条目 → 置 Executing」；Executing 置位期间重复 `ApplyPendingUpgrade`、`DeclinePendingUpgrade`、`RestorePendingUpgrade` 一律返回「处理中」错误；执行结束（成功移除条目 / 失败复位）后恢复可操作。前端按钮 loading 态兜底双击，守卫以后端为权威。

**`InstallBundled` 改造**（`service.go:355`，分支优先级自上而下）：

```text
loadPluginPackage 失败          → 记 error 待办项，返回原错误（app.go 日志保留）
已装且未卸载：
  已装契约不兼容（2.4a）        → installCore(reinstall) + 记 forced 待办项
  needBundledUpgrade 为假       → 跳过（现状）
  declined == zip buildId       → 静默跳过 + info 日志（不记待办项）
  zip 未打标（buildId 空，决策1）→ version 回落判据维持静默升级（现状 installCore）
  其余                          → 记 available 待办项，保留旧版（新行为）
全新/已卸载                      → installCore 安装（现状，bundled/trusted）
```

**顺带清理**：`Uninstall` 成功时移除该插件待办项（防卸载后残留可操作项；`ApplyPendingUpgrade` 重验 DB 兜底双保险）。

### 3.2 前端

- **wrapper**：`frontend/src/apis/http/wrappers/` 新增四个方法封装（`requireResponse` 语义：查询 `requireData=true`，变更 `requireData=false`），`wails3 generate bindings -ts` 先行。
- **store**：`UsePluginUpdateStore.ts`——`pending` 列表（bindings 类型）、`badgeCount` 计算属性（available 计数）、`refresh()` action。
- **红点（2026-08-17 二次调整后为通用机制）**：菜单红点经 `UseMenuBadgeStore` 注册表（菜单项 slotId → 计数）解耦——`DynamicSideMenu` 对任意菜单项（含子菜单标题与子项、插件插槽菜单）按 slotId 查表渲染 `el-badge`（0 隐藏，99+ 溢出），不感知业务来源；生产者写入注册表（`UsePluginUpdateStore.refresh()` 以 `PLUGIN_MENU_SLOT_ID = 'builtin-plugin'` 写入 available 计数）。插件插槽**渲染层天然兼容**（键即 slotId，插件菜单项复合键同样可查），插件侧生产链路（SDK API+事件通道，跨三端）延后至有需求再做。红点色取 fail tone（状态色板失败语义色槽）。
- **启动拉取**：`MainLayout.vue` `onMounted` 调 `usePluginUpdateStore().refresh()`（页面级 mounted 拉取为既有模式，MainLayout 外壳层全局拉取系本方案首例，声明9）。
- **管理页承接**（2026-08-17 实施后用户二次调整定稿）：升级入口在**表格行内**——插件列表多选，操作栏对有 available 待办的行条件显示 [升级] / [跳过此构建]（DataTable `rule` 按行显隐），另有 [状态] 行内按钮打开插件状态抽屉（原单选联动抽屉废止）；工具栏 [批量升级]（安装按钮左侧）顺序升级选中插件中的可升级项（逐项走服务端否决，汇总成功/失败）；顶部不再有「可升级」提示区，仅保留告知区（已跳过+重新提示 / 已自动升级 / 捆绑包安装失败，任一非空才显示）。数据源：进入页面/操作完成后调 `refresh()` 刷新红点与列表。
- **升级确认框**：点击 [升级] → 调 `GetActiveTaskCount(publicId)`（声明5）——N>0 时确认框明示「该插件有 N 个运行中任务，升级前需先暂停」，按钮 [去任务页]（跳转任务管理）/ [取消]，不提供「仍要尝试」（必被服务端否决，热重载方案决策1 语义）；N=0 时确认框展示版本对，[升级] 直接执行。服务端否决为最权威兜底——预检与执行之间存在状态变化窗口（TOCTOU，time-of-check to time-of-use：检查时刻无任务不保证执行时刻仍无），以后端否决收口。
- **否决回执**：`ApplyPendingUpgrade` 返回否决错误（热重载方案参与者 PrepareStop 文案）→ ElMessage error 展示并引导暂停后重试。

## 四、时序与不变量

```text
pre-Run   InstallBundledPlugins → InstallBundled×N（判变记待办 / 强制换 / declined 跳过 / 失败记 error）
Run 后    WindowRuntimeReady → LoadPlugins（加载旧版，可用性不中断）
mounted   MainLayout onMounted → GetPendingUpgrades → store → 「插件」菜单红点（N 个更新）
答复      管理页 [升级] → 确认框（GetActiveTaskCount 预检）→ ApplyPendingUpgrade
          → stopRuntime（运行中任务否决 / Paused 放行）→ removeFiles → installCore → Activate
          → 待办移除 + ElMessage 成功 + 红点与管理页刷新（热重载方案事件契约驱动插件前端扩展注册项同步）
拒绝      管理页 [跳过此构建] → DeclinePendingUpgrade → declined 落库 → 下次启动静默跳过
```

- **检测先于加载**：待办项在 `LoadPlugins` 前就绪（pre-Run），旧版正常加载——不存在「检测期间插件不可用」窗口。
- **答复路径必走换版链**：运行期一切换版经 `ApplyPendingUpgrade`（含否决）；pre-Run 直装仅限强制与 server 场景，且以「InstallBundled 仅 pre-Run 调用」注释约束（风险1）。
- **Paused 任务随升级存活**可续传；跨版本 Resume 兼容性由插件 PluginData schemaVersion fail-fast 兜底（PluginData 为插件写入任务的自管 JSON 数据、schemaVersion 为其格式版本号，超出支持版本即快速失败拒绝执行；热重载方案风险1 已缩小触达面至本路径与启动期强制路径）。
- **declined 清零只经 installCore**：无独立清除代码，结构保证（声明7）。

## 六、测试要点

- 后端单测（扩展 `plugin_bundled_upgrade_test.go`）：分支优先级矩阵——强制 > declined > available > 跳过；declined 等值短路；未打标包静默升级不记待办；`installCore` 重装后 declined 清零；`DeclinePendingUpgrade` 空 buildId 报错；契约判定对 NULL/0 的放行语义与加载终检一致；重装后旧 version 目录不残留（installCore 自带清理回归守护，`service.go:483-495`）。
- `ApplyPendingUpgrade`：运行中任务否决（错误文案可读）；Paused 放行；zip 重验失败（磁盘包被换）报错不移除待办项；成功后待办移除；Executing 置位期间 Apply/Decline/Restore 均报「处理中」。
- `RestorePendingUpgrade`：清 declined 后待办重建；无升级可提示时幂等返回。
- 前端：红点计数随待办增减（0 隐藏 / N 显示 / 99+ 溢出）；操作完成后红点与管理页同步刷新；forced/error 不计数但区块可见。
- 端到端：旧版运行 → 红点亮 → 管理页升级 → 热换版成功 → 插件前端扩展注册项同步（热重载方案事件契约）→ 红点熄灭 → declined 后重启不再亮 → [重新提示] 重建待办再亮 → 新 buildId 重现提示。

## 七、非目标与接口预留

- **非 bundled（local/url/marketplace）网络检查更新：仅留接口，不实现**——本方案的待办列表、DTO（`Source` 字段区分 bundled/网络）、四个 handler 命名均不绑死 bundled；未来网络源生产者（检查更新+下载后）写入同一待办列表即可复用红点、管理页与答复流。下载、版本源、网络错误重试、红点数据刷新/推送机制（风险4）全部延后。
- 消息提醒系统 announce 消费、通知中心持久条目、桌面级系统通知不做（方向调整后红点承担提醒）。
- **server 纯 HTTP 模式（`-tags server` 构建，`build/Taskfile.yml:138`）本期不关注**（决策2，用户裁决 2026-08-17）：系 Wails 模板自带构建形态、非现役用法，作未来方向保留。本期不新增判别分支——该形态下若无浏览器 UI 消费，红点待办无人答复、bundled 插件停留旧版；未来正式启用时需补「无 UI 消费面的升级路径」（可选静默升级回退或强制升级），并核验该形态下 `WindowRuntimeReady → LoadPlugins`（`main.go:147-155`）是否触发（框架行为，未核验）。
- 任务自动暂停/排空不做（热重载方案决策1：用户先自行处理任务）。

## 八、决策记录（方案内已定，供审查对照）

- **方向调整（2026-08-17 用户裁决）**：提醒面弃 announce 聚合卡片、改菜单红点——红点常驻可发现性优于一过性卡片（4.5s 自动关闭），且免于 announce 聚合纪律（同 title 合并、每类一卡）；前序会话「announce 聚合」结论就此废止。升级结果反馈随之改 ElMessage（同步操作反馈，四轨机制判定）。
- 红点仅计 available：红点语义单一（可答复项数）；forced/error 属告知性信息，混入计数会让「点进去能做什么」失焦。
- 拒绝标记落实体列而非 `plugin_storage`：后者是插件自管命名空间，主程序写入语义错位（见 2.2）。
- `ApplyPendingUpgrade` 服务端自持 zip 路径而非复用 `ReinstallFromPath` handler：路径属服务端权威（config 解析），IPC 往返引入篡改/失效面（声明10）。
- 确认框 N>0 不提供「仍要尝试」：服务端必否决——热重载方案决策1：运行中有该插件任务即拦截并显式提醒；提供「仍要尝试」只会制造一次必败调用与困惑。
- server 纯 HTTP 模式本期不纳入：非现役用法（Wails 模板自带构建形态），用户裁决作未来方向保留——不为假设的部署形态增加判别分支；启用时的缺口已记入第七节非目标。
- 强制路径不另做 removeFiles：installCore 重装自带旧目录清理（RootPath 变化即删，`service.go:483-495`），额外清理属冗余；跳过 stopRuntime 的理由是 pre-Run 场景无进程可停，非能力缺失。
