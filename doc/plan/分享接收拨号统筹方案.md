# 分享接收拨号统筹方案（缺陷⑤ 真根因）

> 非纯设计文档，需审查。关联任务图：share-lineage/TREE.md K 节点（⑤ 缺陷真根因分支）。本版为**草案**（2026-09-01）：用户方向 = 接收方统筹拨号，消除并发自由竞争导致的拥塞。与 `doc/plan/分享恢复执行延迟修复方案.md`（内容跳过，解决「重跑已拥有内容」）互补——本方案解决「新作品并发下载拥塞」。

## 审查摘要

**关键声明（抽查项）**
- 声明1：发送方会话并发流上限 8，超限直接 `frameStreamClose` 拒绝——`backend/share/session.go:49`（`defaultMaxStreams = 8`）、`:574-577`（`handleStreamOpen` 拒绝路径）。
- 声明2：中继每 IP 每分钟拨号上限 60，超限拒绝 `rate_limited`——`library-squirrel-relay/config.go:83`（`DialPerIPPerMinute: 60`）、`relay.go:343-344`（拒绝实现）。
- 声明3：接收方每次文件请求独立拨号——`backend/share/receive_client.go:145-146`（`c.opts.dialFn` 每次调用独立连接）；`fetchWithRetry` 重试也拨号——`task_execution.go:854-889`。
- 声明4：`rate_limited` 判定可退避重试（`receive_client.go:72,85`）→ 形成「限流→重试拨号→更限流」反馈循环；EOF（流被拒）同样可重试（`:91` 默认分支）。
- 声明5：实测（2026-09-01 双实例，接收方=本地安装版）任务 3/6 因 rate_limited 失败（接收方 DB `task.error_message`=「中继暂不可用（rate_limited）」）；新作品视频有效吞吐 ~1.8MB/s，为发送方逐流限速 16MiB/s（`session.go:50` `defaultStreamRate`）的 1/8——瓶颈在连接层（流槽竞争 + 拨号限流），不在带宽。

**待决策（均已裁决 2026-09-01，用户拍板）**
- 决策1（**已裁决：8**）：并发流槽上限 = 8（对齐发送方会话上限 `session.go:49`），不额外留余量。
- 决策2（**已裁决：50/min**）：拨号速率上限 = 50/min（中继 60/min 留边缘余量，`relay config.go:83`）。
- 决策3（**已裁决：进程级单例**）：统筹器作用域 = 进程级单例（app.go 装配，多接收树共享 8 槽保守安全，不做树级并行）。
- 决策4（**已裁决：不做**）：`rate_limited` 全局冷却不做——速率门控 50/min 常态下不触发命中，兜底依赖既有退避重试。
- 决策5（**已裁决：不做**）：提高发送方/中继 8 流上限不做——跨仓改动，本次仅接收方协调，不改基础设施。

**自曝风险**
- 风险1：进程级 8 槽在多接收树并发下保守（槽共享、树间串行化），但安全不拥塞；需树级并行时扩展作用域（决策3）。
- 风险2：速率上限与中继 60/min 对齐时无余量，边缘抖动可能仍触发限流；应设低于中继限值（决策2）。
- 风险3：文件级槽位在退避重试期间闲置（槽被持有但无下载），槽位利用率略降——防拥塞换取的代价，可接受。
- 风险4：等槽的子任务显示 0 进度（Processing、字节未动），观感类似「卡住」——但这是有界队列（槽释放即开始，秒级），非失败；与现状（失败 + 8 倍吞吐压制）相比严格更优。

## 问题与用户决策

**现象**（2026-09-01 双实例实机测试）：接收方 10 个 share-receive 子任务（对接收方**全部为新作品**）并发下载，8 个在 34-36s 间隔内完成（大视频下载被竞争拖慢），2 个（任务 3/6）在 00:37:43 双双 **Failed**，error_message=「中继暂不可用（rate_limited）」；新作品视频有效吞吐被压到 ~1.8MB/s（发送方逐流限速 16MiB/s 的 1/8）。

**用户纠正**（2026-09-01）：卡顿发生在**新作品首次下载**，与替换/内容跳过路径无关——`doc/plan/分享恢复执行延迟修复方案.md`（⑤ 内容跳过）针对「重跑已拥有内容」，本次测试全部新作品，该路径不生效。继续排查替换路径无用。

**用户方向**（2026-09-01）：接收方需要一个**统筹拨号**的角色，不能自由竞争导致拥塞。

## 机制（已核码）

1. **并发下载自由竞争**：10 个新作品子任务同时执行 `stageFiles`，每个文件请求 = 1 次独立中继拨号（声明3）。
2. **发送方 8 流槽位竞争**：`handleStreamOpen` 超 8 流直接 `frameStreamClose`（声明1）→ 被拒请求按 EOF 瞬态重试（声明4）→ 每次重试 = 新拨号。
3. **拨号爆炸撞中继限流**：10 作品 × 2 文件 + 持续拒绝重试 → 拨号速率 ~2-3/s（原 ⑤ trace「80s 内 100+ 次」同形态）→ 超中继 60/min（声明2）→ `rate_limited`。
4. **反馈循环**：`rate_limited` 判可重试（声明4）→ 重试拨号 → 窗口期内继续被限 → 4 次耗尽（退避 1→2→4s）→ **任务失败**（任务 3/6）。
5. **吞吐被打垮**：并发压制把有效吞吐从 16MiB/s 打到 ~1.8MB/s（声明5）——发送方带宽有余量，瓶颈在连接层（流槽 + 拨号限流），不在带宽。

## 方案设计

### 概念：收件拨号统筹器（DialCoordinator）

接收方进程内一个统筹拨号的角色，所有 share-receive 文件拉取经它仲裁，双门控：

- **并发流槽**：同时活跃的文件流 ≤ `maxConcurrent`（默认 8，对齐发送方会话上限）。接收方永不打开第 9 条流 → 发送方永不拒绝 → 重试拨号消失 → 拨号数 ≈ 文件数（远低于中继限流）。
- **拨号速率**：每分钟拨号 ≤ `maxDialsPerMinute`（默认 ≤60，对齐中继限流并留余量）。即使有重试/多树，拨号速率也压在中继限流之下 → `rate_limited` 不触发 → 反馈循环不启动。

**纯能力**（对齐 MODULE_BOUNDARY_PURITY）：并发槽 = channel 信号量，速率 = 滑动窗口计数器——不感知 work/store/share 业务实体，输入输出为基础类型；装配（默认值、注入）归 share 模块。

### D1. DialCoordinator 类型（backend/share/dial_coordinator.go 新增）

```go
// DialCoordinator 收件拨号统筹器：统一仲裁 share-receive 各子任务的文件拉取拨号。
// 双门控——并发流槽（防超发送方会话 8 流上限被拒）+ 拨号速率（防超中继每 IP 每分钟
// 限流）。纯并发/速率能力，不感知业务实体。进程级单例，app.go 装配注入。
type DialCoordinator struct {
    slots     chan struct{} // 并发流槽信号量（容量 = maxConcurrent）
    dialCap   int           // 每分钟拨号上限（<=0 不限）
    mu        sync.Mutex
    dialTimes []time.Time   // 滑动窗口拨号事件（窗口 = 1 分钟）
}

// NewDialCoordinator 创建统筹器：maxConcurrent<=0 不限并发，maxDialsPerMinute<=0 不限速率。
func NewDialCoordinator(maxConcurrent, maxDialsPerMinute int) *DialCoordinator

// AcquireSlot 取并发流槽：阻塞至有空槽（ctx 可取消）；槽覆盖整条流的下载期。
func (c *DialCoordinator) AcquireSlot(ctx context.Context) error
// ReleaseSlot 释放并发流槽（流收尾时调用，幂等）。
func (c *DialCoordinator) ReleaseSlot()
// TakeDial 取拨号令牌：滑动窗口速率门控，无配额则等待至滑出窗口（ctx 可取消）。每次拨号前调用。
func (c *DialCoordinator) TakeDial(ctx context.Context) error
```

### D2. 接入点（接收执行链）

- **装配**：app.go 创建 `share.NewDialCoordinator(8, 50)` 单例（并发槽 8 + 速率 50/min，决策1/2）→ 注入 `NewReceiveExecution` 与 `Service`（`ShareService` 供 Receive 预拉 manifest 时共享门控）。
- **receiveClient**（`receive_client.go:107` `newReceiveClient`）持有 coordinator → `fetch`（`:145`）拨号前 `TakeDial(ctx)` + `AcquireSlot(ctx)`，槽随流收尾释放（内容读取器 `Close` 处）——文件拉取与 manifest 预拉（`receive.go:204` `fetchManifest`）同门控，一处接入全链生效。
- **测试可覆写**：`sessionRuntimeOptions` 增 `dialCoordinator` 字段（默认注入进程级单例，单测注入 fake 桩），对齐既有 `streamRate`/`maxStreams` 覆写模式。

### D3. 行为效果

- 10 并发子任务 → 最多 8 条流同时下载，2 个等空槽（阻塞不拨号，非拒绝重试）——等槽子任务显示 0 进度，属有界队列（风险4）。
- 无拒绝 → 无重试拨号 → 拨号数 ≈ 文件数（20）< 60 → 无 rate_limited → 无失败。
- 下载速率贴发送方 16MiB/s 限速运行，接收总时长 = 基础设施上界（最大视频 ~70s），不再被竞争拖慢。

### D4. 边界与对齐

- 发送方 8 流上限与中继 60/min 为**基础设施约束**（本次不改；提高上限跨仓改动归决策5）。
- 接收方统筹器把自身行为对齐到约束之内——「接收方不制造拥塞」。
- `rate_limited` 兜底：速率门控常态下不触发；万一触发（多进程共享 IP 等），既有退避重试在速率门控下不会放大（重试也需取令牌），4 次耗尽失败语义不变。
