# 分享拉取中的作品锁与自指禁止方案

## 审查摘要

**关键声明（抽查项）**：
- 声明1：分享源作品正被拉取时，宿主本地替换/软删会破坏在途拉取——实机发现（单机自分享替换：接收端软删先于拉取、移走同机源文件→「分享方内部错误」，阶段7 报告 `doc/plan/分享接收查重接入普通下载轨道方案.md` 与 `VERIFY-分享接收查重接入普通下载轨道.md`）；真实双机存在同族竞态（宿主替换正在被拉取的作品）
- 声明2：替换链软删入口为 resource 模块 `ReplacementService.SoftDeleteWorkStoreRoles(ctx, workId, roles)`（taskManager 插件任务替换与 share-receive 接收端替换复用同一能力）——`backend/resource/replacement.go:129`
- 声明3：接收端拉取为幂等可重试（断点续传锚=暂存文件已落盘字节数），故锁是「防竞态」而非「防损坏」——`backend/share/README.md`（生命周期节，行号<未核验>）
- 声明4：分享会话带实例维度 `instance_id`（设备绑定实例 ID，会话级溯源）——`doc/plan/分享功能总体方案.md` 决策6
- 声明5：本地 `share_record` 表已持久化（分享方去任务化交付，含生命周期落账）——commit a71875a
- 声明6：进程内全局内存注册表已有先例 `storeRegistry`（fsmonitor 操作抑制，Suppress/Release 形态），锁注册中心同构——`backend/storeRegistry/`

**待决策（均已裁决 2026-08-28，用户拍板）**：
- 决策1（已裁决：独立能力包）：锁注册中心为独立能力包 `backend/shareLock`（业务中立纪律：锁只记 workID + 会话引用，不感知分享领域语义）
- 决策2（已裁决：本地匹配）：自指检测用本地 `share_record` 匹配会话 token（零中继改动；share_record 只存在于产出实例的库中，命中即同实例，天然满足风险2「同实例而非同账号」）
- 决策3（已裁决：work_id 级）：锁粒度取 work_id 级
- 决策4（已裁决：弹窗内嵌）：强制解锁在替换/删除确认弹窗内嵌「强制继续（在途拉取可能失败）」提示

**自曝风险**：
- 风险1：锁查询点覆盖不全——只接替换链而漏回收站复原/彻底删除/宿主软删/外部文件操作（fsmonitor 外部删除）路径，竞态仍存；查询点需按「触碰被拉取作品的活行 store 文件」精确定义
- 风险2：自指检测误判——跨设备同账号拉取自己的分享（不同实例）若仅按分享方身份/账号判定会被误拒；检测必须落在「同实例」而非「同账号」
- 风险3：强制解锁后在途拉取已拉暂存的收尾——接收端暂存保留（可重试）还是清理需定
- 风险4：本方案为延后任务，锁注册中心与自指检测尚无代码原型（设计基于声明1-6 的现状推导）

## 背景与目标

**背景**：share-receive 接入普通下载轨道后（前置方案），实机发现自分享替换时「接收端软删先于拉取、移走同机源文件」的结构性失败。分析确认这是两条并发竞态的外显：

| 竞态 | 触发场景 | 影响 |
| --- | --- | --- |
| 宿主侧 | 作品正被收件人经中继拉取时，宿主本地替换/软删/移动它（真实双机） | 在途拉取读到源文件被移走→失败 |
| 自指 | 单机自分享自接收，接收端软删自己的源文件（仅单机测试形态） | 结构性无解（软删与拉取争同一文件） |

**目标**：注册中心式锁（宿主侧并发防护，禁替换/软删/移动 + 分享方解锁能力）+ 禁止自指（单机自接收明确拒绝）。锁为**软性防误触**——本地资源完全由本地掌控，用户可强制解锁（接受在途拉取可能失败）。

**非目标**：本期（收件查重接入普通下载轨道）已交付并验证的能力不动；锁机制为独立延后交付物。

## 设计

### 一、锁注册中心（独立能力包）

进程内全局内存注册表，app.go 装配单例。形态对齐 `storeRegistry`（声明6）——纯能力、领域中立：

```go
// ShareLockRegistry 分享拉取中的作品锁注册中心（内存态，跨重启自动解除）
// Register 会话开始拉取某作品时登记（记录 workID + 会话引用）；Unregister 会话结束/停止时解除；
// IsLocked 宿主本地替换/软删/移动前查询；ForceUnlock 分享方强制解锁（用户知情：在途拉取可能失败）
type ShareLockRegistry interface {
    Register(ctx context.Context, workIDs []int64, session string)
    Unregister(ctx context.Context, workIDs []int64, session string)
    IsLocked(ctx context.Context, workID int64) bool
    ForceUnlock(ctx context.Context, workID int64)
}
```

- 只记 workID + 会话引用，不感知分享领域语义（业务中立，供后续消费方复用）
- 内存态：进程退出自动解除（对齐 `skipDuplicateCheck` 执行期标记语义，无持久化负担）
- share 模块在拉取涉及作品时 register、会话终态/停止时 unregister

### 二、宿主侧防护接线

- 查询点：`ReplacementService.SoftDeleteWorkStoreRoles` 前置（声明2，taskManager 插件任务替换与 share-receive 接收端替换共用单点）+ 回收站复原/彻底删除等触碰活行 store 文件的路径
- 语义：命中锁 → 返回错误/标记 → 宿主 UI 提示「该作品正在被拉取，强制继续？」→ 确认 → ForceUnlock + 继续
- 双机隔离自然成立：锁注册中心为进程内单例，接收端替换在自己的进程查锁（本进程未 register 该作品）→ 不命中，替换正常；宿主侧替换在同进程查锁 → 命中被阻
- 单机自指：被「禁止自指」（设计三）拦截，接收根本不开始，锁查询路径无自指干扰

### 三、禁止自指

- 检测时机：接收启动（反解载荷后、拨中继/拉取前）。接收启动点 = `Service.Receive`（「分享接收每作品一任务」落地后，manifest 拉取已前置到 Receive 建树前，自指拒绝须在其之前发生，不得等到子任务执行面）
- 判定：本地 `share_record`（声明5）匹配接收到的会话 token，命中即「本实例自产」→ 拒绝接收并提示「不能接收自己分享的内容」
- 判定必须落在「同实例」而非「同账号」（风险2）——跨设备拉取自己的分享是合法场景
- 测试形态收敛：实机验证走双实例；单机自接收被明确拒绝（比半途失败干净）

### 四、解锁语义与 UI

- 分享方解锁：宿主侧操作遇锁 → 弹确认（在途拉取可能失败）→ 强制解锁继续；会话结束/停止自动 unregister
- 自指拒绝：接收启动即提示，不进入拉取
