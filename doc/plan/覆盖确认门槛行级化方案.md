# 覆盖确认门槛行级化方案

## 审查摘要

### 关键声明（抽查项）

- 声明1：当前查重门槛为意图层判定——`hasNonThumbnailStore()`（runMode.storeRoles 含 thumbnail 外任一角色即触发，模型层谓词，backend/taskManager/model.go:75-82），不看已有作品上是否真有该板块的行。锚点：`backend/taskManager/manager.go:435`（批量预检门槛）、`backend/taskManager/model.go:825`（run() 内 fallback 门槛）、`backend/taskManager/model.go:844`（替换判定门槛）。
- 声明2：实际覆盖动作按行删除——`mountResourceStores` 删旧插新走 `DeleteByResourceIdAndTypes(store_type IN 本次 roles)`，行不存在即无覆盖发生。锚点：`backend/taskManager/model.go:1158`、`backend/resource/resource_store_repository.go:65`。
- 声明3：`BackupStores` 内部按行过滤——按 storeTypes 过滤已有行，行不存在即无备份项，行级门槛下调后备份链天然安全零改动。锚点：`backend/backup/store_backup_orchestrator.go:111-117`。
- 声明4：行级判定所需批量查询基建已就位——`resource.Service.ListByWorkIds`（work→resources）+ `ListStoresByResourceIds`（resources→store 行），均为批量、无 N+1。锚点：`backend/resource/service.go:80-106`、`backend/resource/resource_store_repository.go:41-51`。
- 声明5：纯 thumbnail 板块当前也走「定位已有作品 + isReplace=true + 备份」链（仅门槛豁免查重弹窗），门槛移除后该分支语义并入统一判定，`resolveWorkIdByTask`（按任务 (site_id,site_work_id) 定位作品的函数）保留。锚点：`backend/taskManager/model.go:856-865`。
- 声明6：批量查重失败已有降级方向——批量查询失败时降级为 run() 逐个查重（不误放行），行级查询失败须沿用同一保守方向（退回弹窗）。锚点：`backend/taskManager/manager.go:466-474`。
- 声明7：查重时点在插件 Start（网络调用）之前，实际 specs（插件本次声明的 store 规格）此时不可知，行级判定只能精确到「任务板块选择 ∩ 已有行」，到不了「实际 specs」。锚点：`backend/taskManager/model.go:873-888`（板块 A 即作品元数据板块，在查重之后执行）。
- 声明8：前端弹窗已有逐项/全部两档答复与批量接口。锚点：`frontend/src/components/dialogs/ReplaceConfirmDialog.vue:9-51`、`backend/taskManager/handler.go:75-83`（IPC 入口 `ConfirmReplace`/`ConfirmReplaceBatch`，内部转 `manager.go` 的 `ConfirmReplace(taskId, action)`）。
- 声明9：`WaitingForInput` 挂起任务不占并发信号量，本方案不改该并发架构。锚点：`backend/taskManager/manager.go:425-426`（函数注释）、504-516（命中入 waitingForInputMap 不参与派发）。

### 待决策（需用户拍板）

- 决策1（已由用户拍板，记录于此）：**thumbnail 覆盖不豁免**——用户不同意「thumbnail 行覆盖可忽视」的保留意见，板块门槛（hasNonThumbnailStore 整体豁免）移除，thumbnail 行存在且在所选板块内同样触发覆盖确认。本方案按此实施，不阻塞。
- 决策2（不阻塞，默认按方案执行）：行级查询失败时的降级方向——沿用现有保守方向「退回弹窗」（与批量查重失败降级为逐查同向，宁可多弹不漏弹）。如需改为「失败放行不弹」请提出。
- 决策3（不阻塞，默认实施）：前端弹窗文案增强——显示将覆盖的板块（「将替换已有作品的 image/videoTrack 板块」），信息由行级判定产出、随事件携带。如不需要可砍，不影响后端。
- 决策4（已拍板采纳，记录于此）：**空角色集「插件自决全量」任务纳入弹窗**——runMode.storeRoles 为空（StoreRoles=NULL 且 universe 即 InvolvedRoles 也为空，fetchStores=true）时，现状因旧门槛（空角色集整体豁免查重，manager.go:435-437）**从不弹窗**，行级化后变为「已有任意行即弹」。这是决策1（门槛移除）的必然推论——旧门槛的不弹正是整体豁免的产物；且此类任务实为全量重下（覆盖面最大），弹窗合理性高于现状。已在风险1 中如实登记为行为变更。
- 决策5（不阻塞，按现有语义排除）：**仅作品信息任务（fetchStores=false）不参与行级判定**——StoreRoles Valid 且空选 = 仅作品信息板块（不拉任何资源，model.go:84-93 注释），不可能覆盖任何 store 行，按 fetchStores=false 排除在查重外（该类任务本就无非终态语义、不弹窗，见 model.go:1025-1028 的 isNonTerminalMode）。

### 自曝风险

- 风险1（含**行为变更**，源于决策4）：runMode.storeRoles 为「全集空集」语义（StoreRoles=NULL → storeRoles 取 universe 即 InvolvedRoles；universe 也为空 → 插件自决全量，fetchStores=true）时，行级判定无从枚举板块、退化为「已有任意行即弹」。**现状此类任务因旧门槛（空角色集整体豁免查重，manager.go:435-437）从不弹窗，行级化后变为命中即弹——这是决策1 门槛移除的必然行为变更，非"不劣于现状"，已由用户拍板接受（决策4）**。锚点：`backend/taskManager/model.go:84-94`、`backend/taskManager/manager.go:435-437`。
- 风险2：resource_store 行存在但 persistent_store 记录/文件已缺失（数据不一致）时行级判定仍计为「存在」——本方案判定主体为 resource_store 行（覆盖动作删的就是它，见声明2），不 join persistent_store 校验文件实存；不一致行本就属回收站/备份还原等场景的边缘态，宁弹不漏。
- 风险3：插件自定义 resourceType 的行（store_type 仍属 7 内置角色之一）参与判定无碍；但若未来出现「插件声明板块角色但实际不落该角色行」的常态插件，行级判定会持续空命中不弹——该场景下覆盖确也不发生（无行可删），语义自洽，记录备查。
- 风险4：决策4 的行为变更（空角色集任务从「从不弹」变「命中即弹」）对存量用户操作习惯的影响——默认插件（未声明 InvolvedRoles）全量重试任务在已有作品上将开始弹窗。若实测打扰感强，可后续迭代为「按插件 Start 返回的 specs 精确判定」，但那需要重构查重时点（见 2.5），本方案不覆盖。

## 一、背景与动机

### 1.1 现状机制（意图层门槛）

「是否提示覆盖」由三段判定链决定：

1. **板块门槛**（意图层）：`runMode.storeRoles` 含 thumbnail 外任一资源角色（`hasNonThumbnailStore()`）才参与查重；
2. **业务键查重**：任务携带 `SiteID + SiteWorkID`，以 `(site_id, site_work_id)` 匹配已存在 work；
3. **命中挂起**：`TaskStateWaitingForInput`(9) + `PushDuplicateDetected` 前端推送 + 入 `waitingForInputMap`（不占信号量），等 `ConfirmReplace` 答复。

主路径 `batchCheckDuplicates`（manager.go:425，派发前批量预检）+ fallback `runSectionCombo` 内单查（model.go:825，批量查询失败降级时）。

### 1.2 缺陷：门槛判「意图」不判「事实」——三组真实误弹与一组漏弹

| 场景 | 已有作品状态 | 当前行为 | 问题 |
|---|---|---|---|
| 失败重试（workInfo 已入库、下载失败 store 零行） | work 存在、所选板块零行 | 弹「是否替换」 | 无任何文件将被覆盖，弹窗零信息量、纯打扰 |
| 纯缩略图先行后重下非缩略图板块（如轨道/原图） | 仅 thumbnail 行，roles 不含 thumbnail | 弹窗 | 实际纯新增、零行将被覆盖；若重下含 thumbnail 板块则仍弹——thumbnail 行被真实覆盖（决策1） |
| 分离流重下轨道、track 行不存在 | 仅 videoMain 行，roles=videoTrack,audioTrack ∩ = 空 | 弹窗 | 实际纯新增，videoMain 本就不被任务触碰（README『关键设计』末条） |
| 空角色集「插件自决全量」任务（StoreRoles=NULL 且插件未声明 InvolvedRoles） | 已有作品任意板块有行 | **不弹**（漏弹） | 反向缺陷：覆盖面最大的全量重下却零提示——旧门槛对空角色集整体豁免（manager.go:435-437）；行级化后变为「已有任意行即弹」（决策4） |

反向收益：行级判定让「弹窗承诺的风险」与「实际将执行的删除」（按 store_type IN roles 删行，声明2）严格对齐到同一张表，语义自洽。

### 1.3 用户决策

用户拍板（决策1）：thumbnail 的覆盖不应被忽视，板块门槛整体移除——「角色集不含 thumbnail」这一意图层豁免取消，判定完全下沉到行级（任何所选板块的角色在已有作品上存在行，即触发覆盖确认，含 thumbnail 行）。

## 二、方案设计

### 2.1 核心规则（行级门槛）

新判定：**任务板块选择（runMode.storeRoles）∩ 已有作品 resource_store 行的 store_type 集合 ≠ 空** → 弹覆盖确认。

- 判定表：**resource_store**（非 persistent_store）——`mountResourceStores` 删的就是 resource_store 行（挂 persistent_store 引用），查它即查覆盖对象本身；
- thumbnail 不豁免（决策1）：thumbnail 行在所选板块内同样计为覆盖；
- 查重前置条件不变：`SiteID + SiteWorkID` 有效、非 resumeFromDB（跨重启续传）、批量查重已命中（业务键匹配仍是第一关）；
- 全集空集语义（风险1/决策4）：storeRoles 为空（NULL→universe→插件自决全量）时退化为「已有任意行即弹」——现状此类任务从不弹窗，此为门槛移除带来的行为变更（决策4，已拍板）。

### 2.2 数据流（改造后的判定链）

```
任务派发前（batchCheckDuplicates）
  ├─ resumeFromDB → 跳过（不变）
  ├─ 无 SiteID/SiteWorkID → skipDuplicateCheck=true，派发（不变）
  ├─ fetchStores=false（仅作品信息板块，StoreRoles Valid 空选）→ 不参与查重直接派发（决策5：无资源板块可覆盖，与现状不弹一致）
  ├─ storeRoles 为空（全集空集：插件自决全量，fetchStores=true）→ 保留参与查重；命中后跳过行级过滤（退化：已有任意行即弹，决策4/风险1）
  ├─ 批量业务键查重 ListBySiteAndSiteWorkIDs（不变）
  │    └─ 未命中 → skipDuplicateCheck=true，派发（不变）
  └─ 命中 → 批量行级查询（新增，见 2.3）
       ├─ 行级查询失败 → 沿用保守方向：退回弹窗（不误放行，与声明6同向）
       ├─ roles ∩ 已有行 = 空 → 【新】不弹窗：保留 existingWorkId + skipDuplicateCheck=true → 派发
       └─ roles ∩ 已有行 ≠ 空 → 弹窗（不变）：WaitingForInput + PushDuplicateDetected + waitingForInputMap
```

run() 内 fallback（model.go:825 门槛处）同步改造：门槛（fetchStores=false 跳过查重）与单查命中后的行级过滤，均与批量路径同规则。

### 2.2.1 单任务视角的执行差异（覆盖确认后的替换链，不变）

- 替换判定：重入时 `existingWorkId > 0 → workId=已有作品、isReplace=true`（model.go:846-849）——行级不弹但保留 existingWorkId 的任务走同一分支，定位与备份链完整保留；
- 备份：`BackupStores(workId, storeRoles...)` 按行过滤（声明3），行不存在即无备份项——零改动、天然安全；
- 「无 workInfo 板块的资源重执行必须定位已有作品」的守卫（model.go:850-854）保留——不弹窗 ≠ 不需要替换语义。

### 2.3 新增批量查询接口

taskManager deps 新增（由调用方 taskManager 定义接口、提供方实现，遵循 SERVICE_DEPENDENCY_VIA_INTERFACE）：

```go
// WorkStoreRoleChecker 查询已有作品的 resource_store 行 store_type 集合（覆盖判定用）
type WorkStoreRoleChecker interface {
    // ListStoreTypeSetsByWorkIds 批量查询多个作品的 {store_type 集合}；空 workIds 返回空 map
    ListStoreTypeSetsByWorkIds(ctx context.Context, workIds []int64) (map[int64]map[string]struct{}, error)
}
```

实现落在 resource 模块（service 层组装：`ListByWorkIds` + `ListStoresByResourceIds` 两跳已有批量方法拼接，声明4），无需新增 repository 查询——两条 IN 查询，事务外、无 N+1。

### 2.4 事件与前端

`PushDuplicateDetected` 载荷新增 `conflictRoles []string`（将覆盖的板块角色，已按行级命中过滤）：

- 前端弹窗逐项展示「将替换已有作品的 image/videoTrack 板块」（决策3，默认实施）；
- 全部替换/全部跳过/逐项替换/逐项跳过交互不变（声明8）。

### 2.5 不改动项（明确边界）

| 项 | 理由 |
|---|---|
| `(site_id, site_work_id)` 业务键查重 | 重复的判定标准，与行级门槛正交，保持不变 |
| ConfirmReplace 两段式与 skipDuplicateCheck 时序 | 取槽位前置 skipDuplicateCheck 防二次弹窗的机制不变（model.go:537-539） |
| WaitingForInput 不占信号量 | 并发架构不动（声明9） |
| isReplace / resolveWorkIdByTask / 备份链 | 行级门槛与替换语义解耦，声明3/5 证其天然安全 |
| 查重时点 | 保持在插件 Start 前——Start 是网络调用且在信号量槽位后，挪动会破坏不占信号量的等待设计（声明7、9） |

### 2.6 已有代码处理

- `hasNonThumbnailStore()` 谓词：**删除**。其 4 处调用点（manager.go:435、492；model.go:825、844）由行级判定/新规则替代。`TestHasNonThumbnailStore` 同步删除，契约由新表驱动测试锁定。
- 纯 thumbnail 分支（model.go:856-865）：其「定位已有作品 + isReplace=true + 备份」语义由统一判定链吸收——门槛移除后纯 thumbnail 任务同样走查重命中 → 行级命中（thumbnail 行存在）→ 弹窗 → 确认后 isReplace 链，`resolveWorkIdByTask` 保留用于定位。**注意**：若纯 thumbnail 任务行级命中为空（无 thumbnail 行）且无 workInfo，则原分支的「必须定位已有作品」守卫语义由「不弹窗 + existingWorkId 保留 + isReplace 链」覆盖，无缺口。

## 三、实施步骤

1. **resource 模块**：service 层新增 `ListStoreTypeSetsByWorkIds`（两跳批量拼接）+ 单测；
2. **taskManager deps**：新增 `WorkStoreRoleChecker` 接口 + app.go 装配（resource service 注入）；
3. **manager.go `batchCheckDuplicates`**：命中分支二次过滤（2.2 数据流），行级查询失败退回弹窗（决策2）；未命中 → 保留 existingWorkId + skipDuplicateCheck=true 派发【新】；
4. **model.go fallback**：run() 内单查命中后同步行级过滤；
5. **谓词与调用点**：删 `hasNonThumbnailStore()` 及 4 处调用点改写，删 `TestHasNonThumbnailStore`；
6. **事件载荷**：`PushDuplicateDetected` 加 `conflictRoles`，progress_pusher.go 三实现（Wails/Snapshot/Noop）同步签名；
7. **前端**：MainIpcListener 事件解构 + ReplaceConfirmDialog 展示冲突板块（决策3）；
8. **测试**：新增表驱动用例——行全缺（不弹）/部分存在（弹）/thumbnail-only 行命中（弹，决策1）/行级查询失败（退弹）/全集空集退化（已有任意行即弹，决策4）/仅作品信息任务不参与查重（决策5）+ run() fallback 行级过滤用例；`go test ./backend/...`、`CGO_ENABLED=0 go build` 验证；
9. **文档**：taskManager README「关键设计」补行级门槛语义一句。

## 四、影响面

- 后端：`backend/resource/service.go`、`backend/taskManager/{manager,model,progress_pusher}.go`、`app.go` 装配；
- 前端：`frontend/src/MainIpcListener.ts`、`frontend/src/store/UseReplaceConfirmStore.ts`（DuplicateInfo 加 conflictRoles）、`frontend/src/components/dialogs/ReplaceConfirmDialog.vue`；
