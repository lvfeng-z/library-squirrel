### 自曝风险

- **风险1（拉取时机）**：拉取按「已知作品集 C」（illust）触发，series 父集 S 经子集拉取发现。若 series 内各 illust 并发入库，S 被多次 upsert（幂等，无碍）；某子集 C 的 `site_sort_order` 在其自身拉取时即写入，但 S 的完整子集序要等所有兄弟子集都拉取完才稳定——期间序号有间隙（如只有第0、第2个到位）。因前端展示延后（决策3），间隙不可见；最终按 `site_sort_order` 排序正确。
- **风险2（父集 stub 残留）**：拉取发现父集 S 后 upsert；若 S 仅被部分子集声明、且这些子集全部失败回滚，S 可能作为空 workset 残留。低概率，容忍或后续加清理。
- **风险3（拉取方向偏差）**：B 查「容器→成员」，H 查「成员→父集」（发现顺序决定）。若未来出现「只知父集 URL、需查父集发现子集」的场景（当前 pixiv series 经子任务拉取已覆盖），需扩展响应加 `children` 字段或新增反向 RPC。当前设计 `parents`-only，YAGNI。
- **风险4（向前兼容）**：新增 RPC 方法 + 新能力枚举均为增量。旧插件不实现新 RPC（gRPC 返回 Unimplemented），主程序须严格 `hasCapability` 守卫（同 B，声明6）不盲调。proto3 序列化兼容性实测确认。
- **风险5（多父 DAG）**：`re_work_set_work_set` 支持多父，而 series/合集通常是单父树。多父合法但会使 `CollectDescendantWorkIDs`（传递包含）去重保序行为需明确。需文档约束 series 用单父，前端（延后）展示时处理多父。

## 1. 背景与目标

**H 目标**：让插件能声明作品集的父子层级（pixiv series / bilibili 合集等多层级形态）与子集在父集下的排序，主程序据此存储并（前端就绪后）展示合集结构。

**当前痛点**：插件只能声明扁平的「work 归属哪些 workset」（`WorkResponse.workSets`），无法表达「这个 workset 是那个 workset 的子集」。pixiv series 完全无法表达（声明11）；主程序虽有完整的 workset 层级 DB/service 能力（为 merge 功能建），但插件够不到。

**核心洞察**：DB 表 `re_work_set_work_set`、service 层级方法、递归 CTE 查询、前端层级管理 UI 全部就位（声明1-3、9），缺口仅在「插件契约层暴露父子+序的拉取 RPC」+「子集序双轨字段」+「入库编排接线」。

## 2. 设计核心：对齐 B 的「拉取」范式（决策1）

B 节点确立了作品集排序的拉取范式（声明5-6）：主程序入库后异步 pull 插件，按 `(site_id, site_work_set_id)` 查询，响应为带序条目列表。H **完全复刻**此机制，将其从「work-in-workset」推广到「workset-to-workset」：

| 维度 | B（work-in-workset，已有） | H（workset-to-workset，新增） |
|---|---|---|
| **RPC** | `QueryWorkSetOrder` | `QueryWorkSetRelations` |
| **方向** | 主程序 → 插件（pull） | 主程序 → 插件（pull） |
| **触发时机** | work 入库后，对其归属的每个 workset 异步拉取 | **同**——work 入库后，对其归属的每个 workset 异步拉取 |
| **请求** | `(site_id, site_work_set_id)` | `(site_id, site_work_set_id)` |
| **响应** | `[(siteWorkId, sortOrder)]`——集内作品+序 | `[(parentSiteWorkSetId, parentWorkSetName, sortOrder)]`——本集的父集+序 |
| **主程序动作** | 写 `re_work_work_set.site_sort_order` | upsert 父集 + 建父子关系（复用 `AddChildWorkSet` 环路检测）+ 写 `re_work_set_work_set.site_sort_order` |
| **能力声明** | `CapabilityWorkOrderQuery` + `WorkOrderQuerier` | `CapabilityWorkSetRelationQuery` + `WorkSetRelationQuerier` |
| **双轨字段** | `sort_order`（本地）+ `site_sort_order`（原站） | 同构（决策2）：`sort_order`（已存在）+ `site_sort_order`（**新增**） |

**与 B 的唯一偏差（风险3）**：B 查「容器（作品集）里的成员」；H 查「成员（已知作品集）的父集」。原因：父集（series）没有 work 直接归属（work 归属的是 illust 子集），只能经子集拉取发现。拉取机制（异步、按 site workset id、响应带序条目）与 B 完全一致。

**父子关系 + 子集序合并到一个 RPC**：拉取响应同时携带父集身份与子集在父下的序——一次拉取既发现父子关系又拿到序，无需两段式。

## 3. 契约层设计（proto + SDK）

### 3.1 新增 `QueryWorkSetRelations` RPC（对齐 `QueryWorkSetOrder`）

```proto
service TaskHandlerService {
  // ... 既有 RPC ...
  rpc QueryWorkSetOrder(QueryWorkSetOrderRequest) returns (QueryWorkSetOrderResponse);
  // H 新增：查询本作品集的父集关系 + 在各父集下的原站序（主程序作品入库后拉取，仅写 site_sort_order，不碰本地序）
  rpc QueryWorkSetRelations(QueryWorkSetRelationsRequest) returns (QueryWorkSetRelationsResponse);
}

message QueryWorkSetRelationsRequest {
  int64 site_id = 1;            // 站点内部 ID（主程序已知）
  string site_work_set_id = 2;  // 本作品集站点 ID（主程序已通过 WorkResponse.workSets 知其存在）
}

message QueryWorkSetRelationsResponse {
  repeated WorkSetRelationEntry parents = 1;  // 本集的父集 + 在各父集下的序；空=无父/插件不掌握
}

message WorkSetRelationEntry {
  string parentSiteWorkSetId = 1;  // 父作品集站点 ID
  string parentWorkSetName = 2;    // 父集名（父集首次入库时落库；series 标题由此带回——决策5 解决）
  int64 sortOrder = 3;              // 本集在该父集下的原站序号（从 0 起）
}
```

- `TaskWorkSetDTO` 与 `WorkResponse.workSets` **不改**（声明4）——父子关系不内联声明，全走拉取。
- 响应为 `parents` 列表：支持多父 DAG（一个子集可有多个父集，每个父下独立序）。pixiv series 通常单父。
- `parentWorkSetName` 随响应带回：主程序首次发现父集时 upsert 实体并落名（决策5），无需扩展 `TaskCreateResponse`、无需内联声明。

### 3.2 SDK 能力接口（对齐 `WorkOrderQuerier`）

`dto/work_set_dto.go` 新增：

```go
// WorkSetRelationQuerier 声明插件能提供作品集的父集关系 + 子集原站序（可选能力接口）
// 未实现该接口的插件，主程序 hasCapability 返回 false 不盲调，作品集层级不生效

```

- `contract` 子包新增能力常量 `CapabilityWorkSetRelationQuery`（对齐既有 `CapabilityWorkOrderQuery`，封闭枚举扩展）。
- 服务端适配（`transport/plugin_server.go`）：未实现 `WorkSetRelationQuerier` 的 handler 返回空 response（不报错，层级不生效），与 B 的 `QueryWorkSetOrder` 适配一致。
- 新 DTO 别名（`WorkSetRelationEntry = gen.WorkSetRelationEntry`）遵循 C 节点「A 类 proto 单源别名」规则。

## 4. 数据模型（`re_work_set_work_set` 加双轨，决策2）

```go
// backend/base/model/entity/re_work_set_work_set.go
type ReWorkSetWorkSet struct {
    *model.BaseEntity
    ParentWorkSetID sql.NullInt64 `gorm:"..."`
    ChildWorkSetID  sql.NullInt64 `gorm:"..."`
    SortOrder       sql.NullInt64 `gorm:"column:sort_order;..."`        // 本地序（用户拖拽，已存在）
    SiteSortOrder   sql.NullInt64 `gorm:"column:site_sort_order;" json:"siteSortOrder"` // H 新增：原站序（插件拉取，用户不可改）
}
```

- **`sort_order`**（本地序）：建关系时默认 `max+1` 续排；用户拖拽改；默认展示用它。
- **`site_sort_order`**（原站序）：插件 `QueryWorkSetRelations` 拉取写入；用户不可改；「应用原站序」把它拷贝到 `sort_order`。
- GORM AutoMigrate 自动加列（既有表加 nullable 列，无风险）。
- `site_sort_order` 用 `sql.NullInt64`（0 是合法序号，须能写入，`NULLABLE_PARAM_USE_POINTER`/零值可用契约）。
- `reWorkSetWorkSet.Repository` 新增 `UpdateSiteSortChildOrders(ctx, childWorkSetId, entries)` 或 `UpsertRelationWithSiteOrder`（对齐 `reWorkWorkSet.UpdateSiteSortOrders`，遵循 `BATCH_UPDATE_OPTIMIZATION`）。

## 5. 落库编排（`work.SaveWorkInfo` 扩展）

遵循 `ORCHESTRATION_BY_CALLER`（编排归 work 模块）。**全程异步、事务外**（拉取是网络调用，避 `MaxOpenConns=1` 死锁，声明5 同类约束）——父子关系也经拉取发现，故无「事务内同步建关系」步骤（区别于内联方案）。

### 5.1 事务后异步：`syncWorkSetRelations`（对齐 `syncSiteSortOrders`）

在 `SaveWorkInfo` 事务提交后（`backend/work/service.go:1319-1323` 同位置）：

```go
if s.workSetRelationFetcher != nil && len(workResp.WorkSets) > 0 {
    go s.syncWorkSetRelations(task, workResp)  // 30s 超时，同 siteOrderSyncTimeout
}
```

`syncWorkSetRelations` 流程（对齐 `syncSiteSortOrders` 遍历 `workResp.WorkSets`）：

1. 遍历 `workResp.WorkSets`（已入库的 workset Ci），对每个 Ci 调 `workSetRelationFetcher.QueryWorkSetRelations(pluginPublicId, siteId, Ci.siteWorkSetId)`。
2. `hasCapability` 守卫（声明6）：插件未声明 `CapabilityWorkSetRelationQuery` 直接返回 nil。
3. 落库 `applyWorkSetRelations`：对响应中每个 `(parentSiteWorkSetId, parentWorkSetName, sortOrder)`：
   - 按 `(siteId, parentSiteWorkSetId)` upsert 父集实体（携 `parentWorkSetName`）→ 得 `parent.id`；
   - 取已入库的 `Ci.id`；
   - 建立关系（**复用既有 `CollectAncestorWorkSetIds` 环路检测**，声明2）+ 写双轨序号。实施注意：现行 `AddChildWorkSet`（`backend/workSet/service.go:178-197`）不带序号参数、`rel.SortOrder` 落 NULL；实施时需扩展 `AddChildWorkSet` 接受 `localOrder`（`max+1` 续排）参数，或新增带序建立方法，`site_sort_order` 经 `UpdateSiteSortChildOrders` 单独写。关系已存在则幂等 no-op（`SaveRelation` 用 `OnConflict DoNothing`，不覆盖既有 `sort_order`）。
4. 幂等：关系已存在则 `SaveRelation` 幂等 no-op；`site_sort_order` 覆盖写（全量，对齐 B 的 `applySiteSortOrders` 语义，风险1 解）。

### 5.2 依赖注入（对齐 B 的 fetcher 模式）

- `WorkSetRelationFetcher` 接口由 work 模块定义（`backend/work/service.go`，对齐 `WorkSetOrderFetcher` `:141-146`），plugin 模块实现（`workset_relation_fetcher.go`，对齐 `workset_order_fetcher.go`）。

## 7. pixiv series 概念说明与建模自由度（决策4 = 4-B：延后）

> 决策4 已定为 4-B：pixiv series 实施**不纳入 H**，延后为独立节点（M）。本节保留概念说明与建模中立论证，供后续 pixiv 建模节点参考。

### 7.1 概念：series vs manga（层级不同）

```
系列「小明日常」 (series，作品集 S)        ← H 解决这一层（作品集间父子+子集序）
├─ 插画1 (illust，作品集 C1)   第1篇
│   ├─ page 1 (work)                        ← manga 多页，B 已解决（作品集内作品序）
│   └─ page 2 (work)
├─ 插画2 (illust，作品集 C2)   第2篇
└─ 插画3 (illust，作品集 C3)   第3篇
```

- **manga（多页）= 一个作品集内多作品**：已完备（声明10）。
- **series（系列）= 多个作品集的聚合**：完全未处理（声明11）——H 目标。bilibili 合集同理。

### 7.2 pixiv series 的拉取流程（本方案下的端到端）

1. 用户贴 series URL `pixiv.net/user/<uid>/series/<id>`。
2. 插件 Create：解析 series URL（当前不支持，需加），调 series API → 系列标题 + 有序 illust 列表。
3. Create 返回 series 父任务（container）+ N 个 illust 子任务（复用既有 `TaskCreateChildResponse` 拆任务机制，`task_handler.go:210-254`）。
4. 每个 illust 子任务 `CreateWorkInfo` → `WorkResponse`，work 归属 workset C_i（illust，既有逻辑）。
5. 主程序入库 W_i、upsert C_i，**异步拉取 `QueryWorkSetRelations(C_i)`** → 响应 `{parent: S(seriesId, seriesTitle), order: i}`。
6. 主程序 upsert S（携 seriesTitle）、建 C_i→S 关系、写 `site_sort_order = i`。
7. N 个 illust 入库后，S 下 N 个子集 C_1..C_N 各带原站序，series 结构完整。

> series 父任务（container）无需产 `WorkResponse`、无需特别声明——series 父集 S 完全经子任务拉取发现并创建（决策5 解）。pixiv illust 双重身份（series 内有 illust 序 + 自身多页时有 page 序）由两个拉取 RPC 正交承载：`QueryWorkSetRelations`（series→illust 序）与 `QueryWorkSetOrder`（illust→page 序）。

### 7.3 pixiv 插件实施步骤（若纳入 H）

1. URL 解析：`internal/urlparser/parser.go` 加 series URL 模式。
2. API model：`internal/pixivapi/models.go` 的 `AppIllustDetail` 加 `Series` 字段；新增 `app_api.go` 的 `SeriesDetail(seriesID)` 调 `/v1/illust/series/<id>`。
3. Create 拆任务：series URL → series 父任务 + N illust 子任务。
4. 实现 `WorkSetRelationQuerier`：`QueryWorkSetRelations(siteId, illustSiteWorkSetId)` 返回该 illust 所属 series + 在 series 内的序（来自 series API）。

### 7.4 决策4 结论：4-B（仅契约+后端，pixiv 延后）

用户决策：H 仅交付 SDK 契约 + 主程序后端（发布关键的通用能力）；pixiv series 具体建模**延后**为独立节点（M）。理由：插件对站点合集的建模自由度高（pixiv 合集可扁平 workset 直含 works，亦可父 workset 含多个 pid-workset），在 H 预设具体建模会臃肿——契约须保持建模中立，让插件自行决定。

H 的契约设计已满足建模中立：插件可实现 `WorkSetRelationQuerier` 走层级建模，亦可不实现走扁平建模（`hasCapability` 返回 false，主程序不调，层级不生效，扁平 workset 照常工作）。两种建模对 H 契约均透明。

## 8. contractVersion 论证（不 bump）

**结论：H 不 bump `contractVersion`**（保持 = 2）。依据 SDK 明文规则（声明8，`transport/contract.go:5-7`）：仅破坏性变更（删/改字段类型、改 DTO 结构、改 RPC 签名、改前端 props）才 +1；proto **新增 RPC 方法** + **新增能力枚举** + **新增 message** 均为向前兼容的增量。旧插件不实现新 RPC（gRPC Unimplemented），主程序 `hasCapability` 守卫不盲调。

历史佐证：B 的 `QueryWorkSetOrder` RPC 同为增量加入，未触发 bump（契约版本由 C 确立为 1，E 升至 2 仅因 GetValue 返回结构变更）。

前置条件（风险4）：主程序严格 `hasCapability` 守卫新 RPC（同 B），proto3 序列化兼容性实测确认。
