# task-graph（宏观任务派生图）

## 技能概述

| 属性     | 值                                                                                          |
| -------- | ------------------------------------------------------------------------------------------- |
| 名称     | task-graph                                                                                  |
| 作用     | 为每棵派生图（一个根任务）维护一个自包含目录，追踪"根任务 → 派生出的各层宏观任务 → 延后分支 → 当前焦点" |
| 解决问题 | 深度下钻后遗忘根任务、丢失派生链与延后分支、忘记中间层任务存在原因（跨会话/上下文压缩后尤甚）|
| 独立性   | 独立技能，不依赖任何其他技能                                                                |

## 解决的问题

开发中反复出现：一个宏观任务（功能/修复）在实现过程中**派生出多层基础设施任务**，这些基建任务又长又会再派生出新的分支任务。一旦基建做完，就忘记三件事：

1. **最初的根任务**（它又是由哪个上游任务派生来的）；
2. **派生过程中引出、但当时延后的分支任务**；
3. **中间层任务及其被派生的原因**。

现有机制都不覆盖这个空白：`../library-squirrel-docs/plan/` 是单个任务的设计方案（含实现步骤）；`memory/` 是工作完成后才写的回顾性事实；`TaskCreate` 仅会话内、上下文压缩即丢失。本技能用**一棵派生图独占一个自包含目录** + **派生判定纪律**填补该空白——记录宏观任务之间的派生关系，不记录实现步骤。

## 五条铁律（强制，违反即失效）

1. **节点是宏观任务，不是实现步骤**〔首要〕——节点 = 一个有独立目的的交付物（功能 / 修复 / 基建 / 调研），通常值得有自己的 plan 文档。**"加字段、改函数、写测试、更文档"这类实现步骤不是节点**——它们属于该任务的长文档（`../library-squirrel-docs/plan/...` 或 `<ID>.md`），从节点外链。判定新工作：是新的宏观任务（→ 建节点）还是当前任务的实现步骤（→ 写进当前任务的长文档）？
2. **树的父子关系 = 派生，≠ 拆分**——子任务由父任务的工作**引出**。派生与拆分都表现为"**父依赖子**"（子阻塞父；不做子，父无法达成）；区别在于**子是否属于父的实现的一部分**：派生的子是**独立**的基建/能力/修复，**不属于父的功能实现、脱离父仍有用途**（A 依赖 B，但 B 也可服务其他作用）；拆分的子是父目标的**组成部件**（父的实现 = 所有子的集合），脱离父无独立意义——归 plan 文档、**不建子节点**（判定见"节点粒度判定·派生 vs 拆分"）。每条边必须能回答"这个任务为什么存在、是被哪个上游任务派生的"。根任务也要标明它派生自哪个上游（`[上游·外部]` 上下文块）。
3. **派生任务的时机判定（下钻 vs 延后）**——新派生的宏观任务：**阻塞当前**（不做完就无法回到当前 → `derive` 下钻，标 `[当前]`，做完回归）还是**可延后**（注意到了但不挡路 → `reveal` 记分支，标 `[延后]`）？这是根治"分支丢失"的核心。同一时刻**至多一个 `[当前]`**。
4. **结构与状态单一来源**——`TREE.md` 是唯一的结构与状态来源（读它即知全局派生图）；单个任务的长详情放 `<ID>.md`（或既有 `../library-squirrel-docs/plan/`）并从节点外链，**不在别处重复结构**。每次 `resume` 强制复述根任务 + 派生链。
5. **链接同步**——`TREE.md` 是导航中枢，节点信息不得滞后于实际：当某节点新建/确定详情文档（`../library-squirrel-docs/plan/` 或 `<ID>.md`）、或状态/焦点/恢复提示变化时，**立即**在树中该节点行同步（补/改 `| <文档>` 外链、状态记号、`[当前]`、恢复提示）。典型场景：为已 focus 的节点写完 plan 后，必须回树补 `| ../library-squirrel-docs/plan/<x>.md`。

> **轻量约束**：`TREE.md` 里每个节点只写"一行目的 + 派生说明"。节点实现步骤的细节归入该任务的长文档（计划文档优先复用），从节点 `| ../library-squirrel-docs/plan/...` 外链。主文件永远只装宏观任务图。树字符 `├─`/`└─` 已表达父子边，节点行**不再加"派生→"前缀**（冗余）。

### 节点记号：状态与类型分离（强制）

为避免单个记号超载、混淆"状态"与"派生类型"两个维度，**节点行记号只表状态/角色；派生类型在派生说明文字里**。两维度彻底分开，读树无歧义。

**状态/角色记号**（节点行紧跟树字符 `├─`/`└─` 后，**必有且仅一个**）：

| 记号 | 含义 |
|------|------|
| `[未开始]` | 未开工（典型 = 根任务待基建就绪） |
| `[当前]` | 当前焦点（整树至多一个） |
| `[进行中]` | 已开工、非焦点（典型 = `derive` 下钻后暂停等子的父节点） |
| `[完成]` | 完成 |
| `[延后]` | 延后 |
| `[放弃]` | 放弃 |

> 根节点用上表普通状态记号（通常 `[未开始]` 或 `[进行中]`），其"根"身份由树结构（顶层 + `[上游·外部]` 块）体现，不另设记号。

**派生类型**（在 `—` 后的派生说明文字里，**不进节点行记号**）：

| 类型 | 写法 | 语义 |
|------|------|------|
| 阻塞派生（derive） | `<父> 派生(阻塞)：…` | 父依赖子；下钻做完回归 |
| 非阻塞引出（reveal） | `<父> 引出(非阻塞)：…` | 父不依赖子；延后 side-quest |

> **读树方法**：节点行首 `[状态]` 一眼知状态；`—` 后的"派生(阻塞)/引出(非阻塞)"知类型与原因。两者不再共用记号，无歧义。

### 节点粒度判定（何时建节点 vs 写进长文档）

遇到一项工作时，用以下判据判断它是**宏观任务节点**还是**实现步骤**——满足越多越该建节点：

- **独立交付物**：有自己独立的目的/价值，不是"完成父任务的一个动作"。
- **独立文档**：值得有自己的 plan 文档或 memory 条目。
- **可独立派生**：会被上游任务引出，且自己可能再派生下游。
- **可独立开工/验收**：能独立排期、完成、验证。

> ✅ 节点（入树）：优雅暂停、reader 访问串行性、连接复用、gRPC 超时+并行化、终态即时落盘——每个都是独立任务级，有自己的 plan/memory。
> ❌ 实现步骤（入长文档，不入树）：加 softPause 字段、改 cmdWatcher 分流、写单测、修 reportProgress 公式——是完成某宏观任务的具体动作。

#### 派生 vs 拆分（建子节点前必判）

满足上述"独立交付物"判据只是**必要条件**——还要判定这条父子边是**派生**（入树）还是**拆分**（不入树，归 plan）。两者都表现为"父依赖子"（子是父的前置/阻塞）；**核心区别是子是否属于父的实现的一部分**：

| 判据 | 派生（建子节点入树） | 拆分（不建子节点，归 plan） |
|---|---|---|
| 父是否依赖子 | **是**（子阻塞父；不做子，父无法达成） | **是**（父✅ ⟺ 所有子✅） |
| **子是否属于父的实现的一部分**（核心） | **否**——子是独立基建/能力/修复，**脱离父仍有用途**（A 依赖 B，B 也可服务其他作用） | **是**——子是父目标的组成部件，脱离父无独立意义 |
| 父的性质 | 父有自己的目标；子是其前置基建/能力 | 父是聚合容器，其"实现"= 子的集合 |

> 注：`reveal`（延后分支）是另一种入树情况——父**不依赖**该子（做父时发现的岔路、可选 side-quest），它总是入树（标 `[延后]`），不参与本判据。

**拆分归 plan**：父任务的内部组成步骤写进该任务的 plan（或 `<ID>.md`），从父节点外链，**不建子节点**；父节点的进度（哪些组成步骤完成）写在父节点行或恢复提示里。

> ✅ 派生（入树）：A bilibili → B 多板块基建（A 依赖 B 才能存分轨视频，但 B 是通用多轨存储、脱离 bilibili 仍可服务其他站点）；C 高频启停 → D 优雅暂停（C 的正确实现依赖 D 排空在途 chunk，但 D 是独立暂停能力、有自己的 plan/memory）。
> ❌ 拆分（不入树，归 plan）：K「视频多轨合并」= M ffmpeg封装 + N merge业务 + P 前端动作。N/P 是 K 的组成部件（MergeResource/前端合并按钮只为 K 存在、脱离 K 无意义），K 的实现=三者集合 → 拆分，作 K 单节点、写进 K 的 plan。

### 跨树引用（派生谱系相交时）

一个宏观任务可能**既是某树的子节点、又是自己 epic 的根**（如「优雅暂停」既是「高频启停修复」的子、又是自己 epic 的根）。处理方式：在父树里作为子节点 + 一行链接到自己的 epic 目录（`→ ../<slug>/TREE.md`），**不复制其子树结构**——子树结构只在自己 epic 里维护。这样派生谱系可相交而不重复。

## 核心产物：一棵派生图 = 一个目录

每棵派生图（一个根任务）独占一个目录：`../library-squirrel-docs/workflow/active/<slug>/`（`<slug>` 为 kebab-case 根任务名；`../library-squirrel-docs/` 为私有文档库，任务图随库版本化）。根任务完成后整个目录归档到 `../library-squirrel-docs/workflow/archive/<slug>/`。

目录内文件分工（**无重复表示**）：

| 文件        | 职责                                                                                                          | 何时存在           |
| ----------- | ------------------------------------------------------------------------------------------------------------- | ------------------ |
| `TREE.md`   | 唯一的结构与状态来源：宏观任务派生图（每节点 = 状态记号+标题+派生说明+目的，+可选外链）+ 根任务元信息 + 决策约束 | 始终               |
| `<ID>.md`   | 单个宏观任务的**实现步骤/长详情**（设计、改动点、代码片段、测试要点）                                          | 仅当该任务无既有 plan 且详情很长 |

> **优先复用 `../library-squirrel-docs/plan/`**：宏观任务通常已有设计文档，节点直接 `| ../library-squirrel-docs/plan/<x>.md` 外链即可，无需另建 `<ID>.md`。只有当一个派生任务尚未有 plan、又需要记录较长实现细节时，才建 `<ID>.md`。

### `<ID>.md` 模板（仅当无既有 plan 且详情很长时创建）

````markdown
# B — <派生任务标题>

> 状态：[当前] · 派生自：A · 类型：阻塞派生
> 恢复提示：<file:line + 下一个微步骤>

## 实现步骤（本任务的 WBS/改动点，不入 TREE）
1. <实现步骤1>
2. <实现步骤2>
## 详情
<根因分析、代码片段、设计笔记——只放本任务内容，不含整棵派生图>
````

### 字段规范

| 字段          | 说明                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------- |
| 根意图        | 一句话目的 + **派生自哪个上游任务及原因**（上游做了什么、留下什么缝隙而引出本任务）。自包含。 |
| 上游·外部块   | 根任务的派生来源（属其它谱系），仅示派生上下文，不在本树管理状态。                            |
| 当前焦点      | 当前 `[当前]` 节点的 ID。整树至多一个；若无（全部完成或全部延后），见 `resume` 处理。        |
| 下一步        | 一句话，指向当前焦点的下一个具体动作。`park`/`done` 时必须更新。                               |
| 节点行        | `树字符 [状态] ID 标题 — <派生说明(含类型) + 一句话目的> | <详情文档>`，当前节点追加 `← 恢复提示`。 |
| 状态记号      | `[未开始]` / `[当前]` / `[进行中]` / `[完成]` / `[延后]` / `[放弃]`——只表状态，必有且仅一个；根节点用普通状态记号，根身份由树结构体现。 |
| 派生类型      | 在派生说明里：`派生(阻塞)`（derive）/ `引出(非阻塞)`（reveal）。**不进节点行记号**。         |
| 派生说明      | 根节点写"派生自<上游>"；子节点写"<父> 派生(阻塞)/引出(非阻塞)：<原因>"。回答"它为何存在 + 是否阻塞父"。 |
| ID            | 短 ID，默认 A–Z 递增；超过 26 用 A1/A2…。ID 一经分配不改。                                    |
| 恢复提示      | **精确接续点**：file:line + 下一个微步骤。当前节点内联在树行；长版本放该任务详情文档。        |
| 详情文档      | 节点的实现步骤归属：优先 `../library-squirrel-docs/plan/<x>.md`，否则 `<ID>.md`。跨仓库用相对路径。                |
| 决策与约束    | 已定的方案 rationale 与不可回退的不变量。防止后续误改。                                        |

## 协议操作

> 每个会改动结构的操作都必须**改 `TREE.md`**（结构与状态唯一源）；只有当某派生任务无既有 plan 且需记录较长实现步骤时才**额外创建 `<ID>.md`**，并在树中那行 `| <ID>.md` 外链。此外，任何节点的详情文档新建/变更或状态变化，都必须按**铁律5（链接同步）**立即同步该节点行的外链与状态。

### `root` —— 建根（开始一个宏观任务）

1. 用 Write 创建目录 `../library-squirrel-docs/workflow/active/<slug>/` 下的 `TREE.md`：根节点 A 标 `[进行中]`（或 `[未开始]`），根意图含**派生自哪个上游及原因**。
2. 在根上方写 `[上游·外部]` 块，标明派生来源任务及它留下什么缝隙。
3. 根节点若有设计文档，`| ../library-squirrel-docs/plan/<feature>-plan.md` 附在行尾（实现步骤归此文档，不入树）。
4. 询问用户是否启用 **MEMORY.md 恢复指针**（见下，推荐启用）。

### `derive`（派生·下钻）—— 当前工作被新宏观任务 X 阻塞

**先做粒度判定**：X 是新的宏观任务（独立目的、通常值得独立 plan）还是当前任务的实现步骤？
- 若是实现步骤 → **不入树**，写进当前任务的长文档。
- 若是新宏观任务 → 继续：

**时机判定**：不做 X，当前任务就无法达成目标 → 这是派生阻塞，下钻。

1. 分配新 ID，在 `TREE.md` 树中作为**当前焦点的子节点**插入一行（标 `[当前]`，派生说明写"A 派生(阻塞)：…"）。
2. 原当前节点：写恢复提示后，状态记号从 `[当前]` 改为 `[进行中]`。
3. 更新头部 **当前焦点** = X，**下一步** = X 的第一个动作。
4. 若 X 无既有 plan 且预计实现步骤很长 → 创建 `<ID>.md`，树中那行 `| <ID>.md` 外链。

### `reveal`（引出·延后分支）—— 注意到新宏观任务 Y 但非阻塞

**粒度判定**（同上）：Y 是新宏观任务才入树；否则写进当前任务长文档。

**时机判定**：Y 是个独立任务，但不挡当前工作的路 → 记录但不 diversion。

1. 分配新 ID，在 `TREE.md` 树中作为**当前焦点的子节点**插入一行（标 `[延后]`，派生说明写"A 引出(非阻塞)：…"）。
2. **不改变当前焦点，不下钻**。继续当前工作。（这是与 `derive` 的关键区别。）

### `done` —— 节点完成

1. 在 `TREE.md` 树中该节点行：状态记号改 `[完成]`，移除内联恢复提示。
2. 检查树中被该节点阻塞的父任务：父任务是否因此可恢复（其所有派生阻塞子任务都 `[完成]`）。
3. 若父任务可恢复 → **当前焦点** 回到父任务（父记号改 `[当前]`），写它的下一步；若根任务所有 needs 都 `[完成]` → 提示用户考虑 `close`；若仍有 `[延后]` 节点 → 提示用户可 `focus` 某分支。

### `focus` —— 切换到某延后分支继续

1. 在 `TREE.md` 树中：目标 `[延后]` 节点状态记号改 `[当前]`，原 `[当前]` 节点改 `[进行中]`。
2. 更新头部 **当前焦点** 与 **下一步**。

### `park` —— 中途停下

1. 在 `TREE.md` 树中当前节点行的 `←` 后写/刷新**精确恢复提示**；若该节点有详情文档，同步其顶部恢复提示。
2. 更新头部 **下一步**。不改状态（仍 `[当前]`）。

### `resume` —— 反遗忘操作（会话开始 / 上下文压缩后 / "我们刚才弄啥"）

1. 列出 `../library-squirrel-docs/workflow/active/` 下所有目录；多个则让用户选。
2. 读 `TREE.md`。**第一件事：复述根任务 + 它派生自哪个上游、为什么**（铁律4）。
3. **读派生图**，给全局一句话：根 → 派生了哪些层 → 当前在哪、是被谁派生来的。
4. 指出**当前焦点**及其**内联恢复提示**与**下一步**（需细节再读其详情文档）。
5. 列出树中所有 **`[延后]` 节点**（铁律：这些是被引出但延后的分支，别丢）。
6. 若树中无 `[当前]` 节点但有未完成项 → 提示用户选一个 `focus`，或判断是否 `close`。

### `close` —— 根任务完成

1. 确认根任务所有派生阻塞子任务都 `[完成]`、树中无未完成 `[当前]`（`[延后]` 分支可保留记录或提示另起 epic）。
2. 提炼**持久经验/教训** → 写入 `memory/`（遵循 memory frontmatter 规范）。
3. 整个目录移到 `../library-squirrel-docs/workflow/archive/<slug>/`，头部状态改"已完成"。
4. 删除 MEMORY.md 恢复指针（若启用过）。

## 恢复通道（opt-in：MEMORY.md 指针）

`root` 时询问用户是否启用。启用后在项目 `MEMORY.md`（每会话自动加载）追加：

```
- [活跃任务图](../library-squirrel-docs/workflow/active/<slug>/TREE.md) — <根任务一句话>
```

使新会话自动看见"有未完成派生链"并 `resume`；`close` 时删除该行。**指针只写稳定的根任务一句话，不写会变的焦点/状态**（那些在 TREE.md），避免随节点完成而过时。**不改 settings.json、不加 hook。** memory 目录按项目隔离（`~/.claude/projects/<项目>/memory/`），与"每项目一份派生图"天然一致。

## 与现有体系衔接（衔接非耦合）

- **`../library-squirrel-docs/plan/`**：宏观任务的**实现步骤/设计**归这里，节点 `| ../library-squirrel-docs/plan/<x>.md` 外链。派生图是**导航**（任务从哪派生、引出了谁、下一步），plan 是**单个任务的设计**。
- **`memory/`**：`close` 时写持久经验；派生图是**活态**（进行中），memory 是**回顾**（完成后）。
- **跨仓库派生**（SDK/插件等）：节点详情文档用相对路径（`../library-squirrel-sdk/...`）。单棵派生图可覆盖跨仓库的宏观任务。
- **`TaskCreate`**：可并用——TaskList 管会话内即时待办（含实现步骤），派生图管跨会话的宏观任务派生结构。

## 常见陷阱

| 陷阱 | 后果 | 正确做法 |
| ---- | ---- | -------- |
| **把实现步骤（加字段/改函数/写测试）当节点** | 树细碎膨胀、变成 WBS、丢失宏观派生视野 | 铁律1：节点=宏观任务；实现步骤归该任务长文档，从节点外链 |
| **把父任务的内部拆分当派生节点入树** | 边语义混淆（派生/拆分混进同棵树）、父完成语义不清、为补偿反复加标记/注释 | 建子节点前先判：子是否属于父的实现的一部分（脱离父仍有用途）？是→拆分归 plan，不建子节点（铁律2）|
| 把本该 `reveal` 的分支当成 `derive` 下钻 | 主线被无关分支带跑、深度不回归 | `derive` 前先答"不做它，当前任务能否达成？"，不能才下钻 |
| `derive` 后忘记 `done` 回归 | 树残留孤立 `[当前]` 链，焦点混乱 | 铁律3：每次下钻终须 done；`resume` 时检查无孤儿当前链 |
| 树里漏画派生分支 | 正是本技能要根治的丢失 | 一律 `reveal` 入树；`[延后]` 节点必须在树中出现 |
| 根任务不标派生来源 | 忘了"为什么有这个任务" | 铁律2：根意图必含"派生自<上游>及原因" + `[上游·外部]` 块 |
| 在详情文档里重复整棵派生图 | 又回到多文档同步地狱 | 铁律4：结构只在 `TREE.md`；详情文档只放本任务实现步骤 |
| **记号混淆状态与派生类型**（如用同一记号既表"延后状态"又表"非阻塞类型"） | 读树歧义、记号超载 | 记号只表状态/角色；派生类型(阻塞/非阻塞)写进派生说明文字（见"节点记号：状态与类型分离"）|
| 恢复提示写得太泛（如"继续做 X"） | 冷启动接不上 | 写 file:line + 具体下一个微步骤 |
| 多棵派生图混在一个目录 | 焦点不明、互相干扰 | 一棵派生图独占一个目录 |
| 跨谱系任务重复建子树 | 结构重复、同步地狱 | 跨树引用：父树作子节点 + 链接到自己 epic，子树只在自己 epic 维护 |
| 节点链接滞后（写了 plan/详情没回树补外链） | 树失去导航作用，resume 找不到详情 | 铁律5：节点详情/状态一变，立即同步树中外链与状态 |

## 触发与使用

- **何时启用**：用户描述"开始一个功能/修复/重构"，且判断会派生出多层宏观任务（典型信号："这需要先支持/先重构…"，或某任务是在做上一个任务时发现的）。
- **如何调用**：用户说"用 task-graph 追踪"/"/task-graph"，或 Claude 主动建议后启用。
- **持续维护**：启用后，每次派生/引出/完成/暂停都按协议更新 `TREE.md`（必要时详情文档）；新会话或感觉"忘了在干嘛"时 `resume`。
